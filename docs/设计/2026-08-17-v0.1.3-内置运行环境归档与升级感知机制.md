# v0.1.3 内置运行环境归档与升级感知机制设计

> 状态：待评审
> 日期：2026-08-17
> 范围：shell 打包链路 + 首启部署逻辑

## 1. 背景与问题

### 1.1 安装慢（用户实测反馈）

v0.1.2 安装包 236MB，NSIS 安装器阶段耗时数分钟。根因（实测数据）：

- `dsh-runtime/node_modules` 共 **59,365 个文件 / 603MB**
- 其中 **84%（49,571 个）是 <4KB 小文件**，体积仅占 49.5MB
- NSIS 需逐个解压写入 + Windows Defender 逐文件扫描 → 文件数驱动的开销，与体积无关

小文件来源是依赖生态的自然形态（rxjs 操作符拆分、shiki 语言包、univer 图标、pi-ai API 拆文件等），无法通过裁剪消除——归档是唯一对症解法。

### 1.2 DSH 升级对老用户不生效（架构缺口）

当前部署逻辑：老 profile `node_modules` 存在 → 直接复用（skipped），**不会感知内置闭包版本变化**。后果：

- DSH 发新版 → 我们重新 prepare + 打包 → 老用户覆盖安装后闭包仍是旧版
- 升级了等于没升（除非手动删 profile 重来）

### 1.3 依赖版本未锁定

`@deepseek-ai/dsh: ^0.1.0-rc.6` 的 ^ 语义允许 rc 内自动升级，prepare 时会悄悄拉到未经回归验证的新版本。

## 2. 方案设计

### 2.1 tar.gz 单归档（解决安装慢）

**构建侧**（prepare-runtime.mjs 末尾新增一步）：

```
pnpm install 完成后
  → 写 .runtime-version（内容见 2.2）
  → tar -czf dsh-runtime.tar.gz -C dsh-runtime .   ← Windows 10+ 自带 bsdtar，零新依赖
  → 删除 dsh-runtime/ 原始目录（磁盘回收 603MB）
```

**打包侧**（package.json extraResources）：

```
dsh-runtime.tar.gz（~190MB）→ resources/dsh-runtime.tar.gz
（替代原 dsh-runtime/ 整目录复制；after-pack.cjs 的 node.exe 内置不变）
```

**部署侧**（main.mjs ensureProfile bundled 分支改造）：

```
1. 检测 resources/dsh-runtime.tar.gz 存在（dev 模式仍兼容 dsh-runtime/ 目录路径）
2. 预统计：tar -tzf 列文件数 N
3. spawn('tar', ['-xzvf', tarPath, '-C', profileDir])，解析 stderr 行数 → 精确进度（x/N）
4. 解压完成校验 node_modules/@max-null/dsh-memory 存在，失败 → splashError
```

收益：NSIS 阶段 6 万次写入+扫描 → **1 次顺序写入**；首启部署从逐文件复制（1-3 分钟）→ 单次解压（~30 秒）；总磁盘 IO 从 2×6 万文件 → 1×6 万文件。

### 2.2 版本文件机制（解决升级不生效）

**`.runtime-version` 文件**（归档根目录 + profile 部署后同位置）：

```
格式：<ssid-version>-<dsh-version>，例：0.1.3-0.1.0-rc.6
生成：prepare-runtime.mjs 写入（ssid 版本取 shell/package.json，dsh 版本取安装后 node_modules/@deepseek-ai/dsh/package.json）
```

**启动对比逻辑**（main.mjs ensureProfile，bundled 模式）：

```
profile 无 .runtime-version 或内容 ≠ 内置
  → 自动开始重部署（splash 显示「检测到新版运行环境，正在更新…」+ 精确进度 + 取消按钮）
  → 原子替换（见下）→ 写 .runtime-version → 启动
profile 版本 = 内置 → skipped（秒开）
source/pnpm 模式（老逻辑）：
  profileReady（dsh-memory 存在）→ skipped，不校验版本（源码模式升级路径照旧）
```

**原子替换部署流程**（可取消的关键）：

```
1. 解压新归档 → profileDir/node_modules.new（临时目录）
   - 期间用户点「取消更新」→ 删除 node_modules.new → 旧版照常启动（无损回退）
2. 解压完成 + 校验 dsh-memory 存在 → 原子交换：
   删旧 node_modules → node_modules.new 改名 node_modules（毫秒级，无中断窗口）
3. 写 .runtime-version → 正常启动
```

**取消语义**：取消 = 本次跳过更新，splash 提示「已取消更新，继续使用当前版本」→ 正常 boot 旧版；**下次启动再次检测**（版本仍不一致则再次自动部署）。不提供常驻手动按钮，保持 splash 简洁。

**用户可见文案**：
- 重部署中：「检测到新版运行环境，正在更新（约 30 秒）…」+ 精确进度（解压行数/总文件数）
- 可取消：「取消更新」按钮（hover 变红，风格同关闭按钮）

### 2.3 依赖版本精确 pin

`dsh-runtime/package.json` 与 `profile-template/package.json` 的 `@deepseek-ai/dsh` 由 `^0.1.0-rc.6` 改为 `0.1.0-rc.6`（去掉 ^），prepare 结果确定性可复现；DSH 跟进升级作为显式决策（改版本号 → 重跑 prepare → 归档版本号随之更新）。

### 2.4 打包时间收益（小迭代）

| 环节 | 现状 | 改造后 |
|---|---|---|
| after-pack 复制 dsh-runtime | 3-5 分钟（6 万文件） | 秒级（1 个 190MB 文件） |
| NSIS 压缩 | 3-5 分钟（236MB 原始文件） | 2-4 分钟（190MB 已压缩归档，二次压缩收益小） |
| 合计 | 10-15 分钟 | **~5 分钟** |

DSH 未变的小迭代可跳过 prepare-runtime 环节，进一步压缩。

## 4. 风险与对策

| 风险 | 对策 |
|---|---|
| tar.exe 依赖（Windows 10 1803+ 自带，bsdtar） | 目标平台 Windows 10/11，可接受；解压失败 → splashError 明确报错 |
| 大归档解压中途失败 / 用户取消 → profile 半成品 | **原子替换**：先解压到 node_modules.new，校验通过才交换；失败/取消仅删临时目录，旧版无损 |
| 解压 + 交换期间用户强杀进程 | 临时目录残留 → 下次启动检测到 .new 残留先清理再重试 |
| 中文文件名 stderr 乱码干扰进度解析 | 进度按行数统计（每文件一行），不解析内容 |
| 归档二次压缩收益小、体积反弹 | 实测对比（预期 190-200MB，仍小于 236MB） |

## 5. 验证方案

1. `npm run prepare-runtime` → 归档生成 + 体积报告（预期 ~190MB）+ .runtime-version 内容正确
2. `npm run pack` → Setup 0.1.3.exe 体积（预期 ≤200MB）+ resources/dsh-runtime.tar.gz 存在
3. 全新 DSH_HOME 首启 → 解压进度条 → HTTP 200
4. 重启 → skipped 秒开（版本一致）
5. 伪造版本不一致（改 profile .runtime-version）→ 自动重部署（原子替换）→ HTTP 200
6. 重部署中点「取消更新」→ 旧版照常启动，无 node_modules.new 残留
7. 解压中杀进程 → 重启正常（残留清理后重试部署）
8. 老用户迁移（真实 ~/.dsh）→ 版本机制不触发，照旧跳过
9. `npm run typecheck` 通过

## 6. 不做的事（明确边界）

- 不裁剪依赖闭包（瘦身独立任务，需重验 peer 链）
- 不做 electron-updater 增量更新（blockmap 已生成，作为 v0.2 候选）
- 不改 kernel.ts（bundled 模式部署产物结构不变，仅部署方式变化）
