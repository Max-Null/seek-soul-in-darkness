# SSiD 故障恢复模式与「子进程取代单进程」设计（2026-09-13 讨论稿）

> 日期：2026-09-13
> 状态：**讨论稿**（先讨论完、落文档，再动手——用户要求）
> 关联：决策总表 D14（内核移出主进程）

## 一、动机（用户提出，来自 OpenCode 的经验）

> 「之前我折腾 OpenCode 的时候也出过问题，OpenCode 就有这么一个模式，我就回切到这个模式作为保底去修复那个崩了的环境。」

SSiD 当前的死锁：**插件把内核 boot 弄坏了 → 思灵打不开 → 你进不去设置页 → 没法禁用那个插件**。唯一的出路是手工改 `~/.dsh/profiles/ssid/package.json`，对用户不友好。

所以需要一个**不依赖插件加载成功**的入口，用来：
1. 用最小插件集把界面拉起来；
2. 在界面里禁用/卸载坏插件；
3. 回到正常模式。

## 二、调研结论（实测，非推断）

### 2.1 `dsh web` 没有可用参数

`node apps/cli/src/bin.ts web --help` 只有 `--host` / `--port` / `--no-open` / `--trusted-host`。
**没有 `--patch`、没有安全模式类开关。** 所以"从 CLI 传一个纯净 patch"这条路不成立，必须在**壳侧**（`kernel.ts`）注入。

### 2.2 patch 组装点：`kernel.ts:457`

```ts
const homePatches = loadOptionalPatches(BIN_NAME, join(home, PROFILE_PATCH_FILENAME)) ?? []
const patches: PatchOptions[] = [
  ...profile.layers.flatMap(layer => layer.patches),   // 各 bundle（含 @deepseek-ai/dsh-base / dsh-web-app）
  ...profile.patches,                                   // profile 自己的 cordis.patch.yml
  ...homePatches,                                       // ~/.dsh/cordis.patch.yml
]
```

**关键**：`patches` 在 `boot()` 之前组装完毕，且已有先例——下面几行就有一段"往 patches 里 push 一条 config 覆盖"（agent-presets 的 roots 注入，`:475`）。所以纯净模式就是**同一手法再 push 一条**：把非官方行标记 `disabled: true`。

### 2.3 托盘菜单已是原生菜单（主进程持有）

`main.mjs:1400-1403`：`new Tray(...)` + `tray.setContextMenu(Menu.buildFromTemplate([...]))`，现有 5 个 label 项。

**它完全不受内核影响**——这是用户纠正我的那一点，我原先说"UI 按钮依赖插件加载成功"只对**页面内**的设置页按钮成立。托盘菜单是 Electron 主进程的原生菜单，内核崩了照样能点。

→ **托盘是故障恢复入口的正确位置**，比启动参数更贴用户直觉。

## 三、设计

### 3.1 两个入口（互补，都要）

| 入口 | 适用场景 | 为什么需要它 |
|---|---|---|
| **托盘菜单**「以纯净模式重启内核」 | 思灵能打开、但某功能被插件弄坏 | 最健壮：托盘是主进程的，与内核状态无关；用户在界面里就能自救 |
| **启动参数 / .bat**（`SSID_SAFE_MODE=1`） | 思灵**打不开**（boot 直接失败） | 此时托盘也可能没建起来（极端情况），需要外部入口 |

### 3.2 纯净模式的判定规则

**策略：剔除一切非官方行，而不是枚举已知插件。**

```
1) 从 packages/*/package.json 的 dsh.profile.bundles 读"声明了哪些插件"
2) 收集组合树里出现的所有 row id（composeEntries(patches) 一次拿到）
3) 对每个 row id：
     - 若它来自 @deepseek-ai/* 的官方 bundle → 保留
     - 否则 → push { id, disabled: true }
```

**为什么用"剔除非官方"而不是"白名单"**：白名单漏一个就失效；黑名单模式下，**就算将来新增插件也自动被纯净模式排除**。

**数据不动**：只改"加载哪些插件"，**不碰 `~/.dsh` 里的会话、设置、记忆、storage**。这是关键——纯净模式起来后用户看到的是**同一个思灵**（同一批会话），只是没有第三方插件，于是能进设置页禁用坏插件。

### 3.3 「子进程取代单进程」的完整清单

用户拍板：**这次做彻底，让子进程模式成为默认**。需要补齐四项：

| # | 项 | 说明 | 当前状态 |
|---|---|---|---|
| 1 | **打包链路** | `kernel-child` 需 esbuild bundle；打包版用内置 `node.exe` 跑 bundle（dev 用 `tsx` 跑 TS）；确认 electron-builder 的 `extraResources` 带上它 | ✅ **已完成**（2026-09-13，见 §3.5） |
| 2 | **「AI 提问」通知** | 子进程模式下 `userQuestions` 在主进程不可达，需子进程在 `ask()` 前主动上报一条事件 | ❌ 未做 |
| 3 | **`session/event` 类型** | 现为受控断言（`this: Scoped<Session>` 根 ctx 不满足）；应下沉到 session 作用域 | ❌ 未做 |
| 4 | **「只重启内核」** | 子进程模式下 `restartDsh` 改为 kill + respawn 子进程，**不重启 Electron**（窗口/托盘/标题栏都不重建，快很多） | ❌ 未做（当前是 `app.relaunch()` 全重启） |

第 4 项与你最初的观察一致：**子进程模式下重启 DSH 本就不需要重启壳**——现在只是没接上。

### 3.4 默认切换的前提与回退

「子进程取代单进程」= 把 `SSID_KERNEL_CHILD` 的默认值从"关"改成"开"。这需要：

1. 四项全部补齐（尤其打包链路，否则打包版直接起不来）；
2. **保留回退开关**（`SSID_KERNEL_CHILD=0` 强制走同进程）——万一子进程模式在用户机器上有环境差异（如 `ELECTRON_RUN_AS_NODE` 之外还有什么坑），这是逃生门；
3. 真机验证清单（见下）。

### 3.5 打包链路的两个非显然结论（2026-09-13 实施时发现）

**① 子进程的脚本必须在 asar 之外。**
打包版子进程是**纯 `node.exe`**（不是 Electron，`ELECTRON_RUN_AS_NODE` 对它没有意义），
没有 Electron 的 asar 补丁，读不到 asar 虚拟文件系统——asar 内的脚本路径对它是 ENOENT。
故产物走 `extraResources`（→ `resources/kernel-child.bundle.mjs`），并从 `files` 里排除，
由 `host-process.mjs` 用 `process.resourcesPath` 定位。

**② 打包形态必须显式传 `preferBundled`。**
`kernel.ts` 的 runtime 选择（`:412-422`）只有 `preferBundled === true` 才无条件用 profile 闭包；
否则落到 `resolveDshRuntime()`：先认 `$DSH_CHECKOUT`（用户残留变量会把运行时劫持到旧源码，
即 pitfalls #5 幽灵依赖），再认 `<脚本目录>/../../deepseek-harness`——bundle 落在 `resources/` 时
那是安装目录附近，必然不存在，boot 直接失败。子进程无从得知 `app.isPackaged`，
故由主进程经 `SSID_KERNEL_CHILD_PACKAGED=1` 告知。

**bundle 保持自包含**：`import { bootKernel } from './kernel.ts'` 仍是静态导入，esbuild 打包时
把 `kernel.ts` 一并内联（产物 262,093 字节，对照 `kernel.bundle.mjs` 的 257,469 字节，
差额即 bridge 与 child 逻辑），运行时不存在 `./kernel.ts` 这个路径，
因此**不需要**按形态分支的动态导入。

## 四、验证计划

### 4.1 纯净模式
1. **正例**：故意放一个会 boot 失败的插件进 profile → 正常启动应失败 → 纯净模式启动应成功。
2. **负例**：干净 profile 下纯净模式也应正常（不能引入新问题）。
3. **数据完整性**：纯净模式启动后，会话列表/设置/记忆**与正常模式一致**（证明没碰数据）。
4. **恢复闭环**：纯净模式里禁用坏插件 → 正常启动成功。

### 4.2 子进程取代单进程
1. 打包链路：`npm run bundle-kernel-child` 产出 `kernel-child.bundle.mjs`（实测 262,093 字节）。
   **已验（2026-09-13）**：隔离 DSH_HOME + junction 引入 rc.1 闭包跑对照实验——
   传 `SSID_KERNEL_CHILD_PACKAGED=1` 且 `DSH_CHECKOUT` 指向无效路径 → `READY port=58557
   dshVersion=0.1.2-rc.1`、退出码 0（报告版本等于**闭包**版本而非源码的 0.1.5-rc.2，
   即确实用了闭包且忽略了 DSH_CHECKOUT）；同环境不传该标记 → `FATAL DSH_CHECKOUT 指向了无效路径`。
   两条合起来证明 `preferBundled` 生效，同时覆盖了「bundle 在无 tsx 的纯 node 下能 boot」。
   **待补**：真机安装包内确认落点是 `resources/` 而非 asar。
2. 「只重启内核」：点托盘/设置页重启 → 内核 PID 变化、**Electron PID 不变**、窗口不重建。
3. 通知：正常回合计时、审批提醒；**补上「AI 提问」后要单独验一次**。
4. 回退：`SSID_KERNEL_CHILD=0` 能回到同进程。
5. 关闭卫生：退出壳 → 子进程随之退出、端口释放（已在第 3 轮验过，回归时再验一次）。

## 五、风险与取舍

| 风险 | 说明 | 缓解 |
|---|---|---|
| 纯净模式误禁用官方行 | 判定规则若写错，可能把官方行也禁用 → 界面缺块 | 判定按"行的来源"而非"名字前缀"；验证用例 2 覆盖 |
| 子进程成为默认后环境差异 | 如某些机器 `ELECTRON_RUN_AS_NODE` 行为不同 | 保留 `SSID_KERNEL_CHILD=0` 回退；先灰度 |
| 「只重启内核」的会话状态 | 重启内核时正在跑的会话会中断 | 与现在 `app.relaunch()` 的行为一致（都是中断），无需额外处理，但要提示用户 |
| 打包体积 | 新增 `kernel-child.bundle.mjs` | 实测 256 KB（内联了 `kernel.ts`），可忽略 |

## 六、待用户拍板的三个点
