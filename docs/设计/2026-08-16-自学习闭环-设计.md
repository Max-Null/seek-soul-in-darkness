# 自学习闭环设计：从「被动记忆」到「行为画像」（2026-08-16）

> 状态：方案定稿（MaxNull 授权 agent 定设计决策）
> 目标：不新增 agent 角色，用现有插件体系达成「持续观察用户行为偏好 → 自动沉淀习惯 → 注入提醒」的自学习闭环
> 背景：fractal 原 guardian 的「记忆管家」是全量 LLM 分析（贵、噪声大）；OC 的「助理」因机制限制未完成。DSH 的事件链让两者都能以插件形态正确实现

## 一、三段式闭环

```
① 观察（dsh-guardian 扩展，确定性、零 token、24/7）
   事件流 → 检测「习惯信号」→ 计数/切片

② 判断（LLM 按需，低频，flash）
   信号过阈值 → 一次 flash 调用：
   输入 = 信号相关事件切片 + 已有记忆（去重用）
   输出 = { 习惯描述, confidence, 建议状态 }

③ 沉淀（候选区 → 人工闸门 → 记忆）
   判断结果 → guardian 侧栏「习惯候选」tab → 用户确认
   → memory.remember() 写入 suggested → 侧栏记忆面板确认 → auto
   → dsh-memory 的 recall 机制自动注入主 agent 提示词
```

**闭环成立**：观察 → 判断 → 沉淀 → 注入，四个环节全部复用 M1/M2 组件，零新增角色。

## 二、四个设计决策（已定）

### 决策 1：习惯信号（观察什么）

三类信号，全部确定性检测、零 token：

| 信号 | 检测方式 | 例 |
|---|---|---|
| **用户纠正** | 用户消息匹配纠正模式（`不对/错了/再检查/重新做/你漏了`），且前一轮有主 agent 的动作 | "你再检查一下提交前有没有跑测试" |
| **行为重复** | 同模式跨会话出现（如「编辑后跑测试」连续 N 轮）——复用 guardian 已有的无反馈环/编辑统计 | 连续 5 次会话都在编辑后跑测试 |
| **显式确认** | 用户在侧栏确认记忆的动作本身（已由 memory 闸门覆盖） | 确认 = 强信号 |

首版只做**用户纠正信号**——语义最清晰、误报最低，行为重复的序列挖掘留二期（需要更重的相似度判断）。

### 决策 2：分析时机（何时判断）

**会话 idle / 结束时批量分析**（信号积累到阈值 3 次才触发一次 LLM 判断）。理由：
- 不打断主 agent 工作流（实时分析会抢在用户对话中间塞请求）
- 批量时上下文切片更完整（一个习惯的多次证据一起喂给 LLM）
- token 成本可控（低频）

### 决策 3：沉淀路径（写哪）

**两级确认，不直接写 memory**：
1. LLM 判断结果 → guardian 状态的「习惯候选」区（持久化到 guardian storage）
2. 侧栏新 tab「习惯候选」：用户看到候选描述 + 证据摘要 → 逐条确认/丢弃
3. 确认 → `memory.remember()` 写入 suggested（走 dsh-memory 既有的人工闸门，第二次确认才变 auto）

两级闸门的原因：LLM 判断可能错（噪声），侧栏确认一次过滤明显误报，memory 闸门再过滤一次——**自学习绝不自我污染**。

### 决策 4：插件形态

**独立插件 `@max-null/dsh-habit`**，不扩展 dsh-guardian。理由：
- guardian 保持「确定性监控」的单一职责（断言/无反馈环/审查队列，零 LLM 调用）
- habit 是「LLM 判断」职责（信号触发 + flash 调用 + 候选管理）
- 符合 DSH 插件单一职责原则；两个插件通过事件/服务协作（habit 读 guardian 的观察结果）

## 三、dsh-habit 插件设计

```
dsh-habit/
├── package.json          # @max-null/dsh-habit, bundle manifest
├── cordis.patch.yml      # insert: id=habit
├── src/
│   ├── index.ts          # apply：HabitEngine + 侧栏 IPC 面
│   ├── engine.ts         # HabitEngine Service('habit')：信号检测 + 阈值 + 触发分析
│   ├── signals.ts        # 纯函数：纠正消息检测（正则/模式）
│   ├── analyzer.ts       # LLM 分析：切片组装 + 提示词 + 输出解析
│   ├── candidates.ts     # 候选管理：存储 + 去重 + 确认/丢弃
│   └── types.ts
└── tests/
```

### 引擎流程

1. `session/event` 监听（与 guardian 同源，但只关心用户消息）
2. 用户消息匹配纠正模式 → 该会话的纠正计数 +1，记录事件切片（用户消息 + 前一轮主 agent 动作摘要）
3. 会话 `turn/end` 且纠正计数 ≥ 3 → 触发一次 flash 分析（串行队列，防并发）
4. 分析输入：纠正切片（最多 5 条）+ 已有记忆列表（去重判断）
5. 分析输出：`{ habit, confidence, dedupOf }`——与已有记忆语义重复则返回 skip
6. 候选写入 guardian storage 同款 JSON（`~/.dsh/storages/habit`）
7. 侧栏「习惯候选」tab 确认 → memory.remember() → 候选标记已处理

### LLM 分析提示词要点

- 输入：纠正切片（用户原话 + 被纠正的行为上下文）+ 已有记忆（去重）
- 输出：严格 JSON `{ actions: [{ type: create_candidate | skip, habit: "…", confidence: high|medium|low, reason: "…" }] }`
- 纪律：只在证据充分时 create（≥3 次纠正且模式一致）；语义与已有记忆重复必须 skip；不确定宁可 skip
- 模型：flash（判断任务不需要深度思考，成本优先）

## 四、侧栏 UI（M3b）

侧栏加第三个 tab「习惯」：
- 候选列表：习惯描述 + confidence 徽章 + 证据条数 + 确认/丢弃按钮
- 确认 → 调 memory IPC（复用 M1 的 ssid:memory:* 桥）
- 空态文案沿用品牌（「黑暗中未见灵光」）

## 五、验收标准

1. 连续 3 次纠正同一行为 → 产生一条习惯候选（描述 + 证据）
2. 候选在侧栏「习惯」tab 可见，确认后进入记忆 suggested
3. 记忆确认变 auto 后，recall 注入主 agent 提示词（用现有 memory 机制验证）
4. 与已有记忆语义重复的判断 → skip（不产生重复候选）
5. 全流程零新增 agent 角色（habit 是插件，非角色）

## 六、风险与护栏

- **纠正模式误报**（用户说"不对"可能不是纠正 agent）：切片上下文喂给 LLM 判断，低 confidence 候选用户可丢弃
- **LLM 分析成本**：阈值 3 才触发 + flash + 批量，单次成本可忽略；串行队列防并发风暴
- **自学习污染**：两级人工闸门（候选确认 + memory 确认）保证模型不能自我提升习惯——这是 dsh-memory 的核心纪律，直接继承
- **与 M2 guardian 的边界**：guardian 管"即时行为纠偏"（本轮断言/无反馈环），habit 管"跨会话习惯沉淀"（画像）——时间尺度不同，不重叠
