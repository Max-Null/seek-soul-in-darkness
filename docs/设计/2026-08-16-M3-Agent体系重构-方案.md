# M3 · Agent 体系重构方案（2026-08-16）

> 状态：方案草案（对齐后动手）
> 范围：协作编排 + 角色体系 + 模型路由 + 底层机制，四层全重构
> 调研来源：oc-plus 双星系统 agents/*.md 原始设计 + DSH agent/subagent/tool-subagent 源码实测
> 队伍命名（2026-08-16 定稿）：双星（主）· 灵犀（参谋/右脑）· 明镜（军师/审查）· 巧匠（工匠/执行）· 明瞳（制图师/视觉）

## 〇、设计背景（知其所以然）

### 0.1 双星系统的起源：左右脑互补

MaxNull 最初与网页版 DS 讨论的机制：**DS 的思维链是贪婪算法——每一步追求局部最优解。这不是错误，是思维链设计的本质**，但它导致模型无法跳出思维局限看全局：像一个"向着目标不断摸索的左脑"（理性、逐目标、可能绕圈）。

因此引入一个**平行的右脑**：发散、宏观、从目标倒推过程，与左脑互补、双向验证，提供不一样的视角。这就是参谋（灵犀）的设计目的。

**OC 机制限制**：OC 不支持子 agent 之间通信，右脑只能做成"左主右子"的形式（主 agent 委派右脑）。这个限制在 DSH 里依然存在（子 agent 不能互调），所以灵犀仍是 fork 子 agent——但 DSH 的 fork 能继承父上下文，比 OC 的"无上下文 task"更接近真正的右脑。

### 0.2 各角色的原始定位

- **双星**（主）：编排者，四阶段流程（研究→综合→实现→验证），先对齐再动手
- **军师**：独立第三方审查 agent（12 异味清单），不参与决策只审结果
- **工匠**：纯按方案实施，所以用 flash——执行不需要深度思考
- **制图师**：后补的视觉角色（kimi k3），看图是刚需
- **助理**：原设想是"独立上下文的提醒者"——主 agent 因上下文过长/压缩导致注意力涣散而忽略二次审查、文档补齐时，拥有独立上下文的助理做出提醒。**受 OC 机制限制未完全实现**。DSH 的事件链恰是天然载体：M2 的 dsh-guardian（编辑审查队列 + 无反馈环 + 断言提醒）以事件驱动的形态实现了助理的使命，且不占上下文、不被压缩影响、确定性触发——比 agent 形态更可靠。因此助理退役，使命移交 guardian。

### 0.3 自学习闭环（dsh-habit）

原设计里 guardian 与记忆机制配合持续观察用户行为偏好（如"提交前习惯二次审查"），助理调 LLM 做用户画像。本方案以三段式插件闭环实现（详见 `2026-08-16-自学习闭环-设计.md`）：观察（guardian 扩展，零 token 检测用户纠正信号）→ 判断（flash 按需，阈值触发）→ 沉淀（两级人工闸门 + memory recall）。零新增 agent 角色。

### 0.4 首轮工具锚定调研（另一个会话的成果）

社区发现 V4 Pro 对首轮 API 可见工具清单敏感（工具多→"Let me..."绕圈，工具少→"We need..."直奔主题）。关键结论：「干净的机制是真的，神奇的效果未被证实」——issue #51 独立三环境复测未复现 98/99，锚定效应在当前权重上已不稳定。

**对 M3 的指导**：① 子 agent 的 toolFilter 收窄是"工具锚定"的 DSH 正统实现，不需要社区 hack；② 主 agent 首轮工具面用双 preset 对照评测验证（见 0.6）；③ 姿态纪律：机制干净 ≠ 效果神奇，四阶段/左右脑效果必须真实验证。

### 0.5 压缩阈值（M2 成果，影响 agent 注意力）

DSH 官方压缩默认 80% 触发（注意力已涣散），SSiD 提前到 60%（实测三层验证通过）。这是助理设想里"上下文过长导致忽略"问题的第一道防线；guardian 是第二道（行为纠偏）；dsh-habit 是第三道（跨会话习惯沉淀）。

### 0.6 首轮工具面对照评测（进入 M3 的第一个任务）

用现有两个 preset 做真实对照（不搬 fork 原型）：

| 组 | preset | 首轮工具面 |
|---|---|---|
| A | standard（官方） | 大（~25+ 工具 + 注入） |
| B | ssid-double-star（SSiD） | 小（纪律收紧 + 工具精简） |

同一跨文件任务跑两组，记录首轮轨迹类型（"Let me..." vs "We need..."）+ 完成质量 + token 成本。若 B 明显更好 → M3 角色收敛方向获真实数据支持；若无差异 → 锚定效应已过期（issue #51 结论），纪律兜底即可。fork 的 first-turn-anchor 原型作为后手。

## 一、调研结论（决定方案的事实）

| # | 事实 | 来源 |

| 2 | **DSH 无 temperature 透传**：AgentOptions 只有 provider/model/maxTokens。oc-plus 的 0.1/0.3 维度必须放弃，用 persona 纪律替代 | agent/runtime-types.ts 实测 |

## 二、角色体系：7 → 4（2026-08-16 更新：参谋保留、助理使命移交 guardian）

| 角色 | 去留 | 理由 |
|---|---|---|
| 双星 | **主 agent（preset）** | 编排者，四阶段纪律保留 |
| 工匠 | **保留**（continuable + flash） | 阶段 3 执行者，续接刚需 |
| 军师 | **保留**（one-shot + 只读） | 独立第三方审查，12 异味清单 |
| 参谋 | **保留**（fork + 只读 + web_search） | **右脑**：DS 思维链贪婪算法是左脑（理性、逐目标摸索），参谋是平行的右脑（发散、宏观、从目标倒推），双向验证。这是双星系统的哲学内核，不可砍 |
| 制图师 | **保留**（one-shot + kimi k3） | 看图刚需，成本纪律保留 |
| 助理 | **退役（使命移交 guardian）** | 原设想=独立上下文的习惯提醒者（主 agent 因上下文过长/压缩忽略二次审查、文档补齐时提醒）。受 OC 机制限制未完全实现；DSH 的事件链恰是天然载体——M2 的 dsh-guardian 已实现（编辑审查队列 + turn/end 自动提醒），且事件驱动比独立 agent 观察更可靠 |
| 侦查兵 | 已退役 | DSH 原生 web_search 替代 |

> 7→4 的理由：参谋的价值是「右脑互补」而非「方向检查」，所以保留；助理是「提醒者」，guardian 事件驱动实现了它的使命且更可靠；侦查兵被 web_search 原生替代。砍掉的是**实现方式被更好的机制取代**的角色，不是功能。

## 三、底层机制：agent-presets + 每角色一行 tool-subagent

不用 workflow（那是工具编排不是 agent 协作）、不用 ralph（那是循环迭代）。子 agent 角色直接声明在 `ssid-double-star/agent.cordis.yml`：

```yaml
# 工匠：continuable + flash + 编辑工具集
- id: tool-subagent-artisan
  name: '@deepseek-ai/dsh-tool-subagent'
  config:
    provider: spawn
    toolName: subagent_artisan
    backgroundMode: continuable
    agentOptions: { provider: deepseek-official, model: deepseek-v4-flash }
    persona: <工匠 persona>
    toolFilter: { allow: [read, edit, write, glob, grep, bash, pwsh, todo_write] }

# 军师：one-shot + 只读 + 继承主模型（pro）
- id: tool-subagent-strategist
  name: '@deepseek-ai/dsh-tool-subagent'
  config:
    provider: fork          # 继承父上下文才能审全局
    toolName: subagent_strategist
    persona: <军师 persona>
    toolFilter: { allow: [read, glob, grep, web_search] }

# 参谋（右脑）：fork 继承上下文 + 只读 + web_search（发散需查证）
- id: tool-subagent-counselor
  name: '@deepseek-ai/dsh-tool-subagent'
  config:
    provider: fork          # 右脑从目标倒推，需要父任务的完整上下文
    toolName: subagent_counselor
    persona: <参谋 persona：发散、宏观、从目标倒推、双向验证>
    toolFilter: { allow: [read, web_search] }

# 制图师：one-shot + kimi k3 + 只读
- id: tool-subagent-cartographer
  name: '@deepseek-ai/dsh-tool-subagent'
  config:
    provider: spawn
    toolName: subagent_cartographer
    agentOptions: { provider: pi-ai, model: kimi-k3 }
    persona: <制图师 persona>
    toolFilter: { allow: [read] }
```

（toolName 用 `subagent_<角色>` 而非 `subagent`：每个角色一个独立工具，模型能按名委派，语义清晰。）

## 四、协作编排：四阶段纪律保留，机制映射到 DSH 原生

| oc-plus 四阶段 | DSH 落点 |
|---|---|
| 阶段 1 研究（并行工匠探索） | 并行 `subagent_artisan`（continuable，研究完续接实现）或 `fork` 只读探索 |
| 阶段 2 综合（规格落盘） | 主 agent 写 `docs/设计/` 或 `docs/计划/`；自检「规格已落盘」 |
| 阶段 3 实现 | `subagent_artisan` continuable 续接（对应 task_id 续接：同一子会话、保留上下文） |
| 阶段 4 验证 | `subagent_strategist` 审查 + 主 agent 亲自 `git diff`（双星纪律原样保留） |

双星 persona 的「子 agent 续接机制」段改写：task_id → `subagent_id`（continuable 的 durable child id），规则不变（不转发确认问题给用户、不新建任务、不接手剩余工作）。

## 五、模型路由（成本分层）

| 角色 | 模型 | 理由 |
|---|---|---|
| 双星（主） | deepseek-v4-pro | 已有（settings.yaml agent-default-model） |
| 工匠 | deepseek-v4-flash | 执行不需要深度思考，flash 便宜 |
| 军师 | 继承（pro） | 审查需要全局视野，值得 pro |
| 参谋（右脑） | 继承（pro） | 发散推理需要完整思考深度 |
| 制图师 | kimi-k3（pi-ai） | vision 刚需，单次给到位控成本 |

待办：配置 `llm-pi-ai` settings section 挂 kimi k3（M3 首个任务，先确认 kimi 的 pi-ai 兼容性）。

## 六、temperature 维度的替代

DSH 无 temperature 透传。替代方案 = persona 纪律收紧：
- 工匠（原 0.1）：「执行者，不思考；输出=文件+改动+测试结果，不总结不提议」
- 军师（原 0.3）：「输出 3-5 句；没问题说『审查通过』」
- 主 agent 的 reasoningEffort 已在 settings（max）——思考深度由这个维度控制。

## 七、验收标准

1. preset 里四个子 agent 角色可被主 agent 按名委派（`subagent_artisan`/`subagent_strategist`/`subagent_counselor`/`subagent_cartographer`）
2. 复杂编码任务走完整四阶段：研究→综合→实现→验证
3. 工匠可续接（同子会话连续修改，不丢上下文）
4. **左右脑双向验证**：重大决策时主 agent 并行调参谋（右脑倒推）+ 自己（左脑摸索），综合两条路径再决策
5. 制图师用 kimi k3 看图（读图工具验证）
6. 模型路由正确：工匠请求路由到 flash、制图师到 kimi
7. 真实端到端：一个跨文件改动任务完整跑四阶段

## 八、风险与护栏

- **kimi k3 的 pi-ai 兼容性未验证**：若 pi-ai 不兼容，制图师改用 deepseek 官方 vision（若有）或暂缓（M3 其他部分不阻塞）。
- **continuable 子 agent 的资源管理**：DSH continuation manager 持有 handle，长会话需确认 idle 回收。
- **fork vs spawn**：军师用 fork 继承上下文（审全局），但 fork 的子会话会携带完整前缀（token 成本）——若成本过高改 spawn + persona 指令「先读相关文件」。
- **四阶段纪律靠 persona**（提示词工程），不是硬约束——这正是 Guardian 断言触发线的用武之地（阶段 4 自检可接入 guardian 状态）。
