2 · 破坏性变更（全部实测，非读文档推断）

2.1 dsh-persona 配置字段改名 —— 唯一的硬失败

用 rc.2 的真实包实体 + 真 schemastery 跑校验，而非照抄 release notes：

✗ SSiD 原写法 { text: "…" }   →  $.prefix missing required value
✓ rc.2 新写法  { prefix: "…" } →  解析通过（suffix 默认 ""）
  • 0.1.2-rc.1：Config = { text: string }
  • 0.1.5-rc.1/rc.2：Config = { prefix: z.string().required(), suffix: z.string().default(''), complete?, includeRuntimeContext? }
  • rc.1 → rc.2 的 persona 源码零差异（packages/preset/ 下只改了 package.json 版本号）。变更实际由 0.1.5 系列引入，清单标注正确

2.2 段名拆分 + 内核包族必须整体升

dsh-system-prompt 把 deployment:persona 拆成 deployment:persona-prefix / -suffix，新增导出 PERSONA_PREFIX_SECTION / PERSONA_SUFFIX_SECTION。实测：rc.2 的 persona 配 rc.1 的 system-prompt 会在 ESM 链接期直接报 does not provide an export named …。

2.3 client-connection 的 inject 收缩（第三方插件的雷）

failed to apply loader entry dsh-pocket: cannot get property "webServer" without inject
  at client-connection/src/rpc-host.ts:179  ← owner.webServer.register(route)
  at dsh-pocket/lib/web-rpc.js:39 installPocketRpc

精确机制：rpc.handle 的 owner 是 connection 实例自己的 ctx（get rpc() 里 const owner = this.ctx），它只声明 credentials，所以 owner.webServer 必抛。这是 ctx 权限问题，与宿主有没有 webServer 无关（详见 §5 的归因更正）。

5 · 本轮发现与纠正（含我自己的错误）

5.1 共享 checkout 是红线 —— 连带崩掉了 web 版

deepseek-harness/ 同时是 web 版与 SSiD 的内核来源（web profile 不带内核闭包）。我为升级 SSiD 把它切到 0.1.5-rc.2 并 pnpm install + pnpm run build，web 版被连带升级后崩溃。

处置：建独立副本 dsh-web-runtime/（1.62 GB，实测能独立 boot）+ 启动脚本 启动-DSH-Web.bat（设 DSH_CHECKOUT 指向副本）；约束写进 AGENTS.md 铁律 2.1 与手册 §5.0 第 0 条。附带查到：会话格式已是 v3 且无降级路径——降级内核会让已有会话永久打不开，所以「回退内核」不是可选方案。

5.2 归因更正：SSiD 其实有 webServer

我此前把 SSiD 当成「无 webServer 的 Electron 壳」并据此归因，这是错的。实测：组合树里 webserver 行启用，内核端口在监听且返回 HTTP 401，profile patch 只 insert 了 MCP、没有禁用该行。

据此，dsh-pocket 崩溃的机制应按 §2.3 表述（ctx 权限，不是宿主能力）。真正没有 webServer 的宿主是 DSH 官方桌面壳（desktop.cordis.patch.yml 显式 webserver: disabled: true）。判定命令：--dump-config 看 webserver 行有无 disabled。

5.3 源码模式的三个依赖口子（与 rc.2 无关，但升级时才会暴露）

SSiD 用 node --import tsx/esm 启动，tsx 读 shell/tsconfig.json 的 paths 把内核包解析到 checkout 源码——于是实际加载源码、闭包被旁路。源码模式因此要求 checkout 自身完整：

  • paths 跟得上内核加包（缺 57 条）
  • checkout 完整 pnpm install 过（zod/mime-types/@deepseek-ai/node-addon-system 全缺）
  • dist 型包有 lib/ 产物（22 个包缺，pnpm run build 补齐）
5.4 排查纪律：先确认单实例锁的持有者

「启动失败」有两次根本不是内核问题：打包版思灵一直在后台运行占着 single-instance 锁，dev 实例起来后立刻 single-instance lock FAILED -> quit。被拒绝启动看起来像崩溃，实际是「根本没轮到它跑」。

附录 A · 壳实现对比：0.1.2 内核时代 vs 0.1.5 内核时代

先纠正一个容易误解的说法

Electron 指上游框架（双方都用 v44.2.0）；Electron 壳指「怎么起内核、怎么装 UI、怎么通信、怎么打包」的应用层。SSiD 的壳是自研的（shell/main.mjs + kernel.ts），官方有它的 apps/desktop。所以不是「改造了 Electron」，而是「自研了 Electron 壳、没有沿用官方那个」。

另有一处关键事实：这次 rc.2 升级完全没动壳的核心实现——kernel.ts / main.mjs / boot-smoke.ts 一个字节都没改。变的是壳所面对的内核契约，以及三处被内核升级逼出来的配套改动。

A.1 内核契约层：真正变了的东西

契约点0.1.2-rc.10.1.5-rc.2
connection 的 inject['webServer','credentials']['credentials']，webServer 降为可选 ctx.inject(['webServer'],…)
路由挂载来源connection 自己持有 webServer，直接 owner.webServer.register改用 attachWebServer 注入的 webServerCtx；另有 createSharedFetchHandler('/api') 这条不依赖 webServer 的路
rpc.handle 的 ownerconnection 自己的 ctx（有 webServer 权限）同一个 owner，但权限没了 → 必抛 cannot get property "webServer" without inject
persona 字段config.textconfig.prefix（required）+ suffix
persona 段名deployment:persona拆成 deployment:persona-prefix / -suffix
connection 定位webServer 的语义包装层carrier-neutral（Web 载与 Electron 载分发同一 handler）

关键推论：0.1.5 之前 connection 与 webServer 是绑定的，之后解耦了。这让「无 webServer 宿主」成为一等公民——DSH 官方桌面壳正是靠这一点把 webserver 整行禁掉、改用 dsh-app:// 自定义协议。

A.2 壳所面对的运行时形态

维度0.1.2 时代0.1.5 时代（当前）
SSiD 怎么起内核Electron 主进程内直接 boot，单进程同样（壳代码未改）
为什么必须单进程Electron 里 DSH 的 native addon 探测不到标准 Node 的 V8 embedder，ctx.loader.internal 为 undefined；用 registerHooks 改写 bare specifier 的 parentURL 绕开同样（问题依旧存在，未根治）
内核从哪加载看起来在跑闭包tsx 的 paths 把内核包解析到 checkout 源码，闭包被旁路
同进程能拿到什么kernel.get('memory') 直接读 host 服务、kernel.ctx.on('session/event')同样（单进程收益保留）
UI 怎么加载BrowserWindow 加载 http://127.0.0.1:<动态端口>同样
webServer在在（内核端口仍监听、HTTP 401）
A.2 里有个反直觉的结论

「0.1.2 时代跑闭包、0.1.5 时代跑源码」不是升级导致的，而是壳自己的 tsconfig paths 造成的——它一直把内核包指向 checkout 源码。0.1.2 时之所以看起来在跑闭包，是因为加载器当时没被引到源码路径上；升级后源码路径被走通，闭包才被旁路。同一份壳代码，两个时代的运行时来源不同。

A.3 三处被内核升级逼出来的配套改动

#改动为什么是内核逼的
1preset 的 config.text → config.prefixpersona schema 变了，不改就硬失败（$.prefix missing required value）；且 preset 是手工部署的——仓库副本与 ~/.dsh/.agent-presets/ 两处都得改，不在任何自动化链路上
2tsconfig.json paths 补 57 条（289→347）内核加包就要补；rc.2 新增的 @deepseek-ai/dsh-http-proxy（subprocess/src 新 import）是首个症状
3dsh-pocket 2.10.3 → 2.10.6connection 的 inject 收缩使 rpc.handle 必抛；2.10.6 的 inject 含 webServer 并优先自行挂载

另有两条属于环境欠债、与内核版本无关，只是升级时才暴露：checkout 从未完整 pnpm install（zod / mime-types / node-addon-system 全缺）、22 个 dist 型包没有 lib/ 产物。

A.4 一句话总结两个时代的差别

0.1.2 时代0.1.5 时代
壳的职责起内核 + 加载 UI + 同进程读 host 服务完全相同
内核给壳的假设webServer 一定在，connection 依附于它宿主可能没有 webServer，connection 可独立工作
插件怎么写路由webServer.register / connection.rpc.handle 都行想跨宿主就得用 connection.fetch.register（载体中立）
对 SSiD 的实际影响—自身没坏（它有 webServer），但为将来换宿主留了门

结论：「0.1.5 的 SSiD 壳」并不是一种新实现，而是同一份壳跑在新内核契约上。真正的分水岭不在壳，在于内核开始承认「没有 webServer 的宿主」这个形态——那正是官方桌面壳的架构前提。
