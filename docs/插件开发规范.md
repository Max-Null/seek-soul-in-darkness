# SSiD 插件开发规范

> 日期：2026-09-14
> 定位：SSiD 全家桶插件（`@max-null/*`）的开发规范。
> 关系：**不重复造轮子** —— DSH 已有的是权威，本篇只做**索引 + 补充**。

## 一、为什么需要这一篇

DSH 的插件文档其实相当完整，但它们有两个缺口：

1. **面向 DSH 仓库内部的贡献者**，不是面向第三方插件作者。`packages/AGENTS.md` 开头就写着
   「These package-specific rules supplement the repo-wide conventions」。
2. **不随 npm 包分发**。实测 `packages/boot/app-boot` 的 `files` 只有
   `lib/index.js, lib/types/**/*.d.ts`；`packages/client/connection` 同理。第三方装包时
   **看不到任何一条规范**。

更麻烦的是第三类：**有些规范只在源码注释里成型**。本规范的第一个门就是从那里捞出来的 ——
DSH 的 `packages/ui/app-boot/tsdown.config.ts` 注释写着：

> Embed Include while keeping Loader external so the built include tree and app host
> bind to one Loader peer.

这条规则之前不在任何文档里，而违反它的代价是 v0.3.0 装上后插件中心、MCP 面板、侧栏底栏
**全部失效**（请求 405）。

## 三、进门的部分（可机械检查）

**判据**（取自 DSH：「把可机械检查的不变量接进会执行的门，并为每条验收路径证明它能拒绝无效输入」）：

1. 能否在有限时间内机械判定通过 / 不通过
2. 误报率是否可接受
3. 违规是否必然导致故障

三条都满足才进门；否则只写不写门。

| 门 | 检查什么 | 证据来源 |
|---|---|---|
| `check-loader-external` | 构建脚本带 `--external:@deepseek-ai/*`；产物不出现 include 实现特征；产物体积不超上限 | v0.3.0 的 405 故障 + 上引 DSH 注释规则 |
| `check-plugin-peers` | 插件 `@deepseek-ai/*` peerDeps 是否**覆盖**当前内核版本 | `dsh-ssid-panels` 0.1.9 钉在 `^0.1.0-rc.6` 的漂移（2026-09-14 实测） |
| `check-vendor-sync` / `check-profile-sync` / `check-bom` / `check-legacy-names` | 见各自脚本头部注释 | 既有四门，本次未改动 |

跑法：`npm run check:rules`（6 门约 1 秒）。**门的自测在 `npm test` 里**（`check-*.spec.mjs`）——
分工是：自测保证门自身正确、日常就在跑；门扫全仓走 `check:rules`。

**目标内核版本的单一来源**：`shell/profile-template/pnpm-workspace.yaml`（发版基准，
所有 `@deepseek-ai/*` 在那里 pin 成同一版本）。从仓库内取，门才能离线与在 CI 下跑。

## 四、只写的规则（需判断，不做门）

每条都标注证据来源；**没有证据的标「暂定」**，不要让暂定看起来像定论。
这是本规范的一条自我约束：DSH 的 `packages/AGENTS.md` 说「Require evidence for public
choices」——规则本身也是 public choice，同样需要证据。

### 4.1 peerDependencies 的语义 ★

**下限 = 你实际验证过的最早版本；上限 = 你不打算验证的未来边界。**
两条都只声明「作者知道什么」，**与「现在是什么版本」无关**。

- **未改动的插件保持原下限**。它记录的是已证事实；强行抬高等于用时间戳替换证据，
  还丢掉了「兼容更早内核」这条真信息。
- **改过后只验了当前内核** → 下限提到「验证过的最早版本」，而不是机械等于当前内核。
  只验了 0.1.5 却写 `^0.1.0` 是**过度声明**；若也验过 0.1.4，下限就该是 0.1.4。
- **未来由上限负责**：`^0.1.0` → `<0.2.0`，0.2.0 一出现该范围自动失效，逼作者重新表态。
  改下限解决不了未来问题，反而破坏这个机制。
- 证据：DSH「Require evidence for public choices」+ 2026-09-14 的一次讨论纠正
  （我最初提议「下限必须对齐当前内核」，被指出三条反例而废弃）。
- **反面教材**：`check-plugin-peers` **不**判「下限是否最新」——它只判覆盖性
  （能不能跑）。因此 `dsh-ssid-panels` 的 `^0.1.0-rc.6` 在门里是**通过**的。

### 4.2 注册必须是 effect（DSH 硬规则，但门只见其形）

DSH 原话：**Registrations are effects** —— 每个贡献都走 `ctx.effect()` / `ctx.on()`，
registry 的 `register()` 返回 disposer。

- 为什么不做门：判断「这个注册是否真的可回收」需要读语义，正则必然误报。
  DSH 自己的做法是**窄豁免 + 注释说明理由**，而不是关掉规则。
- 若将来做门，形态是：AST 扫描 `apply` 内的裸 `register(...)` 调用，允许注释豁免。

### 4.3 其余只写规则（表）

| 规则 | 为什么不做门 | 来源 |
|---|---|---|
| `inject` 与实际使用一致 | 需要类型信息，交给 `tsc`；正则必然误报 | DSH `packages/AGENTS.md`（可选服务用 `ctx.get`） |
| 不要中心化 dispatcher | 需判断「什么算中心化」，跨文件语义 | DSH `verify-no-bare-dispatcher` |
| `apply` 之外不产生副作用 | 合法场景多，误报率不可接受 | Cordis 生命周期 |
| Model-visible ⟺ logged | 需设计判断 | DSH 根 `AGENTS.md` |
| 模型可见文案的视角与措辞 | 需判断；DSH 自己也只做 prose 规范 | `dsh-prose-standard` |
| Capability seam 三角色完整 | 架构判断 | DSH `docs/glossary.md` |
| 测试描述行为而非正确性 | 需判断 | DSH 根 `AGENTS.md` |

## 六、维护

- **新增规则**：先判「能否机械检查」。能 → 写门 + 自测 + 进 `check-rules.mjs`；不能 →
  写进本文档，**必须标注证据来源**。
- **规则被证伪**：连同证据一起改，不留下「曾经这么要求过」的叙述（DSH 的 `dsh-trim-cot-leakage`
  原则：文档陈述当前状态，变更史进 record）。
- **门红了**：先看它指的哪一条、证据是什么，再决定改代码还是改规则 —— 不要为了变绿而关规则。
