## 一、为什么不在 SSiD 里做

发版流程（尤其 `prepare-runtime.mjs` 与 `electron-builder`）要在工作区里读写大量文件。**技术分析上它不碰运行中的实例**：安装版用的是 `AppData\Local\Programs\ssid-shell\` 里内嵌的 `app.asar` 与 `dsh-runtime.tar.gz`，不是 `shell/` 下的工作区产物——所以重建工作区归档**不会**影响已安装的 SSiD。

但风险不对称：万一某步脚本真动了 profile，赔上的是**正在进行的会话**。为一个「省一次环境切换」的便利去赌那个，不划算。

## 五、本次特有的坑

1. **插件 npm 发布必须早于归档重建**——本次已满足（tone-layer 0.1.0、dsh-memory 0.9.1 均已发布）。
2. **别顺手动 web profile**——接手会话跑在 web 版里，它的 `dsh-context` 刚升到 0.53.3；归档重建期间同样不要在它上面跑 pnpm。
3. **`prepare-runtime` 会删掉 `dsh-runtime` 源目录**——手工抽查前先 `New-Item -ItemType Directory dsh-runtime`。
4. **`verify:release` 有已知过时项**（脚本待修）：`open-sea-skin/plugin/client.js` 检查是假提示；体积上限 213 MB 已被依赖增长突破（v0.3.0 实为 230.5 MB）。脚本自己会提示。
5. **归档里的 release-notes 是发版时快照**——发布后再改 `docs/` 那份不会同步进归档。
6. **发版 = 五件事一次做完**（版本号 / 内置插件对齐 / 归档 / 更新日志 / tag·Release），漏一项即未完成。
