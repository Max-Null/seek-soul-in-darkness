## 拟提交的 issue 正文

**Title**: Automatic compaction waits for 80% of the context window — long past the point where output starts degrading

**Body**:

### What happens

In a long-running session, assistant output degrades into repetition — the reasoning stream loops on fragments, some of which leak into the visible reply. The request **succeeds**: no failure, no `llm/retry-started` in the log. This is generation degradation, not a transport problem, so there is nothing for a retry to catch.

What makes it worth reporting is *where* it happens relative to compaction: **the automatic compaction that exists to bound this context had not fired, and by design would not have fired for another ~130K tokens.**

### Why the threshold sits that far out

`compaction-basic` resolves its trigger from the window:

```ts
// packages/compaction/compaction-basic/src/config.ts:144
const thresholdTokens = Math.floor(contextWindow * policy.thresholdRatio)
```

with `thresholdRatio` defaulting to `0.8` (`config.ts:20`), and the DeepSeek adapter declaring:

```ts
// packages/llm/llm-deepseek/src/adapter.ts:147
export const DEFAULT_CONTEXT_WINDOW = 1_000_000
```

On the default DeepSeek route that puts the automatic threshold at **800,000 tokens**.

The formula assumes a model still behaves normally at 80% of its window. A window is how much fits; it is not a claim about the range in which the model still works. Those two quantities need not scale together, and the configuration surface can only express the trigger as a fraction — `modelPolicies` narrows the scope to one provider/model, but still as a ratio.

### Measurements

One Windows host, DSH `0.1.5-rc.2`, `deepseek-flash` route. Pressure = `inputTokens + cacheReadTokens + cacheWriteTokens` from provider-reported usage. Repetition ratio = share of line-ish units (split on newlines and CJK sentence punctuation) appearing three or more times within a single reasoning output.

Repetition rises with context (session A):

| Pressure | Repetition ratio |
|---|---|
| 675,868 | 32% |
| 685,581 | 45% |
| 697,848 | 76% |
| 699,399 | 67% |

Peaks across two sessions and three separate growth cycles — each cycle ends just short of the same line:

| Session | Peak pressure | Share of window |
|---|---|---|
| A | 792,108 | 79.2% |
| B | 793,912 | 79.4% |
| B (later cycle) | 794,451 | 79.4% |

Every cycle ran up to ~79% and was compacted there, while the degradation signal appears around **67%**. Between the two lies a band of roughly **130K tokens** in which the session is well past comfortable and the guard has no reason to act.

### Caveats

- One host, one model, two sessions. The onset is a single observation — treat ~67% as pilot data, not a constant.
- Task shape is a covariate. The degrading turns were many structurally similar steps (read → write script → run → analyze). A second session reached 79.4% with a lower peak ratio (42%), so token count is a risk factor rather than a sufficient cause.
- The repetition metric is a heuristic over recorded output, not an internal measurement of the model.

### What we would like

Any one of these would let a deployment match the trigger to the model it actually runs:

1. **An absolute threshold.** The retention side already ships both forms — `retainRatio` and `retainTokens`. The trigger side ships only `thresholdRatio` (`config.ts:26-35` lists the full policy key set). A `thresholdTokens` counterpart, mutually exclusive with the ratio and resolved the way `resolveRetention` already does, would let an operator state "this model is stable to N tokens" directly, instead of encoding it as a smaller lie about the window.
2. **If absolute thresholds are out of scope, make the coupling explicit.** Documenting that `thresholdRatio` is a *proxy for model behavior*, and that a deployment with a large declared window should lower it, would at least make the trap visible before someone hits it.
3. **Consider the `repeat-tool-reminder` gap in the same pass.** It detects repeated **tool calls** ("You are repeating the exact same tool call with identical arguments") and nothing else. Text-level repetition — the failure we actually hit — passes through it untouched. Whatever the right fix, the two surfaces currently disagree about what "looping" means.

### Our workaround

Two steps — because the obvious one is inert, and that is itself worth reporting.

**1. A `thresholdRatio` on the host-plane `compaction-basic` row does nothing.** The natural first move is to add `config: { thresholdRatio: 0.5 }` to that row from a profile patch. It composes cleanly and appears in the tree — sitting directly under a `disabled: true` that the `web-app` bundle applies on the host plane (compaction is a per-preset decision there; the host keeps only token metering). Nothing loads it.

`dsh --profile <name> --dump-config` makes this visible in one line. Worth stating plainly: **a valid YAML shape, a field name the schema accepts, and a value inside `(0, 1]` together do not prove the row loads.** A deployment that can only check the schema cannot tell these two cases apart — which is why we report the layering rather than just the workaround.

**2. The threshold that matters lives in the agent preset.** We copied the shipped `standard` preset verbatim into the user preset root (`$DSH_HOME/.agent-presets/ssid-standard/`, an MD5-identical `agent.cordis.yml`), added `thresholdRatio: 0.5` to its `compaction-basic` entry, and pointed `agent-presets.default` at it from the profile patch. On this route that is 500,000 tokens; `retainRatio` stays at its default 0.16.

Two properties of this fix are worth knowing. Presets are chosen **per session**, so it affects only newly created sessions — existing ones keep whatever they were created with. And the copy is a **fork of `standard`**: a future DSH upgrade that restructures that preset will not carry over. We left the comparison command in the patch file that points at it.

We have verified the configuration layer — `--dump-config` shows our patch applied and the preset resolving to `0.5` — but **not yet observed it fire**: that needs a fresh session to run past 500,000 tokens.
