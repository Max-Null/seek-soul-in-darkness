# 思灵 1.1.0 启动失败：随包插件 peer 与内核版本脱钩

> 状态：**已定位并已本机修复**（`resources/ssid-plugins/node_modules/dsh-better-sidebar` 由 0.21.1 换为 0.24.1）
> 待办：把插件集的 pin 改成与内核对齐的版本并发 1.1.1 —— **任何装 1.1.0 的机器都会踩这个坑**
> 相关：手册坑 #58 · 坑 #55（换底座后「这个版本号是谁的」）· 坑 #57（旧 profile 不换代）

## 一、症状

装 1.1.0 后启动即弹「应用无法启动或已意外停止」，正文：

```
web boot: 3 entries did not activate
@huanlin/dsh-plugin-better-sidebar-plugin-office: pending (waiting for service: betterSidebar)
dsh-video-preview: pending (waiting for service: betterSidebar)
dsh-excel-panel: pending (waiting for service: betterSidebar)
诊断报告：…\@deepseek-ai\dsh-desktop\logs\crash-<ts>-web-boot.log
```

**从托盘选「纯净版启动」报同样的错**——这一条是重要判据（见 §三.1）。
`crash-*-web-boot.log` 的 `renderer console` 段与正文一致，没有更多信息。

## 二、根因

`betterSidebar` 是**客户端半球**的服务，由 `dsh-better-sidebar` 的 `lib/client.js` 通过 `ctx.provide('betterSidebar', service)` 注册（`lib/client.js:17513`）。**随包的是 0.21.1，它的 peer 指向内核 `^0.1.7-rc.1`，而 1.1.0 的内核是 `0.2.0-rc.1`** —— 它因此不注册该服务，三个下游一直等不到，客户端 boot 判定失败。

**最迷惑人的一点**：它**根本没进 fiber 图**。`plugin-compatibility` 对每个 bundle 的 `@deepseek-ai/dsh*` peer 跑 `semver.satisfies(...)`（`packages/boot/app-boot/src/plugin-compatibility.ts:75`），不满足时 `profile.ts:675-676` 抛错被同层 `catch` 吞成 `skippedBundles`，**该 bundle 的整个 patch 层不挂载**。于是它**既不会出现在 `did not activate` 列表里**，也不会注册服务 —— 只有等它的下游出现。而 `ctx.provide` 确实写在它的 `apply` 里、`apply` 又是同步函数：**静态读代码永远对不上**，必须拿运行时证据。

机制详解与判据见 `docs/插件测试操作手册.md` §4「peer 与跨 minor（最容易静默失效的一处）」（含 `^0.1.7-rc.1` 展开为 `>=0.1.7-rc.1 <0.2.0-0`、对 `0.2.0-rc.1` 判 false 的推导）。

### 版本矩阵（`npm view` 实测）

| 版本 | peer `@deepseek-ai/dsh-llm` | `dsh.client.inject` |
|---|---|---|
| 0.19.1（0.4.0/1.0.0 时代在用） | `^0.1.5-rc.1` | — |
| **0.21.1（1.1.0 随包）** | **`^0.1.7-rc.1`** | 5 个官方客户端模块 |
| **0.24.1（latest，换成这个）** | **`^0.2.0-rc.1`** | **完全相同** |

`inject` 数组两版一模一样，差别在**构建时配套的内核**。

## 三、排除掉的假设（各带证据）

1. **profile 污染？不是。** 托盘「纯净版启动」同样报错，说明与用户层无关；随后用**从零新建**的隔离 profile（`ssid-iso-110`）复现，症状一字不差。
2. **「peer 看着不匹配」不等于失配 —— 必须按 semver 算。** 我一度以为 0.19.1 的 `^0.1.5-rc.1` 在 1.0.0（内核 0.1.7-rc.2）上是失配却「照样能用」，据此怀疑 peer 不是判据。**算错了**：`^0.1.5-rc.1` 展开为 `>=0.1.5-rc.1 <0.2.0-0`，0.1.7-rc.2 落在区间内 —— 它本来就是满足的。真正失配的只有 `^0.1.7-rc.1` 对 `0.2.0-rc.1`（上界 `<0.2.0-0` 排除全部 0.2.0 预发布）。**peer 就是判据本身**，这道检查 09-23 起就在（`2c67633990`），1.0.0 里已经生效。
3. **`better-locale` 缺失（peer 里唯一的外部包）导致？不是。** `dsh-better-sidebar` 的 host 半边（`lib/index.js`）里 `better-locale` 命中 0 次；client 半边只有懒集成（`attachBetterLocale` 接受 `undefined`），且它声明为 `optional`。
4. **客户端入口缺失？不是。** `lib/client.js` 在（823 KB），`exports["./client"]` 指向它，`dsh.client.platform = 'web'`。
5. **`modules` / `connection` 服务在 0.2.0-rc.1 里不存在？不是。** `packages/client/modules/src/client/index.ts:66` 就是 `ctx.reflect.provide('modules', modules)`。
6. **端口 19388 冲突？不是本次的病。** 见 §五.1 —— 那是隔离复现自己的干扰。

## 四、决定性证据（A/B 对照）

同一台机、同一探针（CDP 抓渲染进程 console）、同一 profile 形态，只换 `dsh-better-sidebar` 的版本：

| | 0.21.1 | 0.24.1 |
|---|---|---|
| `web boot` fatal | **有**：`3 entries did not activate` | **消失** |
| 三个下游 | 全部 `pending` | **`[dsh-excel-panel] v0.5.0 loaded` + `xlsx viewer registered`** |

`xlsx viewer registered` 是它成功拿到 `betterSidebar` 并注册 view 的直接证据。

## 五、处置

```powershell
$sp = "$env:LOCALAPPDATA\Programs\ssid-shell\resources\ssid-plugins\node_modules"
Rename-Item "$sp\dsh-better-sidebar" "$sp\dsh-better-sidebar.bak-0.21.1"
# 解 0.24.1 的 tarball，把 package/ 的内容拷进 $sp\dsh-better-sidebar
```

**profile 不用动**：它的 `node_modules/dsh-better-sidebar` 是指向插件集的 junction，换完通过链接读到的就是新版本。
**代价**：这是直接改装版文件，**重装或自动更新会盖回去** —— 真正的修法是改插件集里的 pin 并发 1.1.1。

## 六、可复用的诊断手法

`web boot: N entries did not activate` 这句由客户端 `packages/client/web/src/boot-client.ts:87` 的 `assertEntriesActive` 抛出，**host 侧日志（`-host.log`）里没有**。抓法：

1. 隔离三件套启动装版（`--user-data-dir` + `DSH_HOME` + `SSID_PROFILE_NAME` + `SSID_LOG_FILE`），并加 `--remote-debugging-port=<port>`；
2. CDP 连 `type=page` 的 target，**先开 Runtime / Log / Page 三个域，再 `Page.reload()`** —— boot 报错发生在启动那一刻，附加太晚就错过了；
3. 参考 `.ssid-iso-test/cdp-console.mjs`。

**判据**：`pending (waiting for service: X)` → 查 X 的提供者**是不是与宿主内核版本配套构建的**（比它 peer 指向的**内核系列**），而不是去读它的 `apply` 有没有写 `ctx.provide`。

## 七、过程中的两个自伤（都已在手册里有条目）

1. **按命令行关键词 `Stop-Process` 会命中脚本自身** —— 我的命令行里含匹配串，于是把自己的 pwsh 杀了，job runner 报 `exit code 4294967295`。收隔离实例必须加 `-Filter "Name='思灵.exe'"` 限定进程名。（同坑 #54 一带）
2. **1.1.0 的 webserver 端口固定 19388**，两个实例不能并行。第一次隔离复现因此失败在 `EADDRINUSE`，host 侧就先崩了、client 的真病被掩盖。**隔离复现前必须先退掉生产实例。**

## 八、预防

1. **插件集里每个随包第三方插件的 peer 内核系列，必须与内核版本对齐。** 打包链让 npm 拉 latest，会在内核落后时埋这种雷 —— 而它**不报错、只静默不注册服务**。
2. 打包链加一道校验：随包插件的 `peerDependencies['@deepseek-ai/dsh-llm']` 必须覆盖本次内核版本。
3. 托盘「纯净版启动」只禁第三方插件，而**出问题的插件是随包的**，所以它对这类故障没有诊断力——排查时不要把它当成「用户层无关」之外的结论。
