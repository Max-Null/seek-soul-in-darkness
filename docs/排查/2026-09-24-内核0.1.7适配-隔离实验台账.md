### 改动 5：`dsh-draft-polish` 适配（settings 认领契约的三处硬要求）

host 半的适配面与「改动 3/4」同源，但**设置失效的根因与前两个不同**：node-appearance / chat-rail 是调用了已删除的 `settingsScope` 服务（报错可见），draft-polish 是**调用契约不满足、被 settings 服务静默跳过**——界面毫无异常，设置全部不生效。

**① 插件的 Config schema 必须以 `Config` 这个名字导出（本插件设置失效的真因）**

`settings/src/index.ts:425-428` 的 `schema(entry)` 读的是 **`entry.fiber.runtime.Config`**——即插件模块导出的 `Config`。本插件此前只导出 `DraftPolishPrefsSchema`，名字对不上 ⇒ settings 根本不认这个插件。随后 `volatileForm(schema)`（`:385-386`）还要求 schema 至少有 1 个可写字段，无 volatile 字段的插件同样整条跳过、不出现在 `describe()` 里。

修法是一行别名导出（`DraftPolishPrefsSchema` 的名字保持不变，其他引用不受影响）：

```ts
export { DraftPolishPrefsSchema as Config } from './config.ts'
```

**② 每个可变字段都要标 `.volatile()`，且嵌套字段的祖先也得标**

`schema.ts` 的 `isVolatilePath` 只承认「祖先节点标了 volatile」的路径；`settings/src/index.ts:388,406` 对非 volatile 路径**直接抛错**（`Config field "X" is not volatile`）。所以对象/字典型字段不能只在叶子标——这与会话前评估文档的说法相反。

**③ 旧代码吞异常是这次故障难查的原因，此处刻意不吞**

原实现把 `settings.register(...)` 抛出的 TypeError 收进一行 `console.warn`，于是「设置全失效」表现为「界面一切正常」。适配后改为加载期直接抛错（`src/index.ts:97-99` 的注释记录了这条纪律）。

**client 半无需改动**：`settings.section` 槽位在 0.1.7 **仍然存在**（`dsh-client-ui-settings/lib/types/client/contract/slots.d.ts:73`，owner props 为 `SettingsSectionOwnerProps { close }`），本插件的左栏入口注册（`src/client/index.tsx:41`）不在迁移面内——这是它与 node-appearance / chat-rail 的关键差别，后两者用的是已删除的服务而非槽位。顺带更正一处过时注释：`settings.general.item` 在 0.1.7 **仍被声明**（同文件 `:120`），并未退役。

**验证**：`typecheck` ✅ · `65/65` 测试 ✅ · `build` ✅ · loader 行 `ACTIVE` · `settings.describe()` namespace 20→21 且 `draft-polish` 有值 · 端到端三态（写 `probe-dp-c` → 读回 `probe-dp-c` → 恢复 `deepseek-v4-flash`）全部经插件自己的 `/draft-polish/api` 完成。

### 改动 4：`dsh-chat-rail` 适配（与 node-appearance 同配方，另有两处新坑）

主体改法与「改动 3」一致（Config 标 volatile、删 installSection、`settingsScope`→`configForms`、槽迁 `plugins.bundle.config`、依赖升档）。**新增两条本插件独有的发现**：

**① `@deepseek-ai/dsh-client-runtime` 已被移除——三个类型各归其位**

该包在 0.1.7 的 `packages/client` 下**没有对应目录**（列目录可验），npm 上停更于 `0.1.1-rc.2`。原来从这里 import 的三个类型现在分别来自：

| 旧 | 新 | 依据 |
| --- | --- | --- |
| `ClientContext` | `Context as ClientContext` from **`@deepseek-ai/cordis`** | client 包内 163 处官方文件全部这个写法 |
| `SessionId` | **`@deepseek-ai/dsh-session/types`** | `apply.ts:8` / `service.ts:23` / `index.ts:13` 同款 |
| `ISessions` | **`@deepseek-ai/dsh-api-session-controller/client`** | 契约定义在 `api/session-controller/src/client/contract/sessions.ts:49` |

**② `ctx.slots` 的 Context 增强来自 renderer 包，不是 ui-slots**

把 `ClientContext` 换成裸 `Context` 后，`ctx.slots` / `ctx.configForms` 都要求对应的 `declare module` 在作用域内。实测：

- `import type {} from '@deepseek-ai/dsh-client-ui-slots/client'` → **TS2307 找不到模块**（ui-slots 是 shell 预加载的静态库，无 `./client` 入口）。
- 正确来源是 **`@deepseek-ai/dsh-client-ui-renderer/client`**（slot 注册表的属主），node-appearance 的注释也写明「the ctx.slots Context merge comes from the renderer package」。

**③ 模块级单例按最小改动处理**：评估文档把 `railSettingsScope` 单例列为「架构障碍」。本次只把它换成 `railSettingsForm`（`ConfigForm` 的 `getSnapshot`/`subscribe`/`set` 与旧面同形，两处绕开 inject face 的订阅点因此一行未改），**不动骨架**。清理单例（改为经参数传递）记作独立改进，不属于内核适配的必需项。

**④ 测试断言随 `.volatile()` 调整**：`tests/projection.spec.ts` 的 `Config['~standard'].validate(undefined)` 原本断言裸布尔，现字段是 `Volatile<boolean>` 包装，改读 `.get()`（同 node-appearance 的 config.spec.ts）。

### 改动 3：`dsh-node-appearance` 完整适配（client 服务面重写）

这是四个「会坏」插件里最复杂的一个（host 半 + client 半 + 槽迁移 + 依赖升级 + 图标改名）。**它的改法可直接套用到 `dsh-chat-rail` / `dsh-draft-polish`**。

**① host 半：`settings.installSection` 已不存在**

0.1.7 的 Settings 服务公开面只有 `configure` / `describe` / `update` / `replace` / `mutate`（`settings/src/index.ts:266,296,302,347,357,367`）。**插件的 Config schema 本身就构成它的 settings section**——官方范例见 `web-search-deepseek/src/index.ts`：`export interface Config` 用 `Volatile<T>` 包字段、`export const Config = z.object({...})` 里逐个 `.volatile()`、`apply` 里用 `config.<field>.get()` 读值，**全篇没有 installSection**。

- `installSection` 段整个删掉，`apply` 变成空体。
- `Config` 接口：三个字段**全部**包 `Volatile<T>`。
- schema：`showThinking` / `colors` / `toolColors` 全部加 `.volatile()`。

⚠️ **`colors` / `toolColors` 也必须标 volatile**（与评估文档 §2.1 的说法相反，有代码证据）：`settings/src/schema.ts` 的 `isVolatilePath` 只承认「祖先节点标了 volatile」的路径，而 `settings/src/index.ts:406` 对非 volatile 路径直接 `throw new Error(... is not volatile)`。漏标会让浏览器半写配色时抛错。标了之后其整棵子树（含 `colors.search`）都可写。

⚠️ **不要写 `z<Config>` 显式泛型**：`.volatile()` 把 schema 的 Mode 变成 `'volatile-defined'`，与接口里 `Volatile<T>` 不是同一个 Mode，显式标注会报 TS2322（`default()` 参数类型不兼容）。官方范例同样不标。

**② client 半：`settingsScope` → `configForms`**

`settingsScope` 在 0.1.7 的 client 包里 **0 命中**（`Select-String` 全 client 目录无结果）。替代者是官方 ui-settings 的 `ConfigForms`（`config-form.ts:241`，服务名 `configForms`）。

`ConfigForm<T>`（`config-form-types.ts:39`）与旧 scope 面**几乎同形**：`getSnapshot()` / `subscribe()` / `set(field, value)` 同名同义，额外有 `mutate(ops, rev)` 与 `unset(field)`。

- `ctx.settingsScope.bind<T>({ namespace: NS })` → **`ctx.configForms.get<T>(NS)`**。参数是 Host 插件的 **entry id**（`ConfigForms.get` 的 JSDoc：Unique Host plugin entry id），与 `cordis.patch.yml` 里的行 id 同值。
- `inject` 数组里 `'settingsScope'` → `'configForms'`。
- `hooks: { xxx: scope }` 可直接换成 `form`——`ConfigForm<T>` 结构上满足 `ObservableSnapshot<ConfigFormSnapshot<T>>`。
- 组件的读路径（`snapshot.value` / `.writable` / `.status`）**字段同名**，不用改。

⚠️ **`set(field, value)` 只接受标量字段**（其 JSDoc：scalar field inside the namespace section）。写 `colors` / `toolColors` 这类**对象**必须走 `mutate()`：
```ts
await form.mutate([{ op: 'set', path: ['colors'], value: { ...value.colors } }] as never)
```
`SettingsPathOpView`（`settings/src/types.ts:52`）= `{ op:'set'; path: string[]; value } | { op:'unset'; path }`，注释说明写入会「creating intermediate objects」，所以整棵子树可以一次写掉。

**③ 槽迁移：`settings.plugin.item` → `plugins.bundle.config`**

`settings.plugin.item` 在 0.1.7 的 client 包里只剩 1 处命中（一条注释），替代者是三个槽（`ui-plugin-manager/src/client/slot-contract.ts:75-121`）：

| 槽 | key | 用途 |
| --- | --- | --- |
| `plugins.item` | list | **官方插件专用**——契约原文「OCCUPIED by the official settings pages」，第三方不该占 |
| `plugins.bundle.config` | **bundle 的包名** | bundle 自己的配置，只渲染 `view: 'page'` |
| `plugins.row.config` | `包名#行id`（`config-ledger.ts` 的 `rowConfigKey`） | 某一行自己的配置页 |

本插件的 `package.json` 有 `dsh.bundle.patch`，自身就是一个 bundle，所以用 `plugins.bundle.config` + **包名**。

### 改动 1：`dsh-ssid-achievements` 会话计数失效（小改）

**根因**：`src/index.ts` 订阅 `agent/session-start`，该事件在 0.1.7 全树 0 命中（0.1.5 在 `core/agent/src/runtime-types.ts`）。cordis 对未知事件名静默 → 监听器永不触发 → `sessions` 恒为 0 → `first-session` 永久不解锁。另发现 `engine.ts` 里兜底的 `session/start` 分支**两版都不存在该事件**，是从头就死的代码。

**改法**（按评估文档建议的稳妥路径，不选 `agent/created`——那是可否决的 serial 监听，抛错会挡住 agent 创建）：

- `src/engine.ts`：新增 `recordSessionOnce(sessionId)`（按会话 id 去重）；`session/event` 分支改按每会话首个 `turn/start` 记账；删掉死的 `session/start` 分支。
- `src/index.ts`：移除 `agent/session-start` 订阅（会话计数已由 engine 接管），保留仍在的 `agent/turn-stopping`。
- `tests/engine.spec.ts`：新增 2 个测试（`turn/start` 记账 + 逐会话去重 + 断言接线里不再有 `agent/session-start`）。

**验证**（真实对话，非模拟）：通过 `agent.followup()` 发一条真实消息 → 会话日志出现完整 `user/message → turn/start → assistant/message → turn/end`（22 事件）→ `/achievements/api/list` 显示 **9 个成就解锁**，含 `first-session`（进度 1/1）。修复前该成就阈值为 1 但计数恒 0，永久不解锁。

`typecheck` 通过、`15/15` 测试通过、`npm run build` 通过。

## 已掌握的坑

1. **`@deepseek-ai/dsh-*` 必须只有一份模块实例**（dev 下 tsx paths 会让它变两份，导致 preset 全线挂不住）。详见 `docs/决策/2026-09-24-内核0.1.7-preset挂载失败根因.md`。
2. **复制插件时要排除 `node_modules`**：`dsh-ssid-panels` 的源目录带 194 MB `node_modules`，整目录递归复制会超时。
3. **`ssid-panels` 的 API 方法名带点**（`sessionRoot.get`、`guardian.snapshot`），路由是 `kind:'prefix'` + 只接受 POST；用 GET 测会得到 405，用错方法名得到 404。
4. profile 闭包缺三个 peer 包会表现为对应行 `failed to import`：`@deepseek-ai/dsh-ptc-runtime`、`dsh-deepseek-account`、`dsh-llm-deepseek`。
5. **插件的 Config schema 必须以 `Config` 这个名字导出**，否则 settings 服务**静默**不认它（`settings/src/index.ts:425` 读的是 `entry.fiber.runtime.Config`）；且 schema 至少要有一个 `.volatile()` 字段，否则 `volatileForm` 把它整条跳过、`describe()` 里根本不出现。失败表现是「界面一切正常、设置全部不生效」——最难查的一类。详见「改动 5」。
6. **判断某行是否「坏」不要只看 PID/启动日志**：`state` 数值 2=ACTIVE、3=FAILED、0=PENDING；`probe-sc-state.js` 是现成的只读探针。而且**写入 settings 会连带改变官方行的状态**（见「已知未解 3」），排查插件问题时别把它算到插件头上。
7. **探针别对「写接口」发空对象**（2026-09-24 自伤）：`quick-toolbar` 的 `POST /quick-toolbar/api/state` 是**整状态覆盖写**（`src/index.ts:138-144` 的 `writeStateFile(normalizeState(body))`），我为了探路由连通性发了一次 `POST {}`，`normalizeState({})` 返回全默认值（`shellVisible: false`）→ 状态文件被覆盖 → 重启后 client 按壳环境规则把悬浮工具栏移除了。**排查了半天的「装 better-sidebar 后工具栏消失」，真凶是自己的探针。** 教训：探写接口要么用 GET，要么带真实全量载荷并事后还原。
8. **`location.reload()` 不等于冷启动**（2026-09-24 实测）：reload 后查 quick-toolbar 的聚合按钮只有 5 个，冷启动后是 9 个（`插件中心`/`会话管理`/`Remote`/`上下文洞察` 四个在 reload 后缺席）。**判据：UI 聚合类结论必须取自冷启动**，reload 只能用来验证「内核侧没变」的那部分。这次差点把 reload 的假象记成「装 better-sidebar 后的回归」。
9. **往隔离 profile 装 npm 第三方包，不能走 `装插件.ps1`**：那个脚本第 40 行是「先 `Remove-Item $dst` 再从源目录复制」，而 npm 包的源目录**就是** `node_modules` 下的 `dst` —— 等于自毁。npm 包的正规装法是 `pnpm add <pkg>@<ver> --config.minimumReleaseAge=0` + **手写** patch 行（从包自带的 `cordis.patch.yml` 抄，如 better-sidebar 那行带 `!!js` 防重复挂载守卫）。

## 已知未解

1. **`ssid-panels` 的 `session.events` 既存缺陷**（评估文档 §3.3）：该 API 在所有版本都不存在，`interruptedTurnClosers(undefined)` 抛 TypeError，相关 HTTP 分支返回 500。属升级前就有的缺陷，尚未修。
2. **UI 自动化受限**：Electron 主窗口里 `contenteditable` 输入框无法用 CDP 的 `Input.insertText` / 焦点注入写入（`focus()` 后 `document.activeElement` 仍被 `H2` 占用）。端到端验证改用 `agent.followup()` 走内核侧，已验证可行。
3. **改一次设置就打挂 `session-controller`，SSiD 随即无法建会话**（DSH 0.1.7-rc.2 缺陷，**升级阻塞项**）

   **现象（100% 重现，两次实验两次命中）**：冷启动后 `session-controller` / `ui-deliverables` / `file-upload` 三行全 `ACTIVE`；此后**任意插件、任意字段**的第一次 settings 写入，都会把 `session-controller` 打成 `state=3` FAILED（错误 `file-upload: Agent resolver is already registered`）、`ui-deliverables` 打成 PENDING，且**不会自愈**。写入调用本身还会抛异常，文案就是启动警告原文（`dsh: warning: 2 entries did not activate …`）。

   **后果**：`ctx.get('sessionController')` 变 `ABSENT`，UI 点「新建会话」直接失败——实测 toast 原文：`新建会话失败：gateway/service-unavailable: typert gateway: session/create: active Service "sessionController" is unavailable`。一句话：**用户改任何一次插件设置，SSiD 就再也建不了会话，直到重启。**

   **触发链**：settings 写入 → `configEditor.edit()` → `reconcileProfilePatches()`（`dsh-app-boot/lib/index.js:3467`）→ `entry.update({config:{patches}})` → include 重载（`cordis-plugin-include/lib/index.js:132`）→ 新 `session-controller` 实例构造时注册 resolver，而**旧实例的 disposer 尚未执行** ⇒ 撞上 file-upload 的单槽 `agentResolver`（`dsh-client-file-upload/lib/index.js:190`，源码对应 `client/file-upload/src/index.ts:91`）。

   **为什么「第一次写必错、之后不再错」**：`reconcileProfilePatches` 的 `introduced` 判定（`:3490`）拿 `previous.fiber === failure.entry.fiber` 比 **fiber 对象身份**，而 reload 必然重建 fiber，所以那次新失败被算作「新引入」并抛错；下一次写入时该行**已经是**失败态、fiber 身份不变，于是不再算 introduced——异常消失，但服务不会回来。

   **修正先前的认识**：此前记为「间歇性、重启即消失的**启动**竞态」，**不准确**——它不在启动期发生，而是由设置写入**稳定触发**；之前看到「重启即恢复」，是因为重启绕过了写入，不是竞态窗口消失了。

   **归属（非本工作区引入）**：`profileContext` 是官方机制——官方 `dsh` CLI 的 profile boot 同样 `provide("profileContext", …)`（`dsh/lib/profile-boot-BZ2ZjNWi.js:273`），而 `prepareProfilePatches` 只在它存在时才把 patches 重写成全量 rows（`dsh-app-boot/lib/index.js:2150`）。SSiD 自建 boot 只是对齐了同一语义（`shell/kernel.ts:634`），没有额外插手这条路径（`kernel-child.ts` 里 `profileContext` **零命中**）。npm 上 `@deepseek-ai/dsh` 的 `next` tag 就是 `0.1.7-rc.2`——**没有更高版本可升**。

   **④ 其他桌面端 DSH 项目是否遇到**（2026-09-24 查证）：**没有找到该问题的报告**。查过 `dsh-tauri/deepseek-harness-desktop`（23 个 open issue，含 [#648](https://github.com/dsh-tauri/deepseek-harness-desktop/issues/648) 会话锁死——根因是 worktree 模式，已由 #650 修复）、`fufankeji/deepseek-harness-studio`，以及全局关键词搜索。**但「没报」不等于「不复现」**——关键差别在架构：

   - **`dsh-tauri` 版是包装官方 `dsh web` CLI**（它自己的运行日志就是 `dsh web: http://127.0.0.1:3083/?token=…`，由 `main::service::workflow::launch` 拉起），因此走官方 `profile-boot` 路径、**有 hmr watch**。
   - **SSiD 是自建 boot**（`shell/kernel.ts` 直接 `dsh.boot()`，刻意不跑官方 `runProfile`），hmr 行 FAILED、没有那个 watcher。
   - 社区搜索还碰到一条同族现象：[Discussion #5864](https://github.com/deepseek-ai/deepseek-harness/discussions/5864)「Plugin-tree boot crash-loops when a plugin imports an export the bundled @deepseek-ai package no longer provides」——同样是「插件树整体坏掉」，但触发条件是 import 缺失导出，与本问题不同。

   **⑤ profileContext 逐字段对比——排除**（这是第 4 个假设）。把官方 `profile-boot-BZ2ZjNWi.js:259-270` 的 profileContext 与 SSiD `kernel.ts:634-644` 逐字段对齐后：

   | 字段 | 官方 | SSiD | 结论 |
   | --- | --- | --- | --- |
   | `name` / `dir` / `patchPath` / `installAnchor` / `cwd` / `home` / `telemetryDisabledEnv` | — | — | ✅ 一致 |
   | `overlays` | `composed.overlays` | `[]` | ✅ 无 `--patch` 时同为空 |
   | `packageManager` | 条件提供 | 未提供 | 只服务 CLI 的插件安装，与 reload 无关 |
   | `startedBundles` | `layers.map(l => l.packageName)` | `PROFILE_BUNDLES` 常量 | ✅ 常量值（`dsh-base` + `dsh-web-app`）与实际 layers **正好一致**；且它的消费者只有 `dsh-hmr`（manifest 变化检测，我们的 hmr 是 FAILED 的、不消费）、`plugin-manager`（保护自身）、类型声明——**与 reload 无关** |

   即：**SSiD 与官方在 reload 相关字段上等价**。这条排除很有分量——它意味着「官方 `dsh web` 同样复现」的可能性进一步上升，而不是「SSiD 特有」。

   **⑥ 对照实验已做——结论：官方路径不复现，这是 SSiD 特有问题，且根因定位到一行**（2026-09-24）

   实验设计：在**全新 home**（`.ssid-iso-test\official-probe`，profile `probe`，闭包用 junction 只读复用）上调用**官方 `runProfile`**——即官方 `dsh` CLI（`lib/bin.js:212`）启动 profile 用的那个函数，脚本见 `.ssid-iso-test\official-probe.mjs`。这样就走的是**官方路径**（有 appReady、有 hmr watch、profileContext 由官方构造）。结果：

   | 判据 | 官方 `runProfile` 路径 | SSiD 自建 boot |
   | --- | --- | --- |
   | 非 ACTIVE 行 | **0 个** | `hmr` + `session-controller` |
   | `hmr` 行 | **ACTIVE (2)** | FAILED (3)，`Profile HMR requires application readiness` |
   | 设置写入返回 | **`status: ok`，无异常** | 抛 `dsh: warning: 2 entries did not activate` |
   | 写入后 `session-controller` | **ACTIVE (2)** | **FAILED (3)** |
   | `sessionController` 服务 | **present** | **ABSENT** |

   即：**同一份闭包、同一版本的 settings.update，官方路径完全无事**。所以这不是 DSH 的 bug，是 **SSiD 自建 boot 的缺陷**——之前「hmr 只当互斥锁、两条路径等价」的判断**是错的**，唯一的结构性差异恰恰就是 **hmr 是否 ACTIVE**。

   **根因（一行差异）**：`shell/kernel.ts:655-660` 的 `provideCmdline` 只传了 `args` 与 `exit`，而官方 `profile-boot` 传三个（`lib/profile-boot-BZ2ZjNWi.js:276-280`）：

   ```js
   provideCmdline(hostCtx, { args: options.args, exit: ..., ready: appReady.service })  // 官方
   provideCmdline(hostCtx, { args: [...], exit })                                       // SSiD ← 少 ready
   ```

   `ready` 即 `appReady` 服务（`dsh-cmdline` 的 `index.d.ts:57` 声明为可选参数 `appReady?: AppReady`，接口只有 `onReady(listener)`）。而 `dsh-hmr/lib/index.js:341-342` 正是靠它才能起步：

   ```js
   const ready = this.ownerContext.get("appReady");
   if (ready === void 0) throw new Error("Profile HMR requires application readiness");
   ```

   **完整因果链**：SSiD 不传 `ready` → `appReady` 服务不存在 → `dsh-hmr` 抛错、**FAILED** → `ctx.get('hmr') === undefined` → `dsh-config-editor/lib/index.js:127-128` 走 `hmr === void 0 ? run() : hmr.runExclusive(run)` 的**裸 `run()` 分支** → 那次 reconcile 触发 entry 重新执行 → `session-controller` 构造函数二次执行，而旧实例的 `ctx.effect` disposer 尚未运行 → 撞上 file-upload 的单槽 `agentResolver` → FAILED、服务消失、建不了会话。

   **修复方案（壳侧，20 行）**：官方 `createAppReady`（`profile-boot-BZ2ZjNWi.js:87-108`）未导出，但其语义可等价重写——`{ service: { onReady(listener) }, commit() }`，在 boot 成功（`ctx.fiber.state === 2 && ctx.get('loader') !== undefined`）后 commit，与官方 `:283` 的调用点一致。**影响面**：只影响 dev 实例（安装版跑打包的 `kernel.bundle.mjs`，不重新打包就不受影响），**当前会话宿主不受影响**。修复后需重启隔离实例验证 `hmr` 变 ACTIVE、且设置写入不再打挂 `session-controller`。

   **② 联网查证（2026-09-24）**：社区**没有**这个问题的报告——`deepseek-ai/deepseek-harness` 的 `open_issues_count` 是 **0**（他们走 Discussions），多轮不同关键词（`Agent resolver`、`sessionController is unavailable`、设置保存后插件挂掉…）均未命中。查到的相近但**不同**的问题：[#4727](https://github.com/deepseek-ai/deepseek-harness/discussions/4727)（preset 挂载失败）、[#5769](https://github.com/deepseek-ai/deepseek-harness/discussions/5769) / [#918](https://github.com/deepseek-ai/deepseek-harness/discussions/918)（`Session.append` 无法标 ignorable，第三方事件类型让会话无法恢复）、[#5873](https://github.com/deepseek-ai/deepseek-harness/discussions/5873)（preset 重命名留下陈旧默认值破坏新建会话）、[dsh-tauri/deepseek-harness-desktop#648](https://github.com/dsh-tauri/deepseek-harness-desktop/issues/648)（worktree 模式导致会话锁死，已由 #650 修复）。社区适配 0.1.7 settings 的实践见 [omdsh-dev/dsh-mnemon#270](https://github.com/omdsh-dev/dsh-mnemon/pull/270)（「0.1.7-alpha.1 移除动态 `settings.register`」，改走宿主 Config 写入器）。社区排障库 [sandbaseai/deepseek-harness-handbook](https://github.com/sandbaseai/deepseek-harness-handbook/tree/main/docs/en/troubleshooting) 有 105 篇，与本问题最接近的是「live reload 与冷启动必须分开判」那条机制说明，**没有对应条目**。

   **③ 已排除的假设**（各带证据，避免重复走）：
   - **不是「SSiD 自实现 patch 热重载」**：`patchReload` 在官方闭包里 **grep 零命中**（它不是 DSH 概念，是壳自己的字段），壳源码里也 grep 不到 `fs.watch` / `createWatcher` / `config-reload` 的自实现。
   - **不是「hmr 行 FAILED 导致」**：`dsh-config-editor/lib/index.js:127-128` 是 `hmr === undefined ? run() : hmr.runExclusive(run)`——hmr 只当**互斥锁**用，没有它照跑；而 hmr 的 watch 路径（`dsh-hmr/lib/index.js:370`）调的是**同一个** `reconcileProfilePatches`。两条路径在这里没有行为差异。
   - **不是「entry 整体 remount」**：写入前后对比 206 个 entry 的 fiber **对象身份，206/206 全同**（`changedFiber: 0`）⇒ 不是重建整棵树。
   - **机制层的剩余事实**：错误堆栈 `at new SessionController` 表明 constructor **在同一个 fiber 上被第二次执行**（cordis 的 fiber 复用重跑），而旧实例的 `ctx.effect` disposer 尚未运行 ⇒ 撞上 file-upload 的单槽。再往下的 cordis 内部执行顺序尚未继续深挖，**对照实验（官方 `dsh web` 是否同样复现）也还没做**——这是判定「官方 bug」还是「SSiD 特有」的唯一硬判据。

4. **`systemPrompt.layers.scoped.size` 是动态量**，随 runtime 建立了几个 scope 层而变（实测出现过 4/5/7）。**不能用它做回归判据**；判据应看 `agentPresets.list()` 有无 `broken`、以及各 `@max-null/*` 行的 state。

## 修复记录：设置写入/热重载打挂 `session-controller`（2026-09-25，**已修复并验收**）

**根因：两条「只在内存里追加」的 patch。**

SSiD 自建 boot 在把 patches 交给内核之前，会额外 `patches.push` 两条条目：

1. `agent-presets` 的 shipped root 注入（官方靠 `composeProfile` 做同样的事，壳不用它，所以自己模拟）；
2. 会话隔离的 `session-persistence-jsonl.root` 覆盖（把会话日志指到 `sessions-<profile>`）。

这两条**只存在于内存**。而之后每一次 reconcile（hmr 醒来时的首次 refresh、或任何设置写入）都走官方
`readProfilePatches`，它**重新读文件**，看不到这两条 ⇒ boot 写进 `include` 的 config 与 reconcile
重算的结果**必然不同** ⇒ cordis 判定 entry config 变化 ⇒ **重新执行整棵 entry 树**（fiber 对象复用、
plugin 被重跑）⇒ `session-controller` 构造函数二次执行，而旧实例的 `ctx.effect` disposer 尚未运行
⇒ 撞上 file-upload 的单槽 `agentResolver` ⇒ FAILED、服务消失、**建不了会话**。

**为什么以前从未暴露**：修好 `appReady` 之前 `hmr` 一直 FAILED，**根本没有东西会去 reconcile**；
补上 `appReady`（`provideCmdline` 的 `ready` 参数）让 hmr 真正起来后，那次 reconcile 才第一次发生。
换句话说，前一轮那个修复是正确的，只是它把一个一直存在的地雷踩响了。

**修复（三处）**：

1. **把两条追加落成运行时 overlay 文件**：`<profile.dir>/.ssid-runtime.patch.yml`，内容用 JSON 写
   （YAML 是 JSON 的超集，官方解析器照读），并让 `profileContext.overlays` 指向它——这样
   `readProfilePatches` 与 boot 读到的是**同一份内容**。
2. **boot 的 patches 改为直接调用官方同一个 `dsh.readProfilePatches(BIN_NAME, profileContext, profile)`**；
   遥测行由它内部按同一判据补齐，壳侧不再自行 push 任何条目。
3. `composeEntries` 与 `boot` 两处**喂克隆**：`applyEntryPatches` 会**就地**改写传入的 patch 条目
   （键序随之变化），不隔离就会让「本进程内那份」与「重读文件那份」持续分叉。

**验证（在删除全部诊断代码后的最终代码上测得）**：

| 判据 | 结果 |
| --- | --- |
| (a) `hmr` 行 | **ACTIVE** |
| (b) 冷启动后 | `session-controller` / `ui-deliverables` / `file-upload` **全部 ACTIVE**；`sessionController` 服务 present |
| (c) 一次设置写入后 | `err: null`；三行**仍全部 ACTIVE**；值正确恢复（`budgetTokens=1024`） |
| (d) UI 点「新建会话」 | **零错误 toast** |

隔离边界复核：真实 profile **489 条目 / `0.1.5-rc.2` / `2026-09-22 02:17:59`**，`思灵.exe` **7 个** —— 全程未受影响。

**顺带确认的关键事实**：`entry.update()` 在 config 相同时**是 no-op**。对照实验（官方 `runProfile` 路径下
强制触碰 patch 文件触发一次真实 reconcile）显示 `session-controller` 仍 ACTIVE、非激活行数为 0
——所以问题从来不是「重跑本身」，而是**两侧 config 真的不同**。这条否定了先前的两个假设：
「hmr 起来就必然重跑」与「官方只是碰巧没触发 watcher」。

**残留（不影响验收，未再深究）**：`include` 与重算结果之间仍存在**纯键序差异**
（同一对象的 `disabled` 与 `config` 先后不同，来自 `preflight` 的 `deny()` 追加键）。实测无害。

## 插件注册机制迁移：patch insert 行 → `dependencies` + `dsh.profile.bundles`（2026-09-25，**已验收**）

**起因**：0.1.7 新增官方插件 `@deepseek-ai/dsh-plugin-manager`（+ 客户端半 `dsh-client-ui-plugin-manager`），侧栏「插件」页给出「官方 / 已安装」两个分组。dev 隔离 profile 打开该页时「已安装」只有 **3**，而当时实际在跑的自制插件有 19 个。

### 数据来源（源码级）

服务面 `@deepseek-ai/dsh-plugin-manager` 的 `listBundles()`（`lib/types/index.js:282-324`）：

- `selected` = profile `package.json` 的 `dsh.profile.bundles`（`:285`）；`dependencies` = 同文件 `dependencies` 的键（`:286`）
- **`const installed = dependencies.includes(name)`（`:291`）**——「已安装」的唯一判据就是「该名字在 profile `package.json` 的 `dependencies` 里」

界面面 `dsh-client-ui-plugin-manager`（`lib/client.js`）：

- `:2720` `listed` = 去掉 6 个内置（`BUILTIN_PROFILE_BUNDLES`，`:1363-1370`）、且 `installed || optional || error` 的行
- `:2721` `mine` = `installed || !optional` → 渲染为 `bundlesTitle`「已安装」（`:2907`），其余归「官方」

**两侧都不读 `cordis.patch.yml` 的 insert 行。** 靠 patch 行挂载的插件在这个管理器眼里不存在：`listPlugins()` 里连 `include` 根本身都标 `readOnlyReason: 'unaddressable'`——既不计入「已安装」，也无法启停。

### 为什么恰好是 3

迁移前 dev profile `package.json` 的 `dependencies` 里，非 `@deepseek-ai/*` 的条目只有三条：`@changfenhuang/dsh-genui@0.11.1`、`dsh-better-sidebar@0.21.1`、`dsh-sidebar-qa@1.0.2`（备份 `profiles/ssid-dev/package.json.bak-pluginreg-20260925-215439`）。19 个自制插件当时全部靠 `cordis.patch.yml` 的 insert 行挂载，**不在 dependencies、也不在 bundles 数组**。

### 迁移做法（dev 侧）

1. 建 `profiles/ssid-dev/vendor/`，逐份复制 19 个自制插件实体（共 2.9 MB）；
2. `package.json`：加 19 条 `"@max-null/dsh-x": "file:./vendor/dsh-x"`，`dsh.profile.bundles` 由 2 条扩到 24 条；
3. `cordis.patch.yml` 只留一条真正的配置覆盖（`ui-settings-general`），**删净全部 insert 行**；
4. `pnpm install --no-frozen-lockfile` → `Packages: +19 -80`，exit 0；
5. 冷启动验收：`session-controller` / `ui-deliverables` / `file-upload` / `hmr` 四行 `state=2`，**全实例非 ACTIVE 行 = 0**；
6. UI 实测（Electron 页面 CDP）：插件页「官方 **7**」「已安装 **22**」——22 = 19 自制 + 3 第三方，与 `listBundles()` 中 `installed:true` 的 22 条逐一对上（探针 `probe-pm2.js` / `ui-pm-count.js`，输出 `pm2-out.txt` / `pm-ui1.txt`）。

### 两条硬约束

- **insert 行与 bundle 声明互斥**：同一插件既写进 `dependencies`/`bundles`、又手写 insert 行 ⇒ **双份挂载**。迁移必须删净 patch 里的 insert 行。`better-sidebar` 那行带的 `disabled: !!js` 防重复守卫是给「无聚合 bundle 的环境」准备的，SSiD 侧用不上。
- **发版基准本来就是新形式**：`shell/profile-template/package.json` 一直是 34 条 bundles + 全量 dependencies（含 5 个 `file:./vendor/*`），**没有 insert 行**——偏差只存在于「从真实 profile 复制出来的历史遗留 profile」，SSiD 发布出去的装版不受影响。

### 未覆盖

真实 profile `~/.dsh/profiles/ssid`（0.1.5-rc.2，本轮全程未动）仍是 patch-insert 形式：升级到 0.1.7 后，它的插件管理页同样只会显示那 3 个第三方插件。升级时要一并做这次迁移（见「待办」）。
