# 多实例共用 storages：工作区登记静默丢失

> 状态：**根因已定位 · 登记层已处置（对账脚本）** · 2026-09-17
> 触发：用户报告「重启 SSiD 后，一批会话从 WorkStation 工作区掉到『未分组』」
> 结论：**与重启无关**。DSH web 与 SSiD 同时运行时共用 `~/.dsh/storages/`，而该目录下的写入是「读—改—写全量覆盖」——两个实例互相覆盖对方的改动。
> 后续：登记层的存量、工具与两处口径勘误见 `docs/决策/2026-09-17-工作区登记对账.md` 与本文 §七。

## 一、现象与定位过程

用户观察到「重启前在 WorkStation 工作区、重启后变成未分组」。逐层查证后，结论与直觉相反：

| 查证点 | 结果 |
|---|---|
| 会话的 cwd 是否与工作区路径不符 | **不符**：未分组会话的 `header.cwd` 逐字等于 `H:\MaxNull\WorkStation` |
| `realpathSync.native` 是否改变了路径形式 | 没有，返回同一字符串（排除路径规范化差异） |
| 工作区登记的时间分布 | WorkStation 登记的 29 个会话**全部创建于 08-19 ~ 08-22**，之后一个都没有 |
| 会话规模 | `~/.dsh/sessions-ssid` 下 235 个会话，**142 个未登记**（⚠️ 这个数字后来被证伪，见 §七） |
| UI 分组依据 | 会话的 `workspaceId`，来自各工作区 `sessionIds` 的反向索引（`workspace/src/index.ts:470`） |

即：**登记在 08-22 之后就停了**，不是重启造成的。

## 二、根因

**08-22** 是 SSiD 引入「会话根隔离」（`sessions-ssid`）的日子——目的正是让 web 与 SSiD 能并行运行。隔离解决了**会话数据**的冲突，但 **`~/.dsh/storages/` 下的其他状态没有跟着隔离**，两个实例仍在同一份文件上竞争。

写入模式（两处同构，无锁、无合并）：

```js
// max-null-plugins/dsh-memory/src/engine.ts:298
writeFileSync(path, `${JSON.stringify(document, null, 2)}\n`)
```

```ts
// deepseek-harness/packages/workspace/workspace/src/entity.ts —— mutate 全量写回 record
```

**为什么 8 月那批会话能在互相覆盖中幸存**：两个实例启动时都加载过它们，**双方内存里都有**，谁写回都删不掉；而新会话只存在于创建者一方的内存里，被另一方写回时即消失。

**为什么用户没看到报错**：登记失败只进 console（`ui-workspace/src/client/navigation.ts:171`）：

```ts
(reason: unknown) => { console.warn('new session failed:', reason) },
```

## 三、共用面（隔离边界在哪里断的）

`~/.dsh/` 下**已隔离**的只有会话数据：

- `sessions-ssid`（SSiD 隔离根）· `sessions`（共享根）

**仍共用、且会被两边写入**的：

| 路径 | 内容 | 写入模式 | 风险 |
|---|---|---|---|
| `storages/workspace.json` | 工作区与登记 | 全量覆盖 | **已确认丢失** |
| `storages/memory.json` | **跨会话记忆** | 全量覆盖（`engine.ts:298`） | **会丢记忆** |
| `storages/query-log.json` | 记忆查询日志 | 全量覆盖（`query-log.ts:301`） | 计数偏差 |
| `storages/guardian/`、`storages/habit/` | 插件统计 | 插件自管 | 统计丢失 |
| `storages/session_projcache/` | 投影缓存 | 可重建 | 低（重算即恢复） |
| `chat-rail-favorites.json`、`quick-toolbar-*.json`、`dream-skin.json`、`plugin-center-*.json` | 插件自建存储 | 全量覆盖 | 收藏/状态丢失 |
| `settings.yaml`、`.credentials.yaml` | 设置与凭据 | — | 覆盖后配置回退 |

**这一条比工作区分组严重**：记忆是「写入即生效」，一旦被另一实例的写回覆盖，用户不会收到任何提示。

## 四、修复选项

### 两个官方后端都声明跨进程 out of scope（2026-09-17 查证）

- `packages/storage/storage-json/src/index.ts:5-9`：「Rename is an atomic replace on POSIX and on Windows … **writer per process and last-write-wins is correct.**」
- `packages/storage/storage-sqlite/README.md` 的 Known Limitations：「**No busy-wait or retry policy** — a competing connection holding a write lock rejects the operation immediately instead of waiting; the domain layer's write chain serializes writes within one process, and **cross-process coordination is out of scope**.」

即：**单进程写者是存储层的设计假设，不是遗漏**。因此换后端不构成根治；而应用层（workspace / memory 的「读—改—写」周期）的协调**无法由后端加锁覆盖**——锁只能罩住单次写入，丢更新的窗口横跨整个周期。

`storage-domain` 的 `backend` 字段可按 domain 路由后端，所以换 sqlite 是配置层可做的；它的实际收益是把「静默丢数据」换成「行级隔离 + 冲突立即报错」。

| 方案 | 做法 | 代价 |
|---|---|---|
| 短期避让 | 不同时运行两个实例 | 立刻可用，但改变使用习惯；且要求不了别人 |
| 中期隔离 | 让 SSiD 使用独立的 `storages`（对称于会话根隔离） | 工作区与记忆**分成两套**——记忆的目的就是跨会话，分离等于自造枷锁（用户 2026-09-17 否决） |
| 换 sqlite 后端 | `storage-domain.backend: sqlite` | 从「静默丢」改善为「明确报错」；但需**自行迁移**（官方无迁移工具），且仍不根治 |
| **根治** | **DSH 侧为 storage 引入跨进程协调（锁或合并写）** | **唯一真正的解**；属上游设计变更，非补丁 |
| 兜底 | 对高价值文件做轮转快照 | 治标，恢复仍需人工 |

**判断**：若双开是常态，中期隔离只是把「互相覆盖」换成「数据分家」——真正的解法是 **root 的写入协调**。但记忆是否**应当**跨环境共享，是一个独立的产品问题：共享意味着两边看到同一份记忆，代价是需要合并语义。

## 五、待确认

## 六、恢复已丢失的登记（已处置）

工具：`shell/scripts/heal-workspace-registry.mjs`——按会话 cwd 归位，规则照 `WorkspaceRegistry.bootstrap()`（前置合并、只加不删、跳过已归档），默认 dry-run，`--apply` 才写并在同目录留备份。

**已实跑（2026-09-17 23:41，实例运行中）**：补入 165 条（WorkStation 29→120、profiles-ssid 13→58、profiles-web 3→12、台本 1→9、deepseek-harness 42→43、新建 `seek-soul-in-darkness\shell` 工作区 11），跳过临时目录 9 条与目录不存在的笔误 cwd 1 条；重启后登记原样保留（264 条），SSiD 正常启动。

**「必须停实例后跑」这个说法要修正**：它只在**工作区变动**时才会被内存态覆盖——该文件上次被写是当天 04:34，之后 18 小时没动，说明不是周期性 flush。所以运行中写回是可行的，条件是写回到重启之间不发生「新建/删除会话、跨分组移动会话、新建工作区」。拿不准就等停机再跑，两种时机脚本都安全（写前留备份）。

## 七、勘误（2026-09-17 晚）

- **「142 个未登记」是错的**。会话目录名有的带 `session-` 前缀、有的不带，第一版统计脚本拿目录名当键，大批会话没匹配上。改用会话日志首帧 header 里的 `id` 重扫后结论反转：登记其实**大体健康**——`deepseek-harness` 42 条全在、`seek-soul-in-darkness` 9 条全在、`test` 2 条全在，缺失集中在两个活跃工作区（WorkStation、profiles-ssid）。**统计脚本错了比没有统计更危险**，它会导向错误的修复方案。
- **「登记在 08-22 之后停了」是现象，不是机制**。机制是：`WorkspaceRegistry.bootstrap()` 只在 `global.initialized === false` 时跑一次（`packages/workspace/workspace/src/index.ts:127-130`），而本机早已 `initialized: true`——于是登记一旦丢失就**再无兜底**。这与 §二写的「写入互相覆盖」是同一条链的两端：覆盖是丢的原因，bootstrap 不跑是丢之后长不回来的原因。
- **统计口径要先自问「算的是哪个集合」**：`sessions-ssid`（237 条）与 `sessions`（286 条）两个根有大量重复 id（会话根隔离时整体复制过），并集只有 333 条。算未登记数时用并集还是各自，结果会差近一倍。
