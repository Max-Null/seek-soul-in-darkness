## 一、症状

思灵 1.1.0 里悬浮球的「置顶会话（7）」二级列，7 条置顶**全部**落进「已失效」档，条目只剩 `session-xxxx…` 形式的裸 id；设置页「关于 SSiD」版本显示 `V…`、「会话存储」段红字「无法读取会话存储状态（插件服务未就绪）；请重启 SSiD 后重试」。

`~/.ssid/session-root.json` 里开关是开的：

```json
{ "isolated": true, "applied": true }
```

`applied` 是**壳自己回写的**「本 boot 是否落在隔离根」（`session-root.ts:writeSessionRootApplied`）—— 本次的教训之一就是它不代表内核行为。

## 二、结论

1. **内核实际读写的会话根是共享根** `~/.dsh/sessions`，而不是隔离开关打开时应当用的 `~/.dsh/sessions-ssid`。**壳的第三层（`applied` 回写）与内核行为不一致。**
2. 用户置顶的 7 个会话**文件全部只在隔离根**（共享根 0/7 命中）→ 当前会话列表里查不到这些 id → `dsh-quick-toolbar` 把它们判为归属不可考，集中到 `unresolved` 档。
3. 所以「已失效」是**显示层对「列表里查不到这个 id」的措辞**，不是数据损坏、不是归档、也不是插件缺陷。

## 四、为什么显示成「已失效」而不是「消失」

`max-null-plugins/dsh-quick-toolbar` 的置顶折叠是纯逻辑（`src/pinned.ts:groupPinned`），单条由 `src/client.ts:resolvePinned` 反查：

```ts
function resolvePinned(id) {
  const snap = sessionsSnapshot()
  if (snap === null) return null
  const row = snap.byId[id]
  if (row === undefined) return null          // ← 本次全部走这条
  return { workspaceId: workspaceOf(id), title: row.displayTitle || id, alive: true }
}
```

返回 `null` 的条目集中到 `kind: 'unresolved'` 那一档（标题 `已失效`，`pinned.ts:21`），**刻意保留显示**：静默隐藏会让用户既看不见它、也没法取消置顶（`pinned.ts:69-71` 的注释即此意）。列表未就绪时整区不渲染（`data-pin-state="no-list"`），所以「显示成已失效」本身就说明**列表是就绪的、只是里面没有这些 id**。

## 五、失效发生在哪一层

profile 里那条覆盖是**壳写进去的**，值是一个依赖环境变量的表达式：

```yaml
- id: session-persistence-jsonl
  config:
    root: !!js 'process.env.SSID_SESSION_ISOLATED_ROOT || ((process.env.DSH_HOME || (process.env.USERPROFILE + "\\.dsh")) + "\\sessions")'
```

即：**有 `SSID_SESSION_ISOLATED_ROOT` 就走隔离根，没有就退回共享根**。而链路上有两个独立前提，任一不成立都得到「共享根」这个结果：

- **C1 · env 没到达内核进程** —— 壳的注入在 `session-root.ts:installSessionRootEnv`（写 `process.env`），要求早于 `host.start()`：fork 版内核是官方基座拉起的**子进程**，继承的是 spawn 那一刻的快照。
- **C2 · profile patch 这层根本没被应用** —— 那不只是会话根，patch 里的 MCP 预制、`connection` 注入等一并失效（旁证：本次 boot 的 PWsh 工具面上没有任何 `mcp__*` 工具）。

**重启后一次分辨**：内核改读隔离根 ⇒ C1（patch 层是好的）；仍读共享根 ⇒ C2。

### 5.2 为什么不能靠改 profile 修

壳的 `mergeProfilePatch`（`ssid-desktop/apps/desktop/src/ssid/profile-seed.ts:408-451`）按**子条目**粒度合并，语义是「出厂条目以模板为准，用户条目原样保留」：

```ts
const owned = new Set(template.blocks.flatMap(block => [...block.ids]))
const merged = `${head}${[...template.blocks.map(block => block.body), ...keptBodies].join('\n')}\n`
```

`session-persistence-jsonl` **在模板里**（`resources/ssid-plugins/cordis.patch.yml`，1.1.0 装机时 9012 bytes），所以手改 profile 里那条 `root` 会在下次启动被模板值盖回去 —— 这也解释了 `profiles/ssid/cordis.patch.yml` 的 mtime 每次启动都变。

## 六、应急热修（已落地，待重启）

### 6.1 用官方 `.env` 层把变量喂给内核

`dsh-app-boot` 的 `loadLayeredEnv`（asar 内 `dsh/node_modules/@deepseek-ai/dsh-app-boot/lib/index.js`）把 `$DSH_HOME/.env` 灌进内核 `process.env`，且**只在变量未定义时填充**：

```js
const user = home === resolve(cwd) ? void 0 : readEnvLayer(binName, home, warn, home)
for (const [name, value] of Object.entries(layer.values)) if (process.env[name] === void 0) process.env[name] = value
```

因此在 `C:\Users\MaxNull\.dsh\.env` 追加两行（正斜杠，避免转义问题）：

```
SSID_SESSION_ISOLATED_ROOT=C:/Users/MaxNull/.dsh/sessions-ssid
SSID_SESSION_SHARED_ROOT=C:/Users/MaxNull/.dsh/sessions
```

**为什么这个写入是安全的**：`readEnvLayer` 只拒绝 **bootstrap-only** 变量名（`BOOTSTRAP_NAMES`：`PATH`/`HOME`/`USERPROFILE`/`SHELL`/`NODE_OPTIONS`/`NODE_PATH`/`NODE_EXTRA_CA_CERTS`/`LD_*`/`BASH_ENV`/`ENV`/`SHELLOPTS`/`BASHOPTS`/`PERL5OPT`/`PERL5LIB`/`PYTHONSTARTUP`/`PYTHONPATH`/`RUBYOPT`/`RUBYLIB`/`JAVA_TOOL_OPTIONS`/`_JAVA_OPTIONS`，前缀 `DSH_`/`XDG_`/`DYLD_`/`BASH_FUNC_`）；`SSID_` 不在其中，不会被拒绝启动。Harness-home 层额外允许四个代理名（`HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`/`NO_PROXY`），该文件本就在用。

这条修法的好处是**自失能**：壳哪天恢复正常注入（`process.env` 里已有该名），`.env` 的值不生效；不需要它时删掉两行即可。

### 6.2 补齐会话，切根不丢东西

把共享根里隔离根没有的 82 个会话目录复制进隔离根（只增不删、幂等、写前备份）：

## 十一、本次新增的坑

1. **`~/.ssid/session-root.json` 的 `applied` 只是壳的自述**，不能当内核行为的证据。判据要落到「内核把文件写进哪个根」（§3.2 那句环境变量取 `DSH_SESSION_ID` 再定位，一秒出结论）。
2. **手改 profile 的 `cordis.patch.yml` 会被模板盖回去**：`mergeProfilePatch` 对模板里存在的条目一律以模板为准。要改这类出厂条目，得连模板（`resources/ssid-plugins/cordis.patch.yml`）一起改，或走源码/发版。
3. **`$DSH_HOME/.env` 是一个可用的兜底 env 通道**（官方 `loadLayeredEnv`，只在变量未定义时填充、只拒 bootstrap-only 名）。它适合「壳注入断链」这类应急，且天然自失能；但它同样属于绕过，不能替代修壳。
4. **两个会话根的历史副本会让「计数」骗人**：`sessions` 152 + `sessions-ssid` 160 的并集是 242，不是 312（同 id 大量重复）。任何按根报数的结论都要先说明算的是哪个集合。

### 12.2 根因（§五 的 C1 具体化）：注入晚于 env 快照，成败取决于 Host 是否重启过

壳把三个注入放在 `DesktopBackendController` 工厂返回的 `start()` 里（`main.ts:696` MCP / `:709` 会话根 / `:716` 登记自愈），而 `new DesktopHostProcess(...)` 在**工厂体内、注入之前**（`main.ts:655`）。它接收的 env 是**构造那一刻的浅拷贝** `{ ...process.env, DSH_CLIENT_VERSION }`：

- `host-process.ts:246` 把该对象存为实例的 `this.environment`；
- `host-process.ts:276` spawn 时 `env: desktopNodeEnvironment(this.node, void 0, this.environment)`；
- `node-environment.ts:12` 只做 `{ ...environment, ELECTRON_RUN_AS_NODE: "1", … }`，**不合并 live `process.env`**（发行版产物 `app.asar/lib/main.js` 逐字核对过，@249404 与 @240052）。

**⇒ 注入写在 `process.env` 上的 `SSID_*` 到不了 Host 子进程。** 这与 `SSID-CHANGES.md:1380` 的既有要求（「注入必须在 `new DesktopHostProcess(...)` 之前 await 完」）直接矛盾 —— 是一次**回归**。

**为什么这台机器"有时好有时坏"**：工厂在 **Host 重启**时会被再次调用，第二次构造的快照就带上了上一轮的注入。本次 boot 的 `~/.dsh/logs/host.log` 里 `dsh: skipping profile bundle` 出现**两段**（@296 与 @356-358），即**两次 Host 启动**；而上一次（14:40 那次 boot）只有一段 → 注入全程未生效。**能否生效取决于 Host 是否重启过**，这就是"1.1.0 上时好时坏"的形状，也解释了为什么 `.env` 热修之外还会有别人报告"升级后历史会话没了"。
