# macOS 打包通道打通（2026-09-29）

## 背景

SSiD 的 mac arm64 安装包只能在 Apple Silicon 上构建，开发机是 Windows，所以这条通道落在 GitHub Actions（`.github/workflows/build-mac.yml`）。workflow 于 2026-09-29 按 fork 形态重写：从 `Max-Null/deepseek-harness` 的 `ssid-desktop-fork` 分支 clone 开发主轴、用 `SSID_PROFILE_TEMPLATE_DIR` 指向出厂插件集声明源、走 `package:mac:arm64:unsigned` 未签名通道。

本文记那次重写之后第一次真跑踩到的五层问题。五层是逐层剥出来的：每一层都要等上一层修好、CI 跑过十几分钟后才露出来。它们**全部只在真 mac 上暴露**——同一份代码在本地 Windows 上全绿。

操作步骤与四个坑的处置表在 `ssid-release` skill §5「macOS（arm64，未签名）」；本文记的是取证过程、判断依据，以及几个被推翻的中间结论。

## 逐层记录

### 一、CI 跑的是旧壳：GitHub 的 fork 分支没跟上

**现象**　tag `v1.1.0` 推送触发的 run `36498249984`，1 分 37 秒即失败于 `[ERR_PNPM_RECURSIVE_RUN_NO_SCRIPT]`——它要跑的 `package:mac:arm64:unsigned` 脚本不存在。

**取证**　GitHub 上的 `ssid-desktop-fork` 停在 `f2f34265d8`，其 `apps/desktop/package.json` 的产品版本还是 `0.1.7-rc.2`，比本地开发主轴落后 278 个提交。此前所有提交都只推到 `origin`（本地镜像 `deepseek-harness`），从未推 GitHub，而 CI 恰恰从 GitHub clone。

**修法**　`git push "--force-with-lease=refs/heads/ssid-desktop-fork:f2f34265d8…" fork ssid-desktop-fork`。

**坑**　第一次写成 `--force-with-lease=fork/ssid-desktop-fork`（远端跟踪引用名），Git 报的是 `non-fast-forward` 而不是 lease 失配——这个参数要的是远端 ref 全名。

**坑**　「Re-run failed jobs」验证不了 workflow 改动：rerun 沿用该 run 所属 ref（这里是 tag）上的 workflow 定义，改动不在那个 commit 上就不生效，只会原样再失败一次。验证 workflow 一律走 `workflow_dispatch --ref main`。

### 二、`.env.macos` 缺失

**现象**　run `36499456976`，9 分 2 秒失败：

```
Error: desktop package: cannot read .../apps/desktop/.env.macos; copy .../.env.macos.example and fill in the local settings
    at loadDesktopPackageEnvironment (desktop-package-environment.mjs:36)
```

**根因**　`package-target.ts:360` 无条件调用 `loadDesktopPackageEnvironment`，读不到目标平台的 dotenv 文件就抛错。这份文件承担 App ID、强更策略与打包并发；`--unsigned` 跳过的是 Apple 签名与公证**凭据**的校验（`validateDesktopPackageEnvironment` 遇 unsigned 提前返回），不包含文件本身。上游 CI 同样在运行前生成它。

**修法**　workflow 在打包前用 heredoc 写一份，取值与本机 `.env.windows` 一致（`com.maxnull.ssid` / `DSH_DESKTOP_AUTO_UPDATE_ENV=test` / 策略源站与 `allowedAuthOrigins`）。

**本地验证**　用真实加载器跑一遍 `loadDesktopPackageEnvironment('darwin', {}, 临时目录)` + `validateDesktopPackageEnvironment(..., { unsigned: true })`，通过；另用 yaml 解析 workflow 后 dump `run` 正文，确认 heredoc 内容顶格、没有被 YAML 块标量带上多余缩进（多余缩进会写坏 dotenv 的键名）。

### 三、内核预签名要 Developer ID

**现象**　run `36500663984`，13 分 36 秒失败：

```
Error: desktop release environment: DSH_DESKTOP_MACOS_SIGNING_IDENTITY must be set to a non-empty value
Error: desktop package: run prepare:dsh failed
```

**根因**　`prepare-dsh.ts:155` 在 `darwin` 下无条件解析签名身份，对内核与 primary-runtime 的原生 Mach-O 做预签名（`signMacOSRuntime`）。这份预签名是设计的组成部分：electron-builder 的 `signIgnore` 排除这几条路径，靠它预先签好。未签名通道没有可用身份，这一步必然抛错——而 Windows 上的 `prepare:dsh` 根本不碰 mac 身份，本地测不出来。

**修法**　`package-target.ts` 把 `DSH_DESKTOP_UNSIGNED` 放进所有子进程共用的 `targetEnv`；新增 `macOSNativeSigningIdentity(environment)`（`macos-runtime.ts`），未签名时返回 `undefined`，`prepare-dsh.ts` 据此跳过两步预签名。

**后续**　这一步最初写成「未签名就整段跳过」，见第五层——跳过之后 `signIgnore` 的假设同时塌了。

### 四、fd 上限：插件集 43099 个文件

**现象**　run `36501936326`：

```
⨯ EMFILE: too many open files, open '.../ssid-plugins/node_modules/es-toolkit/dist/compat/string/upperCase.d.mts'
```

**取证**　本地数同一份插件集：**43099 个文件 / 759.8 MB**（`es-toolkit/dist` 3023、`unicode-regex/lib` 2074、`rxjs/dist` 2006、`@univerjs/*` 3175……）。electron-builder 复制这批 extraResources 时会同时打开远超上限的 fd。

**第一次修（错）**　直接加 `ulimit -n 10240`。实测 runner 的软限制**本来就是 10240**，等于没改，下一轮同样 EMFILE。

**第二次修（仍不够）**　改成顶到硬限制并打印实际值：

```
fd soft=10240 hard=unlimited maxfilesperproc=10240
fd now=unlimited
```

软限制设成 `unlimited` 了，EMFILE 照旧——真正的天花板是内核参数 **`kern.maxfilesperproc=10240`**。

**修法**　打包步骤内先 `sudo sysctl -w kern.maxfiles=400000 kern.maxfilesperproc=200000`，再 `ulimit -n 200000`（必须同一个 shell，GitHub Actions 每个 `run` 是独立 shell）：

```
before: soft=10240 maxfilesperproc=10240
kern.maxfilesperproc: 10240 -> 200000
after: soft=200000 maxfilesperproc=200000
```

EMFILE 消失。

### 五、osx-sign 关不掉的 `--deep` 验证

这一层花了四轮才收敛。

**现象**　run `36504626013` 起：

```
⨯ Command failed: codesign --verify --deep --strict --verbose=2 .../思灵.app
```

来自 `@electron/osx-sign`：它签完所有嵌套代码与 app 本体后，固定跑一次 `codesign --verify --deep`。失败原因被 electron-builder 吞掉，只剩「Command failed」。

**尝试一（错）**　去掉 `signIgnore` 的三条排除，让 osx-sign 连同 `dsh/`、`primary-runtime/`、`ssid-plugins/` 一起签。仍然失败。

**尝试二（诊断，关键）**　给 workflow 加一个仅失败时运行的诊断步骤，用 `--verbose=4` 在同一产物上复现，并普查 Mach-O 签名。结果推翻了推断：

- 事后重跑 `--verify --deep --strict`：**通过**（无输出）
- 普查：**Mach-O 总数=144，未签名=0**
- app 本体：`Signature=adhoc`、`TeamIdentifier=not set`

也就是说**产物本身完好**，出问题的只是签名流程内部那一次验证，而且它不可复现。

**尝试三（错）**　怀疑 `--timestamp`——ad-hoc 身份没有证书，时间戳请求只能空等（实测把 app 本体签名拖到 9 秒）。打开 DEBUG 后看到 osx-sign 实际执行的是：

```
codesign --sign - --force --timestamp --options runtime --entitlements .../macos-entitlements.plist 思灵.app
```

于是加 `mac.timestamp: !unsigned`。仍然失败——`MacTargetHelper.js:183` 写的是 `timestamp: customSignOptions.timestamp || undefined`，传 `false` 会被吞成 `undefined`，osx-sign 落回默认 `true`。**这个参数从配置层关不掉**。

**修法**　不再和那次验证较劲：未签名通道让 electron-builder 整个跳过签名（`identity: null` + `forceCodeSigning: false`，走 `MacTargetHelper.handleNullIdentity()`），改由 `afterPack` 钩子用同一条 `codesign` 命令签整个 app：

```js
await promisify(execFile)('/usr/bin/codesign', [
  '--force', '--deep', '--sign', '-', '--options', 'runtime',
  '--entitlements', fileURLToPath(new URL('./macos-entitlements.plist', import.meta.url)),
  join(context.appOutDir, `${context.packager.appInfo.productFilename}.app`),
])
```

run `36511729774` **全绿**（15 分 50 秒）。

**为什么这个绕过是可接受的**　`--deep --sign` 是 Apple 对需要公证的正式包不推荐的签名方式（会有嵌套签名顺序问题），但未签名通道的产物既不公证也不过 Gatekeeper，而诊断已证明它的签名完整可验证。代价是不再走 osx-sign 的逐个嵌套签名。

**顺带确认的**　mac 打包路径上其余引用签名身份的位置（`electron-builder-config.mjs` 三处、`package-macos.ts`、`macos-signing-keychain.mjs`、`development-app.ts` 的 dev 模式 ad-hoc）都已核对过，不存在第二个漏点。

## 被推翻的中间结论

| 曾以为是 | 实际是 | 怎么推翻的 |
|---|---|---|
| mac 的 fd 软上限是 256 | 软限制本来就是 10240，真限制是内核 `kern.maxfilesperproc=10240` | 把实际值打进 CI 日志 |
| 去掉 `signIgnore`、让 osx-sign 签全就能过验证 | 仍失败；事后普查证明 144 个 Mach-O 全部有签名 | 加诊断步骤，在失败产物上复现 + 普查 |
| `--timestamp` 让 ad-hoc 签名短暂不一致 | 该参数从配置层关不掉；关掉也不是原因 | 读 `MacTargetHelper.js:183` + 实测 |
| 「事后重跑会通过」说明是时序问题 | 重签后立刻验证也通过——失败只出现在 osx-sign 那一次内部调用上 | 诊断步骤里显式复现「签完立即 verify」 |

## 边界

CI 绿证明的是**打包链在真 mac 上跑通、产物生成、每个内嵌二进制都有签名**。它**不**证明产物能在 mac 上双击运行：

- 打包后的冒烟（`smoke-packaged-runtime.ts`）只校验产物路径，不启动应用；
- ad-hoc 签名的包会被 Gatekeeper 拦。

补这块证据需要一台真机：解开 `.zip` → `xattr -dr com.apple.quarantine 思灵.app` → 双击。在此之前，不要把这条通道说成「mac 版可用」。
