# 思灵 1.1.3 控制台报错分诊

> 记录时间 2026-09-30 · 起因：装版 1.1.3 的控制台一次性贴出六类报错
> 用途：判断哪些是真缺陷、哪些是已知待办、哪些只是噪声；并把 503 那笔没对上的账往前推一步

## 一句话结论

六类报错**没有一条影响正常使用**。三条真缺陷（ws 连不上、`shellVersion` 显示 0.0.0、更新桥缺失）、一条已知待办（503）、两条噪声。

## 一、分诊

| 控制台报错 | 定性 | 依据 |
|---|---|---|
| `quick-toolbar/api/state` 503 ×12 | 已知待办，下个版本处理 | 壳协议层在 Host 未就绪时一律回 503；两处调用点各有退避与降级。报告见 `2026-09-29-悬浮球状态回读的启动期503.md` |
| `api/changes.summary` 404 ×2 | **官方设计内**，非故障 | `ui-deliverables/src/present-open.ts` 的 `handleChangesSummary` 只在 `workspaceChanges.summary(id, seq) === undefined` 时回 404，函数注释原文「404 once the Host no longer serves it」；包 README 把「Host restarted since the turn ran」列为预期。翻看历史 turn 时必然出现 |
| `ws://app/sidebar/ws/agent-opens` 连接失败 ×3 | 真缺陷，修复已写未发布 | 见 §二 |
| `[ssid-about] shellVersion: "0.0.0"` | 真缺陷，手册 §6 契约表已登记 | 见 §二 |
| `[ssid-update] 更新桥未注入` | 已知缺口 | 手册 §6 + `插件开发规范.md:107`：`ssid.shell.update` 在 fork 侧从未注册 |
| dream-skin 类名漂移、sidebar-qa「no right sidebar」 | 无害 | 前者日志自带说明（仅 cosmetic）；后者是探测顺序误报——紧随其后的 `registered 2 tabs in DSH's own right sidebar` 表明最终成功 |

**404 的判据**（与前者同形但不同源，别混）：只有零星几条、且对应旧 seq ⇒ 正常；**每个 turn 都 404** 才是 Host 半没注册路由，那才会让改动文件卡片整体消失。

## 二、三条真缺陷

### 1. ws agent-opens：修复已写但未发布

better-sidebar 拿 `location.origin` 当 WebSocket 的 base。页面跑在 `dsh-app://app/` 下时 `location.host` 是字面量 `app`，于是拼出 `ws://app/sidebar/ws/agent-opens` —— 永远解析不了。

修复在本地 clone `third-party-plugins/DSH-better-sidebar` 的分支 `fix/ws-base-0241`（提交 `2718725`）：改用壳注入的 `__DSH_TRANSPORT__.streamBaseUrl`。**npm `latest` 仍是修复前的 0.24.1** —— 用 node 核过产物，`streamBaseUrl` 零命中、`location.origin` 五处。

影响面限于该侧栏推送功能静默退化；侧栏本体与 tab 注册正常。

### 2. 「关于 SSiD」显示 v0.0.0

`dsh-ssid-panels` 读 `process.env.SSID_SHELL_VERSION`，而整个 `ssid-desktop/` **没有任何一处设置它**（内核 env 里也确实没有）。这条注入链属于自建壳，1.0.0 迁 fork 形态时丢失。已补进手册 §6 的壳-内核契约表。

**修它只解决显示**：更新动作本身另有缺口（`ssid.shell.update` 未注册），所以在当前形态下「检查更新」本来就走不通。

### 3. 更新桥未注入

已知缺口，手册 §6 与 `插件开发规范.md` 都记着：`SSID_SHELL_UPDATE_KEY` / `SSID_SHELL_RESTART_KEY` 在 fork 下不存在，`dsh-ssid-panels` 仍按服务键取桥。

## 三、503 那笔账：已确认的与没对上的

### 已确认（隔离实例实测）

壳的一次 `readFloatState` 序列 = **恰好 6 次**请求，时间戳 `76 / 488 / 1295 / 2502 / 4104 / 6114 ms`（间隔 412/807/1207/1602/2010，精确吻合 `400 × (attempt + 1)` 的退避），调用栈只有一个来源 `readFloatState`。

所以报告里「壳 6 次 + 插件 1 次 = 7」的算法在**单次页面加载**下成立。

### 已排除

- **reload 不会产生第二次注入**：实测重载页面只跑一遍，仍是 6 次。
- 插件侧 `saveState` 的 4 个调用处都在用户交互路径上（`2026-09-29` 的报告已排除）。

### 剩下的解释（未收口）

`titlebar.ts` 有**两条**会调用 `inject()` 的路径，而注入脚本**没有幂等守卫**——它开头是「删掉旧的再重建」，不是「已存在就跳过」：

```js
const old = document.getElementById(ID)
if (old) old.remove()
```
```js
window.webContents.on('dom-ready', injectShellFlag)
window.webContents.on('did-finish-load', () => { injectShellFlag(); inject() })
if (!window.webContents.isLoading()) inject()
```

**一次注入 = 6 次请求**，所以只要 `inject()` 跑两遍就是 12 次。这同时能解释 10/11/12 的波动：两串序列的起点与 Host 就绪时刻都不同，各自末尾会有几条落在就绪之后而成功。

**没对上的那一点**：`installSsidTitlebar` 被调用时 webContents 还没有文档，那句 `inject()` 究竟落在空文档（`fetch` 抛 Invalid URL、不产生请求）还是已经落进新文档（产生请求）—— 这是竞态，读码定不了。

### 已定论：注入确实跑了两遍（2026-09-30 实测）

用**主进程直接写文件**的探针（`titlebar.ts` 的 `inject()` 里一行 `appendFileSync`，顺带记录 `webContents.isLoading()`），在 dev 实例上冷启动一次，拿到两行：

```
2026-09-29T17:14:42.996Z inject loading=false
2026-09-29T17:14:43.189Z inject loading=true
```

**193ms 的间隔、两个不同的 `isLoading()`，正好对上 §二 提到的两条路径**：`loading=false` 那次是结尾的 `if (!window.webContents.isLoading()) inject()`（窗口刚创建、还没 `loadURL`）；`loading=true` 那次是 `did-finish-load` 的 `inject()` —— 那一刻子资源仍在加载，所以 `isLoading()` 还是 true。

配上「壳一次 `readFloatState` 序列 = 6 次请求」（本文开头那组实测），**12 = 6 × 2 成立**，那份 09-29 报告 §三 的账就此平掉。

**仍属推断的一条细节**：两次注入的 `fetch` 是否都落在真实文档上。第一次注入时文档还是空白的，而它那句 `executeJavaScript` 是异步 IPC —— 若在新文档 commit 之后才执行，就会在新文档里发请求，那正是 12 而不是 6 的原因；竞态不利时会少几次，这解释了 10/11/12 的波动。要把它也钉死需要 CDP 的 `Network` 域在页面加载前就 attached，而下面那条已证抢不到窗口。

**两条已证不可行的路**（记下来免得重走）：

- **Resource Timing 不能用**：`dsh-app://` 自定义协议下的请求**完全不进** `performance.getEntriesByType('resource')`。实测：在页面里 `fetch('/quick-toolbar/api/state')` 确实拿到 503、请求确实发生，而请求前后两次采样都是 0 条、增量 0（页面里 `location.protocol` = `dsh-app:`）。所以「过滤得到空数组」既可能是没请求、也可能是这指标根本不记录 —— **失效表现与真实结论无法区分**，不能当判据。
- **CDP 抢不到冷启动窗口**：`--remote-debugging-port` 的端点**晚于主进程 JS** 才开始服务，两条配置都失败。常规启动下端口可用（+1717ms）时 page target 已经带着 `dsh-app://app/` 存在（+1941ms）；改用 `--inspect-brk` 把主进程冻在启动第一行，该端点在这期间**完全不可用**，放行后 301ms 才就绪 —— 而窗口与页面那时已经创建。`Target.setAutoAttach` 只对之后新建的 target 生效，两条路差在同一个时间差上。

**探针的正确写法**（下次直接用）：壳里的探针**必须由主进程直接写文件**，不能用 `console.info` —— 原因见 §四 的「GUI 子系统」那条。

## 四、环境事实（供后续排查复用）

**`.ssid-iso-test/启动-iso-110.ps1` 起的隔离实例，Host 必然起不来** —— 它的日志里是：

```
StartupError: dsh: startup failed: 2 required plugins did not activate
  webserver (required)  Error: listen EADDRINUSE: address already in use 127.0.0.1:19388
```

Host 端口在 `apps/desktop-host/src/index.ts:59` **硬编码 `19388`**（注释写明「与官方桌面端同端口会导致两者永远互斥」），所以隔离实例与生产实例**永远不能同时提供 Host 服务**。这不影响它的既定用途（抓 boot 期一片 503 的 console），但**别指望用它跑一个可用的第二实例** —— 参考 `SSiD开发手册` §3.1 / §3.3 的 dev 隔离做法（那边靠 profile patch 把 webserver 挪到 19488）。

**Host 起不来时，壳会弹一个模态对话框打断用户**：标题「The application could not start or stopped unexpectedly.」，正文写「Another DSH instance (such as dsh web or the desktop app) is running. They cannot start at the same time.」—— **文案说的是「另一个实例在运行」，读起来像单实例锁冲突，实际原因就是上面那个 `EADDRINUSE 19388`**（另一个实例确实在运行，占着端口）。对话框只有 Exit / Restart 两个按钮，并给出诊断报告路径 `<user-data>/logs/crash-<ts>-host.log`；那份报告里 `shell pid`、`EADDRINUSE: address already in use 127.0.0.1:19388`、以及 21 个等服务的插件清单都写得很清楚。

**所以起隔离实例之前要跟人打个招呼**（或者别在人在电脑前时起）：它会弹一个需要点掉的全屏模态框，不知道的人会以为自己的实例坏了。`启动-iso-110.ps1` 之所以没把这条写进注释，是因为它本来就是为「抓 boot 期报错」写的，弹框是它的常态。

新增的探针脚本落在 `.ssid-iso-test/`：`launch-iso-probe.ps1`（拉实例，多带通知与截图配置的隔离覆盖，不抢全局热键）、`probe-qt-state.mjs`（reload 后数请求与调用栈）、`cold-probe.mjs` 与 `cold-probe-brk.mjs`（两次冷启动竞速，见 §三）、`launch-iso-brk.ps1`、`diag-resource-timing.mjs`（证明自定义协议不进 Resource Timing）。

**两个会误导人的环境事实**（都是 2026-09-30 加壳探针时撞出来的）：

- **DSH 内核的环境里带着 `ELECTRON_RUN_AS_NODE=1`**（Host 子进程就是这么起来的），所以**在 DSH 会话里起的任何 electron 都走 Node 模式**：`electron --version` 打出来的是 Node 版本（`v24.18.1`）而不是 Electron 版本。想跑 GUI 模式必须先 `Remove-Item env:ELECTRON_RUN_AS_NODE`（dev 启动脚本一直这么做）。
- **Windows 上 Electron 是 GUI 子系统程序，Chromium 模式下没有可用的 stdout** —— 实测 `electron --version` 在 GUI 模式**零输出**，Node 模式才有。推论：**「给壳加主进程 `console.info`、再去日志里数」这条路不成立**，壳里的探针要写成主进程直接写文件。

**dev 实例曾因 Electron 沙箱创建失败而起不来**（2026-09-30 定位并绕开）：`pnpm run start` 下 electron 以 **`STATUS_BREAKPOINT`（2147483651 = `0x80000003`）** 退出，且**在打印任何输出之前**。二分的结果：

- **不是 app 代码，也不是 `dev.ts` 的参数** —— 一个最小 Electron app（只有 `app.whenReady()`）用同样的 WMI 起法也崩，退出码同一个。它连自己的日志都没写出来，说明崩在加载 app 代码之前。
- **是 Electron 的沙箱** —— 加上 `--no-sandbox` 后，最小 app 立即跑通（exit 0，`electron=44.0.0 chrome=152.0.7977.54 node=24.18.1`），dev 壳也完整起来（9222 与 19488 都在听）。
- 已排除：electron 二进制本身正常（Node 模式 `-p process.versions.node` 返回 `24.18.1`）；进程完整性级别是 Medium（不是 Low）；`TEMP`/`TMP` 收进工作区、user-data 也改到工作区内，都没解决；两次启动现象一致（非偶发）；electron 是 09-26 装的、没被换过。

**绕法**：`.ssid-iso-test/launch-dev-nosandbox.ps1` —— 按 `dev.ts` 的同一组参数与环境变量自己起 electron，额外加 `--no-sandbox`，并跳过 `dev.ts` 的两步准备（`.desktop-build/development/project` 与 `targets/win-x64/runtime/primary-runtime` 已由先前的 `pnpm run start` 生成，与 `lib/main.js` 无关）。**没有改 `dev.ts`**，避免给 fork 添一处与上游的差异。注意 `ELECTRON_EXTRA_LAUNCH_ARGS` 这个环境变量**不起作用**（实测无效）。
