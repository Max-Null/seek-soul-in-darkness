## 零、2026-10-02 复查：四处判断被推翻

复核用跨会话扫描（`sessions-ssid` 根 37 个 ≥3MB 会话）加三处独立取证：profile patch 的备份时间序列、会话首帧的 `agentPreset` 字段、`compaction-basic` 的阈值计算源码。

**① 第四节的真凶不是 `mergeProfilePatch`。** 它只保留模板外的条目，没有删过任何东西。09-29 14:24:43 那次写盘把**整个 patch 层替换成了空骨架**——备份 `cordis.patch.yml.bak-1790663085326` 只有 217 字节，内容是 `[]`；14:24:45 才有第二次写盘（回填出厂条目）。这解释了为什么四条 MCP、405 修复、会话根覆盖当时一起消失。

**② 09-18 的处置从未生效过一次，与那次清空无关。** profile patch 里那条写的是 `- id: agent-presets`，而内核条目 id 是 `agent-preset-registry`（`bundle/web-app/cordis.patch.yml:562`）。内核自己的文档写明未知目标「warned and skipped」——静默空转，不报错。会话普查佐证：**2026-09-16 至 10-01 创建的 98 个会话，`agentPreset` 100% 是 `standard`**（含本报告样本）。09-18 另建的 `~/.dsh/.agent-presets/ssid-standard/` 目录也不被任何内核路径读取——preset 注册只走 `register()`，而它只吃 patch 条目。

**③ 第三节的因果方向是反的。** `</parameter>` 首现于 675,687 token，而语义口径下的重复率越线在 600,966——**打转先发生，残留是它的产物**。13 个越线会话里 **11 个完全没有残留**；唯二有残留的两个，残留都晚于退化 7.5–11.5 万 token。残留一旦出现会被大量重放（本会话峰值处的 top 单元是 `×314 ---</parameter>`），所以它是**放大器而非起点**。

**④ 第五节的「678k 之谜」已解。** `compaction-basic/src/config.ts:191`：

    thresholdTokens = min(contextWindow × thresholdRatio, contextWindow − reservedCompletionTokens − headroomTokens)

`headroomTokens` 默认 65,536，预留输出约 256,000 ⇒ `min(800,000, 678,464) = 678,464`。**卡住触发点的是这个与阈值无关的硬顶**，不是 0.8 的比例本身；0.5 一旦生效会把触发点拉到 500,000（低于硬顶，因此确实有效）。

## 三、机制（当前的理解）

1. 某一步里模型把一段**带 XML 闭合标记的命令文本**写进了推理（而不是发起真正的工具调用）。
2. 推理文本按「model-visible ⟺ logged」进日志，也就进了后续每一轮的上下文。
3. 后续推理开始**重放这些碎片**——`</parameter>`、`好`、`输出`。重放又产生新的推理文本，
   再次进上下文。**这是个正反馈：产出物本身成为下一轮的输入污染源。**
4. 重复率随轮次爬升，峰值出现在 t23 附近，之后一直维持在 80%–95%。
5. **压缩不针对这个**：自动压缩在压力到线时才发生（本会话只触发过一次），而 prune 只挖被遮蔽
   的事件。两者都不识别「推理文本里的重复」。

**与 09-18 结论的关系**：那份报告说「token 数是风险因子，不是充分条件；任务形态是协变量」——
本会话支持这一点（67.8 万触发压缩，远低于其样本的 79 万）。**本报告补的是另一半：退化有
一个具体的、可定位的起点物（`</parameter>` 那一类残留），而不是纯粹的压力函数。**

## 五、还没验完的（别当成结论用）

- **`</parameter>` 是不是退化的必要条件？** 本会话里它是首个可定位的失败产物，但只有
  一个样本。**换个会话不一定以它起头**——可能是 `</tool_call>`、别的标记，或者干脆没有
  显式标记（纯粹的语气词循环）。
- **为什么自动压缩在 67.8 万触发，而阈值按 09-18 的分析应是 80 万？** 本会话 `ssid` profile
  里根本没有 `compaction-basic` 的 patch，用的是 DSH 默认 0.8。触发点与 80 万差 12 万，
  **原因未查**（候选：`compaction-basic` 的阈值判据不是单纯的当前压力，还算了下次请求的预估；
  或 `reserveTokens` 一类的余量）。
- **t1 就有 22 万字符推理**（全会话最大）。那是正常的重活，还是早期就有苗头？**未看**。
- **50 万是否足够**仍未验证——而且现在连 0.5 都没在跑。
- 「手动压缩」在本会话里做了 4 次，**是用户自救**。手动压缩之后重复率有没有下降？**未测**。

     （连续 N 步而非单步）。第一个需要引擎侧支持，第二、三个可以先在插件里试。
4. **看别的长会话**：`--root` 跨会话扫一遍，确认「`</parameter>` 类残留」是普遍现象还是个例。

## 七、边界

- **本文的数字来自单一样本。** 23 次越线、98% 峰值、8371 次残留都出自 `session-a8ac8e89`。
