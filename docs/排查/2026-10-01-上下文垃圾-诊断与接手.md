# 上下文垃圾：长会话推理退化的实测机制与接手清单

> 状态：**现象已量化 · 机制有实证 · 09-18 的处置确认未生效（新发现）** · 2026-10-01
> 触发：用户在长会话中途观察到「模型的思考链被上下文里的垃圾搞崩」，要求单独开一轮处理
> 样本：`session-a8ac8e89-501a-48c9-964a-b2d012da9121`（SSiD 正式 profile，本报告写完时仍在进行）
> **这份文档是接手入口，不是结论文档**——数据在，判断留得不够，第六节逐条列了没解决的
> 前身：`2026-09-18-长会话输出退化.md`（根因定位 + 阈值处置）。**先读那份，再读这份。**

## 一、一句话

模型自己的失败产物——**推理里未闭合的 XML 风格工具语法**——被写进会话日志、进入后续每一轮
的上下文，然后从第 8 轮起被反复重放；到第 23 轮，单条推理里 98% 的单元是重复片段。

### 2.3 推理重复率

判据：单条推理按换行与中英句读切分，**出现 ≥3 次的单元占比**。

| 项 | 值 |
|---|---|

| 最早越线 | **452,907 token** |

峰值处的重复单元：

```
t23/s2  98%  ×2006「好」   ×1856「---</parameter>」   ×1188「输出」
t26/s2  95%  ×487「好」    ×415「（输出）」          ×307「</parameter>」

t32/s1  92%  ×174「---</parameter>」  ×171「好」        ×111「（输出）」

**重复单元全是模型自己的推理碎片**——没有一条来自插件注入或工具返回。这与 09-18 的观察一致。

### 2.4 失败的来源：`</parameter>`

|
| **—— 嗯，输出可能是 JSON** ✓
|
| **做。**
|

模型把一段 shell 命令连同 `</parameter>` 一起写进了**推理文本**（那是 Anthropic 风格的
工具调用语法，不是本机任何一层的格式）。同一段里已经能看出循环的雏形——「**做。**」重复两次，
每次前面挂一串 ✓ 结尾的短评。

**时序值得注意**：`</parameter>` 首现于 seq 2090，而自动压缩落在 seq 2110——**垃圾先出现，
压缩 20 个事件之后才发生**。

### 2.5 工具调用本身是健康的

| 指标 | 值 |
|---|---|
| `tool/call` 唯一 id | 1108 |
| `tool/result` 唯一 id | 1107 |
| `isError=true` | 15 |
| 有 call 无 result | 1 |

**所以这不是工具层故障**——没有解析失败、没有重试风暴、没有大量报错。「垃圾」纯粹出在
推理层，且是模型自己产出的。

### 2.6 独立佐证：allostasis 抓到了同一个东西

`dsh-allostasis` 的二期判据（重复率 ≥0.5 **且连续 2 步**）在本会话触发过**一次**：

```
seq 4256 · t38/s3 · ratio 56.7% · units 90 · consecutive 2 · threshold 0.5
top: 「</parameter>」×13、「（输出）」×…
```

**它的 top 重复单元就是 `</parameter>`** —— 与 2.4 节那条失败产物是同一样东西。本报告的全文
统计与插件的单步判据，两条独立路径指向同一个目标物。

**但它只触发了一次**，而扫描脚本在同一会话里数出 23 次越线。差异来自判据本身：allostasis
要求**连续 2 步**、且**每 turn 至多提醒一次**；扫描脚本是「单步 ≥0.5 就算」。

更要紧的是**它触发之后的走向**：t38 之后重复率仍在 80%–95%（t48、t51 的推理量还在高位）。
**提醒发出去了，循环没被打断。** 这与 09-18 记录的「循环守卫只检测重复的工具调用」是同一类
缺口的另一半——那个检测面太窄，这个检测到了却不足以纠偏。

## 三、机制（当前的理解）

1. 某一步里模型把一段**带 XML 闭合标记的命令文本**写进了推理（而不是发起真正的工具调用）。
2. 推理文本按「model-visible ⟺ logged」进日志，也就进了后续每一轮的上下文。
3. 后续推理开始**重放这些碎片**——`</parameter>`、`好`、`输出`。重放又产生新的推理文本，
   再次进上下文。**这是个正反馈：产出物本身成为下一轮的输入污染源。**
4. 重复率随轮次爬升，峰值出现在 t23 附近，之后一直维持在 80%–95%。
5. **压缩不针对这个**：自动压缩在压力到线时才发生（本会话只触发过一次），而 prune 只挖被遮蔽
   的事件。两者都不识别「推理文本里的重复」。

**与 09-18 结论的关系**：那份报告说「token 数是风险因子，不是充分条件；任务形态是协变量」——
本会话支持这一点（67.8 万触发压缩，远低于其样本的 79 万）。**本报告补的是另一半：退化有
一个具体的、可定位的起点物（`</parameter>` 那一类残留），而不是纯粹的压力函数。**

## 四、新发现：09-18 的处置在 ssid profile 里没生效

09-18 的处置是「新建 `ssid-standard` preset（`thresholdRatio: 0.5`）+ 两个 profile 的
`cordis.patch.yml` 各加一条 `agent-presets`」。

**`ssid` profile 的 patch 里现在没有 `agent-presets`，也没有 `compaction-basic`。**

profile 备份的时间序列说明它是**被覆盖掉的**：

| 备份时间 | 含 `agent-presets` | 含 `thresholdRatio` |
|---|---|---|
| 09-28 04:56 / 04:58 / 06:00 / 06:54 | **是** | **是** |
| 09-29 14:24 / 14:40 / 15:05 / 17:00 / 17:17 / 19:32 | 否 | 否 |
| 10-01 01:59 / 02:33 | 否 | 否 |

**09-29 14:24 那次改写把它抹掉了**，此后再没回来。而 `web` profile 的同一份 patch
**仍然带着这两条**（`~/.dsh/profiles/web/cordis.patch.yml` L14–L37）。

**所以本机正式环境（`ssid` profile）从 09-29 下午起就没在用它自己的 0.5 阈值。**

这一条与手册 §7 坑 #60 是同一类事故：**`mergeProfilePatch` 会用模板盖回手改的出厂条目**，
手动加进 profile patch 的设置会在下一次部署时消失。09-18 那份文档把「两个 profile 各加一条」
当成了终点，但**它没有护栏**。

**判据**（接手时先跑这个）：

```powershell
Select-String -Path 'C:\Users\MaxNull\.dsh\profiles\ssid\cordis.patch.yml' -Pattern 'agent-presets|thresholdRatio'
# 有输出 = 还在；无输出 = 又丢了
```

## 五、还没验完的（别当成结论用）

- **`</parameter>` 是不是退化的必要条件？** 本会话里它是首个可定位的失败产物，但只有
  一个样本。**换个会话不一定以它起头**——可能是 `</tool_call>`、别的标记，或者干脆没有
  显式标记（纯粹的语气词循环）。
- **为什么自动压缩在 67.8 万触发，而阈值按 09-18 的分析应是 80 万？** 本会话 `ssid` profile
  里根本没有 `compaction-basic` 的 patch，用的是 DSH 默认 0.8。触发点与 80 万差 12 万，
  **原因未查**（候选：`compaction-basic` 的阈值判据不是单纯的当前压力，还算了下次请求的预估；
  或 `reserveTokens` 一类的余量）。
- **t1 就有 22 万字符推理**（全会话最大）。那是正常的重活，还是早期就有苗头？**未看**。
- **50 万是否足够**仍未验证——而且现在连 0.5 都没在跑。
- 「手动压缩」在本会话里做了 4 次，**是用户自救**。手动压缩之后重复率有没有下降？**未测**。

## 六、接手的起点

### 6.1 先拿数据

```powershell
# 单会话报告（事件普查 + 压力轨迹 + 重复率 + 压缩事件）
node H:\MaxNull\WorkStation\seek-soul-in-darkness\shell\scripts\session-degeneration-scan.mjs `
  'C:\Users\MaxNull\.dsh\sessions-ssid\--H-MaxNull-WorkStation--\session-a8ac8e89-501a-48c9-964a-b2d012da9121\session.v4.jsonl.zstd'

# 跨会话：看这是偶发还是普遍
node ...\session-degeneration-scan.mjs --root C:\Users\MaxNull\.dsh\sessions-ssid --min-size 3MB
```

退出码 0 = 未越线、1 = 有会话越线、2 = 用法或读取失败。

**本项目有同名 skill `dsh-session-forensics`**（目录摘要每轮注入），它的正文写了工具的用法、
判据的来源、以及哪些情况工具答不了（旧格式日志没有推理文本，报 `n/a`——**那是「未知」，
不是「健康」**）。

### 6.2 已经攒下的取证脚本

| 脚本 | 干什么 |
|---|---|
| `.ssid-iso-test/debris-report-data.mjs` | 推理总量、失败产物首现坐标、工具调用健康度（本报告 2.4 / 2.5 的表出自它） |
| `.ssid-iso-test/dump-session-skeleton.mjs` | 列 turn / assistant / allostasis 事件骨架 |
| `.ssid-iso-test/scan-allostasis-events.mjs` | 扫会话日志里的插件私有事件（`--fix` 就地修） |
| `seek-soul-in-darkness/shell/scripts/session-degeneration-scan.mjs` | 官方扫描入口 |

**会话日志是多帧 zstd**（每次 append 写一帧）。手写解析必须按 magic `28 b5 2f fd` 切帧后逐帧解压；
流式解压器只吐第一帧，用它读会误判成「文件里只有一条元事件」。**这个坑在上面几个脚本里都处理过了。**

### 6.3 候选方向（都还没做，按我认为的价值排序）

1. **把 0.5 阈值重新落到 `ssid` profile，并给它加护栏。** 直接改 profile 已经证明会被覆盖
   （第四节）。要问的是「怎么让它活下来」——候选：写进 `profile-template`（发版基准）、
   或写进我们自己插件的 `cordis.patch.yml`、或用 `dsh-ssid-env` 一类的启动期脚本补条目。
   **这是唯一一条「已知有效但被覆盖」的路，先把它修稳。**
2. **查清自动压缩为什么在 67.8 万触发。** 读 `packages/compaction/compaction-basic/src/config.ts`
   的阈值计算，以及 preset 里 `compaction` group 的实际配置。
3. **给「推理文本重复」加检测。** DSH 的 `dsh-repeat-tool-reminder` 只检测重复的**工具调用**，
   从推理重复上穿了过去（09-18 已记录）。`dsh-allostasis` 的二期判据正是干这个的——**本会话
   里它确实在 t38/s3 触发过一次，top 单元就是 `</parameter>`（见 2.6）**，但提醒没有打断循环。
   **所以这一条的真问题不是「能不能检测到」，而是「检测到之后做什么」**：
   - 提醒已经证明不够；
   - allostasis 第三期的压缩动作在它的设计方案 §九 里被暂缓，理由是「退化样本散布在整段
     退化区间，`compactRegion` 只压指定区间能否打断循环尚未验证」——**本报告的数据支持这个
     暂缓**（t23 的 98% 是整条推理，不是某一段）；
   - 剩下没被验证过的候选：**直接截断当前推理**、**对重复段做去重注入**、**换个更强的信号**
     （连续 N 步而非单步）。第一个需要引擎侧支持，第二、三个可以先在插件里试。
4. **看别的长会话**：`--root` 跨会话扫一遍，确认「`</parameter>` 类残留」是普遍现象还是个例。

## 七、边界

- **本文的数字来自单一样本。** 23 次越线、98% 峰值、8371 次残留都出自 `session-a8ac8e89`。
  把它当「长会话都会这样」是过度概括——09-18 已经记录过反例（压力更高的会话重复率反而更低）。
- **重复率是启发式。** 切分规则微调会带来几个百分点差异，只能横向比较同一判据下的数字。
- **本会话仍在进行**，日志还在增长；上表的数字是 2026-10-01 22:55 前后的快照。
