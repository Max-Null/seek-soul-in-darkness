# 长会话输出退化：压缩阈值锚在窗口比例上，而模型的清醒区不在那

> 状态：**根因已定位 · 本地阈值已处置（0.8 → 0.5）** · 2026-09-18
> 触发：SSiD 长会话里助手的回复出现成段重复（用户问「你好像出故障了？是 DS 的 api 又崩了？」）
> 结论：**不是插件导致，也不是 API 故障**。会话累积到约七十万 token 后，模型在推理阶段出现重复退化；
> 而自动压缩阈值 = `thresholdRatio 0.8` × 窗口 = **80 万 token**，退化发生时压缩从未触发——中间约 13 万 token 是「退化无人区」。
> 后续：上游 issue 草稿见 `docs/排查/2026-09-18-上游issue草稿-压缩阈值比例失真.md`；配置改动见 `~/.dsh/profiles/ssid/cordis.patch.yml`。

## 一、现象

助手在长会话末尾的回复里出现成段重复：推理内容反复输出 `（输出）`、`**做** ✓`、`（好）` 一类的碎片，其中一部分泄漏进了正文。

关键特征是**回复成功了**——会话日志里没有失败、没有重试事件。API 故障的形态是请求失败或重试（会话里会出现 `llm/retry-started`），而这次是「返回成功、内容退化」，所以问题在模型侧生成，不在连接上。

## 二、把「感觉」变成数字

会话日志本身就是证据源：DSH 遵循「model-visible ⟺ logged」，每次请求的 provider usage 和完整的流式输出都落在 `session.v3.jsonl.zstd` 里。读它需要三步：

1. **多帧解压**。该文件是**拼接的 zstd 帧**（每次追加一批事件写一帧），不能当普通 zstd 流解。按 `deepseek-harness/packages/session/session-persistence-jsonl/src/zstd.ts` 的 `scanZstdFrames()` 扫出每帧的 `[start, end)`，再逐帧解压后拼接。
2. **取压力值**。每个 `assistant/message` 的 `data.usage` 是 provider 上报的真实计数；上下文压力 = `inputTokens + cacheReadTokens + cacheWriteTokens`。
3. **取推理文本**。`data.stream[]` 里 `type` 为 `reasoning-chunks` / `text-chunks` 的条目，其 **`texts` 数组**（按 token 切分的碎片）拼接即得全文。注意字段名是 `texts`，不是 `chunks`。

重复度判据：把文本按 `[\n。！？]` 切成单元，统计**出现 ≥3 次的单元占比**。

## 三、证据

### 3.1 退化是爬升的，不是突发的

会话 `session-8fa3b15e`（本机 SSiD 会话，窗口 1,000,000）在压缩前的重复率：

| turn/step | seq | 上下文压力 | 重复率 | 高频重复单元 |
|---|---|---|---|---|
| t51/s2 | 4040 | 675,868 | 32% | `**做** ✓`×21、`**写** ✓`×10 |
| t52/s4 | 4066 | 685,581 | 45% | `**做** ✓`×20、`**输出** ✓`×13 |
| t54/s1 | 4093 | 695,143 | 28% | `**`×15、`**做** ✓`×7 |
| t54/s2 | 4098 | 697,848 | **76%** | `（输出）`×25、`**`×21、`**（输出）**`×17 |
| t55/s1 | 4106 | 699,399 | 67% | `**`×31、`**（输出）**`×15、`（好）`×11 |

**约 67 万 token 起出现明确信号，70 万附近到达峰值。** 重复单元全部是模型自己的推理碎片——没有任何一条是插件注入或工具返回的文本。

### 3.2 压缩周期精确停在 79%

自动压缩的触发线是 `thresholdRatio 0.8` × 窗口。本机 deepseek 路由的窗口是 **1,000,000**（`deepseek-harness/packages/llm/llm-deepseek/src/adapter.ts:147` `DEFAULT_CONTEXT_WINDOW = 1_000_000`），**即 80 万 token**。

两个规模最大的会话，各自经历多次压缩周期，每次的观测峰值：

| 会话 | 峰值点 | 上下文压力 | 占比 |
|---|---|---|---|
| `session-8fa3b15e` | t37/s2 | 792,108 | 79.2% |
| `session-9e0b3ac2` | t42/s2 | 793,912 | 79.4% |
| 同上 | t95/s7 | 794,451 | 79.4% |

**三次都停在 79% 附近**——因为它们都是涨到 80 万那条线才被压下来的。这不是巧合，是阈值在起作用。

把它放到全量会话上看，这条线更清楚。扫描 `~/.dsh/sessions-ssid` 下 15 个 ≥3 MB 的会话，其中 **9 个的峰值压力落在 79.0% ~ 79.7% 这条窄带里**：

| 会话 | 峰值压力 | 占窗口 |
|---|---|---|
| `session-11010bb9` | 796,602 | 79.7% |
| `session-9e0b3ac2` | 794,451 | 79.4% |
| `session-353b45ea` | 792,209 | 79.2% |
| `session-8fa3b15e` | 792,108 | 79.2% |
| `session-c22e1d99` | 792,069 | 79.2% |
| `session-f56abede` | 791,831 | 79.2% |
| `session-6a808aae` | 791,256 | 79.1% |
| `session-3f943309` | 791,130 | 79.1% |
| `session-3eda899f` | 789,967 | 79.0% |

**九条独立的增长曲线，全部止步于同一条线。** 当前会话的细节可以进一步对账：峰值 792,108（t37/s2）距 800,000 的阈值只差 **7,892 token**，紧接着的 `compaction/start` 落在 seq 2010——自动压缩正是在那条线上触发的。

### 3.3 排除插件

| 疑点 | 实测 |
|---|---|
| 循环内容是否来自插件注入 | **否**。重复单元是 `（输出）`、`**做** ✓`、`（好）` 等模型自身推理碎片 |
| 插件每轮注入多少 | **约 1,000 token**。`dsh-memory` 有 `DEFAULT_INJECTION_BUDGET = 1500` 字符上限（`max-null-plugins/dsh-memory/src/injection.ts:13`），`dsh-tone-layer` 更少 |
| 上下文体积来自哪里 | **99.98% 是历史对话与工具结果**。退化时刻 `cacheReadTokens = 675,712`，其余计数合计不足 2,200 |

插件注入在 67 万 token 的上下文里占 **0.15%**，撑不起这个现象。

## 四、根因

**阈值表达的是「窗口的比例」，而失效的是「模型的清醒区」。**

`packages/compaction/compaction-basic/src/config.ts:144`：

```ts
const thresholdTokens = Math.floor(contextWindow * policy.thresholdRatio)
```

这个公式隐含一个假设：**模型在窗口的 80% 处仍然正常工作**。对 128K 窗口，阈值落在 102K，勉强还算保守；对 1M 窗口，阈值落在 **80 万**——远超任何模型的稳定工作区间。

**窗口容量是「塞得进去」，不是「用得好」。** 浏览器把 1M 写进模型目录，压缩策略据此按比例外推，两者在长会话里就分叉了：会话被一路用到 79% 才压，而模型在 67% 就已经在打转。

由此产生 **约 13 万 token 的退化无人区**（67 万 ~ 80 万）：系统认为「还不到时候」，模型已经在重复。

**一个放大器**：DSH 的循环守卫 `@deepseek-ai/dsh-repeat-tool-reminder` 只检测**重复的工具调用**（其提示词是 `You are repeating the exact same tool call with identical arguments`），不检测**生成文本**的重复。这次循环发生在推理阶段，从它的检测面穿了过去，没有触发任何提醒。

## 五、处置

### 5.1 生效层级：阈值不在 host 层

自动压缩阈值由 **agent preset** 决定，不在 host 层。这层关系容易踩错，先给判据：

| 层 | 在那里写 `thresholdRatio` | 会不会加载 |
|---|---|---|
| host 层 `compaction-basic`（base bundle 的行） | profile patch 里加 `config` | **✗ 不加载**——web-app bundle 在 host 平面把该行设成 `disabled: true`（它把压缩交给 preset，host 层只保留 token 计量） |
| agent preset 的 `compaction-basic` 子条目 | 真正生效的位置 | ✓ |
| `agent-presets` 的 `config.default` | 决定**新建会话**用哪个 preset | ✓（同样写在 profile patch 里） |

**唯一可靠的验证判据是 `dsh --profile <name> --dump-config`**：看目标条目有没有被 `patched by <patch 文件绝对路径>` 标注、以及它有没有躺在 `disabled: true` 下面。**YAML 合法、字段名对得上 schema、取值落在 `(0, 1]`——这三条同时成立，也证明不了该条目会被加载。**

### 5.2 本机的固定项与处置

| 位置 | 阈值 | 说明 |
|---|---|---|
| DSH 随包发布的 `standard` preset | **未写** → DSH 默认 **0.8**（80 万） | 实测 79% 的来源 |
| `~/.dsh/.agent-presets/ssid-double-star/` | 0.6 | 带「双星」完整人格，**不是**默认 preset |
| `~/.dsh/.agent-presets/ssid-standard/` | **0.5**（50 万） | 本次新建：`standard` 的逐字复刻，只改阈值 |

步骤：

1. **新建 `~/.dsh/.agent-presets/ssid-standard/`**：`agent.cordis.yml` 从
   `node_modules/@deepseek-ai/dsh-agent-presets/presets/standard/agent.cordis.yml` 直接复制
   （MD5 一致），只在其 `compaction` group 的 `compaction-basic` 子条目上加
   `config.thresholdRatio: 0.5`；`preset.yml` 写明名称与用途。落点规则见该包 `lib/index.js:195`
   （`USER_PRESET_DIR = ".agent-presets"`，harness-home 下放自建 preset 的目录）与 `:182`
   （`COMPOSITION_FILE = "agent.cordis.yml"`）。
2. **两个 profile 的 `cordis.patch.yml` 各加一条**，把新会话的默认 preset 指过去：

```yaml
- id: agent-presets
  config:
    default: ssid-standard
```

3. host 层那条 `compaction-basic` patch **保留但改写注释**，注明它当前不生效、只是
   「DSH 若恢复 host 层压缩」时的备用值——留着一条看起来在改阈值的配置，正是这层关系容易被
   看错的原因。

**为什么不直接用 `ssid-double-star`**：它的阈值是 0.6，且带「双星」的完整人格（四阶段流程 +
四个角色 subagent）。**压缩阈值是运维参数，不该和人格绑在一起。**

`ssid-standard` 是 `standard` 的副本，**DSH 升级后若 standard 结构有变化需要跟进**（对比上面
那条 `node_modules/.../presets/standard/` 路径）。两个 patch 文件的注释里都留了这条对比命令。

### 5.3 生效条件

- **需要重启 SSiD**。原因在启动路径：SSiD profile 声明的是 `patchReload: "live"`，但消费它的
  `watchUserPatches()` 只在官方 CLI 的启动流程里被调用
  （`deepseek-harness/apps/cli/src/profile-boot.ts:355-381`）；SSiD 的 `shell/kernel.ts` 自己
  import app-boot 的 `loadProfile` / `composeEntries` 组装 patch 列表（`:490-543`），**没有挂
  任何 patch 监听**。内核日志里的 `@deepseek-ai/cordis-plugin-hmr` 条目来自 dsh-base bundle 的
  insert，不是 patch 监听器。
- **只影响新建会话**。preset 按会话选择，已存在的会话沿用创建时选定的那个。
- 回滚：删掉 `agent-presets` 那条 patch，即回到 DSH 默认的 0.8。

## 六、边界：哪些还没有验证

- **样本不完整**。15 个 ≥3 MB 的会话里 13 个报 `n/a`——它们没有 `reasoning-chunks`（多为旧格式日志），本判据对它们不适用。所以「只有 1 个明显退化」**不能读作「罕见」**：有推理文本可判的只有 2 个大会话，而**两个都出现了退化信号**（峰值 76% 与 47%）。那 13 个的压力照样跑到 79%，只是检测不了——**那是「未知」，不是「健康」**。
- **不能断言「七十万必然退化」**。更高的压力点（79 万会话的那次）重复率反而更低（42%）——说明任务形态是协变量。本次退化的任务形态是**连续多轮同构操作**（读源码 → 写脚本 → 跑 → 分析），推理结构高度相似。token 数是风险因子，不是充分条件。
- **0.5 的实际效果尚未观测**。配置层已验证：`--dump-config` 显示 `agent-presets` 被我们的 patch 标注且 `default: ssid-standard`，preset 文件解析出 `thresholdRatio: 0.5`，重启日志无报错。但**还没有在长会话里看到它于 50 万附近触发**——preset 按会话选择，需要新建会话才能验证。
- **50 万是否足够安全**未定。退化信号最早出现在 67.6 万，但只在单一样本上观测到起点；如需更保守可继续下调。

## 七、顺带发现（与本议题无关）

`~/.dsh/profiles/ssid/cordis.patch.yml` 第一项 patch 条目同时带 `insert` 与 `inject` 两个键：第 90 行的 `inject: [webRuntime, webServer]` 缩进在 `insert` 列表之内，成了该条目的兄弟键；而第 93-94 行另有一条 `- id: connection` 承担同样的 `inject`。前者对 `insert` 条目不起作用，属冗余行。
