## 一、起点

交接材料第五节与 `85e9e2ead3` 的 commit message 都把它记成：

> `main-startup.spec.ts` 80 条撞 5s 默认预算（既有，建议先诊断再定预算）

并附「全量 `apps/desktop/tests` 的 9 个失败文件经 stash 基线对比确认既有（5s 预算撞线），非本次引入」。

实测基线：`Test Files 8 failed | 107 passed`、`Tests 92 failed | 1231 passed`、`Duration 402.23s`。

**「既有」这个判断是对的**（见 §四），但**原因不是预算**，所以「先诊断再定预算」的后半句没有落点。

## 二、先把「慢」这个假设排除掉

判据：**把 budget 提到远超实际耗时，若仍然挂，就不是慢。**

```
--testTimeout=8000    仍然挂
--testTimeout=20000   仍然挂
--testTimeout=120000  仍然挂（tests 120.03s）
```

三条都挂，且 `--bail=1` 显示**从文件里第一条测试就挂**（`routes shell update documents and assets…`）。
到这一步，「5s 预算不够」被证伪；方向转向「有一个 await 永不 settle」。

---

## 三、根因

### 3.1 静默层

`main-startup.spec.ts` 的文件级 `beforeEach` 里有：

```ts
vi.spyOn(console, 'error').mockImplementation(() => {})
vi.spyOn(console, 'info').mockImplementation(() => {})
```

启动链上抛出的任何异常都被吞掉。**没有任何 `ssid:` 日志出来**，正是因为启动链在打印第一行之前就断了。
现场只剩「Test timed out」，把注意力全部引向预算。

### 3.2 异常本身

把上面那行临时改成注释后重跑，异常立刻现形：

```
TypeError: Cannot read properties of undefined (reading 'profile')
```

### 3.3 因果链

1. `main-startup.spec.ts` 的 `DesktopProjectManager` mock **只提供 `applyRelease` 等方法，没有 `paths`**（同文件 L303 倒是 mock 了 `resolveDesktopPaths`，返回 `{ profile: 'desktop-test-profile' }`）。
2. `main.ts` 的 `seedProfilePlugins(manager.paths.profile, carried)` 求值 → `manager.paths` 为 `undefined` → **TypeError**。
3. 这一步位于 `backend-controller.ts` 的 `await prepare()` 内，而 `prepare` 在 **`await manager.applyRelease()` 之后、`host.start()` 之前**。
4. 异常从 `prepare` 抛出 → `host.start()` **永不执行** → 测试在等的 `harness.hostStarted` 永不 resolve。
5. 测试的 `readyForUpdate()`（同文件 L1028）第一个 await 是 `harness.preparing.promise`，第二个是 `harness.hostStarted.promise` —— 于是整文件超时。

### 3.4 它从哪来

| 提交 | main.ts 里的那一行 |
|---|---|
| 官方 HEAD `477b4f4205` | **不存在** `seedProfilePlugins` / `manager.paths` |
| fork `74ad639123` | L770 `seedProfilePlugins(manager.paths.profile)` ← **引入点** |
| `85e9e2ead3` | L831 同一行，只多传了 `carried`，**没动取值来源** |

所以 stash 掉 `85e9e2ead3` 之后回到 fork 版本，**一样红** —— 这解释了为什么它被记成「既有」。
`85e9e2ead3` 的 message 里其实写对了方向（「接入点改用 `activeProject`，不读 `manager.paths`（测试 mock 下为 undefined）」），**只是漏了第二处调用点**。

### 3.5 修法

`activeProject` 与 `manager.paths.profile` 在产品里同源：

```ts
const paths = resolveDesktopPaths()            // L549
const activeProject = paths.profile            // L554
const manager = new DesktopProjectManager(paths, resources)   // L555
```

改成 `seedProfilePlugins(activeProject, carried)`。**一处赋值**：

| | 修复前 | 修复后 |
|---|---|---|
| Tests | 92 failed / 1231 passed | **11 failed / 1312 passed** |
| Duration | 402.23 s | **27.10 s** |

`welcome-startup.spec.ts` 那 2 条同源，一并恢复。

## 五、本次被推翻的三个中间结论

记下来是为了下次少走：这些推论**当时都有像样的理由**。

1. **「`backend-controller.ts` 的 pending 被跨测试复用 → 一挂全挂」** —— 被 `beforeEach` 里的 `vi.resetModules()` 否证：每个测试拿到的都是全新模块实例，`backend` 并不共享。
   （该文件 L63 `if (this.pending !== undefined) return this.pending` 的机制本身属实，只是不在这次的现象里起作用。）
2. **「挂起点是 `await previous?.cleanup`」** —— 基于「第一条之后全挂」的推测；`--bail=1` 显示**第一条就挂**，而第一条时 `previous` 是 `undefined`，该分支根本不执行。
3. **「`vi.useFakeTimers()` 使某处 `setTimeout` 不触发」** —— 启动链上确实有 `setTimeout`（`host-process.ts` L164/L375），但那是 `DesktopHostProcess` 的实现，而测试用 `FakeHost` 替身，**不在路径上**。

三条的共同点：**都是先想出一个能解释症状的机制，再去找支持它的证据**。正确顺序是反过来的 —— 先取到「第一条就挂」「120 秒仍挂」这类硬事实，机制才收窄到唯一。

---

## 六、可复用的判据

- **「超时」不是一种原因，是一种表现。** 先用超大 budget 把「慢」排除，再查「不 settle」，最后才考虑调预算。
- **排查测试挂起之前，先检查有没有 `console.error` / `console.info` 被 mock 静默。** 静默会同时抹掉异常与诊断输出，让现象退化成纯粹的「超时」。
- **`vi.resetModules()` 的测试文件里，「跨测试状态污染」类假设要先验证再采信。**
- **「既有」只说明不是本次引入；它不说明原因，也不说明能不能靠调参解决。**
