# 应变（dsh-allostasis）：提醒发了 10 条，复读没停

> 记录人：DSH agent（会话工作区 `huiyijiyao`） ｜ 日期：2026-10-19 ｜ 插件版本：`@max-null/dsh-allostasis@0.5.1`
> 触发场景：一份 30+ 轮的长会话（离职交接材料整理），后半段进入思考链复读

---

## 一、现象

会话后半段出现严重的**思考链复读**：同一批短语（「好」「发」「输出」，以及一整段「（发。）」）在思考里循环上千次。

**插件不是没反应**——它在这段区间里发了 **10 条提醒**（5 条语言漂移 + 5 条推理退化）。但复读**没有停**，一直持续到**人在对话里直接指出**（「你的思维链退化了」）才终止。

也就是说：**检测链路是通的，打断链路没接上**。

---

## 三、直接「死因」

`streamCut` 的出厂档位是 **`observe`** —— 流内判据照常判定、照常写 `console.debug` 留痕，但**不掐断**。

配置注释里写明了关闭的理由（这是有意的、不是缺陷）：

> 掐断会让被掐那一步的 usage 与 replayState 两格缺失，该轮的 token 汇总因此不可用。要开就显式写 cut。

所以本次现象的直接解释是：**判据全部命中，但没有一个动作能让生成停下来**。

---

## 四、因果链

1. 模型进入复读（同一批短语循环）
2. 步级判据 `repetition ≥ 0.5` 且窗口内 ≥2 步 → 命中，发一条提醒
3. 提醒的形式是「**往请求末尾追加一条消息**」，不改生成、不终止生成
4. 模型下一步继续复读 → 命中 → 再发提醒
5. 累计 5 条后仍在复读
6. 直到人介入

关键在第 3 步：**提醒是「请求侧」的手段，而退化是「生成侧」的问题**。提醒能做的只有「让模型看到自己刚才在复读」，对已经在复读里的生成没有任何强制力。

## 五、已排除路径

| 假设 | 排除依据 |
|---|---|
| 插件没装 | profile `package.json` 的 `dependencies` 与 `dsh.profile.bundles` 均含 `@max-null/dsh-allostasis`；`node_modules\@max-null\dsh-allostasis` 存在 |
| 插件没加载 | 本会话收到 10 条它发的提醒，文案与源码格式一致 |
| 判据没命中 | 那 10 条提醒本身就是命中的产物 |
| 阈值太松 | 实测重复率 96% / 98%，远超 0.5 |
| 提醒链路断了 | 提醒正常出现在对话里 |
| 是「上下文压缩没生效」 | **应变不做压缩**——README 把「压缩预约落盘」列为**计划中**；压缩在 `dsh-context` 那条线上。这条是本次排查里最容易被误认的方向 |
| 上下文太长导致判据失效 | 判据是纯文本统计，不读上下文长度 |
| 是语言漂移那条判据误报 | 语言漂移只负责「用英文思考」，与复读是两条独立判据；退化提醒的读数是独立测的 |

## 六、实测证据

**1. 复读的形态**（来自插件自己的警告文本）

- 重复单位是**短片段**，不是整段：
  - turn 13/2：1586 个片段里 1515 个出现 ≥3 次 —— 最高频「好」×1010
  - turn 14/1：8588 个片段里 8445 个出现 ≥3 次 —— 「好」×4230、「输出」×4193
- 也出现过**整段复读**：一整段「（发。）」连续输出上百次
- 单步之内就已经越线（每步 49%–98%），**不是跨步累计才越线**

**这条对判据选型很重要**：本类复读在**流内单步**上就能观察到，`streamCut: cut` 的判据（单步之内 ratio ≥ 0.5）理论上能覆盖。

**2. 提醒的疗效（与 README 的标定数据对照）**

README 标定：落点在越线上的提醒，**89%–91% 在紧接着一步回落**。本会话**没有回落**：

| 提醒 | 下一 turn 的重复率 |
|---|---|
| 13/2（96%） | 14/1：**98%**（更严重） |
| 14/1（98%） | 15/1：52% |
| 15/1（52%） | 16–19 轮未再报（**但 20/9 又回到 82%**） |
| 20/9（82%） | 21/1：49% |

即：**没有「持续失守」的证据，但有「反复复发」的证据**——中间降下去，几轮后又回到 82%。

**3. 环境侧读数**

- 插件生效配置（`observe` 档）与 README 的 `loaded` 行一致
- 本会话上下文占用很高（30+ 轮、含大量表格与脚本输出），**但 README 已有结论：退化与上下文占用脱钩**（26.1% 占用时重复率 84%、67.9% 时 83–92%）——所以「上下文太长」不是本次的因果项

## 七、未确证部分

以下是我推理但没有实测的，交接时请当作假设而非结论：

1. **开 `cut` 后是否真能打断「短片段高复读」这一类**。README 说流内判据的单步 ratio ≥ 0.5 在回放数据上召回 906/906，但那是**离线回放**；在线掐断对「每步都 50% 左右、整段退化」这种形态的效果未实测（本会话 turn 15/1 与 21/1 就是 49–52%，**贴着阈值**）。
2. **`streamCutMaxResumes: 3` 是否够**。一次不收敛的退化可能需要更多次续跑；反之也可能 3 次太多（每次续跑都往上下文注入一条消息，本身是污染）。
3. **「提醒无效后自动升级为掐断」是否会误伤**。这是最像「该做」的改进，但没有误伤率的数据。

## 八、修复方向（供插件侧取舍）

| # | 方向 | 为什么 | 代价/风险 |
|---|---|---|---|
| 1 | **同一 turn 内第 N 次命中即临时切 `cut`** | 本会话证明了「提醒可以连续 5 次无效」；固定档位无法自适应 | 需要定 N；误伤窗口变大 |
| 2 | **提醒无效的判定显式化**（提醒后一步未回落 → 记一次「失守」，N 次失守升级） | 比「按次数」更贴问题本质：真正该管的是「提醒没用」，不是「命中很多」 | 需要定义「回落」的阈值 |
| 3 | **贴近阈值的退化形态**（49–52%） | 本会话两次命中就贴在 0.5 上；`loopWindowHits` 已有窗口机制，但**单步刚过线**的情形是否该被同等对待未讨论 | 降阈值会放大误报（README 已论证白名单判据误报率高，统计数据是 93% 真阳） |
| 4 | **配置持久化** | 插件的 `cordis.patch.yml` 在**程序目录**（`resources\ssid-plugins\node_modules\...`），**升级/重装思灵即被覆盖**；而 profile 的 `cordis.patch.yml` 是每次启动重新合成的产物，手改也不保 | 这是本机落地 `cut` 的主要痛点，见第九节 |
| 5 | **压缩归位说明** | README 里「压缩预约落盘」是计划中，但使用者容易把「应变」当成「压缩」。建议 README 顶部一句话说清边界 | 无 |

## 九、本机已做的处置（临时措施）

**已开启 `streamCut: cut`**，改的是插件包内那份 patch：

```
C:\Users\21030442\AppData\Local\Programs\ssid-shell\resources\ssid-plugins\node_modules\@max-null\dsh-allostasis\cordis.patch.yml
```

```yaml
- insert:
    - id: allostasis
      name: '@max-null/dsh-allostasis'
      config:
        streamCut: cut
```

⚠️ **两个已知问题**：

1. **需要重启内核才生效**（patch 在 bundle 加载时读）。
2. **升级插件或重装思灵会覆盖这个文件**——下次升级后要重做。

**没有改** profile 的 `cordis.patch.yml`：那份文件是思灵每次启动**重新合成**的产物（内容 = 出厂插件集 + DSH 设置条目，不符就重写），手工加进去的条目活不过下一次启动。这与 2026-09-28 排查 MCP 条目丢失时确认的机制同源。

**长期方案二选一**：

- 插件侧支持 profile 级 config（或环境变量），把「本机想开 cut」这件事挪出程序目录；
- 或在本机挂一个独立 bundle 层（像 `ssid-local-mcp` 那样）只覆盖这一条 config。
