# 思灵在进程识别上的暴露面

> 记录时间 2026-09-29 · 起因：讨论「另一环境有监控软件监控 DSH 进程并禁止启动，思灵会不会也受影响」
> **用途是判断「会不会被误伤」，不是规避清单** —— 下面两处痕迹都有各自的工程理由。

## 一句话结论

**思灵在「名字层」是干净的** —— 进程名、安装路径、窗口标题都不含 DSH。
**但在「命令行层」和「注册表层」各留了一处 `dsh` 痕迹。**
**会不会被拦，取决于那套监控按什么判定。**

## 一、干净的那些

| 识别方式 | 结果 | 实测证据 |
|---|---|---|
| 进程名 `dsh*.exe` | **不命中** | 7 个进程全部名为 `思灵.exe` |
| 安装路径含 `dsh` | **不命中** | `C:\Users\MaxNull\AppData\Local\Programs\ssid-shell\` |
| 窗口标题含 DSH | **不命中** | 实测标题 `升级内核 — 思灵` |
| 文件哈希比对官方产物 | **不命中** | 与官方 DSH 桌面端产物不同 |

## 二、会暴露的两处

### ① 命令行：`--user-data-dir="…\AppData\Roaming\@deepseek-ai\dsh-desktop"`

每个子进程都带这个参数。实测原文：

```
"C:\Users\MaxNull\AppData\Local\Programs\ssid-shell\思灵.exe" --type=gpu-process
  --user-data-dir="C:\Users\MaxNull\AppData\Roaming\@deepseek-ai/dsh-desktop" …
```

**为什么会有 —— 不是疏忽，是单实例锁策略的直接后果**（工作区铁律 2.2）：

- 壳代码里**没有 `app.setName()` 调用**；`app.name` 直接来自 `apps/desktop/package.json` 的 `name` 字段（值就是 `@deepseek-ai/dsh-desktop`）。
- `apps/desktop/tests/main-startup.spec.ts:895,903` **显式断言这个值**，说明它是被有意保持的行为。
- 目的是让 dev 实例与装版**共用同一个 `%APPDATA%\@deepseek-ai\dsh-desktop\lockfile`**，从而天然互斥 —— 否则两个实例会同时跑起来抢同一份 profile。

而 Electron 的 `--user-data-dir` 默认由 `app.name` 推导，于是命令行带上了这个字符串。

### ② 注册表：`dsh://` 协议处理程序

两处都存在（实测）：

| 位置 | 默认值 | 子键 | 打开命令 |
|---|---|---|---|
| `HKEY_CLASSES_ROOT\dsh` | `URL:dsh` | `shell` | `"…\win-unpacked\思灵.exe" "%1"` |
| `HKEY_CURRENT_USER\Software\Classes\dsh` | `URL:dsh` | `shell` | 同上 |

来源：打包配置 `apps/desktop/scripts/electron-builder-config.mjs:115` —

```js
protocols: [{ name: '思灵', schemes: ['dsh'] }],
```

**注意**：当前这两条指向的是 **dev 的打包产物路径**（`H:\MaxNull\WorkStation\.ssid-build\checkout\…\unsigned-artifacts\win-unpacked\思灵.exe`），说明它们是**上次打包测试留下的**，不是装版安装时写入的。装版若换机器安装，写入的会是装版自己的路径。

## 三、其它可能的识别面

| 方式 | 结果与说明 |
|---|---|
| Electron 通用特征（进程结构、`resources.pak`、`ffmpeg.dll` 等） | **命中** —— 但这条也会命中所有 Electron 应用（VS Code、Slack、Discord…），单独的"禁止 DSH"不太可能按这个判定 |
| 数字签名 | 实测 `Get-AuthenticodeSignature '…\ssid-shell\思灵.exe'` → **`NotSigned`**（233.1 MB）。若策略是「仅允许已签名程序运行」，unsigned 版会被单独拦下 —— **这与 DSH 无关，是签名状态问题** |
| 网络行为（连 `api.deepseek.com`） | 命中，但那属于流量管控，不是"禁止启动进程" |
| 加载的 asar 内部路径（`resources/app.asar/dsh/`） | 外部扫描看不到（asar 是打包的），除非扫描器会解包 |

## 四、判断需要的外部信息

**唯一决定答案的变量是「那套监控怎么识别 DSH」**：

| 监控的判定方式 | 思灵会不会被拦 |
|---|---|
| 进程名 / 安装路径匹配 | **不会** |
| **命令行关键字匹配** | **会**（`--user-data-dir` 里的包名） |
| **注册表扫描** | **会**（`dsh://` 协议） |
| 企业白名单（只允许已批准程序） | **会**，且与名字无关 |

另需知道「禁止启动」的**表现**：弹窗提示 / 静默终止 / 拉黑名单 —— 这决定万一被命中时的后果严重程度（静默终止最麻烦，因为看不出原因）。

## 五、最省事的验证方式

**直接在那个环境里装一次，看它报什么。** 被拦通常拦在启动那一刻，现象很直接 —— 比从"识别方式"倒推可靠得多。若只是警告而能启动，那就没有实际影响。

## 六、立场

若那是**受管控环境**，正确做法是**走申请例外**，不是想办法让思灵看起来不像 DSH。

上面列的暴露面用于判断「会不会被误伤」；那两处痕迹各有工程理由（单实例锁、协议注册），**改动它们应该是为了功能正确性，不该是为了绕过管控**。

## 证据来源

- 进程与命令行：`Get-CimInstance Win32_Process -Filter "Name = '思灵.exe'"`
- 窗口标题：`Get-Process -Name '思灵' | Select-Object MainWindowTitle`
- 注册表：`HKCR\dsh`、`HKCU\Software\Classes\dsh`
- 签名：`Get-AuthenticodeSignature '…\ssid-shell\思灵.exe'` → `NotSigned`
- 代码：`apps/desktop/package.json` 的 `name` 字段；`apps/desktop/tests/main-startup.spec.ts:895,903`
- 打包配置：`apps/desktop/scripts/electron-builder-config.mjs:115`
