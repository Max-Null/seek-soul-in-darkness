## 拟提交的 issue 正文

**Title**: Draft attachments are dropped when switching sessions, while switching workspaces carries them over

**Body**:

### What happens

In the composer, type some text and attach an image to session A (do not send). Switch to session B — B's composer is empty, which is correct: drafts are per-session. Switch back to A: **the text is still there, the image is gone.**

Observed on Windows, DSH `0.2.0-rc.2`. Nothing is reported to the user.

### Why the text survives and the attachment does not

The two halves of a draft live in different places.

**Text** is in the per-session persisted store:

```ts
// packages/client/ui-conversation/src/client/stores.ts
init: (): ConversationStoreState => ({ draft: '', view: null, viewRequest: null }),
```

**Attachment ids** are an instance field on the input shell:

```ts
// packages/client/ui-conversation/src/client/input/facade.ts
private attachmentIds: readonly DraftAttachmentId[] = []
```

and that shell rides the session scope fiber, whose teardown releases them:

```ts
// packages/client/ui-conversation/src/client/input/hub.ts
const shell = new SessionInputShell({ /* … */ })
this.shells.set(binding, shell)
actx.effect(() => {
  const offs = [ /* … */ ]
  return () => {
    for (const off of offs) off()
    const drafts = shell.dispose()
    this.shells.delete(binding)
    const conversation = this.rootCtx.get('conversation') as ConversationAttachmentFace | undefined
    for (const attachmentId of drafts) conversation?.releaseDraftAttachment(attachmentId)
  }
}, 'conversation.input: session shell')
```

`releaseDraftAttachment` does not merely drop a reference — it deletes and revokes:

```ts
// packages/client/ui-conversation/src/client/service.ts
releaseDraftAttachment(id: DraftAttachmentId): void {
  // … this.draftAttachments.delete(id) …
  // … revokePreview(previewUrl) for image previews …
}
```

### The two switching paths disagree

Switching **workspace** explicitly carries the attachment across:

```ts
// packages/client/ui-conversation/src/client/apply.ts
selectWorkspace: workspaceId => workspaceNavigation.openWorkspace(workspaceId, (nextId) => {
  if (sessionId !== undefined && nextId !== sessionId) {
    const from = inputHub.shell(sessionId)
    const draft = from.snapshot.draft
    const attachmentIds = from.snapshot.attachmentIds
    const next = inputHub.shell(nextId)
    if (attachmentIds.length === 0 || next.addAttachments(attachmentIds)) {
      concreteConversation(ctx).rebindDraftFiles(nextId, attachmentIds)
      // … carries draft + attachmentIds, then removes them from the source shell …
    }
  }
})
```

Switching **session** has no equivalent step: the shell is torn down and the attachments are released. From the user's side both actions are "go read another conversation", yet one keeps the image and the other does not. Since a `rebindDraftFiles`/`addAttachments` path exists for the workspace case, keeping draft attachments looks intended — so this reads as a gap rather than a deliberate policy. If attachment survival is deliberately not guaranteed, documenting that (and dropping them without a visible trace) would also settle it.

### Minimal reproduction

1. Open a session; type text and attach an image (leave it unsent).
2. Switch to any other session — its composer is empty (expected).
3. Switch back to the first session.
   - **Expected**: both the text and the image come back.
   - **Actual**: the text comes back; the image is gone.

### Related, independent papercut: `createDrafts` is absent from the type surface

While tracing this we hit a second issue on the same subsystem. The runtime method that turns `File`s into draft attachments is used internally but is not on the `IConversation` type surface:

```ts
// packages/client/ui-conversation/src/client/service.ts
createDrafts(sessionId: SessionId, files: readonly File[]): readonly ComposerAttachment[]
```

A third-party client plugin therefore has to reach it by casting a local interface. When it was renamed from `createDraftImages(files)` to `createDrafts(sessionId, files)`, that cast silently resolved to `undefined`, the plugin fell back to its text-only path, and nothing warned — the feature just stopped adding images. Exposing `createDrafts` (or a supported draft-attachment service method) on the type surface would turn that class of silent failure into a compile-time error.
