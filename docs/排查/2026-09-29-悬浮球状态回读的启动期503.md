# 悬浮球状态回读在启动期刷 503

> **状态：待办 —— 下个版本处理**（2026-09-29 记录，未实施）
>
> 记录时间 2026-09-29 · 起因：dev 控制台出现 11 条
> `dsh-app://app/quick-toolbar/api/state 503 (Service Unavailable)`
> **用途是判断这是不是缺陷、下个版本要不要动、动哪里** —— 结论是**已知时序、有降级、功能不受影响**，但有一处对不上账。
>
> **动手之前先做一件事**：查清 §三 那 4 次差额的来源。**它决定方案 A 只改壳够不够** —— 若差额来自第三个调用点，只改 `titlebar.ts` 治不干净。

## 一句话结论

**503 是壳的协议层在 Host 未就绪时的既定回答，不是插件故障。** 页面静态资源不等 Host、API 请求要等，所以「页面先渲染、API 后可用」是设计使然；早期那几个请求必然被挡。
**功能不受影响**：壳与插件读不到都退回默认态，点一下标题栏的悬浮球开关照样能切。
**但请求次数对不上账**：按代码算 7 次，实测 11 次 —— 这一处没有查清，见 §三。

## 一、503 的确切产生点

`ssid-desktop/apps/desktop/src/main.ts:954-969`：

```ts
protocol.handle(SCHEME, (request) => {
  const url = new URL(request.url)
  if (url.hostname === 'shell') return serveWebDocument(request, join(app.getAppPath(), 'renderer'))
  if (url.hostname === 'app') {
    if (url.pathname === '/' || url.pathname === '/index.html' || url.pathname.startsWith('/assets/')
      || ['/favicon.svg', '/manifest.webmanifest'].includes(url.pathname)) {
      return serveWebDocument(request, join(resources.dsh, 'node_modules', '@deepseek-ai', 'dsh-web-frontend', 'dist'))
    }
    if (backend.host === undefined || hostUrl === undefined || hostCookie === undefined) {
      return Promise.resolve(new Response(null, { status: 503 }))      // ← 这里
    }
    return forwardWebRequest(request, hostUrl, hostCookie)
  }
  return Promise.resolve(new Response(null, { status: 404 }))
})
```

判据是 **Host 三件套（`backend.host` / `hostUrl` / `hostCookie`）任一未就绪**。
响应体为空、无 `Retry-After`、也没有任何区分「尚未就绪」与「真的坏了」的标记 —— 前端只能靠 status 猜。

## 二、谁在请求这条路径

| 请求方 | 位置 | 重试策略 |
|---|---|---|
| 壳的标题栏 | `ssid-desktop/apps/desktop/src/ssid/titlebar.ts:529-537` | `attempt < 5`，退避 `400ms × (attempt + 1)` |
| 插件 client 半 | `max-null-plugins/dsh-quick-toolbar/src/client.ts:581-599` | **无重试**，失败即 `done()`，走默认态 |

壳这一侧**自己知道这件事**，源码注释写得很直白（`titlebar.ts:526-528`）：

```
// 悬浮球状态回读。这个请求要等 Host 就绪才有答案：壳的协议 handler 在 Host 未起来时直接
// 返回 503（main.ts 的 protocol.handle），而这句注入常赶在 Host ready 之前跑 —— 于是控制台
// 会刷出 503。退避重试若干次；始终读不到就停在默认态，功能不受影响（点一下照样能切）。
```

也就是说：**这是被预期、被接受的行为**，不是回归。

## 三、对不上账的那一处

按代码算：`titlebar.ts` 的 `attempt < 5` 从 0 数到 5 = **6 次**；加插件 `loadState` 的 **1 次** = **7 次**。
实测日志里是 **11 次**。**差 4 次，原因未查清。**

可能的方向（**都未验证**）：页面在启动期重载过一次；或存在第三个调用点尚未找到。

**已排除一条**（2026-09-29 复核）：插件侧其实有**两个**对同一路由的调用点 —— 上面表格只记了 `loadState`（GET，`client.ts:582`），另有一个 `saveState`（**POST**，`client.ts:602`），它有 4 个调用处（`client.ts:1501` / `1547` / `1623` / `1831`）。数字上 6 + 1 + 4 恰好等于实测的 11，看着像答案 —— **但四处全在用户交互路径上**（折叠切换、钉住点击、拖动结束、标题栏悬浮球开关事件），启动期不会自行触发。所以那个吻合是巧合。

注意这条排除**不等于**「POST 不会被 503 挡」：`saveState` 与 `loadState` 走同一条 `dsh-app://app/` 路径，Host 未就绪时一样会被挡，只是它 `.catch` 吞掉且调用时机在交互之后。**排查启动期那 11 条时不必再怀疑它**，但如果将来统计「这个路由一天被撞多少次」，它要算进去。

**这一条不该凭猜收口**：下个版本动它之前，先在渲染进程里数一次调用来源（例如临时给 `protocol.handle` 的 503 分支加计数与调用栈），再来定「少刷几次」的目标值。

## 四、复现与判读

Host 就绪后直连该路由：

```powershell
Invoke-WebRequest -Uri 'http://127.0.0.1:19488/quick-toolbar/api/state' -UseBasicParsing
# 实测：200 {"ok":true,"state":{"pos":{"x":62,"y":331},"collapsed":true,"pinned":false,"shellVisible":true}}
```

**判读口径**：**直连 200 + 控制台 503 = 启动期时序问题**（本次即此）；**直连也 503** 才是 Host 真的没起来，那是另一回事。

## 五、下个版本可以怎么动（未实施，供决策）

| 方案 | 位置 | 代价 |
|---|---|---|
| **A. 等 Host 就绪再读**，而不是退避去撞 | 壳 `titlebar.ts:529-537` | 需要 ready 信号；该信号已存在 —— `DESKTOP_IPC.boot`（`main.ts:977-982`）在 `await startup` 之后才返回，渲染进程可以等它 |
| **B. 让 503 可区分**：未就绪回 `425 Too Early`，或至少带 `Retry-After` | 壳 `main.ts:963-965` | 语义更准，但两个调用点的判据都要跟着改 |
| **C. 插件侧加退避重试** | `client.ts:581-599` | 改动最小；只让日志干净些，不解决时序本身 |

**倾向 A**：它是唯一能让「控制台不再刷这几行」的方案；B 的语义收益要靠前端配合才拿得到，而 C 只是把噪音推后。

## 六、这不是插件缺陷

- 插件的 **host 半正常**：路由已注册，直连返回 200 与正确状态（见 §四）。
- 插件的 **client 半正常**：悬浮球照常显示与工作。
- 503 出现在**任何 `dsh-app://app/` 下的非静态资源请求**上。quick-toolbar 只是**当前唯一带 host 路由的插件**，所以它显形在这里；换一个带 host 路由的插件，同样会刷。
