# 内核 0.1.7 适配：壳侧方案（评估稿）

> 日期：2026-09-24 ｜ 状态：**评估稿，未实施** ｜ 依据：DSH `dsh-v0.1.7-rc.2` 源码（工作树 `%TEMP%\dsh-017-src`）与壳当前代码（`shell/kernel.ts` @ 0.1.5-rc.2 形态）
> 关联：`dsh-anatomy/版本对比/2026-09-24-0.1.7-rc.2-vs-0.1.6-alpha.2.md`

## 为什么先做壳

自制插件的 settings 面适配（`.volatile()`、`plugins.item`、`ctx.configForms`）**全部以「设置体系已激活」为前提**；而 0.1.7 下设置体系由 `profileContext` 门控（见 §2 P0-c）。壳不先适配，插件改得再好也不生效。此外壳的模块解析问题会在**启动阶段**直接崩，轮不到插件出错。

## 一、现状（0.1.5-rc.2）

壳自己 boot DSH（不走官方 `apps/cli`）：

```
kernel.ts:489  installProfilePackageResolver(profileDir/package.json)
kernel.ts:495  const dsh = await import('@deepseek-ai/dsh-app-boot')
kernel.ts:502  dsh.initProfile(...)          // 首次
kernel.ts:506  await dsh.healProfilesModuleFallback({ installAnchor, home })   ← 落盘建平面
kernel.ts:507  const profile = dsh.loadProfile(BIN_NAME, PROFILE_NAME, installAnchor, home)
kernel.ts:622  await dsh.boot(BIN_NAME, rootConfig, patches, hostCtx => {
                 provide(DSH_LAUNCH_ENVIRONMENT_KEY) / provide(SSID_SHELL_*) / provideCmdline
               })
```

`module-resolution.ts:11-12` 说明其解析策略：用 Node 24 `registerHooks` 把 loader 发出的 bare specifier 的 parentURL 改写到 profile 目录，再靠 Node 向上查找命中

- profile 自己的 `node_modules`（第三方插件）
- `~/.dsh/profiles/node_modules` —— **由 `healProfilesModuleFallback` 建立的平面 symlink**，覆盖所有 `@deepseek-ai/dsh-*`

## 三、适配方案

### 3.1 顺序调整（关键）

```
旧：initProfile → heal → loadProfile → boot
新：initProfile → loadProfile → createRuntimeResolution → boot(..., prepare 里注入)
```

依据：官方新流程里 `loadProfile` 不再依赖平面（`profile-boot.ts:167-173` 的 `prepareProfile` 只读文件：`resolveProfileDir` / `removeLinkProjections` / `normalizeShippedProfile` / `loadProfileDirectory`），而 `createRuntimeResolution` **需要 `profile` 作为入参**，所以只能排在 `loadProfile` 之后。

### 3.2 三处代码改动

**① `kernel.ts:506` 替换**

```ts
// 旧
await dsh.healProfilesModuleFallback({ installAnchor, home })
// 新
const resolution = await dsh.createRuntimeResolution({ installAnchor, profile, home })
```
（`profile` 需先由 `loadProfile` 得到 → 与下一行的顺序对调）

**② boot 的 prepare 回调里注入 `PluginPackages`**

```ts
const ctx = await dsh.boot(BIN_NAME, rootConfig, structuredClone(patches), async (hostCtx) => {
  hostCtx.provide(DSH_LAUNCH_ENVIRONMENT_KEY, environment)
  await hostCtx.plugin(dsh.PluginPackages, { resolution })   // ← 新增，须在任何 entry mount 之前
  // …原有 SSID_SHELL_* provide 与 provideCmdline
})
```
`PluginPackages` 从 `@deepseek-ai/dsh-app-boot` 导出（新版 `index.ts:86`）。

**③ 提供 `profileContext`（决定设置体系是否活着）**

```ts
hostCtx.provide('profileContext', profileContext)   // 形状待定，见 §4
```

### 3.3 壳自己的 resolver 怎么办

`installProfilePackageResolver` 的存在理由是 electron 场景：`ctx.loader.internal` 为 undefined、loader 退化成从 `tree.ts` 位置 `import(name)`（`module-resolution.ts:4-7`）。**新版官方的 `profile-resolution/resolver.ts` 是否覆盖该场景尚未验证** → 两种可能：

- 若官方 resolver 覆盖 electron：壳可**删掉**自己的 resolver，只留 `PluginPackages` 注入；
- 若不覆盖：壳保留 resolver，但**改为消费 `resolution.entries`**（`name → packageDir` 的完整表，新版 `profile.ts:124-136`），即把「改写 parentURL 让 Node 向上找平面」改成「直接按表映射 specifier → packageDir」，不再依赖平面存在。

`resolution` 的可用字段：`profilesDir` / `profileDir` / `localPackageNames` / `entries[{name, packageDir, version, declarer, scope}]` / `linkedRoots[{name, realPath}]`。

## 四、待验证项（实施前必须落实）

1. **`ProfileContext` 的完整形状**：官方在 `apps/cli/src/profile-boot.ts` 构造它（类型从 app-boot 导出）。壳要自己造一个，需确认哪些字段被下游消费（`config-editor` 读 `profileContext.patchPath`；`settings` 读 `home` / `name`）。
2. **官方 resolver 是否覆盖 electron 的 `loader.internal === undefined` 场景**（决定壳的 resolver 是删还是改）。
3. **`createRuntimeResolution` 在壳的场景下所需入参**：`{ installAnchor, profile, home }` 是否足够（官方传 `{ installAnchor, profile }`，`home` 有默认值）。
4. **`agent-presets` → `agent-preset-registry` 的 root 注入新写法**（新版 `agent-preset-registry` 的 Config 形状）。
5. **实机验证路径**：本项改动必须用隔离实例（`.ssid-iso-test`）验证，且**不可在承载会话的实例上直接改内核**（铁律 2）。

## 五、与插件适配的关系

壳侧 P0-a/b/c 是**插件适配的前置**：P0-c 不解决，`settings` 服务不存在，则所有 `.volatile()` 改造、`plugins.item` 双视图改造都没有落点（设置页本身不渲染）。建议顺序：**壳 P0 三件 → 插件 settings 面四件 → 其余插件 → 配置清理**。
