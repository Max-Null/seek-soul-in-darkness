## 拟提交的 issue 正文

**Title**: Workspace membership never recovers once lost — `bootstrap()` stops running as soon as the first workspace exists

**Body**:

### What happens

Session membership in a workspace is a single account: `WorkspaceRecord.sessionIds`. If an id is lost from that list, **nothing ever puts it back** — the session file stays intact on disk, but the UI shows it as ungrouped forever.

Observed on Windows, DSH `0.1.5-rc.2`. The memberships below were *removed* by the concurrent-host issue in #6882 — what this report is about is that **nothing puts them back**: the numbers are what one running host sees now, long after the other host stopped.

| Workspace | Registered | Sessions whose `header.cwd` equals this workspace path |
|---|---|---|
| `H:\…\WorkStation` | 29 | **120** |
| `~/.dsh/profiles/ssid` | 13 | **58** |
| `~/.dsh/profiles/web` | 3 | **12** |
| (three further workspaces) | 43 | **63** |

165 sessions in total are on disk, readable, with a `cwd` that exactly matches an existing workspace — and absent from every `sessionIds`.

### Why: the reconciliation pass is gated on a flag that normal use sets immediately

`packages/workspace/workspace/src/index.ts` has a full reconciliation routine — `bootstrap()` (`:425-507`) groups stored headers by cwd, creates workspaces for paths that have none, and merges unaccounted sessions into the matching workspace. It is only reached here:

```ts
// :127-133
if (!this.state.initialized) {
  const headers = await this.listStoredHeaders()
  await this.replaceHeaderIndex(headers)
  await this.bootstrap(headers)
} else if (this.table.size > 0) {
  await this.replaceHeaderIndex(await this.listStoredHeaders())   // rebuilds the id→path index only
}
```

`initialized` is written to `true` by `bootstrap()` itself (`:506`) — **and also by the ordinary create/delete paths** (`:330`, `:362`). So the condition is not "the registry has been fully reconciled"; it is "a workspace has ever been created or deleted". Creating the first workspace turns the reconciliation off permanently.

The `else` branch is not a substitute: `replaceHeaderIndex` rebuilds the id→path index used for filtering, but never touches `sessionIds`.

### Why this is not simply "by design"

We can see the reason for the gate, and it is a good one: `bootstrap()` merges unaccounted sessions into existing workspaces, so running it every startup would undo a deliberate `detachSession` (`entity.ts:165`) — a session the user moved out would silently come back. `spec.ts:44` describes the flag as *"`initialized` distinguishes a valid empty registry"* — an intent about **validity**, not about **reconciliation**.

But the effect is that `attachSession` (`entity.ts:146`) becomes a **single point of failure with no recovery path**: whatever loses one write there, the membership is gone for good, silently. Losing one write is not exotic — concurrent hosts sharing a `DSH_HOME` (see #6882) is the one we hit, and a hand-edited or partially-restored `workspace.json` would do it just as well.

### How we hit it

Two hosts sharing `$DSH_HOME` (`dsh web` plus a desktop shell) overwrite each other's whole-unit `workspace.json` writes (the mechanism is in #6882). Every overwritten write removed some memberships. Because of the gate above, none of them came back — the loss accumulated quietly for weeks, until the session list visibly disagreed with the disk.

### What we would like

Any one of these would remove the dead end:

1. **An explicit repair entry point** — a public `reconcile()`/`repair()` on the workspace registry (or a CLI/API surface for it). It does not have to run automatically; it has to *exist*, so a host can offer "restore workspace membership" instead of asking users to edit `sessionIds` by hand. A "merge unaccounted sessions, never remove" semantic would match `bootstrap()` and stay compatible with `detachSession`.
2. **If an entry point is out of scope: a diagnostic.** On startup, the registry already walks stored headers (`:128`) and filters candidates (`reportFilteredCandidates`, `:138`). Counting "stored sessions whose cwd matches an existing workspace but which are accounted nowhere" and logging a warning when it is non-zero would have told us months earlier — today the mismatch is completely invisible.
3. **If the one-shot semantics is intentional and permanent, documenting it** as a Known Limitation would let downstream hosts decide to keep their own reconciliation.

### Downstream workaround (for reference)

We wrote a script that reads every stored session header, groups by `cwd`, and prepends unaccounted ids into the matching workspace's `sessionIds` — the same rules as `bootstrap()`, never removing, skipping `archivedSessionIds`. It must be run **while the host is stopped**, because a running registry holds the whole document in memory and rewrites it. That constraint is exactly why an in-tree entry point would be better than every downstream host reimplementing this.
