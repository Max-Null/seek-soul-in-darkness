# 插件测试操作手册

> **面向所有会话**（人或其他会话里的 agent）：改我们自己的插件之后，怎么在 SSiD dev 环境里验证。
> 环境流转、L2 证据链、dev 启动参数见 [`SSiD开发手册.md`](SSiD开发手册.md) 的「开发环境与测试流转」「验证留痕」「0. 快速开始」三节——**本文不重复它们，只补充落点与判据**。
> 形态基准：fork 版 v1.0.0+（内核随包）。最后核对：2026-10-01，内核 `0.2.0-rc.1`（§2.1 补 `--no-sandbox` 与 `SSID_PLUGIN_SET_DIR` 两个缺口）。

## 0. 一分钟版

0. **确认眼前这个实例用的是哪个 home**（§0.5）—— 裸跑会与装版共用，隔离实例不会
1. 在 `max-null-plugins/<插件>/` 改代码 → `pnpm build`
2. 把产物放到**落点**（§1，选错会连带影响装版）
3. 起 dev 实例（§2）
4. 看日志里的**三个失败信号**（§3），全 0 = 加载通过
5. 按 L2 checklist 留痕（§6）

## 0.5 先确认：眼前这个实例用的是哪个 home

**这一步不能跳，也是本文最容易想当然的地方。**

`SSiD开发手册` 的「三套 DSH 环境」把 SSiD dev 写作「`shell` dev 裸跑」—— 而**裸跑 = 不设 `DSH_HOME`**，于是它落到 `~/.dsh/profiles/ssid`，**与装版共用**。`.ssid-iso-test` 那套隔离实例用另一个 home（`home-100`）。两者对「文件放哪里」的影响完全相反，所以动手前先确定面对的是哪一种。

**最可靠的判据**：看那个实例的启动日志，开头有一段就写着

```
desktop development: DSH_HOME=<路径>
```

它直接给出这个实例读的 profile 根。`--user-data-dir` 也在命令行里，但两套起法可能指向同一个默认位置，**不能用来区分**。

**两个已经踩过的坑：**

- **`DSH_HOME` 是环境变量，不在命令行里。** 只查 `CommandLine` 会看到 `--user-data-dir` 而看不到 `DSH_HOME` —— 由此推断「这个实例没设 `DSH_HOME`」是**错的**。
- **不要用「哪个 home 在更新」反推。** `~/.dsh` 持续被写是**常态** —— 装版里通常正跑着会话（你自己可能就在其中一个里）。反过来，隔离实例启动后若没有新会话，它的 `sessions-<名字>` 目录**不会更新**，看上去像"没在用"。

**拿不到日志时**：在那个实例的会话里直接读 `$env:DSH_HOME`；或看该 home 下 `sessions-*` 的**目录名**（`sessions-ssid` → profile 名 `ssid`；`sessions-ssid-dev` → `ssid-dev`）—— 但目录名只说明"曾经用过"，不如日志确切。

## 1. 落点：三种放法，影响面不同

**前提**：你已经知道当前实例用哪个 home（见 §0.5）。下表第一行是裸跑（与装版共用）时的情况，后两行是隔离实例的情况。

profile 的 `node_modules` 里**每个包都是 junction**，装版与 dev 隔离实例**指向同一处**：

```
~/.dsh/profiles/ssid/node_modules/<pkg>          ─┐
                                                  ├─→ <resources>/ssid-plugins/node_modules/<pkg>
<iso>/home-100/profiles/ssid-dev/node_modules/<pkg> ─┘
```

因此「把插件放进 profile」有三种含义，影响面完全不同：

| 放法 | 影响面 | 什么时候用 |
|---|---|---|
| 写 `<resources>/ssid-plugins/node_modules/<pkg>`（junction 的**目标**） | **装版 + dev 一起变**（装版重启后生效） | 只在准备整体升级时装版时 |
| 写某个 profile 的 `node_modules/<pkg>` 并**换成实体目录** | **只影响该 profile** | 要在 dev 里试、不想动装版时 |
| 写**隔离插件集**（`.ssid-iso-test/ssid-plugins-dev/node_modules/<pkg>`） | **只影响隔离实例** | **本文推荐**：dev 测试的默认落点 |

**两条容易踩的**：

- **`pnpm install` / 部署链会重建 junction**，手工换的实体可能被冲掉，于是又回到共享。
- **不要递归删除 junction**：`Remove-Item -Recurse` 对 junction 会连**目标内容**一起删。删链接用 `cmd /c rmdir`；删实体目录前先扫内部有没有链接。

## 2. 起 dev 实例

隔离三件套（完整说明见手册 §3.3）：`--user-data-dir` + `DSH_HOME` + `SSID_PROFILE_NAME`，另建议传 `SSID_MCP_CG_WS` 指向空目录（否则 codegraph 首启弹窗卡住无人值守启动）。

现成环境：`.ssid-iso-test`，profile 名 `ssid-dev`，DSH_HOME 指 `home-100`。**现成脚本：`.ssid-iso-test/launch-dev-with-pluginset.ps1`**（本机可用形态，见 §2.1）。

### 2.1 `pnpm run start` 的两个缺口（2026-10-01 补，本机实测）

`apps/desktop` 的 `start` = `tsx scripts/dev.ts --skip-build`。它在本机起不来，**而且就算起来也是零插件**：

| 缺口 | 现象 | 判据 / 对策 |
|---|---|---|
| **缺 `--no-sandbox`** | electron 秒退、**一个字都不输出** | 退出码 `0x80000003`（STATUS_BREAKPOINT，Chromium 沙箱建不起来）。`dev.ts` 把 Electron 参数写死，没有注入开关的口子 → 加 `--no-sandbox` 自己起（`launch-dev-nosandbox.ps1` 即此形态；**它有这个、没有下一个**） |
| **缺 `SSID_PLUGIN_SET_DIR`** | 窗口起得来，但**一个思灵插件都不加载** | 日志 `ssid: plugin set: no usable ssid-plugins.json under <electron>/dist/resources/ssid-plugins`。dev 的 `process.resourcesPath` 指向 **Electron 自带的 resources**，那里没有随包插件集 → 传 `SSID_PLUGIN_SET_DIR=<插件集根>`（壳的 `resolvePluginSetRoot()`，`apps/desktop/src/main.ts:234`，专为此留口）。**内核遇到解析不到的插件是静默跳过，界面不报错** |

**插件集根必须带 `ssid-plugins.json` 清单**（`{"schemaVersion":1,"bundles":[…]}`）——壳靠它认插件集。`.ssid-iso-test/ssid-plugins-dev` 一度只有 `node_modules` 而缺清单，从装版 `resources/ssid-plugins/ssid-plugins.json` 复制过去即可（当时 32 条、`missing=0`）。

**前提**：`.desktop-build/development/project` 与 `targets/win-x64/runtime/primary-runtime` 已由 `pnpm run start` 的准备步骤生成过（它们与 `lib/main.js` 无关，不必每次重跑）——`launch-dev-nosandbox.ps1` 的注释也写了这条。

**验证不用 token**：dev 壳的页面走自定义协议 `dsh-app://app/`，CDP（9222）取该 target 即可求值；只有 `dsh web` CLI 与装版才是 http + token。

```powershell
# 推荐起法（--no-sandbox 与 SSID_PLUGIN_SET_DIR 都带了）
$cmd = 'powershell.exe -NoProfile -ExecutionPolicy Bypass -File "H:\MaxNull\WorkStation\.ssid-iso-test\launch-dev-with-pluginset.ps1"'
Invoke-CimMethod -ClassName Win32_Process -MethodName Create -Arguments @{ CommandLine = $cmd }
# 约 40 秒后 CDP 在 9222；日志落 .ssid-iso-test/logs/dev-ci.log / dev-ci.err.log

# 先看这三行是否正常，再谈功能验证
#   ssid: shell version <ver>
#   ssid: session roots isolated=…\sessions-<profile>     ← profile 名进去了没
#   ssid: plugin set: linked=… kept=… missing=…           ← 插件集挂上没（missing 应为 0）
```

**`ELECTRON_RUN_AS_NODE` 必须清掉**：DSH 会话自己跑在 Electron 里，会给子进程带上这个变量，于是 `electron.exe` 以 Node 模式启动并报 `bad option: --remote-debugging-port=…` / `bad option: --user-data-dir=…`。`bad option:` 是 **Node** 的报错格式，看到它就是这个原因。

**启动前确认没有旧实例**：调试端口被占用时新实例的 inspector 起不来，表现为日志停在早期、不报错。占用端口是 `9229` / `9222` / `9230`。

## 3. 看什么：三个失败信号

日志里搜这三个词，正常时应**全部为 0**：

| 信号 | 含义 | 怎么办 |
|---|---|---|
| `did not activate` | bundle 进了 fiber 图但没激活，通常是缺服务 | 看它等什么服务 |
| `pending (waiting for service: …)` | 有插件在等一个**没加载**的服务 | 往回找提供该服务的那行 |
| `incompatible` | **peer 声明与宿主版本不符** | 见 §4 |

**`incompatible` 最需要注意**：peer 不匹配时插件**不会被加载，也不会出现在 `did not activate` 列表里** —— 它在进入 fiber 图之前就被跳过了。界面上不报错，只是少一批插件。

判定加载成功的正向证据：日志里出现插件自己的语句（如 `[genui] client active`、`[dsh-sidebar-qa] applied`、`[dsh-excel-panel] v0.5.0 loaded`）。

## 4. peer 与跨 minor（最容易静默失效的一处）

`packages/boot/app-boot/src/plugin-compatibility.ts:75` 对每个 bundle 的 **`@deepseek-ai/dsh` / `@deepseek-ai/dsh-*` peer** 跑 `semver.satisfies(宿主, range, { includePrerelease: true })`；不满足时 `profile.ts:675-676` 抛错，被同层 `catch` 吞成 `skippedBundles`，**该 bundle 的整个 patch 层不挂载**。

**caret 的上界是「下一个 minor」**：`^0.1.7-rc.1` 展开为 `>=0.1.7-rc.1 <0.2.0-0`，对 `0.2.0-rc.1` 判定为 false（`includePrerelease` 只放宽预发布子句，不改上界）。所以**内核一跨 minor，所有写成 `^0.1.x` 的插件一起失配**。

**两条出路**：

- **改插件的 peer 范围**（正解）：写成覆盖两代的范围（如 `>=0.1.7-rc.1 <0.3.0`），或直接跟当前基线（`^0.2.0-rc.1`，代价是踢掉旧内核）。判据是**插件有没有真的用新内核的 API**：没用 → 宽范围两边都能跑；用了 → 只能窄，旧内核跳过是预期。
- **profile 的 `compatibility.json` 授予豁免**：`{ "<包名>@<精确版本>": ["<精确 DSH 版本>"] }`。**按精确版本匹配 —— 插件一升级就要同步改**，否则对新版本无效。豁免是「已知情并接受风险」，不是修复。

## 5. 升级隔离集里的插件

`.ssid-iso-test/升级dev插件.ps1` 做掉五步：下载 → 解包 → 依赖检查 → 替换实体 → 重建豁免。

```powershell
cd H:\MaxNull\WorkStation\.ssid-iso-test
pwsh -File 升级dev插件.ps1 ds-harness-remote@0.4.23
# 之后手工：停 dev → 启 dev → 看三个失败信号
```

它只动隔离集与隔离 profile，不碰装版的随包插件集。**停/启 dev 故意不自动化** —— 那要动运行中的实例，自动化只会让端口冲突更难发现。

## 6. 判定通过

按手册「验证留痕」的 L2 checklist（挂载点 / 开关往返 / console 0 error / 实体版本 = 目标 / 截图 / 记一行）。**未留痕视为未验证。**

## 7. 两条硬约束

- **dev 与打包不能并行**：两者共用 `.desktop-build/targets/<target>/runtime/primary-runtime`（`desktop-build-paths.mjs` 的 `developmentRuntimeDirectory()` 与 target 路径指到同一处）。同时跑会互相破坏 —— dev 报 `EPERM`，打包在 `smokePrimaryRuntime` 报 `node.exe ENOENT`；2026-09-28 两次 19 分钟的打包因此白跑。**要打包先停 dev。**
- **改壳代码必须重新 build**：`apps/desktop/package.json` 的 `main` 指向 `lib/main.js`（tsdown 产物），「改 `src/` 即生效」在这里不成立。类型检查一律用 `tsc -b`（`npx tsc --noEmit -p …` 会假绿）。
