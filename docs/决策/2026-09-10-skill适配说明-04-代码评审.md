## 一、为什么做这一个（以及一个根本差异）

### 1.1 上游的场景是「评审 PR」，SSiD 的主要场景不是

上游 description 第一句：*Use when reviewing a pull request in the deepseek-harness repo*。它整份 skill 围绕「**别人提了 PR，你来评**」组织：确认 live base/head、跑 `change-scope`、按来源清单逐项过、把缺陷挂在 diff 行上。

**SSiD 是单人（人 + AI）开发，没有 PR 评审流程**。但这不意味着删掉它——**判据是「看什么」，与「谁看」无关**。适配后是**两个场景共用一份判据**：

| 场景 | 触发 | 与上游的关系 |
|---|---|---|
| **主场景：交付前自审** | AI 写完代码/文档，交付给用户验收之前 | 判据相同，只是「评审者」是被评代码的同一方（这反而**提高**了对 #1「新行文语义评审」的要求——自己写自己评最容易放过） |
| **次场景：给上游提 PR 前自查** | 向 DSH / 第三方插件提 PR | **SSiD 有真实先例**：`docs/决策/2026-08-19-DSH修复PR-3198方案落盘.md`、`docs/决策/2026-08-22-open-sea-skin增强版提交上游PR.md`。此时上游流程（base 确认、行内评论）**照旧适用** |

### 1.2 它是 01/02/03 的汇聚点

上游 Sources of truth 里直接引用 `dsh-prose-standard`（→ 03）与 `dsh-ci-test-reliability`（→ 01）。所以 04 是**依赖链的上游**：

```
04 代码评审 ──引用──> 01 测试可靠性（测试与拆除判据）
           ──引用──> 03 行文标准（新增文案的语义评审）
```

**结论：01/02/03 必须先于 04 存在**，否则 04 的 Blocking #1 与 Manual「测试可靠性」两条会指向空。这是**第三组依赖关系**（前两组：02↔03 双向依赖、01 被 06 引用）。

### 2.2 清点表的一处判断需要更正：Cordis 注册**不是** DSH 专有

`2026-09-10-DSH-skills适配清点.md` §126 把「#4（Cordis 注册）」列为 DSH 专有条款。**实测推翻**：

| 证据 | 位置 |
|---|---|
| `ctx.effect(() => ctx.webServer.register({` | `dsh-capture/src/index.ts:172`（另有 draft-polish:119、memory/routes.ts:272） |
| `this.ctx.storage.backend.register('habit', backend)` + `this.ctx.effect(() => async () => { await backend.close() }, 'habit.backendClose')` | `dsh-habit/src/engine.ts:78-79` |
| 同上（guardian） | `dsh-guardian/src/engine.ts:138-139` |
| `ctx.on('session/event', ...)` | `dsh-habit/src/engine.ts:91`、`dsh-guardian/src/engine.ts:153`、`dsh-ssid-achievements/src/engine.ts:245,258` |
| `ctx.tools.register(defineTool({...}))` | `dsh-memory/src/index.ts` **10 处**（L236…L467） |
| `ctx.slots.inject(...) / ctx.slots.register(...)` | `dsh-capture/src/client/index.ts:104,111`、`dsh-node-appearance/src/client/index.ts:78` |
| `projectionCtx.sessionProjections.register(...)` | `dsh-chat-rail/src/index.ts:211` |

**SSiD 的插件是彻头彻尾的 cordis 插件**，注册点遍布 storage backend、webServer、tools、slots、session projections。「注册即效果、`register()` 返回 disposer」这条规范**完全适用**。

**更要紧的是**：`dsh-habit` 与 `dsh-guardian` 已经写出了**教科书式 cleanup**（`register` + `ctx.effect` 返回 `backend.close()`）。但：

> **插件测试里没有任何 disposal 断言**——在 `max-null-plugins/**/*.test.ts` 里搜 `dispose|disposer|ctx.scope` **零命中**。

**所以 #4 在 SSiD 不是「专有条款该删」，而是「当前缺失的守卫」**——注册写了清理，却没有任何测试证明它清了。这条要**保留并提权**。

### 4. `## Manual checks`（16 条）→ **改写（16 → 14 条）**

**12 条原样保留**（判据与语言、仓库无关）：意图与接口契约 / 生命周期与并发 / 能力与消费者匹配 / 范围·归属·必要性 / 配置与公开选择 / 模型视角 / 强制点（denial 路径） / 借用与派生状态 / 边界覆盖最终操作 / 测试强度 / 测试可靠性 / 真实入口。

**2 条改写**：

- **#10 Real entry path**：上游的入口是 Loader / bin / worker / ACP bridge。SSiD 的对应是 **Electron 壳（`main.mjs`）→ `kernel.bundle.mjs` → profile 装载**，以及插件的 `package.json` 导出面（`main` / `exports` / `dsh.client`）。保留上游最有用的一句：**"手工挂载的插件抓不到非法的 Loader 导出"**——对应 SSiD 就是「手工 import 抓不到 `cordis.patch.yml` / exports 面的错误」。
- **#14 Implemented Agent Notes match shipped reality** → 改为**「决策记录与已交付现实一致」**：SSiD 的 `docs/决策/` 无状态机，所以不做「proposed → implemented 的移动与改写」，只要求**决策记录里陈述的机制、路径、名字与实际交付一致**；不一致时**改记录或改代码，不留着两说**。
- **#15 Transcript changes**（snapshot）→ 改为**截图基线**：SSiD 无 transcript snapshot 制度，但有 Playwright 截图基线（`shell/tests/plugin-adapt/baselines/`，`pnpm baseline` 生成）。保留上游的核心判断：**"expected-output 的 diff 要当作行为变更来评审，不是格式噪音"**——对应截图就是"基线变了要问为什么变，不是重新生成就完事"。

**2 条删除**：

- **#13 Invariant lifecycle and negative controls** → 删（无 invariant 机制）。**但它有一半要救**：上游那句"**一条蓄意无效的用例必须经由真实运行器按预期规则失败**"（负向控制）与 invariant 无关，是**通用**的——**并入 #11 测试强度**。
- **#16 Bilingual changes** → 删（无双语制度）。

### 5. `## Reporting findings` → **改写（渠道不同）**

上游：缺陷挂**最紧的相关 diff 行内**，跨切面用 PR 级评论，用既有 review thread 回复；收到评审时逐条核实、**以技术理由修正或反驳，不做表演性同意**。

**适配**：

- **主场景（自审）**：报告进 **GUI 会话内的交付说明**——按 **阻塞项 / 建议** 分开，每条给「缺陷 + 位置 + 影响 + 证据」四元组（上游四要素逐字保留）。**"omit issues already enforced by a green gate"** 保留——已被 L1 门禁守住的事不重复报告。
- **上游 PR 场景**：上游流程照旧（行内评论 + PR 级评论）。
- **"verify each claim and fix or rebut it on technical grounds without performative agreement"** —— 逐字保留。这条对 AI 尤其重要：**收到用户反馈时不要表演性同意，要么改、要么给技术理由**。

### 6. 从 `dsh-doc` 并入的 6 条质量判据（见 09 号说明）→ **新增**

> `dsh-doc`（861 行）被判 `⛔ 不单独适配`，但它的 "Quality criteria" 节**正是评审时要问的问题**，因此在 09 的合订理由里移交到本节。
> **并入位置**：`Manual checks` 里审阅**新增或修改的文档**时逐条过；同样适用于审阅新增的 skill 正文。

| # | 判据 | 要问的问题 |
|---:|---|---|
| 1 | **Brief** | 常用路径**只含其结局所需的事实**；穷尽真相保持在**一个直接链接或一层细节**之外 |
| 2 | **Intuitive** | **前置先于依赖概念**；**下一步动作是显然的**；标题用读者会搜的词 |
| 3 | **Friendly** | 读者能**识别成功**、**行动前理解风险**、**从可能的失败中恢复**、并能选择是否继续深入 |
| 4 | **Accurate** | 每条持久断言**有一个属主**，以及**与其风险相称的验证路径** |
| 5 | **★ Agent-readable** | 元数据、稳定标题、锚点、术语、归属、当前/提议状态**支持定向检索，而不必加载整个语料** |
| 6 | **Newcomer-complete** | 一个没有仓库上下文的专业工程师，能**通过 3–5 个链接页重建相关架构或特性** |

**第 5 条对 SSiD 尤其要紧**：它判的正是「**skill 与文档能不能被 agent 定向检索**」——也就是本系列全部适配工作的目标。若一份 skill 的元数据、标题、术语做不到定向检索，那么它写得再对，agent 也会**因为读不到而用不上**。

**并入的算术**：上游 `Manual checks` 的 16 条判定（16 → 14）**不变**；这 6 条是**评审时额外要问的清单**，不是替代品。
