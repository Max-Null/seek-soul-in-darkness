## 1. Wine 与原生 Windows CI

`2026-08-08-native-windows-pull-request-ci.md`

### 他们遇到的事

对 Wine 的定性非常干脆：

> Wine checks the win32 toolchain **over a Linux kernel and case-sensitive ext4 with a hoisted dependency layout**. It **cannot prove NTFS, DACL, ConPTY, crash durability, or native process behavior**.

**Wine 在 Linux 内核和大小写敏感的 ext4 上、用 hoisted 依赖布局检查 win32 工具链。它不能证明 NTFS、DACL、ConPTY、崩溃持久性或原生进程行为。**

**所以它不是"更便宜的 Windows 检查"，而是一个覆盖面不同的检查。** 由此：PR 正确性需要**独立于合并后 Wine 结果**的原生 Windows 构建与进程检查。

第二件事是一次覆盖审计：**陈旧的分数状态恢复了受支持 LSP 源码的临时排除**——于是原生 Windows 被要求**在同一个 100% 逐文件阈值下执行完整的受支持源码清单，而不是依赖一个更小的平台专属分母**。

### 判断：三层裁决强度

每个 PR 启动**四个独立的原生 job**。关键在于它们与必需聚合的关系**各不相同**：

| job | 与 `all checks passed` 的关系 |
|---|---|
| `windows-build`、`windows-native-tests` | **是依赖**，结果阻塞 |
| `windows-coverage` | **普通 job，缺席于聚合的 `needs`**——所以"它的 100% 逐文件结果**保持红色且可见，而不延迟必需的裁决**" |
| `windows-observational` | **缺席于 `needs` 且用 `continue-on-error`**，因为 Linux 拥有阻塞性的静态/文档/包/构建产物裁决 |

中间那一档值得单独记住：**"保持红色且可见，但不延迟必需裁决"是介于"阻塞"和"跳过"之间的第三种状态。** 第 05 批的 `pending`、第 10 批的三种 `always()` 义务，都是同一族的设计——**不要把所有不阻塞的东西都塞进"忽略"。**

另一处与第 13 批形成对照的用法：逐 job 的截止时间是 60–120 分钟，作用是 **"约束卡住的工作，而不把性能目标当作正确性截止时间"**。**超时用来防挂死是对的，用来表达性能目标是错的**——两篇合起来把这条讲全了。

### 凭什么这么判断

| 方案 | 否决理由 |
|---|---|
| 让每个原生 Windows 结果都成为聚合的依赖 | 最高保真，**但让每次合并都等待覆盖和重复的观察清单** |
| **在 PR 上只跑 Wine** | Wine 快速到达阻塞性 win32 分支，**但可以在一个真实的 NT、NTFS、PowerShell、进程或 addon 契约被破坏时报告绿色** |
| 把每个非阻塞原生 job 都标 `continue-on-error` | 覆盖保持普通 job 且在 `needs` 之外，**所以阈值失败保持红色可见而不阻塞聚合** |
| **排除看起来不支持的文件，或削弱 Windows fixture** | **受影响的行为是受支持的。** 对等平台分支被**狭窄地标记**；**可移植的结果留在分母里**，通过主机真实的 fixture 演练 |
| 保持 GitHub 标准 `windows-2025` | 它能可靠完成，**但 32 分钟的串行结果让自动原生信号实用性差得多** |
| **用 32 核或更大的 runner** | **32 核比较只比 16 核改进 1.47 秒，并在 Node 的 CJS lexer 里失败**；更早的 32/64 核试验在同一类里失败 |

第 4 条是一条硬纪律：**不要为了测试变绿而缩小被测范围。** "受影响的行为是受支持的"——**所以它不是"不测的东西"，是"本来就该测、之前漏了的东西"**。

第 6 条则是**用实测反驳"加资源就行"**：更多容量增加了分配成本，却没有稳定的端到端收益。

### 一处"第一次真实运行就抓到东西"的记录

> The first native run **exposed two failures hidden by the compatibility lane**.

**第一次原生运行就暴露了两个被兼容泳道隐藏的失败**：文档投影测试**只按 `/` 切分**推导图片 basename；Chokidar 消费者**通过 `%TEMP%` 的 `C:\Users\RUNNER~1` 8.3 别名**收到路径，**而 libuv 返回长目录名**，触发了它的 Windows 事件路径断言。

后者的修复被总结成一条可复用的规则：**在打开 watcher 之前规范化"已存在的原生 watch base 或最深已存在祖先"，并保留缺失的后缀。**

### 他们承认的代价

- **原生覆盖和观察结果仍可能在 `all checks passed` 变绿时待定或红色**——所以**分支保护消费定向的构建/进程检查，而评审者和后续自动化消费其余的原生结果**
- **原生 job 在多处重复 setup 并重复构建，但它们降低了每个 job 的进程数**，并暴露被兼容泳道隐藏的缺陷
- **维护者必须保留两套刻意的执行拓扑**（Wine 快照 vs 原生工作区），而且：

  > A failure unique to either topology must be **classified against that boundary** rather than **weakened or silently skipped**.

  **一个只对任一拓扑唯一的失败，必须针对那个边界分类**——不是被削弱，也不是被静默跳过。

## 2. 自托管上的隔离 Node 兼容 job

`2026-09-06-node-compatibility-selfhosted.md`

### 他们遇到的事

Node 22.19/24.9/26 兼容 job **消耗托管 Linux 分钟数**，即使仓库已经选了自托管池。而搬迁的风险很具体：

> Moving version installers onto a persistent shared machine can create **tool-directory collisions** and **accumulate generated cache files outside runner cleanup**.

**工具目录冲突**，以及**在 runner 清理之外累积生成的缓存文件**。

### 判断：用"重复下载"换"隔离"

- **临时工具缓存**："**用重复的 Node 下载换取跨并发 runner 和 Node 版本的隔离**"
- 一个 **setup-node-only 的 ESM preload** 在 action 进程内给缓存赋值——因为**Actions runner 会在读完步骤配置之后覆写保留的环境变量**（所以只能在进程内改）
- **一个执行期的路径检查拒绝 runner temp 之外的安装**
- **兼容进程不继承那个 preload**；**不引入全局 Node 符号链接或系统包改动**
- **托管 job 保留它们的工具与包缓存；自托管 job 不恢复也不上传托管包缓存**

### 凭什么这么判断

| 方案 | 否决理由 |
|---|---|
| 保持所有兼容 job 托管 | 避免额外共享主机负载，**但继续为"不需要不同操作系统或架构"的 Linux 运行时检查付费** |
| **使用共享的 Node 安装或全局版本管理器链接** | **job 必须并发跑不同的 Node 发布版。可变的共享链接会让选定的版本取决于另一个 job 的时序** |
| 在同一次变更里把 Python SDK job 也搬过来 | **它的 setup-python 安装和全局 pip 安装 uv 需要独立的隔离证据**；**它的短托管 job 并不是 Node 优化所需要的** |

第 2 条是一条通用判据：**任何"共享的可变位置"都会把并发变成时序依赖。** 这与第 09 批 worktree hooks 那篇（共享 hooks 目录）是同一种病，只是这次的赌注是"选中的 Node 版本"。

第 3 条是"不捎带"的又一例（第 05、07 批同款）。

### 一处很实用的证据记录法

Verification 段直接列出了三个真实 CI run 的编号与结论，包括一个**只读能力探针**报告：Linux x64、**192 在线逻辑 CPU**、GCC/G++ 13.3、Make 4.3、Python 3.12.3——以及**"Python 3.10 缺席，强化了单独的 SDK 供应需求"**。

然后用一句边界收尾：

> These observations establish **version and path compatibility, not an exclusive-host capacity guarantee**.

**这些观察确立了版本与路径兼容性，不是独占主机的容量保证。** ——**用实测支撑结论，同时说清实测覆盖不到的地方。**

### 他们承认的代价

- 池**每个可信 PR 收到三个额外 job**；而 "**9 月 6 日的清单报告 31 个 Linux 注册，不是 31 台独立机器**"（第 08 批同款的诚实）
- **共享 VM 的争用与下载延迟仍然是铺开风险；变量保留了托管恢复能力**

## 3. 从独立 App 副本并行 macOS 公证

`2026-09-09-parallel-macos-notarization.md`

### 他们遇到的事

DMG（安装）与 ZIP（更新）需要两份产物。原本**在创建 DMG 之前等待 App 公证，把两次 Apple 提交串行化了**。

而真正的障碍不是带宽：

> **Stapling modifies the App**, so **concurrent notarization and packaging cannot safely share that writable directory**.

**stapling 会修改 App，所以并发公证与打包不能安全地共享那个可写目录。** ——**并行化的障碍是"同一个可写对象被两条流水线同时改"，不是服务排队。**

### 判断：先复制，再各走各的

- 签名并验证**一个 App**，然后用 `ditto` **创建两份独立副本**
- **App 泳道**：公证 + staple 它的副本 + 验证签名/票据/Gatekeeper，**并让 electron-builder 创建 ZIP 与 updater 元数据**
- **DMG 泳道**：立刻打包它的副本、签名镜像，用既有的 artifact 完成钩子**公证、staple 并验证镜像**
- 每个 electron-builder 进程**收到实际的 `.app` 路径**（`--prepackaged`）、**一个隔离的输出目录**、`--publish never`

内容上有一个精细差异：**ZIP 里的 App 是单独 staple 过的**（因为 ZIP 更新会被独立解压，依赖在线或缓存票据）；**DMG 里的 App 没有单独 staple 的票据，由 DMG 的外层票据覆盖嵌套代码**。

### 用"记录缺席"表达失败

> Only two successful lanes allow promotion... The caller writes the release completion record **last**. **An error leaves that record absent, so the existing upload validation rejects the incomplete release.**

**调用者最后写发布完成记录。一个错误会让那个记录缺席，所以既有的上传校验会拒绝不完整的发布。**

**不是加一个"是否成功"的标志位，而是让成功才产生那个必需的东西**——这样"忘了检查标志"这种漏洞在结构上不存在。（与第 03 批"绕过必须在结构上不可能"同源。）

### 凭什么这么判断

| 方案 | 否决理由 |
|---|---|
| **两条泳道共享一个 App** | **一个 DMG 读取者可以与 `stapler` 写入重叠，产生一个非确定性的 bundle**。独立副本让"提交的字节"与"分发的字节"在每条泳道内保持稳定 |
| 只公证 DMG | **ZIP 更新独立分发且需要一个 staple 过的 App** |
| **保持串行公证，只加代理** | **同一个 214.84 MiB 的 DMG，直传 203.83 秒、经测试的系统代理 38.59 秒，但两条路线都不移除 Apple 提交之间的串行依赖** |
| 在一次 electron-builder 调用里跑两个目标 | **ZIP 必须读那个 staple 过的副本** |

第 3 条是本批最好的一个分析样本：

**代理把上传时间改善了 5 倍以上（203.83 → 38.59 秒），但它没有打中真正的瓶颈——两次 Apple 提交之间的串行等待。** 一个手段只要改善了某个可见指标，就很容易被当成"问题解决了"，**而当真正的约束是另一个量时，这个改善不会缩短总时长**。

同一段还划了一条边界：**"代理配置仍然是构建主机的事；打包脚本不改变主机网络设置。"**

### 他们承认的代价（含样本量声明）

- 实测（2026-09-09，同一台 Mac、同一代理）：**并行 490.78 秒 vs 串行 751.33 秒，降低 34.7%**；两条泳道相隔 8 毫秒开始，App/ZIP 用 307.36 秒、DMG 用 268.54 秒完成；Apple 两次都接受，上传相隔约一秒
- 紧跟一句限制：

  > Each configuration has **one full-build sample**, so **cache and Apple queue variation prevent attributing the entire difference to concurrency**.

  **每个配置只有一个完整构建样本，所以缓存和 Apple 队列变化使整个差异不能被归因于并发。**
- 两份额外 App 副本增加了峰值磁盘占用；**两次上传可能争用带宽**；**"阶段计时描述的是观察到的行为，而不是一个 CI 延迟预算"**
- **一个失败的泳道会等另一条完成再清理**——"这可能延迟失败报告，**但避免了删除仍被一个子进程持有的文件**"
- 测试用**屏障**证明重叠、票据隔离、双侧错误收集、拒绝发布不完整产物；**一个受控的串行回归会让重叠断言失败**

## 对索引里跨批模式的印证

**模式 C（别把不同的事混成一种状态）——"第三种状态"。**

"`windows-coverage` 缺席于聚合 `needs`，所以它的阈值失败**保持红色且可见，而不延迟必需的裁决**"。**阻塞 / 可见但不阻塞 / 忽略，是三种不同的处置**，把它们压成两种必然损失信息。

**模式 A——"用实测支撑结论，同时说清实测覆盖不到的地方"。**

"这些观察确立了版本与路径兼容性，**不是独占主机的容量保证**"；"每个配置只有一个完整构建样本，所以**不能被归因于并发**"。**两处都是在给出结论的同时，主动削掉结论够不到的部分。**

**一个可以复用的新判据：一个手段改善了可见指标，不等于打中了瓶颈。**

代理把上传从 203.83 秒降到 38.59 秒（5.3 倍），**而总时长没变**，因为真正的约束是两次 Apple 提交之间的串行等待。**看到某个数字大幅改善时，要再问一次：这个数字是约束吗？**

## 这批的共同判断标准

**① 说清一个手段"不能证明"什么。**
Wine **不能**证明 NTFS、DACL、ConPTY、崩溃持久性、原生进程行为。**它不是"更便宜的 Windows 检查"，而是覆盖面不同的检查**——所以不能拿它替代原生 job，只能让它承担它真正覆盖的那部分。

**② "红色但可见、不阻塞"是第三种状态。**
不是所有不该阻塞的东西都该被忽略。**分三档（阻塞 / 可见不阻塞 / 忽略），比只有两档能保留更多信息。**

**③ 不要为了测试变绿而缩小被测范围。**
"排除看起来不支持的文件"被拒绝，理由是**"受影响的行为是受支持的"**——它是"之前漏测的东西"，不是"不该测的东西"。

**④ 更多资源不等于更好，要用实测判断。**
32 核只比 16 核改进 1.47 秒，而且在 CJS lexer 里失败。**"加资源"是需要证据的主张，不是默认答案。**

**⑤ 任何共享的可变位置，都会把并发变成时序依赖。**
"可变的共享链接会让选定的版本取决于另一个 job 的时序。" **隔离的代价（重复下载）要明说，但换来的是结果的可复现。**

**⑥ 一个手段改善了可见指标，不等于它打中了瓶颈。**
代理把上传时间改善 5 倍以上，**而真正的约束是两次 Apple 提交之间的串行等待**。**看到某个数字大幅改善时，要再问一次：这个数字是约束吗？**

**⑦ 用"必需物缺席"表达失败，而不是用一个可能被漏检的标志。**
发布完成记录**最后写**，出错时它就不存在——**于是"忘了检查标志"这种漏洞在结构上不可能发生。**

**⑧ 结论要附带它够不到的边界。**
"确立了版本与路径兼容性，**不是容量保证**"；"只有一个样本，**不能把差异归因于并发**"。

**⑨ 清理要等所有所有者结算。**
"失败的泳道等另一条完成再清理——**延迟失败报告，但避免删除仍被子进程持有的文件**。" **报告的及时性让位于资源的正确释放。**
