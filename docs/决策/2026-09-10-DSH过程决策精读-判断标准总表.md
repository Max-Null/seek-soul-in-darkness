## 一、地基：为什么要有规范

**1. 可机械判定的不变量必须编码成检查，散文规则不作数。** `[01]`
依据是两处独立印证——总纲的立场，以及文档预算门禁那句："积累**就发生在规则和评审注意力都在场的时候**；没有机械兜底的散文规则在这里被证明不成立。"

**2. 沉默不是中立：不写下规则，规则会被推断出来，而且更严。** `[03]`
依赖政策从没写进 `AGENTS.md`，于是执行者从现状推断出"别加依赖"——**比任何人实际决定的都严格**。空缺的位置从来不会被留空。

**3. 删门禁和加门禁一样需要记录，门槛更高。** `[01]`
删 Knip 的三个条件：失败模式已被更窄的检查覆盖、泛化结果只是参考性而例外是硬维护成本、例外清单使普通变更依赖一份失真的图。

**4. 规范只禁了一半，漏洞就从另一半漏进来。** `[02]`
文档标准禁了"变更历史"（previously/now、PR 引用），却没管"引用"——于是 `(decision 12)`、`(audit C2)` 这类解析不到的序号一直往仓库里漏。
**看任何规范都该问：跟它对称的那一半在哪？**

## 二、写一条规则

**5. 规范要写成"可判定的拒绝"，不是风格建议。** `[08]`
样式规范的 12 项检查表，每一项都是"**看到 X，拒绝**"。**检验标准：一个人读完这条规范，能不能在不咨询作者的情况下得出唯一结论？**

**6. 写的人与评审的人共用同一张表。** `[08]`
自我检查与评审检查是同一次动作——**这堵掉了"规范知道但没执行"的空间**。

**7. 换一个宽泛的词等于什么都没做。** `[02]`
"把抽象标签统一换成 source/origin/metadata"被否决：**另一个宽泛标签仍然让读者去猜**。只是把谜题换了个面。

**8. 约束要在被约束者无知觉的情况下生效。** `[08]`
暗色模式靠属性选择器的**整表覆盖**，于是**组件里零主题选择器**。**好的约束不需要被约束者配合。**

**9. 表越大，表里每一项的权威越弱。** `[08]`
拒绝 token 化字号与间距的理由："**膨胀的 token 表会稀释颜色 token 的权威性**。" **约束范围由"它能守住多少"决定，不是"它能覆盖多少"。**

**10. 用可预测性换精确性，通常是划算的。** `[06]`
一条更精确的规则（"这个类型是否每轮都被循环持有/派生/流式/记录"）输给了一条更粗糙但可预测的规则（按仓库布局）：**要求"逐例判断重要性"的规则会在两个方向同时出错——收进不该收的，漏掉该收的**。

**11. 一条政策不该依赖两套独立管理的权限。** `[11]`
不是因为做不到，而是因为**那把一个运维面变成了两个**。

**12. 不接受过渡态。** `[01]`
"全语料一个要求"——没有 per-file rollout、没有日期截止线、没有类别特例。**过渡态是永久泄漏的开始。**

**13. 缺席必须被标注，否则读的人无法解读。** `[11]`
"无约束的缺席，在'审计过的零'和'忘记写文档'之间是模糊的。" **空白也是一种陈述，它需要被授权。**

## 三、设计一个门禁 / 检查

**14. 错误的门禁会训练坏行为——比没有门禁更糟。** `[01]`
一刀切天花板"恰好惩罚正确的长文档"，并产生逐文件覆盖的翻腾，**"训练贡献者橡皮图章式地批准提高上限"**。

**15. 门禁的价值在强制决策的时机，不在度量精度。** `[01]`
字数**不能判断质量**，但它**恰好在内容被添加的那一刻**逼出"该放哪"的决定——那是作者最清楚上下文的时刻。

**16. 绕过必须在结构上不可能。** `[01]`
manifest **只列排除项**，不列包含项："不能让任何条目绕过发现流程而获得更弱的检查。"

**17. 校验要搭已有的车。** `[09]`
断言放进测试泳道本来就在跑的 spec——**零新门进程、零新调度槽位、零新 CI 步骤**。这是对"门禁本身是要维护的代码"那条代价的直接回应。

**18. 自动修复必须在信息不足时拒绝动手。** `[08]`
未分类的运行时导出**阻塞所有 `--fix` 写入**。**证据不够时的"尽力而为"，等于用一个更强的语气说出一个更弱的判断。**

**19. 验证与生成要分开。** `[10]`
hook **只验证不重新生成**，所以"绕过 hook 不能静默地祝福翻译漂移"。**如果验证会顺手修正，绕过它就成了作弊通道。**

**20. 独立检查不能与被检查对象共享实现假设。** `[13]`
"调度和验证共享实现假设"——**同一个实现既调度又验证时，它的错误会同时骗过两边。**

**21. 每条违规自带 `文件:行` 定位。** `[01][08]`
漂移报告没有定位等于没跑；未分类导出给**一条可点击的 `path:line:column`**。

**22. 测试要有负控。** `[11]`
移除一个目标、错误路由一个 job、恢复一个陈旧依赖——**每一个都必须产生预期失败**，否则你不知道这个测试能不能红。

**23. 门禁管形式，评审管内容——而且要写明谁管什么。** `[11]`
"评审仍然拥有覆盖率、链接相关性和事实准确性。"

**24. 不能被机械判定的规则，要么推迟，要么明说缺口。** `[02]`
他们对"禁用词汇"**推迟**了门禁并列出高精度候选清单备用，同时**主动写出**"覆盖缺口：没有门禁拒绝新的序号引用——这条规则由评审承担"。**两条路都比'假装有门禁'诚实。**

**25. 让检查"意外可选"不是中立行为。** `[09]`
"停止自动安装 hooks 会让廉价的提交/推送检查意外变成可选的，**尤其是在短命的 agent worktree 里**。"

## 四、处理不确定性：诚实的空白（出现 9 次，最强形态在 `[10]`）

**26. 不确定的地方要标注，不要补齐。** `[02][04][05][06]`
无法重建 alternatives 的旧笔记，永久保留一行"此处不可重建"，**而不是补一段像样的理由**。

**27. 算不出来时，不要给出一个看起来对的答案。** `[10]` ← **最强形态**
Git 合并驱动的启动器**能算出一个干净的文本合并结果，却仍然返回冲突**——因为那个结果没经过驱动的校验。**未经校验的结果冒充校验过的结果，比明确失败更危险。**

**28. 数值不可得时，记录"形态"。** `[11]`
精确 token 数依赖 tokenizer／序列化／配置／运行时数据，**它不稳定，所以不进契约**；契约退到"每次请求固定／条件性／保留／替换／有上限／零直接"这一层。

**29. 不声称自己验证不了的东西。** `[11][12]`
"本地调度测试**不声称**原生运行时或 Wine 执行"；"选择器测试**不声称**复现那些构建"。

**30. 区分"已验证 / 推定 / 已知缺口"。** `[15]`
8 和 32 vCPU 标签"**按命名对称推定**，首次使用前请手动 dispatch 确认"；Landlock 等排除"仍基于**散文式 dispatch 实测**，记录为已知缺口"。**不是笼统标注"未经验证"，而是说清它凭什么被推定、以及怎么才能验证。**

**31. 结论要附带它够不到的边界。** `[14]`
"确立了版本与路径兼容性，**不是容量保证**"；"只有一个样本，**不能把差异归因于并发**"。

**32. 明确接受代价，不要软化措辞。** `[11][15]`
"明确接受这四项检查的**合并后才发现**"；"**明确接受 standby 饥饿**"。**同时说清代价的边界：是"晚发现"，不是"不发现"。**

## 五、证据与验证

**33. 相似性不构成同一性。** `[04]`
四种伪装：视觉相似（不同运行的帧）、结果相似（聊天记录显示成功但隐藏失败路径）、来源相似（历史加速看起来是现成答案）、名称相似（宽泛标签替代语义分类）。

**34. 要验到"评审者真正使用的那条路径"。** `[04][07][12]`
GIF 发布不满足于"push 成功"，要重读活体 body、用 Markdown API 渲染、抓取上传 URL 确认 `200 image/gif`——**那才是评审者实际看的东西**。

**35. 通用问法：这个验证手段短路掉了什么？** `[07]`
**被短路的那一段，就是故障的藏身处。** "fixture 全绿不算完成"的依据正是："fixture 短路掉的正是链路运载链，**而两个经验确认的 bug 都藏在那里**。"

**36. 验证必须确保它验证的是你以为的那个东西。** `[12]`
三处防护：**移除继承的 Node 解析钩子**（否则可能解到源码而非 tarball）、**checkout 显式清理未跟踪与被忽略的输出**、**"一个热的 pnpm store 不能替代 tarball 载荷"**。

**37. 验证手段不能改变被验证的行为。** `[04]`
用 fixture 替换不可访问的原生 UI 被否决，因为**那通过改变被观察的产品路径来让自动化更容易**。**凡是让"验证更容易"的改动，都要先问它有没有改变被验证的东西。**

**38. 只有稳定配置下的已完成运行，才构成调参的证据。** `[12]`
"仅仅进展缓慢永远不会提高并发，**因为反复重启会抹掉唯一的证据**。" **在基线不稳时调参，会破坏调参所依赖的证据本身。**

**39. 每个 bug 修复钉一个断言，且钉在它所属的层。** `[07]`
一个原本只能靠 12 秒浏览器哨兵防守的问题，被钉成**纯 Node 的秒级用例**。

**40. 失败时也要留下完整证据。** `[12]`
失败测试**仍然发出 blob**，让合并报告完整状态之后才返回失败。**"失败"和"证据残缺"是两件事，不要用一个掩盖另一个。**

**41. 用"必需物缺席"表达失败，而不是一个可能被漏检的标志。** `[14]`
发布完成记录**最后写**，出错时它就不存在——**于是"忘了检查标志"这种漏洞在结构上不可能发生。**

**42. 判断错误方向，并往安全的那一侧倾斜。** `[09]`
运行时披露层**刻意覆盖每一个可挂载的插件**："**对一份法律声明来说，披露不足才是代价高昂的方向。**" **每条规则都该问：如果我错了，会往哪边错？**

**43. 先弄清度量机制，再比较方案。** `[15]`
"更低的每分钟价格不保证更低的每 job 成本——**因为 GitHub 把每个 job 向上取整到整分钟**。" **离散化的度量会让比例直觉失效。**

**44. 不从单一实验外推。** `[15]`
"不从这个单一实验外推任何小时或月度的节省。"

**45. 一个手段改善了可见指标，不等于它打中了瓶颈。** `[14]`
代理把上传从 203.83 秒降到 38.59 秒（**5.3 倍**），**而总时长没变**——真正的约束是两次 Apple 提交之间的串行等待。**看到某个数字大幅改善时，要再问一次：这个数字是约束吗？**

**46. 用"同类里哪些没出问题"来收窄故障条件。** `[15]`
"触发条件是 probe 一个已匹配 symlink 之下的路径，**不是 `**` 扫过含 symlink 的树**"——依据是**同 run 里其他同类调用点保持绿色**。

## 六、状态与语义

**47. 未满足 ≠ 失败；没有 ≠ 有但不同。** `[05]`
`pending`（条件未满足，可解决）/ `success` / `error`（评估本身失败）；registry 的"没有那个版本"与"有但内容不同"是两个状态——**两种"已经存在"只有一个是真的问题**。

**48. 同一个字段名不该回答两个问题。** `[10]`
`devDependencies` 回答"安装器要不要下载"，**不能**回答"要不要披露"；`always()` 要区分"失败聚合"、"资源清理"、"被取消运行的簿记"三种义务。**当一个字段名开始承担第二个问题时，错误就藏在两个问题的差集里。**

**49. 状态要表达交接，不要表达判定。** `[03]`
"谁拥有下一步"能驱动行为；"GitHub 认为可合并"会在具体反例上说谎。

**50. 三种处置，不是两种：阻塞 / 可见但不阻塞 / 忽略。** `[14]`
`windows-coverage` 缺席于聚合 `needs`，所以"它的阈值失败**保持红色且可见，而不延迟必需的裁决**"。**把三种压成两种必然损失信息。**

**51. 判定的归属必须唯一。** `[12]`
"阈值所有权属于合并后的报告"——**一个有意不完整的部分，不能对自己作整体判定。**

**52. 幂等 = 重复执行不产生新状态。** `[05]`
跳过状态建立在**内容相等**（integrity 相同）而非版本相等上。**好流程的标志是：重跑它是一件无聊的事。**

**53. 身份用标识符，不用显示名。** `[12]`
"一个显示名不标识工作流文件；另一个工作流可以使用同样的标题。" **显示名可被复用，路径/ID 才是身份。**

**54. 形式检查不是语义检查。** `[05]`
Issue 政策检查了正文长度和标题语言，**却无法确立"请求的工作、预期行为、交付物是否清晰"**。**每条政策都该被问一次：它失败的时候，能不能指出缺失的那个决策？**

**55. 自动化的边界由"谁拥有这份元数据"划定。** `[03]`
本地能确定的事自动做；**共享元数据或影响链外的事留给人类**。

**56. 混淆状态时，错误的方向是"把失败显示成通过"。** `[10]`
success-only 的聚合"**能把失败的依赖藏在一个被跳过的必需检查后面**"——比漏报更危险，因为漏报还有机会被发现。

## 七、派生物与单一归属

**57. 一份事实只该有一个家，而且那个家要可预测。** `[06]`
索引复制路径与日期、类型该跟着包走而不是"重要性"、每个粘贴声明只有一个家——三个层面上的同一个要求。

**58. 第二份真相有两种成本：漂移，以及争用。** `[06]`
生成的索引不只是"要同步"，**它还把你无关的改动拖进同一份文件**。

**59. 三问决定"消除"还是"自动化"。** `[09]`
**① 它是必需的吗？② 源变化时能自动重生成吗？③ 校验能搭现成的车吗？** 三问都否就该消除它；都满足就该接受它并把同步自动化。
反面教材：把校验做成专门的 `doc-sync` 门，它"**唯一的失败模式，是在一个贡献者推完无关的依赖升级几分钟后，告诉他去重跑生成器**"——**把同步成本推给一个人**。

**60. 当源信息不足以生成正确的副本时，这个副本的问题不是"需要维护"，而是"不可能正确"。** `[11]`
AST **能找到注册，但推断不出语义条件**（历史保留、输出截断、父子可见性）。

**61. 冻结要真的冻结，包括放弃维护义务。** `[06]`
归档笔记**被所有其他文档门禁排除**，且**不随重命名包、变化的行为、翻译标准、格式规则、断裂链接更新**。**只冻结内容而不划掉维护义务，等于没冻结。**

**62. 归档与删除的语义不能混。** `[06]`
归档 = "已实现的历史决策"。过时的提案要**明确拒绝**，没价值的拒绝要**删除**，而不是找第二个低价值存放区。

**63. 删除时要区分"引用"与"理由"。** `[02]`
死产物的引用可以删，但**事实分句要保留或重述**。

**64. 契约要住在实现本地。** `[11]`
"包 README 是实现本地的契约；一份中央副本会增加另一个漂移点。" **决定内容住哪里的，是"谁在改动它"，不是"谁在阅读它"。**

**65. 本地分歧要记账。** `[07]`
"Cordis vendor 副本与上游又多了一处类型结构分歧，同步时必须重新应用或显式退役。" **每一笔本地定制都是未来要偿还的债。**

**66. 临时物清理掉，方法与证据留下。** `[15]`
"临时的基准工作流和它的安全测试不在最终树里；**实验提交和链接的 run 保留了方法和证据**。"

## 八、变更与边界

**67. 越界的机制不能走那条被阻塞的路径。** `[08]`
CI 故障切换被设计成**仓库变量**而非一次合并，因为"**它在检查是红的时候也能工作**"。**设计应急机制时先问：它依赖的通道，在它要应对的那种故障里还通吗？**

**68. 冗余 ≠ 替换。** `[08]`
"让自建池永远留在必需路径里"被否决：**那是拿 B 的可用性换 A 的可用性——移动了单点故障，没有增加回退。**

**69. 变更要列参与者清单，逐个点名。** `[15]`
谁参与、谁不参与、**为什么**不参与（凭据 / 宿主能力 / 产物喂养发布链 / 工作流 spec 钉住）。**"谁不受影响"和"为什么不受影响"是同一份清单的两半。**

**70. "没做的事"也要写明。** `[15]`
release 演练 job "**不获得 `blacksmith` 分支**"。**沉默会被读成"忘了"，而不是"决定不做"。**

**71. 整体替换作为默认不可接受。** `[15]`
三条理由都不是态度：**破坏工作流契约 spec、扭曲基准测量、移动信任边界 job 而无决策记录。**

**72. 范围可以是一个否决理由，但要说清是范围而不是能力。** `[15]`
"移到自托管——**被范围否决**。"

**73. 限定范围本身就是防御。** `[04]`
"**有限的场景/修复范围，防止一个宽泛的性能请求变成一次无关的架构重写。**"

**74. 拒绝把手头问题变成一个通用层。** `[09]`
"构建通用 hook 管理器"被否决：**顺序、参数转发、失败语义、升级会变成与目标无关的仓库自有行为。**

**75. 顺手能做的事，如果不是本次决策的一部分，就不做。** `[05]`
自动元数据修复被拒绝的理由是"**它们是独立的决策，而不是随一次政策简化捎带进来**"。**范围蔓延最隐蔽的形式，就是那些看起来相关且容易的事。**

**76. 优化不该改变拓扑。** `[12]`
"必须留在既有 job 内"——拆 job 会带来 checkout、安装、制品传输和 merge job。

**77. 文档和代码在同一次变更里移动。** `[09]`
"必须移动 `engines.node`、兼容矩阵和**这篇 Agent Note**"——**文档是必须同步移动的三样东西之一。**

**78. 政策反转时要记录被否决政策的完整理由。** `[10]`
旧豁免当初要保护什么、它的成本被什么界定、以及**"明确接受 standby 饥饿"**。

**79. 回退时，给未来的重试者留下前置条件。** `[15]`
四条约束 + 门槛："**必须在实际池上重新验证吞吐量与失败可复现性，在任何路由变更之前。**" **一次失败的迁移留下的不是"别再试了"，而是"要再试的话，先满足这些"。**

**80. 失败的迁移要完整记录，包括根因。** `[15]`
时间线精确到分钟、失败现象、以及真正的根因：**"验收标准从未被测量，提案一直停在 `proposed`。"**

**81. 不做的事也要列出来。** `[03]`
"不重建评审轮次、不查询 `reviewDecision`、**不加定时对账器**"——**它划出了"这条命令管到哪为止"**。

**82. 选介入点，要选在所有路径都必经的地方。** `[10]`
包装一个命令只能覆盖"使用那个命令"的场景；**合并驱动是裸 Git、stack 工具、rebase、cherry-pick 共享的扩展点**。

**83. 部分成功必须非零退出。** `[10]`
"调用者不能把一次部分解析误认为完成的合并。" **能做完多少就做多少，但汇报时必须说"没做完"。**

**84. 失败契约要含"可观察状态"。** `[10]`
那张表三列：失败、**可观察状态**、恢复。**恢复的第一步是识别，所以识别条件属于契约。**

**85. 说清能力的边界，不把"可取消"包装成"会变快"。** `[10]`
"取消是一个**请求**，不是立即终止的保证……它让过时验证可被取消，**不承诺**固定的运行时长或取消延迟。"

## 九、工具与资源

**86. 趁爆炸半径小的时候换承重工具。** `[07]`
"现在换"的依据是**可枚举的**：还没有任何东西发布、工具只需做三件事、唯一专属资产小而机械。

**87. 让工具的错误成为防线。** `[07]`
pnpm 篇**刻意不加** hoisted 逃生舱，因为非扁平 `node_modules` 让**幻影依赖大声失败**——他们对一个"整个质量故事都是机械门禁"的仓库称之为 *a feature*。**选工具时问的不是"它的报错会不会烦到我"，而是"它的报错恰好是我需要的那个信号吗"。**

**88. pin 比范围好；类型不能领先于运行时下限。** `[09]`
浮动的 major 条目"**会随时间长上去，并静默停止演练声明的下限**"；类型跑在运行时前面，**会把运行时故障伪装成编译通过**。

**89. 更多资源不等于更好，要用实测判断。** `[14]`
32 核只比 16 核改进 **1.47 秒**，而且在 Node 的 CJS lexer 里失败。**"加资源"是需要证据的主张，不是默认答案。**

**90. 任何共享的可变位置，都会把并发变成时序依赖。** `[09][14]`
共享的 Git hooks 目录会让"一个 worktree 的安装改变另一个的行为"；可变的共享 Node 链接会"**让选定的版本取决于另一个 job 的时序**"。**隔离的代价要明说，但换来的是结果的可复现。**

**91. 结构性修复优先于周期清理；区分"混乱"与"缓存"。** `[13]`
"编译缓存是**缓存**，不是**残留**。每次运行删除它会丢弃缓存存在的意义。" **当增长是某个东西的正常行为时，问题在"它长在哪"，不在"它长了"。**

**92. 超时用来防挂死是对的，用来表达性能目标是错的。** `[13][14]`
"调度方差会取消正确的工作，**并压制诊断回归所需的证据**"；而正确的用法是"**约束卡住的工作，而不把性能目标当作正确性截止时间**"。

**93. 隔离/清理要按"finally 不会被执行"来设计。** `[12]`
`TMPDIR` 指向 `runner.temp`，为的是**即使进程被杀、`finally` 没跑，临时物仍在清理范围内**。

**94. 清理要等所有所有者结算。** `[14]`
"失败的泳道等另一条完成再清理——**延迟失败报告，但避免删除仍被子进程持有的文件**。"

## 十、工作方式

**95. 不留悬空的红。** `[07]`
行为变更让用例变红时**当场对账**（修测试或修代码，以契约为仲裁）。**一个挂着的红，会让之后每一次"红了"都失去意义。**

**96. 知道该怎么修就直接修，别评论。** `[04]`
"只评论不修复"被否决的理由：**它保留无效状态并要求人工清理**。**把一个可自动完成的修复降级成一条提示，是把自己的成本转给未来的某个人。**

**97. 分层要沿着架构的自然接缝，而且层间不重复测试。** `[07]`
上层只测自己的层；纯函数层不引入任何 fake。**重复测试不是"更保险"，是让信号的归属变模糊。**

**98. 探针必须用正例和近似负例校准。** `[02]`
"用已知正例和一个近似负例校准"——**只测正例的探针，无法知道自己有没有误伤。**

**99. 强制的摩擦可以是刻意的。** `[02]`
`Alternatives considered` 是"刻意的摩擦"，因为**"一个没有记录它击败了什么的决策，会招致它本来要防止的重新打官司"**。

**100. 自描述优先于依赖上下文。** `[02]`
`Agent Note: ` 前缀让文件挪出树外仍能自述体裁。**假设读者在错误的上下文里读到它。**

**101. 不要为了测试变绿而缩小被测范围。** `[14]`
"排除看起来不支持的文件"被拒绝，理由是**"受影响的行为是受支持的"**——它是"之前漏测的东西"，不是"不该测的东西"。

**102. 测试环境比真实环境更完备时，测不出缺席。** `[05]`
workspace 安装总是有每个包，**所以所有测试都通过，而发布的包对拒绝可选 peer 的消费者是坏的**。**凡是"我这个环境里一定有"的假设，都要问一句：在所有真实环境里也一定有吗？**

**103. 潜伏的 bug 需要专门的搜寻。** `[05]`
那条 `^0.0.1` **从未失败，只因版本从未离开 `0.0.1`**。这类 bug 不会通过"跑测试"暴露，只能通过**推理条件边界**（"如果这个值变了会怎样"）发现。

**104. 新增能力带来新增义务。** `[13]`
"连续录制保留中间状态，**所以评审者必须检查选定区间是否有敏感内容与可读性**。"

**105. 代价要量化，然后判定它可不可接受。** `[13]`
"缓存在 `runner.temp` 里累积，runner 不清空它——**但在数据卷上（约 1% inode）那无害**。" **先量，再判，而不是含糊地说"影响很小"。**

### 那条张力已经解答（补记）

此前在这里记着一条"未解决的张力"——"可机械判定的必须机械化"与"能不能机械判定本身需要判断"之间的矛盾。**它现在有一手判据**，出处是 `archived/process/2026-07-19-require-agent-notes-for-non-trivial-changes.md`：

> **评审强制这条语义边界。没有任何自动门禁试图把一个 diff 分类为平凡或非平凡**，所以这条政策不增加门禁阶段或运行时。

被否决的对照方案给出了完整理由：

> **加一道 CI 的 diff 分类门禁。** 一个机械检查**无法可靠判断一个语义变更是否平凡**，而另一道门禁会增加运行时，**并招致误报或表面合规（superficial compliance）**。

**判据：当机器的判定不可靠时，问它跑起来还有没有剩余价值。**

| 机器的判定 | 处置 |
|---|---|
| 可靠 | 完全机械化（第 ① 档） |
| **不可靠，但跑起来仍有参考价值** | 降级为**参考性**——跑，但不阻塞合并（例：Knip 的未使用代码扫描） |
| **不可靠，且跑起来只有害处** | 交给**评审**，不跑（例："这个 diff 是否平凡"） |

**"表面合规"是这里的关键词**：一道不可靠的门禁**不会让人去解决它想解决的问题，而是让人学会迎合它**。这与第 01 批的"一刀切天花板会**训练贡献者橡皮图章式地批准提高上限**"是同一失败模式的两种表述。

## 怎么用这份表

**如果你是作者**：写规范时对照第二、三节（规则与门禁）；写变更时对照第八节。

**如果你是评审者**：第五、六节可直接当检查清单；第四节问"这个结论的边界在哪"。

**如果只能记三条**：

1. **模式 A**——不确定就标注，不补齐。
2. **第五节第 45 条**——一个手段改善了可见指标，不等于打中了瓶颈。
3. **第六节第 48 条**——同一个字段名不该回答两个问题。
