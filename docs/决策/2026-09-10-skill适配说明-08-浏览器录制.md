### 5. `## Record the flow`（含 `### Capture video`）→ **原样保留**

**逐字保留的要点**：

- 沿用可用浏览器控制工作流的 setup / interaction / cleanup；暴露 `recordVideo` 时在同一受控上下文启用视频以捕获更多中间帧；**"视频可用性不决定该选哪个浏览器控制工作流"**
- 只有在浏览器控制不可用时，才用仓库声明的 Playwright 依赖在隔离无头浏览器里操作，**并在溯源里声明这个退路**；**不要安装另一个驱动，也不要打开用户的浏览器**
- `### Capture video` 里那条**必须保留的长注释**：`viewport` 与 `recordVideo.size` **要显式匹配**，否则 Playwright 会把视频缩到 800×800 以内，**导致 UI 文字不可读**
- **`context.close()` 要在 `video.saveAs()` 之前 await**；**只关 browser 不保证视频已 flush**；**每个页面有自己的视频，显式选择被演示的页面，不要拼接不相关的页面或运行**
- **"选择 3–6 个有意义状态的短故事"**；行动前等待**唯一语义定位器**；用 `exact: true` 做可及名称等值与**无法匹配提示词回显**的精确文本完成判定；**固定等待可以在状态验证后提供阅读停留，但绝不用于确立就绪**
- 演示工具调用 / 拒绝 / 恢复时，**打开它的详情或轨迹**，让视频显示工具身份、状态或稳定错误码、以及下游结果
- **不捕获任何机密、个人数据、无关标签页或通知**；**浏览器视频包含页面内容而非浏览器外壳**——避免在应用里渲染带凭据的 URL；**审阅整个选定区间，包括中间状态**；**保持单一视口**

### 6. `## Encode the GIF`（含 `### Screenshot capture`）→ **原样保留（并如实标注当前不可用）**

**逐字保留**：

- **依赖缺失时的行为**（§2.2 已引）：**报告依赖，而不是未经授权安装软件**
- `export GIF_SKILL_DIR=...` **必须单独一行**——**同一命令里的内联赋值无法影响参数展开**
- `--start` / `--end` 选**一段连续区间**；默认保留整段 1× 速度并加**2 秒末尾停留**；`--speed` 改变播放速度，**必须在 GIF 旁披露速度与选定区间，免得演示暗示了实测响应延迟**；**用观察到的视频时间，不要猜墙钟偏移**
- **`--fps` 提高不能恢复源录制没捕获到的运动**；**保留原始 WebM 用于 QA；不要拼接不同运行或合成缺失状态**
- 编码器的自检行为（探测 WebM 容器时长、在调色板转换前应用裁剪与变速、检查编码后时长/动画/宽度/字节大小；**拒绝空区间、越界区间、短于两个输出帧的选择、模式不当的标志与意外覆盖**）
- 体积过大时**先降 `--max-width`，再降 `--colors` 或 `--fps`；保持文字可读**；**`--force` 只在解决确切输出路径后使用**
- `### Screenshot capture`：**从一次隔离运行里捕获 3–6 个已验证状态**；按 `00-initial.png` / `01-typed.png` 命名；**尺寸与裁剪一致**；瞬态状态要在**同一次浏览器脚本调用内**轮询 DOM 标记后捕获
- **一个 duration 适用于每张截图，否则每帧给一个正数，并把稳定状态停留得最久**；**目录输入会拒绝少于两帧、尺寸不一致或 duration 数量不匹配**

**必须新增的现状说明（有据）**：**SSiD 当前没有安装 `ffmpeg` / `ffprobe`，所以编码器暂时不可用**。适配版必须写明：

> 本 skill 的编码步骤需要 `ffmpeg` 与 `ffprobe`；**SSiD 开发机未安装**。按上游纪律**报告依赖而不自行安装**；若要启用录制能力，需由用户决定如何提供这两个二进制（Windows 上通常还需注意 PATH 与许可证）。

### 7. `## Verify the artifact` → **原样保留**

**4 步逐字保留**，其中第 2 步是**全篇最容易跳过、也最重要的一步**：

> **目视阅读编码后的 GIF 本身，而不只是源帧。** 确认过渡可读、最后状态停留足够久、没有敏感内容出现。**若查看器只渲染第一帧，用 `ffmpeg` 从编码后的 GIF 解码代表性帧并检查它们；编码前的截图不能证明编码后的顺序、调色板或末尾停留。**

### 9. `scripts/encode_gif.py`（337 行）→ **原样复用**

**逐字复制，不修改**。理由（有据）：

- **零 SSiD 专有依赖**：只 import `argparse` / `json` / `math` / `shutil` / `subprocess` / `tempfile` / `pathlib` / `typing`
- 外部依赖只有 `ffmpeg` / `ffprobe`（**平台无关**）
- 它自带输入校验（拒绝空/越界区间、短于两帧的选择、模式不当的标志、意外覆盖）——**这些校验本身就是判据的载体，改它就是改判据**

**唯一要做的包装**：随包分发时确认 `python3` 可解析（Windows 上可能是 `python`）。**不要为此改脚本逻辑**。

> **生成 skill 时的实测补录（比预想更隐蔽）**：本机的 `python3` **解析存在但跑不起来**——它指向 `%LOCALAPPDATA%\Microsoft\WindowsApps\python3.exe`（**0 字节**的 Store 应用别名残留），执行返回 **9009**；而 `python` 指向 `C:\Python312\python.exe`（3.12.1）可用。
> **关键教训**：`Get-Command python3` 报告它存在（`CommandType = Application`），所以**存在性检查不等于可用性检查**——必须真跑一次 `--version` 才算核实。这与 06 §三.3 的「零命中不证明任何事，直到命中已知正例」是同一类纪律：**信号存在 ≠ 信号为真**。已写进 skill 正文。
