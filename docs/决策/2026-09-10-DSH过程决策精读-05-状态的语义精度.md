## 1. 私有 npm 发布作为三个独立序列

`2026-08-10-npm-release-sequences.md` · **本篇 184 行，是这 94 篇里最长的之一**

### 他们遇到的事

仓库有三组**互不相关**的可发布包，而它们在三件事上都不同——**版本基线、变更率、构建要求**：

- `packages/*/*` 和 `apps/*` 随产品移动
- `vendor/*`（九个 rescope 过的 Cordis 框架包）只在上游重新同步或本地修改变化时移动
- `native/*` 需要 musl 工具链，且每个架构构建一次

> Forcing them through one pipeline means every product release republishes the framework and the native binaries.

**强迫它们走一条流水线，意味着每次产品发布都要重新发布框架和原生二进制。**

### 一个潜伏了很久的 bug（本批最精彩的细节）

他们发现 933 个手写的 `peerDependencies: "^0.0.1"` 存在于兄弟 dsh 包之间。为什么这是 bug：

- `pnpm pack` 会替换 `workspace:` 协议，但**对 semver 范围不管不顾**
- `^0.0.1` 的含义是 `>=0.0.1 <0.0.2`——**它把 `0.0.2` 排除在外**
- 而 semver **会把预发布版本排除在一个自身不带预发布的范围之外**，所以它也排除了 `0.0.1-rc.1`

> Those entries never failed only because the version never left `0.0.1`.

**这些条目从未失败，仅仅因为版本从未离开过 `0.0.1`。** 一个一直在那儿、只是条件还没满足的 bug。

### 判断（六块，我只取判断价值最高的部分）

**① 三个独立序列。** `packages/`、`vendor/`、`native/` 各有一个 bump 序列和一个发布，**不共享版本、不共享触发、不共享等待**。

**② 版本从本地命令落入仓库，CI 只检查和上传。**

每个序列有一个 bump-and-commit 命令：推导目标版本 → 写入相关 manifest → `pnpm install --lockfile-only` → 连同 lockfile 一起提交。于是**已发布的版本可以直接从仓库读到**。人类在 commit 合并到 master 之后创建 tag；**CI 从不写仓库，因此也不需要仓库写权限**。

**③ "registry 决定什么该出去"——三个状态。**

发布时不读取任何 tag，也不读任何"本次发布包含什么"的清单。对每个打包好的 tarball，把版本与 registry 比对：

| 状态 | 动作 |
|---|---|
| registry 没有那个版本 | 发布 |
| registry 有，且 tarball 的 sha512 **等于**记录的 `dist.integrity` | **跳过**：这是对同一个产物的重跑 |
| registry 有，且 integrity **不同** | **失败**，报告"内容变了却没有 bump 版本" |

第三个状态是精髓：它抓住**改了代码却没升版本**的情况。而前两个状态一起提供了幂等性——**对同一产物重跑发布，什么都不会重发，也不需要人工挑选包**。

**④ 让 tag 成为账本，而不是新建账本文件。**

变更判断**不增加任何状态文件**：每个包有自己的 tag，**那个 tag 记录了它上次从哪个 commit 发布**。bump 读取最新的 `vendor-<package>-v*` tag，把包目录与该 tag 做 diff。

其中一条规则特别细，也特别重要：**对 `files` 只选 `lib/` 的包，构建输入（`src/**`、`tsconfig*.json`、构建配置）也算变化。** 理由：

> a built payload is not tracked by git: without it, a real source change reads as "nothing changed" and the next publication fails on a version whose bytes moved

**构建产物不被 git 跟踪；没有这条规则，一次真实的源码变更会被读成"什么都没变"。**

还有一条更硬的区分：

> A tag is a commit pointer, not proof of publication.

**tag 是 commit 指针，不是发布证明。** 所以 bump 会去问 registry：它最新的 tag 所命名的版本真的存在吗？不存在就**失败并交给人类解决**——因为一个为"最终失败了的发布"推的 tag，否则会被读成"已发布"，从而**无限期地跳过那个包**。

**⑤ 可选依赖绝不在模块作用域加载（一段完整的推理链）。**

这段值得逐句抄：

- `optionalDependencies` 里的依赖、或带 `peerDependenciesMeta.<name>.optional` 的 peer，**可能不在安装树里**——**那个缺席正是"可选"的全部承诺**
- **静态 import 在导入模块被加载时就被求值**，所以一个缺席的包会从"这个能力不可用"变成**所有到达那个导入模块的代码的加载失败**
- 而这个失败**只出现在缺少那个包的安装树里，偏偏这里没有任何测试构造过这样的树**：

> a workspace install always has every package, so the unit tests, the snapshots, and the packed-install probe all pass while the published package is broken for the consumer who declined the optional peer

**workspace 安装总是有每一个包，所以单元测试、快照、打包安装探针全部通过——而发布的包，对那个拒绝了可选 peer 的消费者来说是坏的。**

这是"**测试环境比真实环境更完备，所以永远测不出缺席**"的典型。门禁的补救方式是**读每个包自己的 manifest** 来决定"允许什么缺席"，再去扫真正会发布的文件。

细节上还有两处判断：**值 vs 类型要针对绑定的 Program 判定，而不是看 import 语法**（因为 `verbatimModuleSyntax` 是关的）；以及——

> A dynamic `import()` only moves the failure to first use... reaching for it is a sign the dependency is not optional

**动态 `import()` 只是把失败挪到首次使用**；伸手去拿它，恰恰说明这个依赖**并不是可选的**——所以门禁**不把它当作补救方案提供**。

**⑥ 两条 registry 现实。**

- 写入之间至少间隔两秒并带退避重试，因为连续发布多个包会**跑过 registry 自己的处理**，招致 `E409 Failed to save packument`
- **每次重试都先重读 registry**：一个被报告为失败的操作**可能实际上已经落地了**，所以"现在存在、且 integrity 正是这个 tarball 的"应当算已发布，而不是要再放一次的版本

### 凭什么这么判断（12 个被否决方案，取最利的几条）

| 方案 | 否决理由 |
|---|---|
| **`<base>-<timestamp>-<short SHA>` 版本** | 与"把已发布版本留在仓库里"冲突：版本内嵌 commit SHA，而把版本写回又会产生新 commit，于是 **SHA 只能命名被发布的父 commit**，链接需要一整套约定来解释 |
| **`vendor/published.json` 账本** | **它增加一个必须不与 registry 漂移的状态文件。** 每包一个 tag 提供同样的 commit 指针，而 tag 反正必须存在——**所以它没有引入状态的第二份拷贝** |
| **只从版本判断"已发布"，不比较内容** | **跳过只看版本，会漏掉"改了代码但没升版本"——而这是唯一会悄悄把陈旧字节留在 registry 上的失败。** 代价是一次 registry 查询 |
| **按入口闭包选择子集** | 从两个入口爬 `dependencies` 得到 156 个包（比全集少 61 个）。**但本仓库的插件是从 `cordis.yml` 按名字挂载、而不是 import 的**——有两个包落在依赖闭包之外却在运行时被需要。按代码依赖选包会失败为"消费者装了它却起不来"，而且**需要一份常设证明"没有漏掉任何被挂载的包"** |
| **在 CI 里跑 bump 并把版本推回去** | 需要工作流的仓库写权限，而且**发布分支上的版本 commit 会与人类的 commit 撞车** |
| **一个工作流加 `family` 输入** | 一个文件里放两种版本模型，会把并发组、tag 前缀、演练触发器**分叉成条件表达式**；一族一个文件**既更短也更好读** |

第 2 条再次印证第 01 批的核心模式：**拒绝"产生第二份需要同步的真相"**。

### 他们承认的代价（原文列了 9 条，这里是关键的几条）

- **tag 可能与 registry 漂移**（只在有凭据的机器上被抓到）
- **变更判断依赖可见的 tag**：浅克隆或没有 tag 的 checkout，会把 vendored 判断退化成"首次发布全部"——**`fetch-depth: 0` 是前置条件，不是优化**
- **私有包需要凭据安装**
- **字节可重现性是假设，不是测量**：

  > Nothing measures that yet: if the build embeds absolute paths or timestamps, a re-run reports a false failure. **Measure it before the first publication a re-run might follow.**

  跳过状态建立在"同一个 commit 打包两次产生相同字节"这个前提上，**但没有任何东西在测量它**。
- **对更老的产物重跑发布，可能把 `latest` 往后移**（因为发布是逐版本决定的）
- **首次发布是一大步**：九个 vendored 包加整个 dsh 集一次发布，任何载荷缺陷都会在单次发布中暴露——**这就是为什么先用一个预发布版本驱动完整路径**

## 2. 阻塞的加权批准保持待定

`2026-09-09-blocked-weighted-approvals-remain-pending.md`

### 他们遇到的事

加权批准的 commit status **必须区分两件不同的事**：

1. **一个未被满足的合并条件**
2. **一次失败的政策评估**

一个来自**有写权限评审者**的有效 `CHANGES_REQUESTED`，会阻止 PR 满足批准政策——**但它是一个可逆的评审状态，不是一次评估失败**。

为他们发布 `failure` 会造成两个后果：

- **把批准决策与发布者自身的健康混为一谈**
- **把这一种未满足的政策条件，与草稿 PR、批准点不足区别对待**——而后者保持 pending，且贡献者可以解决

### 判断

- 发布 `pending` 的三种情况：草稿 PR、批准点不足、**来自有写权限评审者的有效 `CHANGES_REQUESTED`**
- **阻塞性评审支配点数**——所以即使计数的批准达到阈值，状态**仍然保持 pending**
- 只有"已就绪 + 达到点数阈值 + 没有阻塞性评审"三者齐备才发 `success`
- **评估本身失败**（而非政策未被满足）才发布 `error` 状态并让那个 job 失败

### 凭什么这么判断

| 被否决的方案 | 否决理由 |
|---|---|
| 为阻塞性评审发布 `failure` | 它**把一个未满足且可逆的合并条件表示成了故障**，并把政策结果与发布者健康混为一谈 |
| 让批准点数覆盖阻塞性评审 | 这会让分数成为唯一成功条件，但**允许一个有效决定仍在请求修改的评审者存在时出现成功状态** |

### 他们承认的代价

- 必需状态的分支规则仍然会拦住 PR（因为 `pending` 不满足必需状态），所以**约束力没有损失**
- **消费者不会仅因为有阻塞性评审就收到失败的 commit status**——他们需要读状态描述或有效评审，才能区分一个阻塞者与其他待定条件

最后一条是**主动暴露的可观测性损失**：为了语义精确，消费者多了一步工作，这件事被写下来了。

## 3. 语义化 Issue 模板与呈现中立的政策

`2026-09-03-semantic-issue-templates-and-policy.md`

### 他们遇到的事

两个问题：

- Issue 和 PR 模板**把受理问题与评审证据混在一起**，还把完整内容藏进 `<details>` 里；**未使用的前言、单独的 Idea 与 Research 模板，增加了选择却没有改变仓库如何规划工作**
- 更根本的一个：Issue 政策**把 Markdown 呈现当成了仓库元数据**——它要求 `<details>` 元素、50 单位的可见正文、中文标题、标题元数据前缀、以及一行 `Owner:` 正文

对后者的判断一句话击穿：

> produced failures **without identifying a missing semantic decision**

**这些规则产生了失败，却没有识别出任何缺失的语义决策。** 政策在检查形式，而形式与内容无关。

### 判断

- 模板只覆盖 Bug、Feature、Task。**Idea 和 Research 归属 Task，除非未来的决策给它们不同的生命周期行为**
- 模板前言**只含** `name`、`about`、`type`
- **Markdown 标题定义层级，HTML 注释解释每个标题下该放什么**（用注释承载指导，而不是用政策承载形式）
- Issue 政策**不再检查**：`<details>` 呈现、可见正文长度、标题语言、标题前缀、正文所有权行

### 凭什么这么判断

| 方案 | 否决理由 |
|---|---|
| 保留 Idea 和 Research 模板 | 它们的表单**没有确立与 Task 不同的生命周期或政策行为**，所以分开的入口**增加了选择，却没有保留有意义的类型区别** |
| 把呈现规则保留为警告 | **这些规则可能让本来可行动的 Issue 失败，而且无法确立"请求的工作、预期行为或交付物是否清晰"** |
| 增加自动元数据修复或 Issue 分类 | 那些行为需要新的变更规则、权限、失败处理和运营证据；**它们仍然是独立的决策，而不是随一次政策简化捎带进来** |

第 3 条值得单独记住：**明确拒绝"顺手捎带"**。一个简化动作不做额外的事，即使那些事看起来相关。

### 他们承认的代价

政策**不重写历史标签、不选择缺失的 Issue Type、不同步 Priority、不迁移现有数据**；**未来任何针对那些操作的自动化，都需要它自己的决策和评审范围**。

## 这批的共同判断标准

**① 未满足 ≠ 失败。**
"没有满足条件"和"东西坏了"是两种状态，混在一起会让真正需要警报的情况被淹没。审批篇给了最清晰的切法：`pending`（条件未满足，可解决）/ `success` / `error`（评估本身失败）。

**② 没有 ≠ 有但不同。**
npm 篇的第三个 registry 状态（内容变了但版本没变）之所以必须独立存在，是因为它和"重跑"看起来都是"这个版本已经存在了"。**两种"已经存在"只有一个是真的问题。**

**③ 形式检查不是语义检查。**
Issue 政策检查了正文长度和标题语言，**却无法确立"请求的工作、预期行为、交付物是否清晰"**。任何一条政策都该被问一次：**它失败的时候，能不能指出缺失的那个决策？**

**④ 潜伏的 bug 需要专门的搜寻。**
那条 `^0.0.1` **从未失败，只因版本从未离开 `0.0.1`**。这类 bug 不会通过"跑测试"暴露，只能通过**推理条件边界**发现——"如果这个值变了会怎样"。

**⑤ 测试环境比真实环境更完备时，测不出缺席。**
workspace 安装总是包含每一个包，于是所有测试都通过，而发布的包对拒绝可选 peer 的消费者是坏的。**凡是"我这个环境里一定有"的假设，都要问一句：在所有真实环境里也一定有吗？**

**⑥ 假设要标记为假设，并定下验证时点。**
"字节可重现性是假设，不是测量"——而且给出了行动指令：**在第一次可能被重跑的发布之前先测它**。这与第 02、04 批"诚实的空白"是同一立场的第三次现身。

**⑦ 幂等不是"重复执行不出错"，是"重复执行不产生新状态"。**
跳过状态建立在**内容相等**（integrity 相同）而不是版本相等上，所以"对同一产物重跑"这类日常操作不需要任何人工判断。**一个好流程的标志是：重跑它是一件无聊的事。**

**⑧ 顺手能做的事，如果不是本次决策的一部分，就不做。**
"自动修复元数据 / 自动分类"被拒绝的理由是"它们是独立的决策，而不是随一次政策简化捎带进来"。**范围蔓延最隐蔽的形式，就是那些看起来相关且容易的事。**
