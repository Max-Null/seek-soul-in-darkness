## 1. Package Model Experience 契约

`2026-07-12-package-model-experience-contract.md`

### 他们遇到的事

一个包 README 可以解释 API 和运行时机制，**却不回答主导 agent harness 行为与成本的那些问题**：

> what from this package reaches a model request, under which conditions, how long those tokens remain, and whether later requests preserve a reusable KV-cache prefix

**这个包的什么内容会到达模型请求、在什么条件下、那些 token 停留多久、后续请求是否保留可复用的 KV-cache 前缀。**

而麻烦在于**这个遗漏在插件架构里尤其难审计**：

> A consumer may turn a backend result into a tool message, a policy plugin may replace success with an error, compaction may remove old history, and an agent-scoped registration may change one agent's prompt or schemas while leaving every other agent unchanged.

消费者可能把后端结果变成工具消息；策略插件可能把成功替换成错误；压缩可能移除旧历史；**而一个 agent 作用域的注册可能改变某个 agent 的 prompt 或 schema，同时让其他所有 agent 保持不变**。

于是两边都走不通：**只读那些"名义上面向模型"的包会错过真实的上下文效应；而跨每个依赖读源码，对常规评审来说太贵。**

### 判断：契约写在包 README（实现本地）

- 每个有面向模型或模型相邻契约的包 **README 以规范的 Model Experience 段结尾**
- 有直接/条件/有上限/生命周期/多面/辅助模型效应的包，**每个上下文面用一个 H3**；每个面含三个有序 H4：`What the model sees`、`Token effect`、`KV Cache effect`，**每个字段以一段散文开始**
- 无效应或完全由别包渲染的路径，用**审计过的短形式**：一句以 `None, as ` 或 `Indirectly, through ` 开头的句子 + 一个 `KV Cache effect` H4

### 三处"区分两个事实"的精确措辞

**① "不失效"不等于"保证命中"。**

> "Does not invalidate" means **the package preserves an already-reusable prefix**, not that **a provider promises a cache hit or retention period**.

**"Does not invalidate" 的意思是"这个包保留了一个已经可复用的前缀"，而不是"provider 保证缓存命中或保留期"。** 一句话划清了自己能承诺的与上游才能承诺的。

**② 稳定契约是"形态"，不是"数值"。**

被否决的方案是"要求数字化的 token 计数"，理由是：

> exact counts depend on the selected model tokenizer, adapter serialization, configuration, and runtime data. **The stable contract is the growth shape**: fixed per request, conditional per call, retained, replaced, capped, or zero-direct.

**精确计数取决于 tokenizer、适配器序列化、配置和运行时数据——它不可稳定。** 于是契约退到**可稳定判定的那一层**：增长形态（每次请求固定／每次调用条件性／保留／替换／有上限／零直接效应）。

**③ 缺席必须有解释。**

> unconstrained absence is **ambiguous between an audited zero and forgotten documentation**

**无约束的缺席，在"审计过的零"和"忘记写文档"之间是模糊的。** 所以省略**只留给**被校验器点名并附理由的模型无关包——**其余零影响的包也必须写一句明确的话**。

这是"诚实的空白"的反面用法：**空白本身可以是诚实的，但前提是它被标注过。** 没有标注的空白，读的人无法区分"这里确实没有"和"这里漏了"。

### 凭什么这么判断（7 个被否决方案，取最利的）

| 方案 | 否决理由 |
|---|---|
| **只记录注册了 prompt 或工具的包** | **后端、策略插件、适配器、持久化、作用域和压缩都会改变 token 的内容或生命周期，却不拥有面向模型的 schema** |
| **从源码生成一个中央上下文成本目录** | **AST 能找到注册，但无法推断语义条件**——历史保留、输出截断、父子可见性、辅助模型边界。**包 README 是实现本地的契约；一份中央副本会增加另一个漂移点** |
| 要求数字化的 token 计数 | 见上——精确计数不稳定 |
| 用一张表 | 精确的源码文本和条件结果形态**让单元格密集、难以扫读** |
| 允许每个零影响包都省略 | 见上——缺席的歧义 |
| 零影响/简单间接包也用完整结构化形式 | **那是在一个事实周围重复标签** |
| 只靠约定、不设门禁 | **一个仓库范围的契约还必须覆盖每一个未来的包；评审记忆无法可靠地察觉一个被省略的 README 段** |

第 2 条是模式 B（第二份真相）的又一次印证，而且给出了新论据：**AST 能提取"结构"，但提取不出"语义条件"**——所以生成物在这里不可能正确，不只是"会漂移"。

### 门禁管到哪为止

校验器检查：三种分类、规范的末段顺序、字段标题深度与顺序、非空字段段落、H5 对逐字块的所有权、**具体字面量证据**、锚定的工具目录链接。

而最后一句划了边界：**"评审仍然拥有覆盖率、链接相关性和事实准确性。"** —— **门禁管形式，评审管内容**，谁管什么写在明面上。

## 2. Project 本地的 Issue 规划字段

`2026-09-02-project-local-issue-planning-fields.md`

### 他们遇到的事

一段很具体的权限与存储耦合：

> A workflow token with Project write access **can** read and update Project custom fields **while GitHub rejects Issue-field reads**, so using both storage systems makes **one policy depend on two independently administered permission sets**.

一个带 Project 写权限的工作流 token 能读写 Project 自定义字段，**而 GitHub 拒绝 Issue 字段的读取**——于是同时使用两个存储系统，会让**一条政策依赖于两套独立管理的权限集**。

这是"**一条政策不该被两套权限绑住**"的判据——**不是因为技术上做不到，而是因为它把一个运维面变成了两个。**

### 判断

- 规划字段（`Priority`、`Severity`、`Cost`、`Start Date`、`Target Date`）**归 `DSH Issue Management` Project 所有**
- 仓库政策**从配置的 Project 解析**；**它拒绝 Issue 支撑的字段或错误的数据类型**
- 组织级 Issue 字段**只保留为 `Legacy ...` 迁移来源**，不被仓库工作流读取
- `Start Date` **只对 `pull_request.opened` 初始化**，且**只在当前 Project 值为空时写入**

### 凭什么这么判断

| 方案 | 否决理由 |
|---|---|
| 保持组织级 Issue 字段 | 它们让一个值跨 Project 可见，**但工作流不需要那个作用域，而且 GitHub App 会需要单独的组织级 Issue Fields 访问权** |
| **双写 Issue 和 Project 字段** | 镜像字段保留了跨 Project 可见性，**但每一个写入者和手工编辑都能制造漂移，并需要一条对账政策** |
| 处理每个订阅的 PR 事件，或覆盖 Start Date | 更晚的事件可以修复缺失日期，**但它们会在工作开始之后才分配日期，或替换一次手工计划** |

第 3 条里那个取舍值得记：**"修复缺失值"的机会同时也是"覆盖人的决定"的机会**——所以宁可保留"仅 opened、仅空值"的窄行为，**也不要一个能修复更多、但也会破坏更多的东西**。

### 他们承认的代价

- 规划元数据**被限定在一个 Project 成员资格内**（同一个 Issue 在另一个 Project 里可以有不同值）
- **字段重命名或类型变更会让工作流失败，而不是回退到 legacy 字段**（fail-loud 优于静默降级）
- **空值读取让普通重试幂等**——但：
  > Project field updates have **no compare-and-set precondition**, so simultaneous pull requests can both observe an empty Start Date and **the last mutation can win**.

  **Project 字段更新没有 compare-and-set 前置条件，所以同时的 PR 可能都观察到空的 Start Date，最后一次变更胜出。** 竞态被明确写出来，而不是被"重试幂等"这句话掩盖过去。

## 3. 仅 master 的平台 CI

`2026-09-06-master-only-platform-ci.md`

### 他们遇到的事

macOS Intel/ARM 与 Linux ARM64 的 Python 运行时构建，加上通过 Wine 的 Windows 构建/站点检查，**在每一个 PR 修订上消耗付费托管容量**。

而关键在于**证据的重叠**：**原生 Linux 和 Windows x64 已经提供必需的 executable 和 installed-wheel 证据，原生 Windows 检查也在合并前覆盖了构建与进程行为**。

### 判断

- PR 上要求 Linux x64 与 Windows x64 的运行时验证；**Linux ARM64 与两个 macOS 目标只在 master 推送时选中**
- **Python 发布保留全部五个目标**
- Wine **在托管 Ubuntu 上作为独立的 master job 跑一次**——因为它既提供检查，也提供默认分支的缓存生产，**所以不需要单独的缓存播种 job**

### 明确接受代价

被否决方案的第一条把取舍摊开：

> This policy **explicitly accepts post-merge discovery for these four checks**.

**这个政策明确接受这四项检查的"合并后才发现"。**

Consequences 里再次直说：

> A macOS, Linux ARM64, or Wine-specific regression **can merge while required PR checks are green**.

**一个 macOS／Linux ARM64／Wine 特定的回归，可以在必需的 PR 检查全绿时合并。** 代价没有被措辞软化。

而与之配套的边界也很清楚：**master 失败仍然是普通的失败 job，不是 `continue-on-error` 观察**——**代价是"晚发现"，不是"不发现"。**

### 三处"不声称自己验证不了的东西"

**① 本地调度测试不声称平台执行。**

> Real platform execution **remains CI-owned**; local scheduling tests **do not claim native runtime or Wine execution**.

**② 负控证明门禁"能红"。**

> Executed negative controls **remove the Intel target, misroute Wine, and restore the stale aggregate dependency; each produces its intended failure**.

移除 Intel 目标、错误路由 Wine、恢复陈旧的聚合依赖——**每一个都产生预期的失败**。这是第 01 批"能红再改"纪律的又一次落地。

**③ 被取代的笔记仍然保留独立价值。**

它**部分取代**了四篇更早的笔记，然后说明那些笔记"仍然为 artifact provenance、平台保真度、串行完整性和信任规则而活跃"——**部分取代要写明保留了什么**。

## 对索引里跨批模式的印证

**模式 A（诚实的空白）——第 8 次，这次是"把不稳定的部分排除出契约"。**

"稳定的契约是增长形态，不是数值"——**它没有假装能给出一个可靠的数字，而是把契约收缩到能稳定判定的那一层**。同一篇里的"缺席必须有解释"是这条模式的反面用法：**空白可以是诚实的，但必须是被标注过的空白**，否则读者无法区分"这里没有"和"这里漏了"。

**模式 B（拒绝第二份真相）——新论据。**

拒绝"从源码生成中央上下文目录"的理由不只"会漂移"，还有更根本的一条：**AST 能找到注册，但推断不出语义条件**。**当源信息不足以生成正确的副本时，这个副本不是"需要维护"，而是"不可能正确"。**

**模式 C（别把不同的事混成一种状态）——"Does not invalidate" 的定义。**

**"不使前缀失效" ≠ "保证缓存命中"**：前者是这个包能承诺的，后者只有 provider 能承诺。**一句话划清了责任边界。**

## 这批的共同判断标准

**① 契约要住在实现本地。**
"包 README 是实现本地的契约；一份中央副本会增加另一个漂移点。"**决定某份内容住哪里的，是"谁在改动它"，而不是"谁在阅读它"。**

**② 数值不可得时，记录形态。**
精确 token 数依赖 tokenizer、序列化、配置和运行时数据——**它不稳定，所以不进契约**。契约退到"每次请求固定／条件性／保留／替换／有上限／零直接"这一层：**能被稳定判定的部分**。

**③ 缺席必须被标注，否则读的人无法解读。**
"无约束的缺席，在'审计过的零'和'忘记写文档'之间是模糊的。"**空白也是一种陈述，它需要被授权。**

**④ 一条政策不该依赖两套独立管理的权限。**
不是因为做不到，而是因为**那把一个运维面变成了两个**。

**⑤ "修复缺失值"的机会，往往也是"覆盖人的决定"的机会。**
所以 Start Date 只在 opened 且为空时写。**能修复更多的东西，常常也能破坏更多——取舍要按最坏方向算。**

**⑥ 明确接受代价，不要软化措辞。**
"明确接受这四项检查的合并后才发现""一个回归可以在必需的 PR 检查全绿时合并"。**同时说清代价的边界：是"晚发现"，不是"不发现"。**

**⑦ 不声称自己验证不了的东西。**
本地调度测试**不声称原生运行时或 Wine 执行**。**验证手段的边界要写在它的说明里**，否则会被当成它保证了更多。

**⑧ 门禁管形式，评审管内容——而且要写明谁管什么。**
"评审仍然拥有覆盖率、链接相关性和事实准确性。"

**⑨ 测试要有负控。**
移除一个目标、错误路由一个 job、恢复一个陈旧依赖——**每一个都必须产生预期失败**，否则你不知道这个测试能不能红。
