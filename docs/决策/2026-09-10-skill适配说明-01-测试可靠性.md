### 2.2 dsh-ssid-panels 的测试没有接线

`plugins/dsh-ssid-panels/tests/` 下有 `prompt-seeds.test.ts`（4581 B）与 `release-notes.test.ts`（1589 B），用 `node:test` 写就，但：

- `node_modules/` 里**没装 vitest**，devDependencies 里也没有（所以它们确实不是 vitest 测试）
- 唯一入口是 `ssid-release` skill 里的手跑命令（`SKILL.md:33`、`:50`），且该 skill 记了一个坑：**必须在仓库根或有本地 tsx 的目录跑**，绝对路径 + 错误 cwd 会 `ERR_MODULE_NOT_FOUND`

**为什么这条要写进适配说明**：它正是上游第 1 节 "Read the owning rules" 要防的情形——**测试存在 ≠ 测试在跑**。CI 不会跑它们，新人不知道要跑。适配版应把"哪些测试由谁在什么时机跑"当作**判据的输入**写清楚，而不是假设"有测试就有纪律"。

### 2. Model the execution topology（4 层重叠模型）→ **改写**

上游四层：同一 Vitest 文件内 → 不同 worker 进程 → 同一 job 内的独立进程 → 共享主机的不同 job。

**SSiD 侧**：没有"共享主机的不同 job"这一层（无自托管池）。实际拓扑是三到四层：

| SSiD 层 | 对应上游 |
|---|---|
| 同一 spec 文件内的用例 | 第 1 层（保留） |
| 并行的 spec 文件 / vitest worker | 第 2 层（保留，但 vitest 与 node:test 表现不同） |
| shell 与插件同时跑测试 | 第 3 层（改写：SSiD 的形态是"多个包的测试同时跑"） |
| 本地开发机与 CI runner | 第 4 层（改写：由"共享主机"变为"本地 vs GitHub runner"） |

**保留的核心判据（原样）**：
> **进程隔离不隔离主机的端口、可预测文件系统路径、外部服务、数据库、socket 或继承的子进程。**

以及：
> **"不要因为一个 fixture 缺隔离就把整个套件串行化。"**（"顺序化一个 Vitest 块无法保护主机资源免受另一个文件、进程、job 或 runner 的干扰"）

### 3. Allocate resources atomically → **原样保留**

判据与运行器无关：

- **用资源所有者的分配器，而不是"先检查可用、稍后再占"**：网络用 `listen(0)` 并**在服务器报告 listening 之后**才读回地址；**绝不要扫描空闲端口然后稍后绑定**
- 用 `mkdtemp` 建私有临时根；**不要获取可预测的共享路径**
- 给共享数据库、socket、会话、输出位置**唯一的按用例命名空间**
- 需要"路径必须尚不存在"时用独占创建
- **稳定的录制标识符要与临时传输地址分开**
- **而"仅作为解析器输入或期望值出现的字面路径/URL 不是被获取的资源——不要因为看起来是固定的就改写它们"**

**SSiD 注意点（已核实，且这条判据当场抓到问题）**：`shell/tests/plugin-adapt/` 下的探针脚本存在三类硬编码，而该目录的 `README.md` **自己已写明**"页面 URL 是随机端口（如 52221），**断言勿硬编码端口**"：

| 问题 | 数量与实例 |
|---|---|
| **硬编码 token（已入库）** | **5 个文件**：`check-seed.mjs:2`、`grab-clean-modules.mjs:5`、`grab-clean-web.mjs:5`、`probe-3083.mjs:2`、`rc1-clean-check.mjs:3` |
| **硬编码端口** | 约 28 个文件直接写 `'http://127.0.0.1:9222'`（未走 `SSID_CDP` 回退）；另有 5 个写 `3083` / `54170` |
| **硬编码用户绝对路径** | `rc1-clean-check.mjs:4`：`executablePath: 'C:\\Users\\MaxNull\\AppData\\Local\\ms-playwright\\chromium-1237\\...'` |

git 跟踪状态已核实：**66 个文件被跟踪**，`.gitignore` 只排除 `node_modules/`、`test-results/`、`report/`，上述文件**全部已入库**。

**关于 token 的风险判断**：那些 URL 里的是 DSH 的 **launch token**（`?token=`），而 `2026-08-24-browser-token-authentication.md` 记明"**launch token 本身从不持久化，每次进程启动都变**"——所以它们很可能已失效。**但这只是依据该决策记录的推断，我没有验证这些具体 token 的当前有效性。** 真正的问题是模式本身：把 token 写进测试脚本并提交，这个习惯不该留。

**规范写法在同一个目录里就有**：约 22 个文件用了 `process.env.SSID_CDP ?? 'http://127.0.0.1:9222'`，README 还提到用 `findDshPage` 按 `http://` + 非 `file:` 匹配页面。**所以这不是"不会写"，是两批脚本的写法不一致。**

**这正是本节判据的价值证明**——"用资源所有者的分配器，而不是先检查可用、稍后再占"与"不要获取可预测的共享路径"，在 SSiD 的第一批审计对象上就直接命中。

### 4. Contain process-global state → **原样保留**

清单与手法完整可用：`process.env`、`cwd`、假计时器、locale 与时区、模块 mock、注册表、console 钩子、`globalThis`、全局 `fetch` 拦截——**都当独占可变资源**。

手法保留原样：捕获原值是缺失还是存在 → 恢复那个确切状态 → 立即注册恢复 → 最小作用域 `try/finally` → 保留 `afterEach` 兜底 → 拦截最窄的确切请求。

**SSiD 注意点**：**两个运行器都是显式导入**（SSiD 没开 vitest 的 `globals: true`），所以这节的手法在两边写法几乎一致——node:test 用 `import test from 'node:test'` + `import assert from 'node:assert/strict'`，vitest 用 `import { describe, it, expect, beforeEach, afterEach } from 'vitest'`。**两版示例仍要给，但差异比预想的小。**

### 5. Respect platform-owned semantics（4 条 Windows）→ **原样保留，且价值更高**

四条全部与 SSiD 强相关（你们要出 Windows NSIS 与 macOS 包）：

- **写回值只在断言容忍写回失败时才安全**（mtime 精度、NTFS 的 100 纳秒刻度）
- **Windows 环境变量名大小写不敏感**——`http_proxy` 与 `HTTP_PROXY` 当作两个键的 fixture 在那里只有一个条目
- **Windows 异步释放文件句柄**——POSIX 上立即完成的 rename/remove 需要**按实测争用规模定大小的有界重试**
- **Windows 没有 POSIX 权限与信号语义**——依赖它们的用例**显式平台跳过并写明原因**，而不是到处弱化断言

**新增建议**：SSiD 已有 macOS 相关构建（`build-mac.yml`、`ssid-mac-launcher.command`、`ssid-mac-launcher`），而上游只讲 Windows vs POSIX。适配版应补一条 macOS 侧的经验——**但具体内容我不知道**，建议从 SSiD 的发版复盘中提取（`docs/发版流程规范.md` 与 `docs/排查/`）。

### 6. Budget timeouts against the lane → **改写（机制不同，且 SSiD 现状是三种态度）**

上游三条判断**全部保留**——它们是运行器中立的，一条都不用改：

- **用例级超时覆盖运行器默认值**，而不是让位给它——所以低于 lane 预算的值等于**降低**了 CI 已授予的量
- **提升测试预算时要一起提升钩子预算**——否则"只提升 case 预算会把一次争用失败挪进 `afterEach`"
- **被测对象本身是超时时，外层等待要远大于被测超时**——证明 20 ms 截止触发的用例**不能与测试框架自己的等待赛跑**

#### 6.1 把"运行器默认值"换成实际数字

上游用的是抽象说法（"runner 的 `--testTimeout`"）。SSiD 两种运行器并存，必须写清各自的实际默认值：

| 运行器 | 用例级默认 | 钩子级默认 | 证据（可复现） |
|---|---|---|---|
| vitest 4.1.11 | **5000 ms** | **10000 ms** | `node_modules/vitest/dist/chunks/cac.*.js` 的 CLI 描述原文：Default timeout of a test in milliseconds (default: 5000)；hook 同处为 10000；写 0 表示完全禁用 |
| node:test（Node v26.2.0） | **`Infinity`** | 同（钩子即子测试，各带 `timeout`） | `@types/node@22.20.1/test.d.ts` 的 `TestOptions.timeout` 明确标 `@default Infinity`，并注明"未指定时子测试继承父测试的值" |
| Playwright | SSiD 自设 **60000 ms** | — | `shell/tests/plugin-adapt/playwright.config.ts` |

**这张表给出上游没有的机制解释**：vitest 的两个默认值构成 **hook : test = 2 : 1** 的隐含比例。所以"只提升用例预算"在 vitest 上**不是风格问题，而是必然破坏默认设计**——把 `testTimeout` 提到 30 s 而不管 `hookTimeout`（仍是 10 s），比例反转成 1 : 3，"争用失败从 case 挪进 afterEach"就必然发生。**上游判据因此从"经验"变成"可推导"。**

**同时暴露上游一处盲区**：两个运行器的默认值方向**相反**——vitest 默认 5 秒（**有限**，风险是慢用例假失败、看起来像 flake），node:test 默认 `Infinity`（**无限**，风险是挂住的用例永不失败、lane 永不结束）。**同一份"预算"判据要同时防"太紧"与"缺失信号"两种病**，而上游只面对前一种。

#### 6.2 SSiD 的三种态度，要分别说明

- **Playwright —— 已经做对，应作为正面样板写进 skill**：60 s 用例 / 30 s 导航 / 15 s 动作的**三层递减**预算，外加 `retries: 0`（主动不掩盖 flake，与第 10 节判据一致）。这是全仓库超时纪律最好的一处。
- **vitest —— 裸默认**：4 个 `vitest.config.ts` 只设 `include` / `environment`，**没人判断过 5 秒够不够**。风险是起进程、等文件系统一类慢用例间歇撞线，表现为"flake"而非"配置问题"。
- **node:test —— 无上限**：这是**更危险**的一侧。挂住的用例不会失败，只会让 lane 永不结束；超时在这里不是"太紧"而是**缺失失败信号**。而它偏偏是 SSiD 的主力运行器（4 处载体）。

#### 6.3 两种运行器的写法（同一判据给两版示例）

| | vitest | node:test |
|---|---|---|
| 导入 | `import { describe, it, expect, vi } from 'vitest'`（**显式导入**，SSiD 没开 `globals: true`） | `import test from 'node:test'` + `import assert from 'node:assert/strict'` |
| 用例级 | 第三参数 `it('名字', fn, 30_000)`；或全局配置 `testTimeout` | 第二参数 `test('名字', { timeout: 30_000 }, fn)`（签名见 `test.d.ts` L127） |
| 钩子级 | `hookTimeout`（独立配置项） | **无独立配置项**——钩子就是子测试，各带 `timeout`，未指定则继承父测试 |
| 断言 | `expect(x).toBe(y)` | `assert.equal(x, y)`（strict） |
| 组织 | `describe` / `it` | `test` 可嵌套 |

**这是上游没有的复杂度**：上游只需对一种运行器讲话，SSiD 必须两版并存，且**判据本身不得分叉**（否则就成了两份 skill，违背"一份判据"）。

> **由本节派生、但不属于 skill 正文的两条 SSiD 改进项**（单独跟踪，不要混进 skill）：
> 1. 在 `vitest.config.ts` 里**显式写出** `testTimeout` / `hookTimeout`（哪怕就是默认值）——把**隐式默认**变成**可复核的决定**
> 2. 给 `shell/package.json` 的 node:test 脚本补 `--test-timeout=<ms>`，给无限的默认值一个上限

### 7. Synchronize on state → **原样保留**

- **"固定的 sleep 不是 setup 完成或清理结算的证据。"**
- 等显式就绪事件、握手、状态转移、自有 promise、可外部观察的条件
- **"超时只用来界定等待，绝不用作让断言成立的条件。"**
- 用 deferred promise 或 barrier 把竞态放在确定点，**并证明相关操作确实重叠**
- **不要断言依赖调度器的顺序**，除非那个顺序就是被测的产品行为
- 时间本身是主题时，注入或伪造时钟，**并总是恢复真实计时器**

### 8. Dispose to quiescence → **原样保留**

- **获取后立即注册清理**，这样断言失败也会释放资源
- 清理要：停止新回调/请求 → 摘掉监听器 → 恢复全局钩子 → 终止自有工作 → **等待子进程退出、服务器关闭、worker 终止或等价完成信号**
- **"调用 `abort()`、`close()` 或 `kill()` 而不等待自有的完成信号，是不完整的拆除。"**
- 晚完成可能发生时，**证明释放能阻止它变更另一个用例**

**SSiD 注意点**：Electron 与 Playwright 相关测试的拆除尤其吃这套——`shell/tests/plugin-adapt/` 的浏览器测试若没等到 `browser.close()` 完成就进入下一个文件，正是这条要抓的。

### 9. Prove the intended regression → **原样保留**

- 可行时先观察一次普通回归在修复前失败
- **对新的静态或语料守护，临时引入被拒绝的用例并观察预期失败**（与手册 §9 的"先跑红"一致，但这条更具体：**针对守护类检查**）
- **对竞态用 barrier 证明重叠；重复执行本身不是竞态测试**
- 对端口、socket、共享路径、子进程，**当跨进程隔离是修复的一部分时，要并发跑独立测试进程**
- **fixture 用自己的截止时间 spawn 时，要先断言没有信号或超时结束了子进程，再去断言退出状态**——否则一个被杀死的子进程会被报成状态不匹配
- **验证外部状态、事件、文件、日志、退出或释放，而不是相信组件自报**
- **"压力运行补充确定性回归；它们不替代它。"**

### 10. Reject flake-masking fixes → **原样保留（全篇最可直接移植的一节）**

七条"不要把这些当作确定性本地测试的根因修复"：

1. 不指明所等待状态就加大超时
2. 加重试
3. 把所有文件改成串行
4. 吞掉错误或未处理的 rejection
5. 弱化断言
6. 把不稳定行为归一化掉
7. 在清理或断言前加 sleep

**外加一条重要的例外与区分**（也保留）：

- 重试对**有文档记载的瞬态外部提供方测试**仍然有效（对应 SSiD 的模型调用类测试）
- **"恢复预算不是掩盖"**——把套件提升到它本来就有的 lane 预算，或按 runner 上**实测的争用**定有界重试，"**命名了等待的工作并归还了 lane 已授予的量**"

### 11. Diagnose existing flakes → **改写（参考文件要重做）**

上游 `references/ci-flake-diagnosis.md`（60 行）绑在 DSH 的 CI 拓扑上。**应重写**，内容改为 SSiD 的诊断路径（本地复现 → Playwright trace → 日志定位）。这一节的具体内容**我不掌握**，需要从 SSiD 现有的排查记录里提取（`docs/排查/` 下已有 `2026-08-20-窗口不定时跳出-排查记录.md` 一类的素材）。

保留上游的定位：

> **"只做诊断的请求保持只读：报告原因与证据，除非用户同时要求修复。"**

### 12. Validate and report → **改写（命令）**

上游的"按风险加拓扑证据"四条**保留**（全局变更要恢复证据 / 生命周期或子进程要静默拆除证据 / 端口或共享路径要并发独立进程证据 / 新守护要负对照）。

**命令要换成 SSiD 的**（下表逐个核实自 `package.json` 原文，不是凭印象）：
