# skill 适配说明 · 写作规则

> **这份文档的作用**：后续每一份适配说明都按它写。它把 01、02 两次实际踩到的坑固化成**可执行的检查**，而不是「要仔细」这类空话。
> **读者**：主要是 agent（本项目约定人工不逐步复核）。所以它按 skill 的写法写——明确的触发条件、可执行的步骤、反例。

## 二、验证规则（三层）

上游 superpowers 的 Iron Law 是 `NO SKILL WITHOUT A FAILING TEST FIRST`——那是**写新 skill** 的纪律。我们做的是**移植**，直接套用会要求 12 个 skill 全跑压力场景，成本不现实。所以改成三层：

| 条款类型 | 要不要新基线 | 怎么验证 |
|---|---|---|
| 未改动的判据 | 不用 | 继承上游检验——DSH 的真实开发史已替我们测过 |
| 等价替换（路径 / 命令 / 文件名） | 不用 | 可解析性检查：引用真实存在、命令真能跑 |
| **改写与新增的判据** | **要** | 必须指出证据来源——DSH 的 Agent Note 或 SSiD 的真实事故；**指不出来就不新增** |

**这套规则的代价，写清楚**：它验证的是「判据有据可查」，**不是**「判据真能改变 agent 行为」。后者要跑压力场景，成本极高。取舍：上游判据的有效性由 DSH 真实开发史背书；我们新增的判据只能保证有据可查。更强的保证只能等包发布后从真实使用里回收——就像 DSH 自己做的：事故进 Agent Note，再进判据。

## 三、数字纪律（**最容易犯的错，已犯两次**）

**强制规则**：

> **适配说明里的每一个数字，必须在文末「数字自检」一节给出可复现的命令。写不出命令的数字，不许写进正文。**

**已发生的错误**：**01 共 5 处、02 共 2 处**，本质是同一个病 —— 拿记忆或估算当事实。

| 说明 | 错误 | 真值 | 成因 |
|---|---|---|---|
| 01 | 「用 vitest 的插件 12 个」 | **10 个** | 估算 |
| 01 | 「dsh-chat-rail 用 vitest」 | **纯 node:test**（devDeps 无 vitest） | 上一条的衍生 |
| 01 | 「vitest 是全局注入」 | **也是显式导入**（没开 `globals: true`） | 上一条的衍生 |
| 01 | 「这些文档都不存在」 | **`vitest.config.ts` 存在 4 个** | 未核 |
| 01 | 「原样保留 6 节」 | **7 节** | 算术 |
| 02 | 「release-notes 18 个」 | **19 个** | 估算 |
| 02 | 「keep rules 10 条」 | **9 条** | 估算 |

**注意前三条的同源关系**：一个错误的事实会**在全文多处复现**——01 的「12 个」同时出现在 §一、§三.7、§四。所以修一个数字时，要**全篇搜一遍它的所有出现处**，否则只修一半。

**两条操作细则**：

1. **每个数字要有专属命令**。全文 `^\d\. ` 计数得 13，那是 Taxonomy（8）+ Workflow（5），**不是 Workflow 的条目数**。不理解命令在数什么，等于没数。
2. **工具本身也要验证**。`Get-Content x | Measure-Object -Line` **会忽略空行**——它给出 86/53/34，而正确值是 131/81/45。当时我差点拿这个假证据去「修正」正确的数字。**假证据比没证据更危险。** 用 `@(Get-Content x).Count`。
3. **「我数过的」不算证据**。任何形如「N 类 / N 条 / N 个」的表述，**写之前先跑计数命令**。阅读印象数出来的数，错误率不是偶然的：**01 犯 5 次、02 犯 2 次、03 犯 1 次（把 12 类位置写成 13 类），三份说明共 8 次**。这条不是「要更小心」，而是**不许凭印象出数**。
4. **「默认位置没有」不等于「没有」**。查「某机制是否存在」时，必须查**配置解析后的实际路径**，而不是默认目录。实例（06 踩到）：查 DSH 的 git 钩子只看 `.git/hooks`，得出「DSH 也没有钩子」的**错误**结论——实际 `core.hooksPath` 指向 `.git/dsh-hooks`（lefthook 管理，含 `pre-commit` / `pre-merge-commit` / `pre-push`）。正确程序：**先读配置**（`git rev-parse --git-path <name>` 一类），**再查那个路径**，两条都查过才可下否定结论。
5. **引用原文要复制，不要重建**。两类表现：① `edit` 的 `old_string` 凭记忆写会失败（已发生一次——实际是「引用 01，须同批」，我记成「须同批进包」）；② 文档里引用上游原句时，必须**从文件复制**，「我记得是这么写的」不构成引用依据。
6. **交付前做一次数字复检（强制）**。成品（skill 文件、npm 包）交付之前，**把所有数字命令重跑一遍并逐项核对**。理由：到 2026-09-11 为止本系列共犯 **12 次**「数一数」错误（01 五次、02 两次、03 两次、09 一次、02 的 SOURCE 两次），其中两次是**写完之后才被命令推翻**的（03 的「11 类」、02 SOURCE 的「上游 17 节 / 缺 13 节」）——**写的时候"感觉自己数过"，实际是估的**。第 1 条要求的是"写之前跑命令"，本条要求的是"交付前再跑一遍"。

> **第 1、5 条是同一个根因**：默认自己的记忆可靠，于是**重建**而不**复制**。全部"数一数"错误都是它，`edit` 失败也是它。**凡是能复制的地方，就不要重建。**

## 四、算术核对（强制）

每份适配说明的「汇总」一节必须有一行算术核对：

```
（保留 + 保留并扩充 + 改写 + 重写 + 删除）= 上游部件总数 ✓
```

**上游部件总数怎么定**：`SKILL.md` 的 `## ` 小节数 + 引言 + `references/` 文件数，用命令数出来（见 §三）。01 在这里错过一次。

## 五、版面自检（发出前逐条过）

1. **引用可解析**：正文引用的每个路径用 `Test-Path` 核过；引用的外部 URL 注明来源（本机文件 / 网络获取要分开标）。
2. **判定齐全**：上游每个部件都有判定，不遗漏、不合并糊弄。
3. **四类用词统一**：原样保留 / 保留并扩充 / 改写 / 重写 / 删除。**「重写」与「改写」要分开**——重写是内容重做（如 references 换成中文案例），改写是同一内容换表述。
4. **依赖链检查**：若该 skill 引用其他 skill（`REQUIRED BACKGROUND` 之类），必须在文里声明**是否同批进包**。判据依赖缺了，skill 就会过度执行。02 已示范（依赖 03，必须同批）。
5. **description 合规**：只写**触发条件**，不总结工作流。依据是 `writing-skills` 的实测——描述里写了工作流，agent 会照描述做、**跳过正文**（实测：描述写「任务间做代码评审」，agent 就只做一次评审，尽管流程图明画了两次）。
6. **新增判据带证据**：按 §二第 3 行，每条新增都写明来源。
7. **术语一致**：同一事物全篇同名。上游叫 `keep rules` 就一直叫 `keep rules`，不要中途换成「保留条款」。
