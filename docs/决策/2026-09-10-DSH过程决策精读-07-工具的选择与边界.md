## 1. pnpm 而非 Yarn 4

`2026-06-16-pnpm-over-yarn.md`

### 他们遇到的事

仓库原本跑在 **Yarn 4 + `node-modules` linker** 上——原文承认这是一个**刻意保守的选择**：行为像 npm 的扁平布局，同时拿到 Yarn 的 workspaces 和 `yarn constraints`。

> It worked.

**它能用。** 但两个趋势让"能用"不够：

- Yarn 4 的 Plug'n'Play 血统**让 `node-modules` linker 成为偏离常轨的模式**
- 更广的 JS 生态——工具默认值、CI actions、Corepack 示例、贡献者熟悉度——**越来越以 pnpm 为中心**

而对一个**主要由 agent 构建、偶尔由人类贡献者阅读**的仓库，"**大多数工具和人期待的那个包管理器**"有真实价值：**更少的意外、更好走通的失败路径、更多可复制的答案**。最后一条尤其贴切——生态默认的那个，意味着你能搜到答案。

### 凭什么判断"现在是换的时候"

这段时机论证值得学：

- 仓库**还不发布任何东西**（每个包都是 `private: true`）
- 开发、测试、源码 demo 都走各自声明的 TypeScript 启动器
- 所以包管理器只需要做三件事：**(a) 解析和链接 `node_modules`、(b) 运行 workspace 脚本、(c) 强制 workspace 约束**
- 唯一的 Yarn 专属资产是 `yarn.config.cjs`，**小而机械**，容易重新表达

结论一句话：**趁爆炸半径还小的时候，用一个更健康生态的选项替换一个承重工具。**

### 判断：把工具的错误变成防线

最关键的一条设计：

> We deliberately add **no** `node-linker=hoisted` / `shamefully-hoist` escape hatch: pnpm's non-flat `node_modules` makes phantom dependencies (importing an undeclared transitive dep) fail loudly, which is a *feature* for a repo whose whole quality story is mechanical gates.

**他们刻意不加逃生舱。** 幻影依赖（导入一个未声明的传递依赖）在扁平布局下能侥幸工作，在 pnpm 的非扁平 `node_modules` 下**会大声失败**——而他们把这当作 feature，因为"整个质量故事都是机械门禁"。

**门禁套件（typecheck、lint、test、build）就是"不存在这类幻影导入"的安全网证明。**

另一条：**构建脚本允许清单**。pnpm 10+ 默认不运行依赖的生命周期脚本，他们显式列了 `allowBuilds`——**仓库已经对模型/工具输出采取的同一套供应链加固姿态，现在应用到安装期的代码执行**。同一个姿态，换了作用面。

### 凭什么这么判断

| 方案 | 否决理由 |
|---|---|
| 保持 Yarn 4 | 零改动，**但赌在一个更少人走的 linker 模式，和一个绑定到单一包管理器的约束引擎上** |
| npm workspaces | 无处不在，**但没有约束故事，monorepo 工效更弱** |
| **pnpm + hoisted linker** | 迁移更平滑，**但丢掉了幻影依赖的安全性——而那正是这次迁移的主要正确性理由** |
| 总是通过 Node 运行 `npm_execpath` | 对 pnpm 的 JS 分发有效，**但要求 Node 去解析 `@pnpm/exe` 提供的 ELF / Mach-O / PE 可执行文件** |
| 通过 shell 运行重入命令 | 接受更多启动器形式，**但改变了每个子命令的引号、元字符展开、可执行文件解析和信号行为** |

第 3 条体现了一种一致性：**如果一个方案的卖点是"迁移更平滑"，而它恰好削掉了你迁移的全部理由，那就没有理由。**

### 他们承认的代价（本批最值得记的一段）

先是一处功能损失：约束检查**失去了 Yarn 的自动修复**（`workspace.set()` 可以就地重写 manifest），新脚本只检查、非零退出。判断是"可接受"——因为**CI 从来不跑 `--fix`**，一行手工编辑也很少见。

然后是**性能数据**，先标前置条件：

> measured at migration time on the dev NFS filesystem; **single-digit-run samples, high variance — directional, not a benchmark suite**

| 场景 | Yarn 4 | pnpm 11 |
|---|---|---|
| 冷启动（空 cache/store，无 `node_modules`） | ~14 s | **~16 s** |
| 热重链（store 热，删掉 `node_modules`） | ~12–14 s | **~15–22 s** |
| 冻结、`node_modules` 存在（no-op 复核） | ~2–8 s | ~0.5–7 s |

**大多数格子对 pnpm 不利。** 而他们接着解释了为什么这个测试本就测不出真实优势：pnpm 的内容寻址存储本应在磁盘占用上大胜（一个全局 store 硬链接进每个 `node_modules`，而 Yarn 每个 worktree 复制 ~279 MB，有些开发者同时留十几个 worktree）——但**测试 store 和 `node_modules` 在不同文件系统上，硬链接失效了**。

然后是那句总结：

> The honest summary: install speed on our NFS dev filesystem is a wash within noise; the move is justified by ecosystem alignment, phantom-dependency safety, and cross-checkout disk dedup — **not by a raw install-time win**.

**诚实的总结：安装速度在噪声范围内是平局；这次迁移的正当理由是生态对齐、幻影依赖安全和跨 checkout 磁盘去重——不是原始的安装时间收益。**

一份**削弱了自己迁移理由**的数据，被完整贴出来，还附上"我们的测试环境让这个优势无法显现"的解释。这是第 02、04、05、06 批"诚实的空白"立场的又一次现身。

## 2. TSC 优先的构建与单一编译器所有权

`2026-06-17-ts-build-config.md`

### 他们遇到的事

- `build` **让两个工具都做 TypeScript 转换**：用 `tsc` 产 `.d.ts`，用 `tsdown` 产打包的 `.js`
- `typecheck` 倾向于**用一个根配置**验证 packages、vendor 源码、examples、tests 和 scripts

具体冲突写得很细：

- `tsdown` 用 `oxc` 转换 TypeScript，**与 `tsc` 行为不同**——**打包的 `.d.ts` 与 Cordis 内部的相对模块增强形态冲突**；**打包的 `.js` 与 `tsc -b` 的逐文件 `.js` 行为也不同**（如装饰器转换）
- `vendor/*/src`、examples、tests、scripts **不能全部朴素地放进一个根严格程序**：直接在根严格配置下检查 vendor 源码**会触发许多超出本项目所有权的类型错误**；而 `packages/*/*` 对 vendor 的依赖被解析到 `vendor/*/lib`，本来就是**为了不同的 tsconfig 严格度**

### 判断

- **`tsdown` 不再是 TypeScript 编译或声明输出的所有者**——它在每个 lib 阶段只在 `tsc` 发射之后读取 JavaScript、产出发布入口和浏览器包
- 每个普通模块**有一个本地 tsconfig**，供 build、typecheck 和直接运行源码的工具（tsx、vitest、源码加载器）共用
- 严格度差异用**项目引用**做边界，而不是一个根程序
- **构建不自动调用 clean**，所以普通构建保留增量状态

### 一段与主题无关但值得单独记的细节

`clean` 在删除一个已存在的目标之前，**会解析目标的父目录，如果解析出的父目录在仓库之外就拒绝执行**：

> so a symlinked project reference cannot redirect cleanup outside the checkout

**一个符号链接的项目引用，不能把清理重定向到 checkout 之外。** 这类防护很便宜，但它防的是"清理脚本删掉你的家目录"这一档事故。

### 凭什么这么判断

| 方案 | 否决理由 |
|---|---|
| 保持 `tsdown`/oxc 作为 TS 转换器 | oxc 的转换**不是 `tsc` 行为**；打包的 `.d.ts` 与 Cordis 的模块增强形态冲突 |
| 一个根严格程序覆盖所有目录 | **vendor 源码在根严格标志下触发超出项目所有权的类型错误** |
| 每次构建前清理 | **会丢弃 `tsc` 和打包器拥有的增量状态**，即使工作区布局没变 |
| 删除每个包级的 `node_modules` | 有效的包依赖链接**不会**导致工作区发现失败；删除它们**会把构建清理变成依赖重装** |

### 他们承认的代价

发布面的规则被完整写下来：`lib/types/*.d.ts` 是发布声明输出、`.d.ts.map` **只作本地编译产物保留**、`lib/types/*.js` **通常只是打包器输入**（只有当某个运行时导出显式指向发射树时才发布）、`lib/index.*` 是发布运行时输出。

还有一条坦白的负债：**Cordis vendor 副本与上游又多了一处类型结构分歧，在上游同步时必须被重新应用或显式退役**。**每一个本地分歧都是一笔要在未来偿还的债，他们把它记在账上。**

## 3. GUI 测试系统的三层结构

`2026-07-20-gui-testing-system.md`

### 他们遇到的事

GUI 栈横跨多种应用形态，而**在一种形态内又有多个运行时环境**（Node host、数据协议层、浏览器对象层、React/DOM）。

原文的结论很直接：**单泳道测试套件无法给出有意义的信号。** 每一环都需要自己的有效测试，**加上**全链路测试的基础能力。

### 判断：按架构的自然测试钩子切三层

| 层 | 被测对象 | 关键技术 |
|---|---|---|
| **1 协议同构** | 生成的 Remote 描述符 + ApiGateway + Connection RPC 载体（参数/结果/错误/流/取消） | **同构点上的全链路**：进程内验证描述符编解码与分发；无浏览器演练同样的 `/api` 载体分帧与信任检查 |
| **2 对象层编排** | Session / SessionManager / ConnectionController（状态机与时序：拼接/去重/分页/乐观草稿清除/pendingBuffers/重连/退避） | **"事件序列进 → 快照出"的黄金路径**：可编程 fake + 控制时序的 deferred + 控制退避的假计时器 |
| **3 组装呈现** | 构建产物 × 真实客户端 loader 与插件组合 | 语义快照在 jsdom 下启动全部八个已构建插件；裸 Playwright 冒烟单独证明真实浏览器/载体边界 |

**层间纪律一句话**：

> each tier tests its own layer, upper tiers never re-test lower ones

**每一层测自己的层，上层从不重复测试下层。** 落到具体：应用语义快照**只钉住跨组装插件边界的用户可见投影**；Playwright 冒烟**只证明浏览器与载体的活性**；**线上语义归第 1 层，数据语义归第 2 层**。而纯函数层（lineage/partial/notifier/transcript-adapter）在同包的 tests/ 里**零 fake 直接测试**。

### 反回归纪律（本批最有价值的一节）

**① 每一个 bug 修复都钉住一个断言。**

按 bug 的可见面归位：浏览器可见的 bug 钉进它所属的浏览器 spec；数据层的 bug 钉进匹配的 spec。他们给了一个先例说明这样做的收益：

> the res-close misjudgment pinned in the webserver bridge suite — **pure Node, reproduces in seconds, no longer needs the 12s browser sentinel as the only defense**

一个原本只能靠 12 秒浏览器哨兵防守的问题，被钉成纯 Node 的秒级用例。

**② fixture 全绿不算完成，真链路也必须通过。**

这条直接印证第 04 批的模式 D：

> what the fixture short-circuits is exactly the wire carriage chain (node:http bridge close semantics, real network timing); **both empirically confirmed bugs hid there**

**fixture 短路掉的正是链路运载链**（node:http 桥接的 close 语义、真实网络时序）——而**两个经验确认的 bug 都藏在那里**。所以凡是触碰 connection/bridge/handler/SSE 的改动**必须跑浏览器泳道**。

**③ 盘上代码即答案。**

行为变更让现有用例变红时**当场对账**（修测试或修代码，以契约作仲裁），**不留悬空的红**。

### 凭什么这么判断

| 被否决 | 一行理由 |
|---|---|
| 单一 e2e（一切都过浏览器） | 浏览器启动慢 N 倍且时序不可控；**线上的/对象层的不变量可以在 node 环境里毫秒级完整断言** |
| 把校验脚本迁到 vitest | 一个有序脚本共享一个浏览器会话；拆开要么把它形式化（顺序+共享页面），要么**把前导重跑 N 次**；而**流式 PASS/FAIL 输出正是 agent 的定位接口** |
| 在测试里复用 FixtureApiClient | demo 跑在真实时钟上，测试需要手工控制的 deferred 时序——**目的正交**；强制复用会把测试链到 demo 的节奏上 |
| 为 GUI 包单独一个 vitest 配置 | 包级 tests/ 已被根的 include 扫描；**路径过滤就是那个紧回路——零新配置** |
| 推迟 hooks/组件层的单元测试 | jsdom 仍是覆盖率主线（快速的逐文件组件行为）；**必需的浏览器重放门禁在组装层补充它，而不是替代它** |

第 2 条里那句值得单独记：**"流式的 PASS/FAIL 输出正是 agent 的定位接口"**——他们把测试输出格式当成 agent 工作流的一部分来设计，而不是当成给人看的日志。

### 他们承认的代价

- **层间纪律仍由评审承担**（只有 Linux CI 机械强制浏览器黄金输出的新鲜度）
- **每个新的应用快照都必须避开不稳定的布局或时钟输出**

## 这批的共同判断标准

**① 趁爆炸半径小的时候换承重工具。**
时机论证写得很具体：还没有任何东西发布、工具只需做三件事、唯一专属资产小而机械。**"现在换"的依据是可枚举的，不是感觉。**

**② 让工具的错误成为防线。**
幻影依赖 fail loudly 是 feature；构建脚本白名单把"安装期执行任意代码"变成显式决定。**别去关掉那个正在替你挡事的报错。**

**③ 单一所有权。**
一个编译器拥有 TypeScript 转换（不是两个），一个事实一个家（第 06 批）。**同一件事有两个所有者，冲突迟早会以"两边都对"的形式爆发。**

**④ 分层要沿着架构的自然接缝，而且层间不重复测试。**
上层只测自己的层，不重测下层；纯函数层不引入任何 fake。**重复测试不是"更保险"，是让信号的归属变模糊。**

**⑤ fixture 全绿不算完成。**
要问一句：**这个 fixture 短路掉了什么？** 那正是真实故障藏身的地方。

**⑥ 每个 bug 修复钉一个断言，且钉在它所属的层。**
这是同一个 bug 在归属层被**秒级复现**的成本，对比它作为"唯一防线"需要 12 秒浏览器哨兵的现状。

**⑦ 不留悬空的红。**
行为变更导致用例变红时当场对账（修测试或修代码，用契约仲裁）。**一个挂着的红，会让后面每一次"红了"都失去意义。**

**⑧ 本地分歧要记账。**
"Cordis vendor 副本与上游又多了一处类型结构分歧，同步时必须重新应用或显式退役"——**每一笔本地定制都是未来要偿还的债，写进文档才不会被遗忘。**
