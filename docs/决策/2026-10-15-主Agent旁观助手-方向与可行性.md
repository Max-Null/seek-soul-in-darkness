# 主 Agent 的旁观助手 —— 方向与可行性（2026-10-15）

> **状态**：进行中 —— 方向已确认（用户 2026-10-15 拍板），设计待启动。
> **由来**：[skill 召回机制调研](../调研/2026-10-14-skill召回机制-调研与实验.md) 的目的是判断这个想法是否可行——
> 调研本身不是终点，它是这次可行性判断的手段。
> **同族**：[长会话输出退化](../排查/2026-09-18-长会话输出退化.md)（同一压力族谱的另一个症状）；
> 机制上的已实现先例见 `max-null-plugins/dsh-allostasis/docs/设计/2026-09-20-应变-设计方案.md`。

## 一、命题

> 给主 Agent 配一个**同会话的旁观角色**，按一组**从约定沉淀出来的判据**观察每一轮，
> 在检测到违反时注入一次提醒；判据离线炼成、可复核、可增删。

用户自己的类比：**主治医师手术时一旁递手术刀的护士**。三个要素各自都有机制对应物：

| 护士的要素 | 在 DSH 里对应什么 | 现状 |
|---|---|---|
| 站得近——看得见主刀在干什么 | 同会话插件直接读事件流 | 已有：`dsh-allostasis` 每步读最近一条推理原文 |
| 不抢刀——不替主刀做手术 | 只注入提醒，不接管工具调用 | 已有：`agent/pre-step` 追加一条消息，改不改由主 Agent 决定 |
| 递该递的——关键时刻把对的东西递上去 | 按判据在违反点提醒 | **缺**：现有判据全部硬编码 |

## 二、可行性结论

**角色可行；载体不是「第二个 agent」。**

### 2.1 支撑角色的证据

| 发现 | 出处 |
|---|---|
| 失效真实、可量化，且是 skill 特有 | 调研 §四：调用率 19.48% → 2.53%（固定位置口径）；同压力下普通工具只降约 40% |
| 失效机制清楚：skill 是唯一需要二阶判断的工具 | 调研 §六 |
| 「有没有该用没用」是封闭问题，比「该用哪个」容易 | 调研 §9.1 |
| 同会话插件能看见会话里正在发生的一切 | `dsh-allostasis/src/index.ts:1-52`：三个挂载点，每步读会话内最新内容 |

### 2.2 否证「第二个 agent」的证据

| 限制 | 出处 |
|---|---|
| 看不见：agent 之间是消息传递，不是共享状态 | 调研 §9.2 |
| 来不及：队友被唤醒才动，而检测要每轮都看 | 调研 §9.4 |
| 会染上同一个病：同模型 + 同 skill 目录 ⇒ 同一个错 | 调研 §9.3；换厂商实测一致率 49.0%（§7.2） |

三条限制同源——**它不在主会话里**。同会话插件一次解掉三条：在会话进程内（看得见）、
挂在每一步的钩子上（来得及）、运行时不调用模型（不犯模型的错）。

### 2.3 三个「匹配」方案被否，是这条路的前提而非反例

调研否掉的是「让某个智能体每轮实时判断该用哪个 skill」（BM25 43.1%、事后补触发词、
换厂商独立模型 49.0%）。这个否证一旦成立，「判断必须离线化」就不是选择、是唯一剩下的路：
判断在离线时炼成判据，运行时只做匹配与提醒。**护士不需要每秒重新思考该递什么刀。**

## 三、技术基础：两个半成品——allostasis 实现了「守」，habit 实现了「炼」

`@max-null/dsh-allostasis` 已经长成这个护士的形态，差别只在「护理项」：

- **它有什么**：三个挂载点（`agent/pre-step` / `llm/stream` / `agent/turn-stopping`）；
  每步读会话内最新内容；判定后追加提醒；同 turn 节流（`admitPerTurn`）；
  判定结果不写会话日志（自定义事件类型会让整份日志被拒读）。
- **它的四条判据**：中文锚定、推理退化、流内掐断、空回合。
- **它缺什么**：
  1. 判据不可增删——**阈值可配（走 `config.ts` 的配置面），判据本身不可配**（判定逻辑在代码里）；
  2. 没有统一的角色状态——每条判据各自为政（`WeakMap` 分散持有）；
  3. 判据之间无关系——表达不了「先 A 后 B」这类跨判据约定。

### 另一半：「炼」已经长在 habit 里

`@max-null/dsh-habit`（自学习习惯引擎）的三段闭环，与我们设想的「炼」高度重合——查过它的
README 与 `src/signals.ts`：

| 环节 | habit 已有 | 落点 |
|---|---|---|
| 发现候选 | 20 条纠正短语 + 200 字上限，确定性、零 token | `src/signals.ts` |
| 触发判断 | 同会话累积 ≥3 条信号 → 才做一次低成本模型调用 | `signalThreshold` 默认 3 |
| 判断输入 | ≤5 条证据 + 既有习惯列表（原则：「质量来自精确上下文，不是数量」） | README §Design notes |
| 人门 | 候选 → UI 确认 → 写进 `dsh-memory`（`suggested` → `auto`）；**模型不能自提升** | README §Service |
| 免疫上下文衰减 | 事件驱动插件，明写「No new agent role」 | README 第 9-10 行 |

**它的产物只有记忆**（自然语言注入，靠模型自觉遵守）。于是生态里出现一个缺口：habit 记录、
allostasis 监督，而**记录出来的东西到不了监督端**——那正是原设想里「它记下的就是它要守的约」
缺掉的那一环。落点决策见 §六。

## 四、判据的生命周期（设计要回答的四问）

| 问题 | 当前判断 | 依据 / 未决 |
|---|---|---|
| ① 谁提出来 | 约定住在记忆里 | `dsh-memory` 已有「规则 / 委托 / 判据」类记忆；约定是它的自然成员 |
| ② 谁炼 | 在会话里炼、人确认后沉淀 | allostasis 的四条判据就是这么炼出来的（先否掉「中文字符占比」「最长英文游程」两个更直观的指标）。模型实时判断不可靠，但一次性炼 + 人复核可行 |
| ③ 炼完放哪 | **能外置，「可增删」成立**（查证见 §五） | 判据分两层：几何在代码、实例在数据；数据面三条载体都有我方先例 |
| ④ 误报怎么改 | 反馈走「人观察 + 在会话里指出」 | 用户明示的设计原则：人的角色是观察者、提醒模型自检，不代替判断。改的动作落在判据本身，不在会话里调参 |

**③ 是技术分水岭**：判据能否放在插件外、可读写、不重载即生效——决定「可增删」是真的还是空的。
**已查证（2026-10-15）：能，而且三条载体都有我方插件的先例。见 §五。**

## 五、判据载体的查证结果（2026-10-15）

### 5.1 判据必须先分成两层

`dsh-allostasis` 的 `config.ts` 已经画出这条线：可配的是**阈值、档位与一段文案**；而小样本门槛
（`MIN_WORDS` / `MIN_UNITS` / `REPEAT_MIN_COUNT`）与实义单元规则**不在配置面**——注释给的理由是
「它们不是偏好，改了就是把密度与比例算飞，**属于判据几何的一部分**」。于是：

| 层 | 内容 | 能外置吗 |
|---|---|---|
| **几何** | 怎么算（密度、窗口累计、比例、求值逻辑） | **不能**，永远在代码里 |
| **实例** | 有哪些判据、参数、适用范围、提醒文案 | **能**，是数据 |

### 5.2 三条载体（都有先例，不是理论选项）

| 载体 | 我方先例 | 谁写 | 生效方式 | 校验 |
|---|---|---|---|---|
| `cordis.patch.yml` 的 config 段 | `allostasis` 的 `silentTurn: steer`；`storage-json` 的 `root: !!js …` | 人（YAML、可 diff、进 git） | Loader 带 live file watching → 改即热重载 | schemastery；格式错误一律 fail loud（顶层非数组、条目非对象、`!!js` 空表达式都报错） |
| `ctx.storageDomain` 领域 KV | `workspace`（`storages-ssid/workspace.json`） | 程序（模型炼完写入） | **读取同步自内存** → 写完对下一个 `pre-step` 立即可见，无需重载 | zod schema，`invalid-record` 会指名表与键；每次写入按序发 `domain/changed` |
| 自有存储区（自注册后端 + KvUnit） | `dsh-guardian`（`engine.ts:139-140` 自建 `JsonStorageBackend` 再 `ctx.storage.backend.register`，落在 `storages-ssid/guardian/`）、`habit` 同 | 程序 | 自己控制重读时机 | 自己负责 |

三条都在思灵当前环境里跑着：`storages-ssid/` 下同时有 `workspace.json`、`session_projcache.json`、
`dsh_automation_center.json`、`schedule.json`、`message_feedback.json`，以及 `guardian/` 与 `habit/` 两个目录。

### 5.3 「不重载即生效」不需要额外机制

`storageDomain` 的读是**内存同步读**（写入在后端持久化之后才改内存），所以判据被改写后，
下一个 `pre-step` 就读到新的——不必订阅事件、也不必重启。

### 5.4 这个答案把第 ② 问变成了选择题

- 判据由**人**写 → `cordis.patch.yml` 的 config：人可读、可 diff、进 git、可 review。
- 判据由**模型**在会话里炼 → `storageDomain` 或自有存储区：程序写入，schema 校验兜底。
- **两者共存**是自然的：几何与求值引擎在代码；实例一部分是人的硬约定（config），
  一部分是炼出来的（存储）。

## 六、落点：做在 dsh-habit（2026-10-15 定）

**决定**：不新造插件，把「学而守」做进 `@max-null/dsh-habit`——判据库与求值引擎都在它里面；
`dsh-allostasis` 继续管它那四条算法式判据，两者不合并。

**理由**

1. **它就是你原本设想的那个「同一个 agent」**：记录者与监督者合一，因为「它记下的就是它要守的约」。
   拆成两个插件，那道桥反而要另外造。
2. **「炼」的前两段它已经做对了**，而且难点都在细节里（确定性观察、阈值触发、窄输入、两级人门），
   重造一遍大概率会踩同样的坑。
3. **它已经有入口**：侧栏「习惯」面板现成，判据可以挂在同一个地方管。

**改造面（四处，都可枚举）**

| 段 | 现状 | 加执行端后 | 改哪里 |
|---|---|---|---|
| ① 观察 | `session/event` 扫 20 条纠正短语，200 字上限 | **再加一类信号**：前瞻性约定（「以后都…」「每次…」）。纠正学出偏好，约定才学出流程；200 字上限对约定不适用 | `src/signals.ts` |
| ② 判断 | 阈值触发一次调用，产物是「习惯描述」 | 产物**分叉**：可形式化的落判据，写不成的照旧落记忆 | `src/analyzer.ts` |
| ③ 沉淀 | 候选区 → 人确认 → 写进 dsh-memory | 可形式化的**进判据库**、其余进记忆 | `src/candidates.ts` + 侧栏面板 |
| ④ 执行 | **不存在** | 挂 `agent/pre-step`（输入侧）与 `agent/turn-stopping`（收尾侧），求值判据并在违反时动作 | 新模块；`index.ts` 的 `inject` 要加 `'agents'`（现在是 `['storage','llm']`） |

**定位随之改变**：habit 现在 README 明写「不向会话注入任何内容」（纯后台沉淀）；加了执行端之后
它会注入提醒。这是有意的定位演进——「行为提示类」在 SSiD 规范里同样豁免截图要求，不是障碍，
但 README 与截图段要跟着改。

**边界（与 allostasis 的分工）**：按判据的**形态**分——allostasis 管算法式（需要自定义计算：
密度、窗口累计、流内掐断），habit 管声明式（观察什么 + 条件 + 要求的动作，也就是学得出来的形状）。
两者都挂在 `pre-step` 上但各值各的班，判据集不重叠。

## 七、未决点

1. **判据 schema 的表达力**——它现在才是真正的边界：不是「能不能外置」，而是
   「一个声明式 schema 能覆盖多少真实约定」。能表达成「观察什么 + 条件 + 要求的动作 + 时间窗 + 文案」
   的，写一段数据即可增删；需要自定义算法的，仍要写代码。
   第一版建议只覆盖单轮局部证据（用户文本 + 本轮 `tool/call`），不碰跨轮状态与跨判据编排。
2. **判据的 schema**：见[判据 schema 草案](2026-10-15-主Agent旁观助手-判据schema草案.md)。
3. **判据的载体**：config 与存储两条路都可用（§5.2）。用户已定「**LLM 炼是主路径、人炼是兜底**」，
   于是主路径落在存储侧，config 留给硬约定。
4. **与 `dsh-assistant-center` 的关系**：那个插件的执行模型是「到点 → 创建全新根 Agent 会话 → 跑任务」，
   服务的是**有自己节奏的执行者**，与「旁观主 Agent」不是一回事。两者同名不同物，不要合并。
