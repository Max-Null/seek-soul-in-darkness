# DSH 作为 AI 中台内核：评估框架（2026-09-10）

> 背景：用户曾考虑以 DSH 作为公司 AI 中台的内核，因当时 DSH 刚发布而未采纳。本文件固化那次判断的依据，并给出未来的就绪判据与可立即采用的中间道路。
> 依据：本工作区对主库的持续观察（`dsh-anatomy/版本对比/`）+ 官方 `AGENTS.md`、`docs/architecture.md` 的原文表述。

> 状态：已决策（推断 · 2026-09-12）

## 1. 当时的判断与依据

不采纳的理由有硬依据，不是印象：

- 官方 `AGENTS.md` 明写 "Public APIs are pre-stable; update every consumer."
- 会话格式处于 v0 → v1 → v2 → v3 的演进中（v3 于 0.1.5-alpha.1 落地，rc.1 与 rc.2 之间仍在补迁移细节）
- 发布节奏：24 天 16 个 tag（08-17 ~ 09-10）；09-08 → 09-10 三天内四个版本
- 无 LTS 概念、无商业支持渠道

结论：不是「简陋」，是「未定型」。

## 2. 就绪观察信号

| 维度 | 2026-09-10 现状 | 就绪信号 |
|---|---|---|
| API 稳定性 | pre-stable，每次变更须更新所有消费者 | 发布 stable（非 rc/alpha）+ 稳定性承诺窗口 |
| 会话格式 | v3 刚落地，迁移机制已建但仍在演进 | 格式冻结，或有 LTS 级别的迁移保证 |
| 发布节奏 | 三天四个版本 | 季度级，且破坏性变更预先公告 |
| 工程成熟度 | test/ci 占比升至 34%（在补基建） | 覆盖率与性能有硬门禁 |
| 支持体系 | 无 LTS、无服务渠道 | 有 LTS 分支与服务渠道 |

一句话判据：**官方开始承诺「某接口 N 年不变」之日，才是可以压上中台之时。**

## 3. 中间道路：把 DSH 当可替换的 Agent 运行时

即使现在，也可以按「可替换」的方式使用 DSH，不必等它稳定：

1. 业务逻辑留在自己的服务里；DSH 只负责 Agent 编排与工具调用
2. AI 能力通过 DSH 的工具/插件暴露，但接口由我们定义
3. 不把 DSH 内部契约写进业务代码（会话格式细节、slot 名、投影缓存结构）
4. DSH 升级时只改适配层；将来替换 DSH 也不伤害业务

这套做法与 DSH 自身的设计哲学相容：官方声明「没有特权内核可改，一切皆插件」，意味着它本来就预期被组合与替换。

## 4. 边界：哪些不是 DSH 的责任

中台化的真正难点不在「能否用 DSH 承载 Agent」，而在：

- 多租户隔离
- 多服务编排
- 长生命周期运维

这三件由中台自己负责。边界划清，DSH 是好用的组件；划不清，它每次升级都会变成故障源。

## 5. 评估节奏

每季度对照 §2 表评估一次，或在下列事件发生时立即重评：

- 官方发布 stable（非 rc/alpha）版本
- 官方宣布会话格式冻结或 LTS 计划
- 官方为插件 API 给出稳定性承诺
- 官方桌面端正式发布（产品化信号）
