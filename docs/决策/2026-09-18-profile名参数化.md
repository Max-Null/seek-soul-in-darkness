# profile 名参数化：`SSID_PROFILE_NAME` 与会话根跟随

> 2026-09-18 · 状态：**已实现并实测**（typecheck / 84 项单测 / 7 门检查 / 隔离冒烟全过）
> 起因：用户提议「profile 放 `~/.dsh/profiles/ssid-dev`」，用于并行开测试实例
> 关联：手册 §3（环境变量与开关）· `docs/决策/2026-09-13-SSiD决策总表-内核升级与壳路线.md`（隔离三件套的来源）

## 一、起因与查证

用户的目标是**让 dev 与安装版能同时跑**，用于自动化测试。三件套（`--user-data-dir` + `DSH_HOME` + `SSID_LOG_FILE`）已经能做到"与运行中的实例零冲突"，但用户的直觉是"给 profile 起个不同名字更干净"，并且担心**会话根互相干扰**。

查证结论分两半：

- **担心成立**：两个宿主并发写同一份会话 JSONL 会反复造成 `corrupt session log: seq gap`（08-22 引入会话根隔离前的实测结论）。
- **但 profile 名不是那个开关**：会话根名是写死的 `sessions-ssid`（`kernel.ts:574`），只跟 `DSH_HOME` 走。留在同一个 `~/.dsh` 下换 profile 名，既改不动（壳里 `PROFILE_NAME = 'ssid'` 与 `main.mjs:298` 的 `join(dshHome,'profiles','ssid')` 都是字面量，无环境变量覆盖），也**不会**隔离会话根，而且 `storages/` 仍与 web、安装版共用——那才是 09-17 覆盖事故的现场。

于是把"名字"这件事做成真正的维度：**profile 名参数化，会话根跟着它走**。

## 二、决策

1. **新增 `SSID_PROFILE_NAME`**，默认 `ssid`。默认值下所有派生路径与历史版本逐字一致（`profiles/ssid`、`sessions-ssid`），升级后的既有实例认得出自己的 profile。
2. **会话根名跟随 profile 名**（`sessions-<名>`）。参数化 profile 而不参数化会话根，等于让两个实例各写各的 profile、却挤在同一份会话日志上——那是最坏组合。
3. **校验与 `resolveProfileDir` 对齐**：拒绝路径分隔符与 `.` / `..` / `node_modules`，避免这个变量把写入带出 `profiles/`。非法值在模块顶层就抛，启动即失败（配置错误应当显式失败，而不是静默落回默认名）。
4. **不动 `~/.ssid/`**：该目录下的路径在壳与插件里都写死 `homedir()`（`heartbeat.log`、`session-root.json`、`pending-plugin-updates/` 等），参数化它要动所有读它的插件，属另一个量级；本次把它记为**已知残留共享面**。

## 三、实现

单一来源 `shell/lib/profile-name.mjs`：`resolveProfileName(env)` 与 `sessionsRootDirName(profileName)`。四个消费点：

| 位置 | 改动 |
|---|---|
| `shell/kernel.ts` | `PROFILE_NAME` 由 `'ssid'` 改为 `resolveProfileName()`；隔离会话根由 `join(home,'sessions-ssid')` 改为 `join(home, sessionsRootDirName(PROFILE_NAME))` |
| `shell/main.mjs` | 顶层新增 `PROFILE_NAME`；`profileDir` 与 codegraph 的 `sessionRoots` 改用它派生 |
| `shell/scripts/boot-bundled.mjs` | 同步（内核闭包冒烟脚本） |
| `shell/scripts/heal-workspace-registry.mjs` | 会话根清单由写死的 `['sessions-ssid','sessions']` 改为扫 `$DSH_HOME` 下所有 `sessions` / `sessions-<名>` 目录（备份后缀 `sessions.bak-*` 不匹配） |

内核侧之所以只有两处：`PROFILE_NAME` 定义在 `kernel.ts`，子进程入口 `kernel-child.ts` 通过 `import { bootKernel } from './kernel.ts'` 复用同一份定义。主进程侧 `profileDir` 也只定义一次，其余全是复用。

**检查门保持看 `ssid`**（`check-bom` / `check-vendor-sync` / `check-profile-sync` / `sync-vendor`）——它们校验的是出厂形态与正式实例的一致性，`ssid-dev` 是开发期产物，不该进这些门。

## 四、证据

- `npm run typecheck`：通过。
- `npm test`：**84 项全过**，其中新增 5 项（`tests/profile-name.spec.ts`）：默认回落、去空白、拒绝非法值、**默认名下会话根与历史目录名逐字一致**、以及跟随分开。
- `npm run check:rules`：**7 门全过**（含 `dsh-clean`：DSH 源码仍只读不改）；bundle 重建后复跑一遍仍是 7 门。
- bundle：`kernel.bundle.mjs` / `kernel-child.bundle.mjs` 重建，内联后可见 `var PROFILE_NAME = resolveProfileName();` 与 `join2(home, sessionsRootDirName(PROFILE_NAME))`。
- **实机冒烟（无 GUI，不占单实例锁）**：在 `H:\MaxNull\WorkStation\.ssid-iso-test` 这个隔离 home 下、`SSID_PROFILE_NAME=ssid-dev` 启动内核——`SSiD boot OK: http://127.0.0.1:64469/ -> HTTP 401`，隔离 home 里落下 `profiles/ssid-dev`、`storages/`、`skills/`、`prompt-library/`；同时**真实环境分毫未动**（`~/.dsh/profiles/ssid` mtime 仍是 03:31:11，`sessions-ssid` 仍是 09-12）。
- 冒烟第一次失败反而是关键证据：错误信息里的 `Require stack: <隔离home>\profiles\ssid-dev\package.json` 直接显示内核按新名字找 profile（默认会是 `ssid`）。失败原因是隔离 profile 还没铺 `node_modules`，补上 junction 后即 boot 成功。

## 五、用法

```powershell
# 隔离实例的 profile：配置拷副本、node_modules 用 junction 零拷贝共用真实插件实体
$iso = "H:\MaxNull\WorkStation\.ssid-iso-test"
$src = "$env:USERPROFILE\.dsh\profiles\ssid"
New-Item -ItemType Junction -Path "$iso\profiles\ssid-dev\node_modules" -Target "$src\node_modules"
# 然后把 package.json / cordis.patch.yml / pnpm-lock.yaml / vendor 拷进副本

# 先行验证（无 GUI）
$env:DSH_HOME = $iso; $env:SSID_PROFILE_NAME = 'ssid-dev'; npm run smoke
# 起完整实例：再加 --user-data-dir 与 SSID_LOG_FILE
```

两个伴生约束：隔离期**不要**设 `SSID_DEV_DEPLOY=1`（profile 是 junction 指过去的，真部署会打穿到真实 profile）；无 GUI 的 `npm run smoke` 需要 `SSID_MCP_CG_WS` 指向一个空目录，否则 codegraph 的首次引导会卡住无人值守启动。

## 六、残留与边界

- `~/.ssid/` 未参数化：并行实例仍共享 `heartbeat.log`、`session-root.json`（会互相回写 `applied`，取值相同故无害）、`pending-plugin-updates/`（内核 boot 前消费，**这是唯一有实际影响的共享点**——并行期别做插件升级，或确保该队列为空）。
- 隔离实例的插件实体与真实 profile **是同一份**（junction），所以它测到的是真实插件行为；但反过来说，**往隔离 profile 装插件会写到真实实体**。
- `SSID_PROFILE_NAME` 只改壳的路径推导，不改变 `BIN_NAME`（`ssid`）——`dsh.loadProfile(bin, profile, …)` 的 bin 名仍是一个。
