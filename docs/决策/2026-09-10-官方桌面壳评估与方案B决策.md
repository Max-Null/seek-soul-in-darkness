# 官方桌面壳（apps/desktop）评估与方案 B 决策

> 日期：2026-09-10 · 状态：方案 B 已选定，可行性验证进行中
> 证据库：`DSHfork` @ `dsh-v0.1.5-alpha.2`（独立观察站，origin=官方主库）
> 证据来源：官方源码 / README、npm registry、GitHub Releases API、CDP 对运行中桌面端的实测
> 相关文档：`dsh-observations/2026-09-09-0.1.5-alpha.2-vs-0.1.2-rc.1.md`

## 1. 背景

用户判断：自建桌面壳（SSiD `shell/`）持续踩坑（部署覆盖丢用户层、更新回滚链、运行时供给），而官方已推出 Electron 桌面壳，其底座值得借用。目标：**以官方壳为底座，改成 SSiD 的样子**。

## 2. 官方壳是什么（事实盘点）

- **位置**：`apps/desktop`（`@deepseek-ai/dsh-desktop`，0.1.5-alpha.2）+ 私有 `apps/desktop-host`
- **分发状态（2026-09-10 实测）**：npm `@deepseek-ai/dsh-desktop` → 404；GitHub Release `dsh-v0.1.5-alpha.2` 的 `assets` 为空 → **官方尚未发布任何安装包，只能从源码构建**
- **许可**：仓库根 `LICENSE` = **MIT**（可修改、分发、商用，保留版权声明）
- **架构要点**（摘自 `apps/desktop/README.md`）：

| 机制 | 官方设计 |
|---|---|
| 运行时 | Electron 自带上游 Node.js（打包时下载 24.17.0）+ 自带 pnpm；不用系统 Node/pnpm |
| 传输 | **不开监听端口**：`dsh-app://` 承载 Web 资产与 Fetch 流量，帧化字节管道承载请求/响应块，Node IPC 只传生命周期控制 |
| Profile | 独占 `$DSH_HOME/profiles/desktop`；CLI 不能 boot 或修改它 |
| 与 CLI 的数据关系 | **共享** sessions / settings / credentials / workspaces / storage；**不共享**可执行包、插件激活、lockfile、node_modules |
| 包来源 | 自带离线 seed store（macOS 分 16 个未压缩 tar 分片）+ 本地打包的第一方 tarball；插件是普通 npm 包，走固定 `https://registry.npmjs.org/` |
| 安装/变更 | staging → 启动完整 backend 健康检查 → 通过才替换 active profile；journal + 一个回滚 profile |
| 更新 | electron-updater + blockmap 差分；Electron 壳与 dsh 版本强绑定为一个签名更新单元 |
| 签名 | macOS Developer ID + 公证（逐个签 Mach-O CAS 对象、重写 pnpm hash）；Windows EV 证书 + SignTool + RFC 3161 时间戳 |
| 单实例 | Electron `requestSingleInstanceLock()`（进程生命周期锁） |
| 已知禁用 | Web 的「Open In…」在 Desktop 被禁用，因为其 host 插件需要 HTTP 路由，而 **Desktop 不提供 `webServer`** |

## 3. 关键约束

1. **DSH 主库只引用不改**（工作区铁律）→ 所有改造必须在 fork 或 SSiD 仓库内完成。
2. **官方壳不提供 `webServer`** → 依赖 HTTP 路由的 host 插件在官方壳内不可用。
3. **官方壳与 CLI 共享 `$DSH_HOME` 的会话数据** → 与运行中的 web 宿主并发访问同一会话根。
4. **官方壳仍在 alpha**（0.1.5-alpha.1 才引入右侧栏；两周内两个版本）→ 直接依赖其 API 有跟进成本。

## 4. 方案对比

| 方案 | 做法 | 拿到什么 | 代价 | 量级 |
|---|---|---|---|---|
| A 品牌层 | 在 fork 里改官方壳外观/文案/图标/启动屏，装 @max-null 插件 | 官方工程能力 + SSiD 外观 | 丢掉依赖 HTTP 路由的插件 | 小 |
| **B 官方壳当底座** | A + 预装 @max-null 插件 + 适配 host↔client 通道 | 外观 + 工程能力 | 需迁移通信层；跟进官方升级 | 中 |
| C SSiD 吸官方机制 | 不换壳，搬离线 seed / staging 健康检查 / 回滚 / 签名链路 | 插件生态完整 + 工程能力 | 自己维护；拿不到官方现成打包流程 | 中 |
| D vendored fork | 复制 apps/desktop 进 SSiD 仓改 | 完全可控 | 与官方迭代脱节 | 大 |

**决策：方案 B**（用户拍板）。理由：官方壳的运行时供给与部署回滚链正是 SSiD 当前痛点所在。

## 5. 方案 B 逐项算账

| 官方机制 | 价值 | 注意 / 代价 |
|---|---|---|
| staging + 健康检查 + 回滚 | **最高**（正对 SSiD 部署覆盖丢用户层、失败崩溃链） | shell 侧逻辑，可独立搬 |
| 自带 Node/pnpm | 高（消除系统环境变量与 pnpm 版本漂移） | 安装包变大；Node 版本跟随官方 |
| 离线 seed 分片 | 高（离线安装 + 差分更新） | macOS 流程重：逐个签 Mach-O CAS 对象、重写 pnpm hash |
| electron-updater + 签名 | 中高（省自写 updater） | 证书/公证账号仍是自己的 |
| 单实例锁 | 中（防双实例抢 profile） | 需与 SSiD 多实例/会话根隔离语义对齐 |
| 帧化字节管道（无端口） | **有争议**：无端口冲突、无认证/CORS 暴露面 | 插件 HTTP 路由失效 |

**唯一需要拍板的矛盾**：要「零端口」就不能保留依赖 HTTP 路由的插件；若补回环 HTTP 服务，「零端口」名存实亡。
**建议**：取「不对外监听」的实质——绑 `127.0.0.1` + 随机端口 + 一次性 token，插件路由可用、局域网不可达。真正值钱的是 staging/回滚与自带运行时，不是绝对零端口。

## 6. 关键发现：我们的插件与官方壳的真实距离（实测）

**教训（重要）**：`package.json` 的 dependencies/peerDependencies **不是** DSH 插件的服务依赖真相——服务依赖用 cordis 的 `inject` 声明。前一轮据此得出的"无插件依赖 webserver"结论是**错的**。

实测（grep `@max-null/*` 的 `src/`）：

| 插件 | 依赖形态 | 官方壳（webServer 已被禁用）结果 |
|---|---|---|
| `dsh-memory`（host 半） | 静态必需：`inject = ['storage','systemPrompt','tools','webServer','webRuntime']` | **静默不激活**（cordis 语义已实测，见 §8.1） |
| `dsh-capture` | 静态必需：`inject = ['webServer','webRuntime']` | 静默不激活 |
| `dsh-draft-polish` | 静态必需：`inject = ['webServer','sessionQuery','llm','loader']` | 静默不激活 |
| `dsh-ssid-achievements` | 静态必需：`inject = ['tools','webServer','webRuntime']` | 静默不激活 |
| `dsh-chat-rail` | 动态可选：`ctx.inject(['webServer'], …)` | 激活，路由相关功能降级 |
| `dsh-quick-toolbar` | 动态可选：`ctx.inject(['webServer','connection'], …)` | 激活，同上 |
| `dsh-memory` → betterSidebar | 动态可选：`root.inject(['betterSidebar'], …)` | 优雅降级（面板入口不注册） |

**两条替代通道（详见 §8.3）**：① 轻量——`ctx.connection.fetch.register({ path, methods, requestBody, fetch })`（carrier-neutral 精确路由，走 `/api`，Web 载体与 Electron shell 载体都分发同一个 handler）；② 正规——`@deepseek-ai/dsh-api-remotes`（Typert 类型化 RPC + API Gateway）。**不需要自建 webServer 桥**。

**关于 better-sidebar**：它是第三方插件（`omdsh-dev/DSH-better-sidebar`），SSiD 只是**预制**了它，**不是自有资产**。它能否在官方壳里跑是它自己的适配问题，不应绑住 SSiD 的架构决策。

## 7. 已实测的官方壳行为（2026-09-10，CDP + 源码）

1. **`DSH_HOME` 未隔离**：`dev.ts` 写的是 `process.env.DSH_HOME ?? <DSHfork 内部路径>`，而 shell 里已有 `DSH_HOME=C:\Users\MaxNull\.dsh`，隔离默认值被短路 → 桌面端直接使用主 home，并写入了 `storages/`、`workspace.json`、`session_projcache/`。
2. **会话视图不同步**：`desktop-host` 内无任何 watch/poll/subscribe（grep 为空）→ 桌面端只读到启动时的快照，web 侧后续写入不反映。
3. **导航条被容器查询隐藏**：`TurnNavigator.module.css` 有 `@container (max-width: 900px) { .slot { display: none } }`，`ChatView.module.css:20` 有 `container-type: inline-size`（规则确实生效）。窗口 1264px + 右侧栏 301px → 聊天区约 678px → 展开后导航条实测 `w=0`（隐藏），**不是被遮挡**；`elementFromPoint` 命中导航条自身（`hitIsNav=true`）。过渡动画期间两者不同源，可能出现短暂重叠（未实测到）。
4. **官方右侧栏 API 面**：`ctx.sidebarRightTabs.register({ id, kind, patterns?, priority?, canOpen?, title, guide? })` + 主体注册到 keyed slot `sidebar.right.pane.tab`；优先级档 `extension > builtin > fallback`，且**扩展可接管内建**（内建与扩展各占一格，只渲染生效的那个）；控制器 `openResource/openTab/focus/split/float/dock/_undo/_redo`。
5. **官方桌面端无市场/发现入口**：只有已安装插件的 list/install/remove/update，来源固定为 npm registry。

## 8. 验证结果（2026-09-10 实测）

### 8.1 cordis `inject` 语义（最小实验：`DSHfork/.tmp-cordis-inject-probe.mjs`）

| 用例 | 结果 |
|---|---|
| 静态 `inject: ['webServer']`，服务从未提供 | `pending` —— **插件静默不激活，无报错、无警告** |
| 静态 inject，注册后再提供服务 | `pending` → `applied` —— 服务出现后自动激活 |
| 静态 inject，注册时服务已存在 | `applied` |
| 动态 `ctx.inject(['webServer'], cb)`，服务缺失 | `not-run` —— 回调不执行（安全降级） |
| `inject: { required: [], optional: ['webServer'] }` | `pending` —— 该写法在 cordis 4.0.0-rc.7 下**不生效** |

**结论**：静态 `inject` 缺失服务 → 插件**静默失效**（功能消失且无任何提示，最危险的一种）；动态 `ctx.inject` → 优雅降级。这解释了为什么插件在换壳后"看起来装上了却没反应"。

### 8.2 官方桌面端在配置层面禁用了 webServer

`apps/desktop-host/config/desktop.cordis.patch.yml` 开头即：

```
# Electron reuses the browser composition without its network and browser-launch rows.
- id: web-startup
  disabled: true
- id: webserver
  disabled: true
- id: web-runtime
  disabled: true
- id: client-hmr
  disabled: true
- id: open-in-app
  disabled: true
- id: ui-open-in-app
  disabled: true
- id: directory-picker
  disabled: true
```

→ 与 README 的「Desktop does not provide a `webServer`」一致，且是**配置层面的硬禁用**。我们的 4 个静态依赖 `webServer` + `webRuntime` 的插件在官方壳里会静默失效。

### 8.3 官方给了替代通道（不必自建 webServer 桥）

`@deepseek-ai/dsh-client-connection` 提供 **carrier-neutral** 的精确路由注册：

```
ctx.connection.fetch.register({ path, methods, requestBody, fetch })  // 返回 disposer
```

- Web 载体（浏览器 HTTP）与 shell 载体（Electron IPC 桥）**分发同一个 shared fetch handler**
- `desktop-host` 的 fetch 桥把 `/api` 前缀请求交给 `connection.createSharedFetchHandler('/api')`；其余走 `assetHandler`（只处理 `/plugins/` 与静态资源）
- 路径为**精确匹配**（`fetchRoutes.get(pathname)`），未认领请求返回 404

→ 插件把 `ctx.webServer.register(...)` 换成 `ctx.connection.fetch.register(...)`（路径在 `/api` 下）即可在官方壳内工作；更重的场景再迁 Typert remote。

## 9. 实施策略（若验证通过）

1. **不要整体复制官方壳**：保持目录结构对齐 + 定制点收敛为补丁面（品牌资源、i18n 词典、desktop profile 的 seed 清单、通信通道适配）。
2. **分阶段取**：第一刀只切 `staging → 健康检查 → 回滚` + 自带 Node/pnpm（不碰端口语义，收益立即可验证）；第二刀再决定是否换掉帧化管道。
3. **跟踪策略**：定期 merge 官方 master，保持目录与命名对齐，冲突面最小化。

**改动**（`max-null-plugins/dsh-capture`）：

- `src/index.ts`：`inject` 从 `['webServer','webRuntime']` → `['connection']`；三条路由（get/set/trigger）从 `ctx.webServer.register({ kind:'prefix', path:'/ssid/api/screenshot' })` 改为 `ctx.connection.fetch.register({ path:'/api/ssid/screenshot/<method>', methods:['POST'], requestBody:'buffered', fetch })`；handler 从 node:http `(req,res)` 改为 Fetch `(request) => Response`；删除自建 Host/Origin fence（carrier 已统一应用 trust/auth）

### 10.2 任务②：chat-rail / quick-toolbar 在官方壳的挂载分析（已完成）

| 插件 | 静态 inject | 依赖 webServer 的功能 | 官方壳（无 webServer）结论 |
|---|---|---|---|
| `dsh-chat-rail` | **无** | 仅 `favoritesRouteDefinition`（收藏路由） | 激活；轮次导航（走 `sessionProjections`）正常，收藏功能降级 |

## 11. 双轨兼容结论与可反馈项（2026-09-10）

### 11.1 `connection` 在 web 端同样存在 → 改造是单向的

`packages/bundle/web-app/cordis.patch.yml` 含 connection 行：

```
# Owns both ends of the web transport: node half binds the gateway to the
# webserver under /api; browser half is the fetch/SSE client.
- id: connection
  name: '@deepseek-ai/dsh-client-connection'
  inject: [webRuntime]
  config:
    trustedHosts: !!js ctx.webRuntime.trustedHosts
```

即：**web 载体下 connection 把路由挂到 webserver 的 `/api`；桌面载体下由 shell 直接分发**（`desktop.cordis.patch.yml` 保留 connection、只禁 webserver/web-runtime）。因此用 `ctx.connection.fetch.register` 注册的路由**两端都可达**——从 webServer 迁到 connection 是**单向迁移**（改一次，两端都能跑），不是二选一。

唯一共同约束：路径必须在 `/api` 之下（两种载体都满足）。

### 11.2 可反馈给官方：把 desktop-host 的分发改成"先查路由表"

现状（`apps/desktop-host/src/index.ts`）：

```
pathname.startsWith('/api') ? await api.fetch(request) : await assets.fetch(request)
```

即先按前缀筛、再查路由表。若改为**先查 connection 路由表、未命中再走静态资源**，插件就能注册任意路径（包括 webServer 风格的 `/ssid/api/...`），实现"可变轨"。

**边界**：这只解决路径问题；handler 形态（node:http `(req,res)` → Fetch `(request)=>Response`）与 prefix → 精确匹配仍需插件侧改造。真正的零改造需要官方维护一层完整的 `webServer` 兼容垫片，那是另一个量级的维护负担。官方是否愿意改未知，但**我们自己的 fork 落地方案 B 时顺手改这几行是低成本收益**。

## 12. 适配规范草案（待适配完成后升格为《SSiD开发手册》§9 正式规范）

> **状态：草案 / 待验证。**
> 升格条件：① 在一个 rc.1 环境（SSiD dev 或 web profile）实测通过；② 至少一个插件（`dsh-capture` 已完成改造）在两种载体上跑通。
> 升格去向：`docs/SSiD开发手册.md` §9「插件开发与测试规范」新增小节「host 侧通信通道」。

### 12.1 规范条文（草案）

1. **host 侧新增 HTTP 端点一律用 `ctx.connection.fetch.register`**，不用 `ctx.webServer.register`。
   理由：`connection` 是 carrier-neutral（web 载体把路由挂到 webserver 的 `/api`；Electron shell 载体由帧化管道直接分发），而 `webServer` 只在 web 载体存在，官方桌面端已在配置层禁用。
2. **路由路径必须在 `/api` 之下**（如 `/api/ssid/<plugin>/<method>`）。两种载体的分发都只把 `/api` 前缀交给 connection 路由表。
3. **精确路径匹配**：一个 `kind: 'prefix'` 路由要拆成若干条精确路径（未命中即 404）。
4. **handler 用标准 Fetch API**：`(request: Request) => Promise<Response>`，不再用 node:http 的 `(req, res)`。
5. **不要自建 Host/Origin fence**：carrier 在 handler 运行前已应用信任与鉴权策略。
6. **注入声明用 `inject: ['connection']`**；避免静态 `inject` 里出现 `webServer` / `webRuntime`——静态声明缺失服务会让插件**静默不激活**。
7. **客户端请求路径与 host 注册路径保持一致**（同为 `/api/...`）。

## 13. 暂缓推进决策（2026-09-10 拍板）

### 13.1 rc.1 与 0.1.5 的 connection 断代（实测）

| | rc.1（当前 SSiD / web 内核） | 0.1.5-alpha.2 |
|---|---|---|
| `ConnectionFetchMethod` | `'GET' \| 'HEAD'` | `'GET' \| 'HEAD' \| 'POST'` |
| `ConnectionFetchRoute.requestBody` | 无 | 有（buffered / streaming） |
| connection 的 `inject` | `['webServer','credentials']` | `['credentials']` |
| 路由实现 | `ctx.webServer.register(route)` | carrier 直接分发 |
| 无 webServer 时 | connection 也不激活 | connection 仍可用 |
| 本质 | webServer 的包装层 | carrier-neutral |

**结论**：`connection.fetch.register` 的 carrier-neutral 语义是 **0.1.5 才引入的**；rc.1 上它只是 webServer 的语义包装，且不支持 POST。连锁影响：

- 本次 `dsh-capture` 改造（POST + `requestBody`）**在 rc.1 上不可用**，不能同步进 SSiD dev；
- 方案 B（官方壳做底座）的**前提是内核升到 0.1.5+**；
- §12 规范草案需加版本分界；升格前置 ① 判定为**不成立**。
