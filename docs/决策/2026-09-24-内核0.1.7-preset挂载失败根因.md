# 2026-09-24 内核 0.1.7 适配：preset 全线挂载失败的根因与修复

## 现象

SSiD dev（Electron + tsx 跑源码）升级到 DSH `0.1.7-rc.2` 后，**每一个 agent preset 的每一行都挂载失败**：

```
agent-preset/invalid: persona (@deepseek-ai/dsh-persona): prompt section
"deployment:persona-prefix" is already registered
tool-subagent: standing `modelSelectionSettings` requires a scoped preset Context
```

后果：`initial Session restoration failed: SessionCreateError`，**无法创建会话**。

## 关键取证（活体内核 + CDP）

用 `SSID_KERNEL_INSPECT=1` 给 kernel-child 挂 Node inspector，再用 `cdp-probe.mjs` 连进去问状态（见「调试手段」节）：

| 观测 | 值 | 含义 |
| --- | --- | --- |
| `agentPresets.list()` | 5 个 preset 全部 `broken` | 不是 persona 一条的问题 |
| `systemPrompt.layers.scoped.size` | `0` | **没有任何 scope 层被建立** |
| standard 的报错行 | 只有 persona + tool-subagent | 这两条是全局层真实占用 |
| ptc / cordis 的报错行 | 19 条，含 `tool:pwsh`、`tool:read`… | 这些是**被前一个 preset 污染**的 |
| `createScope` + `scopeOf` 自测 | 正常 | scope 原语本身没问题 |

对照实验：用官方 `@deepseek-ai/dsh/profile-boot` 的 `runProfile()` 在**同一 profile、同一闭包**上启动，`scoped = 4`、preset 正常。→ **不是 DSH 的问题，是壳的装配问题。**

## 根因：同一个包在进程里被加载了两份

`@deepseek-ai/dsh-scope` 的 `kScope` 是**模块级私有 Symbol**：

```ts
const kScope = Symbol('dsh.scope')          // 每个模块实例一个
export const scopeOf = (ctx) => ctx[kScope] // 用自己那份 symbol 去读
```

于是同一个包有两份实例时，「给 ctx 打 scope 标记」与「按标记找回 scope」用的是**不同的 Symbol**，scope 永远读不回来 —— 每一行都注册进全局层，第二行起就撞名。

实测到的两份来源（用 resolve 钩子打点得到）：

| 导入方 | 解析结果 |
| --- | --- |
| `dsh-agent-preset-registry/lib/index.js`（在 `node_modules/` 内） | profile 闭包 `…/node_modules/@deepseek-ai/dsh-scope/lib/index.js` |
| `dsh-system-prompt`（被 tsx 的 paths 解析到 checkout 源码） | checkout `deepseek-harness/packages/core/scope/src/index.ts` |

触发条件是 `shell/tsconfig.json` 的 `paths`：dev 形态下 tsx 会把 `@deepseek-ai/dsh-*` 指向 checkout 的 `src`，而 tsx 的 paths **不作用于 `node_modules/` 内的文件** —— 两类发起方各拿一份。

装版没有 tsx，全部走闭包，只有一份，所以只有 dev 坏。

## 修复

`shell/module-resolution.ts` 的 resolve 钩子：**`@deepseek-ai/dsh-*` 一律停在 profile 闭包**，不论发起方是 loader、闭包内的文件，还是被 tsx 解析到源码的包。

关键点是用 `createRequire(profileBaseUrl).resolve()` 求值 —— 它走 Node 的解析器、不经 ESM 钩子，因此**绕开 tsx 的 paths**。原先「把 parentURL 换成 profile 再交给下一个解析器」的做法会被 tsx 截胡。

两处必须保持的边界：

- **`cordis` 系（`@deepseek-ai/cordis`、`cordis-plugin-*`）不能收进闭包**：dev 下它们是 checkout 源码、loader 也来自同一份源码，换掉会造成源码 loader × 闭包 cordis，实测报 `does not provide an export named 'FiberState'`。
- 闭包里没有的 bare specifier 仍走原来的 parentURL 重写。

另需补齐 profile 闭包缺的三个传递依赖（它们是 peer，装闭包时容易漏）：
`@deepseek-ai/dsh-ptc-runtime`、`@deepseek-ai/dsh-deepseek-account`、`@deepseek-ai/dsh-llm-deepseek`。缺了会表现为对应行的 `failed to import`，进而让 `standard` / `cordis` preset 挂在 `workflow-ptc: waiting for ptcRuntime`。

## 验证

修复后：`scoped = 5`，四个 preset 全部正常挂载，主日志零错误行，`SessionCreateError` 消失。

## 调试手段（保留）

排查这类「活体内核状态」问题，不必靠改代码重启：

1. `SSID_KERNEL_INSPECT=1` 启动隔离实例 → `host-process.mjs` 给 kernel-child 挂 `--inspect=0`，端口打印进 `ssid-dev.kernel.log`。
2. kernel-child 把内核挂到 `globalThis.__ssid_kernel`（仅一行引用，无行为副作用）。
3. `.ssid-iso-test/cdp-probe.mjs <port> <expr.js>` 用 CDP 在宿主进程里求值。

注意：`Runtime.evaluate` 不能动态 `import()`（`ERR_VM_DYNAMIC_IMPORT_CALLBACK_MISSING`），要求值就用同步表达式。

## 与社区的对照

同一族问题在社区反复出现，根因描述一致：

- DSH Discussion #3557：`profiles/node_modules` 是符号链接农场以保证**模块级状态如 `kScope` symbol 互通**，但 pnpm hoisting 把 `@deepseek-ai/*` 以真实副本装进 profile → 两个模块实例 → symbol 对不上。
- DSH Discussion #4727 / #6342：`preset failed to mount` + `prompt section "deployment-persona" is already registered`。
- 多个桌面壳（DSH-EAC、myYangyunfan 等）写了 `profile-module-heal` 做同一件事：清掉遮蔽 fallback junction 的真实目录副本。
