## 1. 自动合成翻译配对记录

`2026-08-08-automatic-translation-pairing-merges.md`

### 他们遇到的事

第 01 批读过的那套双语配对记录，在合并时暴露了一个结构性问题：

> Two branches that independently update different parts of the same confirmed pair therefore **conflict on both hash lines even when Git cleanly composes both Markdown owners**.

两个分支独立更新同一个已确认配对的不同部分——**即使 Git 干净地合并了两侧的 Markdown，也会在两行哈希上冲突**。而选择任何一侧都会留下陈旧的哈希，**手工重新生成记录则是在重复一个确定性操作**，并**阻止了一次本来可以是自动的合并**。

### 判断：让合并驱动重新推导，而不是选择一侧

用一个仓库自有的 `dsh-translation-pairing` **合并驱动**：

- 解析 ancestor/current/other 记录，加载它们哈希命名的**六个 owner blob**
- **独立地为英文和中文三件套运行 Git 的默认三方文本合并**，要求两个都干净
- 验证语言切换器与配对结构签名，把两个合并后的 blob 的**哈希写成规范记录**
- **它合成的是双方父提交中已经存在的确认；它从不记录一次普通的单边文档编辑**

最后一句是这套机制的安全边界：**它能自动合成的，只有"两边都已经确认过"这一种情况。**

### 本批最值得记的一处设计："算不出来时不假装算出来了"

Git 的驱动通过一个**签入的 shell 启动器**调用（启动器本身不需要 Node），而启动器在每次执行前会**探测运行时和入口点**。探测失败时：

> When the runtime or entrypoint is unavailable, the launcher **materializes Git's ordinary three-way text result in the sidecar but returns a conflict even when that text merge is clean**, so Git retains the unmerged index stages and **never accepts unverified metadata**.

**它把 Git 的普通三方文本结果物化到 sidecar 里，但即使那个文本合并是干净的，也返回冲突。**

**它明明能算出一个结果，却拒绝让这个结果被当作有效。** 因为那个文本结果**没有经过驱动的那套校验**（六个 blob 的哈希、语言切换器、结构签名）。**用未经校验的结果冒充校验过的结果，比明确失败更危险**——这是模式 A（诚实的空白）到目前为止最强的一个形态：不是"我不知道所以留白"，而是"**我能给出一个看起来对的答案，但我知道它没被验证过**"。

### 一张失败契约表

他们为正常 `git merge` 期间的每种失败写明了**可观察状态**与**恢复方式**：

| 失败 | 可观察状态 | 恢复 |
|---|---|---|
| 全新安装无法探测驱动或装 Lefthook | 不发布新配置；任何新加入的集成**被回滚到先前的 hook 查找** | 恢复依赖并重跑安装器 |
| 安装后 Node/tsx/入口点变得不可用 | 合并在 sidecar 处于 `UU` 时停止，索引阶段 1/2/3 保留，`MERGE_HEAD` 存在，不创建提交 | 恢复依赖并跑解析器，或 `git merge --abort` |
| 驱动拒绝记录 | 合并停止，驱动打印 owner 修复与显式解析器路径 | 修复后跑打印出的流程或中止 |
| 驱动进程以高于 128 的状态崩溃 | **Git 中止合并策略，不发布 `MERGE_HEAD` 或未合并索引阶段** | 修复运行时并重跑合并 |
| `pre-merge-commit` 拒绝一次本来干净的合并 | 无未合并条目残留，完整结果带 `MERGE_HEAD` 被暂存，不创建合并提交 | 修复 hook 并 `git commit`，或中止 |

**"可观察状态"这一列很有价值**：它把"出问题时你会看到什么"变成契约的一部分——**恢复的第一步是识别，所以识别条件必须写下来。**

### 两处"防止误认为完成"的设计

**① 部分成功必须非零退出。**

`resolve-translation-pairing-conflicts` 在合并停止后应用同样算法：

> It writes and stages every safe record as one batch even when another pair still needs manual work, then reports the remaining pairing conflicts and **exits unsuccessfully so callers cannot mistake a partial resolution for a completed merge**.

**它把每个安全的记录作为一批写入，即使另一对仍需手工处理**——然后**非零退出**，因为"调用者不能把一次部分解析误认为完成的合并"。

**② hook 只验证，不重新生成。**

> They validate driver output but **do not regenerate records**, so **bypassing a hook cannot silently bless translation drift**; the corpus-wide `doc-sync` check remains authoritative in CI.

**它们验证驱动输出，但不重新生成记录**——于是**绕过 hook 不能静默地祝福翻译漂移**。

如果 hook 顺手重新生成，那"绕过 hook"就变成了"用陈旧记录蒙混过关"的通道。**验证与生成分开，让绕过失效。**

### 凭什么这么判断（4 个被否决方案）

| 方案 | 否决理由 |
|---|---|
| 取 ours 或用 Git 的 union 驱动 | 任何一侧的父记录命名的都是**合并前**的内容，而 union 会产生重复或无序的哈希键。**两者都不代表合并后的 owner** |
| 在 `post-merge` 或只在 commit hook 里重新生成 | **`post-merge` 在冲突合并后不运行**，无法影响其结果；**commit hook 只在索引已无未解决条目之后才到达**——单独一个 hook 清不掉那个生成的冲突 |
| **把每次合并都包进一个仓库命令** | 包装器能解析，且显式解析器保留了那条恢复路径，**但裸 Git、stack 工具、rebase 和 cherry-pick 仍然会在它之前停下来** |
| 在 GitHub 上通过 Actions 或 app 解析 | 托管自动化可以更新 PR 分支，**但它增加凭据、并发控制和分支变更**；本地与 agent 驱动的 merge-forward 工作流**已经有 checkout 和 push 权限**，仓库**让远程自动化远离这个机制** |

第 3 条是一个关于**介入层次**的判断：包装某一个命令，只能覆盖"用那个命令"的路径；而**合并驱动是所有那些操作共享的文件级扩展点**。**选介入点时，要选在"所有相关路径都必经"的地方，而不是"你恰好会用的那条路"上。**

### 他们承认的代价

- **GitHub 托管的可合并性计算不运行 worktree-local 的可执行文件**，所以贡献者或 agent **仍然必须合并 base 并推送结果提交**，远程冲突徽章才会清除
- 自动合成**依赖已安装的 Node 依赖**；**运行时丢失会产生一个可见的未解决文本结果，而不是选中陈旧的元数据**（"失败要可见"）

## 2. 浏览器第三方库作为构建输入

`2026-09-08-browser-third-party-build-inputs.md`

### 他们遇到的事

预构建的浏览器插件**把第三方实现内联在 JavaScript 里**，但生产 npm 依赖**仍然让安装器单独下载那些库并解析它们的 peer**。后果具体到版本：

> When React is declared only for development, **installers can select a different React version for those extra dependencies than the browser artifact uses**.

而且明确排除了"这是版本问题"的可能：**相关两个包都支持当前的 React 18，这个问题不需要 React 升级。** 它是**分类**问题。

### 判断：两个事实要分开

决定本身简单——**纯浏览器的第三方依赖属于 `devDependencies`**。但支撑它的判断是本批最锋利的一处：

> **License classification follows distributed content.** ... resolved third-party implementations **remain runtime disclosures even when manifests declare them for development**.

**许可证分类跟随"分发的内容"**——通过真实浏览器构建配置解析出的第三方实现，**仍然是运行时披露，即使 manifest 把它们声明为开发依赖**。

而反方向同样成立：**测试工具、被擦除的类型导入、构建工具，不会仅仅因为出现在 `devDependencies` 里就变成分发的代码。**

被否决的那个方案把这件事说得最清楚：

> **Distributing browser code and having an installer download a same-named package are different facts**; that distinction cannot remove license checks on distributed code.

**"分发浏览器代码"与"让安装器下载一个同名包"，是两个不同的事实。** 同一个 manifest 区段，回答**"要不要下载"**和**"要不要披露"**是两个不同的问题——**用同一个字段名去回答两个问题，必然在某一头出错。**

### 另外三条判断

- 分类器**从源码导入和 JSX 收集构建输入**；**Host 运行时可达的第三方库优先作为 `dependencies`**；**类型 only 的源码引用不产生 Host 运行时依赖**
- **npm 区段不选择浏览器打包行为**：动态插件内联私有库并从平台表获取 React；静态浏览器库保留裸导入和样式给最终的 Vite 构建
- **许可证解析同样不得依赖现有的 `lib/` 文件或写构建输出**（分类保持基于源码）

### 凭什么这么判断

| 方案 | 否决理由 |
|---|---|
| 声明另一个生产 React，或覆盖 peer 解析 | **保留了一个浏览器并不使用的额外安装图，而没有让那个安装的副本成为浏览器的共享实例** |
| 提前内联每个静态库依赖 | **改变了 Vite 的第三方 chunk、缓存与 CSS 处理**；而分类并不需要那些构建改动 |
| 移动每个含 Client 包的第三方依赖 | 双面包**仍然加载 Host 库**（ZIP 用的 `fflate`、RPC 校验用的 `zod`）；**那些安装关系必须保留** |
| 直接按 manifest 区段分类许可证披露 | 见上——两个不同的事实 |

第 2 条值得单记：**分类问题不要顺手改构建**。**改变打包行为是另一个问题，把它混进来会让这次改动既难评审又难回滚。**

### 他们承认的代价

> Developers independently consuming static packages or public types **supply the corresponding build dependencies themselves**; this decision **adds no standalone browser-library support promise**.

**独立消费静态包或公共类型的开发者需要自行提供构建依赖**——而且明说**这个决定不增加任何独立的浏览器库支持承诺**。**受益者之外还有受损者，写清楚。**

## 3. 取消被取代的 CI 验证

`2026-09-09-cancel-superseded-ci.md`

### 他们遇到的事

> Validation of an obsolete PR revision or master commit **consumes runner capacity without establishing the newest revision's status**.

对一个**过时**的修订做验证，**消耗容量却不确立最新修订的状态**。而附带的一句指出隐性成本：**无条件的聚合裁决和覆盖率历史上传，还会让被取消的运行继续做簿记。**

### 判断：三种义务，三种条件

这篇的核心是**把 `always()` / `!cancelled()` 按义务拆开**：

| 用途 | 条件 | 理由 |
|---|---|---|
| PR 聚合裁决 | `!cancelled() && github.event_name == 'pull_request'` | **显式的 status 函数在依赖失败/跳过之后仍保留求值**，而不是接受 GitHub 默认的 success-only 条件 |
| 覆盖率时长历史 | `!cancelled()` | **失败的覆盖率仍能保存有用的测量；被取消的覆盖率不上传它们** |
| Wine 资源清理 | `always()` | **仍然是必要的资源清理，而不是可选簿记** |

被否决的那个"大简化"把区别点明了：

> **Replace every `always()` condition.** ... **Failure aggregation and resource cleanup have different obligations.** A success-only aggregate **can hide failed dependencies behind a skipped required check**; removing unconditional Wine cleanup **can leave resources running**. **Only cancelled-run bookkeeping is suppressed.**

**失败聚合、资源清理、被取消运行的簿记是三种不同的义务。** 一个 success-only 的聚合**能把失败的依赖藏在一个被跳过的必需检查后面**——这是**最危险的那一类简化：它让失败看起来像通过**。

### 一条原则性的豁免

发布自有的构建被排除在取消之外，理由只有一句：

> Release-owned builds are exempt because **they belong to an intentional publication transaction**.

**它们属于一次有意的发布事务。** 判据由此清楚：**过时的验证可以取消，因为它的价值随新版本出现而贬值；而一次有意的发布事务不会因为"有更新的提交"而失效。**

### 一次"明确接受代价"的政策反转

这篇**逆转**了更早的故障切换运行手册里的取消豁免。难能可贵的是它**完整记录了旧政策的理由**，而不是一句"过时了"：

- 旧豁免（`github.event_name != 'push'`）**偏爱周期性的就绪证据**：每个 standby 用一个门 worker 执行完整的未分片聚合，**可能比 master 合并之间的间隔还长**
- **即使那个政策也不保证每次演练都完成**
- GitHub **每个组只保留一个待处理运行，替换中间的待处理推送**；而取消是在新触发的运行上求值的，所以一个共享 master 组的手动基准**仍然可能取消一次演练**
- 那次罕见的中断**被接受，预期后续推送会提供证据**
- 旧政策的成本**被 master-only 运行时检查、Wine 和两次演练所界定**

然后是结论，写得毫不含糊：

> This policy is rejected in favor of **freeing capacity for current validation, explicitly accepting standby starvation**.

**这个政策被否决，以换取为当前验证腾出容量，明确接受 standby 饥饿。**

**"explicitly accepting"** —— 他们知道新政策会让 standby 演练饿死，并把它写出来，而不是假装没有代价。

### 凭什么这么判断

| 方案 | 否决理由 |
|---|---|
| 保留正在运行的 master-push 演练 | 见上（旧政策的完整成本被摊开后否决） |
| **用 job 级 concurrency 保护一次演练，或只取消 PR 事件** | **job 级组不能把一个 job 从整个 workflow 的取消中豁免**；只取消 PR 也会豁免手动 dispatch——**一次重复的 runner 基准可以占用十二个 larger runner 长达十五分钟，而不是替换一次过时的测量** |
| 保留每次合并后、夜间和 pack 运行 | 历史完成度提供更多证据，**但过时的验证会与最新的运行竞争**；而且这些验证**不发布包**，所以保留每一次运行**与保护一次有意的发布事务不是同一个要求** |
| 替换每个 `always()` | 见上——三种义务不同 |

### 他们承认的代价（含一句关于"承诺"的澄清）

- **快速的 master 更新可以重复取消更长的 standby 演练，在它们产生裁决之前**。运维必须使用最新的**已完成**裁决，**检查它的年龄和提交**才能依赖它；**一个已调度、运行中、或被取消的演练不是就绪证据**
- 政策**不保证**每个中间提交、夜间触发或基准完成
- 最后一条尤其精确：

> Cancellation is a **request** handled by GitHub Actions and its runners, **not a guarantee of immediate termination or bounded queue delay**. ... The policy **makes obsolete validation cancellable; it does not promise a fixed runtime or cancellation latency**.

**"让过时的验证可被取消"不等于"取消会及时发生"。** 他们把能力的边界说清楚，**不把"可取消"包装成"能省多少时间"**。

## 对索引里跨批模式的印证

**模式 A（诚实的空白）——第 7 次，且是最强形态。**

启动器那处设计：**它能算出一个干净的文本合并结果，却仍然返回冲突**，因为那个结果没经过驱动的校验。这比前几次的"标注缺失"或"公开不利数据"更进一步：**它主动放弃一个看似可用的答案，只因为它没被验证过。**

**模式 C（别把不同的事混成一种状态）——强印证。**

三种 `always()` 义务的拆分、以及"分发代码 vs 下载同名包"的拆分，都属于这条。而且这次出现了它的**危险形态**：**success-only 的聚合能把失败的依赖藏在一个被跳过的必需检查后面**——**混淆两种状态时，错误的方向是"把失败显示成通过"。**

## 这批的共同判断标准

**① 同一个字段名不该回答两个问题。**
`devDependencies` 回答"安装器要不要下载"，但**不能**回答"要不要披露"；`always()` 回答"要不要无条件执行"，但**不能**区分"失败聚合"和"资源清理"。**当一个字段名开始承担第二个问题时，错误就藏在两者的差集里。**

**② 算不出来时，不要给出一个看起来对的答案。**
启动器明明能产出干净的文本合并，却返回冲突——因为**未经校验的结果冒充校验过的结果，比明确失败更危险**。这是模式 A 的判据，也是这条标准最纯的表述。

**③ 选介入点，要选在所有路径都必经的地方。**
包装一个命令只能覆盖"使用那个命令"的场景；**合并驱动是裸 Git、stack 工具、rebase、cherry-pick 共享的文件级扩展点**。

**④ 部分成功必须非零退出。**
"调用者不能把一次部分解析误认为完成的合并。"**能做完多少就做多少，但汇报时必须说"没做完"。**

**⑤ 失败契约要含"可观察状态"。**
那张表有三列：失败、**可观察状态**、恢复。**恢复的第一步是识别，所以识别条件属于契约。**

**⑥ 验证与生成要分开。**
hook 只验证不重新生成，所以**绕过 hook 不能静默祝福漂移**。**如果验证会顺手修正，绕过它就成了作弊通道。**

**⑦ 政策反转时要记录被否决政策的完整理由。**
他们写下了旧豁免当初要保护什么、它的成本被什么界定、以及**"明确接受 standby 饥饿"**。**记录代价，而不要假装新政策没有代价。**

**⑧ 说清能力的边界，不把"可取消"包装成"会变快"。**
"取消是一个请求，不是立即终止的保证""它让过时验证可被取消，不承诺固定的运行时长或取消延迟。"
