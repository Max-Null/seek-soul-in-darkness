## 四、差异化判断：它们做的是"流程"，我们要做的是"判据"

**两者都在做人类软件工程方法论的 agent 化**——TDD、代码评审、系统化调试、计划、头脑风暴，这些都是人类开发者熟悉的流程，被写成 skill 给 agent 执行。

**我们的材料来源完全不同**：

| 维度 | 两个移植项目 | 我们 |
|---|---|---|
| **来源** | obra/superpowers、Matt Pocock（**作者个人经验**） | **DSH 官方 47 篇决策记录 + 12 个官方 skill + 974 篇 Agent Note** |
| **内容性质** | **流程**：先做什么、后做什么 | **判据**：凭什么这么判断 |
| **回答的问题** | "怎么做" | "**为什么这么做、什么时候不该这么做**" |
| **立场** | 通用（任何 agent harness 都适用） | **DSH 特定**（agent 主导开发的仓库该怎样） |

**它们没有覆盖的，正是我们的核心内容**：

- **门禁设计**——什么时候该自动化、什么时候必须交给评审、什么叫"表面合规"
- **证据标准**——相似性不构成同一性、独立预言机、度量机制会改变结论
- **诚实的空白**——不确定时标注而非补齐（9 次出现的跨批模式）
- **机械化的梯度**——从完全机械化到删除的八档处置
- **决策记录制度**——Agent Note 的生命周期、强制的 Alternatives、归档与冻结
- **被否决方案的价值**——"决定告诉你结果，否决告诉你边界"

**最接近的一个**是 `superpower-verification-before-completion`（"宣称完成之前先跑验证拿证据"）——但它是**流程要求**（在什么时机做什么动作），不是**判断标准**（什么算够格的证据、什么时候验证手段本身会失效）。

**结论：重合度低，但必须在 README 里主动划清**，否则读者看到"又一个 skill 包"就划过去了。

## 五、实施范本：从 `dsh-superpowers` 可直接借鉴的六件事

这个项目把我们要走的路走通了。**以下都是它有、我们该照做的**：

**① 实现方式**：`src/superpowers.ts` 是一个 **`SkillProvider`，rank 550**，**惰性加载** `SKILL.md` 正文。README 明写"**可被项目/用户技能覆盖**"。

**rank 550 的含义**（结合 DSH 源码的 rank 表）：
```
100 项目 .dsh/skills   200 项目 .agents/skills   250 runtime
300 customSkillDirs    400 user-dsh    500 user-agents
550 ← 第三方 skill 插件   600 bundled（官方内置）
```
**第三方 skill 插件排在 550**——这是生态里已形成的约定，我们该跟随。

**② 安装命令**（DSH 官方 CLI）：
```sh
dsh plugin --profile web add @jasonfreelab/dsh-superpowers
dsh plugin --profile web remove @jasonfreelab/dsh-superpowers
dsh --profile web --dump-config | grep -A2 '@jasonfreelab/dsh-superpowers'
```

**③ 包结构**：
```
src/superpowers.ts       # SkillProvider（rank 550），惰性加载 SKILL.md
skills/                  # 技能目录（含 references/）
lib/                     # 构建产物【已提交】→ GitHub 直装零构建
scripts/                 # test.mjs + verify.mjs
cordis.patch.yml         # bundle patch
.github/workflows/       # ci.yml + release.yml + release-please.yml
```

**④ 双语文档策略**：**技能正文保持英文原文**，中文只做 README（`README.zh.md`）。理由写的是"英文国际化"——**这与我们"保留 DSH 来源"的想法一致，skill 正文用英文便于与上游对照，说明性文档才翻译**。

**⑤ 自动化发布**：`release-please`（版本 + CHANGELOG + Release 说明）+ npm 可信发布。

**⑥ 自测**：`npm test` 做"内容卫生 + 真实 SkillRegistry"测试，`npm run verify` 做结构校验 + 运行时冒烟。

## 六、一处需要澄清的差异：`dsh.plugin.json` 不是官方格式

`mattpocock-skills-dsh` 用了一个 `dsh.plugin.json`：

```json
{ "id": "gongyijie85/mattpocock-skills-dsh", "version": "0.1.6",
  "main": "./lib/index.js",
  "engines": { "dsh": ">=0.1.0-rc.6" },
  "contributes": { "tools": [], "skills": ["ask-matt", ...] } }
```

**但我 grep 了 `DSHfork/packages/` 下的全部 TypeScript，没有 `dsh.plugin.json` 这个文件名**。所以它**不是 DSH 官方的清单格式**，而是某个第三方工具/插件中心的约定。

**这意味着两条路**：
- **`dsh-superpowers` 的路**：`cordis.patch.yml` + 代码里的 `SkillProvider`（**DSH 原生，我们倾向这条**）
- **`mattpocock-skills-dsh` 的路**：`dsh.plugin.json` 声明式（**依赖一个非官方的消费者**）

**我们走前者**——它与 DSH 官方机制直接对齐，不依赖任何第三方清单格式。

## 七、对既有决策的影响

1. **名字**：你定的 `@max-null/dsh-skills` 可以。GitHub 仓库名在不同 owner 下可同名（不会与 `CocoSgt/dsh-skills` 冲突），npm 有 `@max-null` scope 隔离。**风险只是搜索混淆**——但如你所说，我们更贴近"DSH skills"这个语义。
2. **实现方式**：确认走 **provider 式（方案 A）**，并且按 `dsh-superpowers` 的范本用 **rank 550**（不是我之前推测的 600）。
3. **落点**：不再是 SSiD 的 `.agents/skills/`，而是**独立 npm 包**；SSiD 侧用 npm 声明集成（你已定）。
4. **双语**：技能正文可用英文（与上游 DSH 对照方便），说明文档做中文——**这个策略已被同类项目验证**。
