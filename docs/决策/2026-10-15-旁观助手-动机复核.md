## 一、结论速览

1. **原判据的数字有口径问题。** 调研 §四 的「用户点名轮次调用率 11.76%」，其「点名」判定是
   **关键词命中**（用户消息里出现过「提交 / 拉取 / 审查 / ppt / 剧本杀…」即算）。于是提问、反馈、
   大段讨论全都进分母。同口径重跑得 **8.7%**（229 轮 / 20 次调用）。
2. **换严口径后是 37.1%**（35 轮 / 13 次调用），真实值落在 **8.7%–37.1%** 之间、靠上缘（见 §三）。
   也就是说：**漏用确实存在，但原口径把分母撑大了约 6 倍**。
3. **四次受控实验全部没能复现「长会话失效」**（§二）。决定「模型会不会调用 skill」的变量是
   **技能在不在目录里**，不是上下文长度 —— 175k 上下文里它照样在第 2 步自己调用。
4. **形态分析给出了真正的答案**（§四）：严口径下 22 条漏用里，**21 条是「模型自己用 `pwsh`
   手搓 git 把事做完了」**，0 条是「什么都没做」。所以漏用的准确定义是
   **「没走项目既有的 skill 流程」**，而不是「想不起来」或「没做」。

## 二、四次受控实验

**装置**：`.ssid-iso-test` 的未打包 dev 构建（`launch-dev-with-pluginset.ps1`，`DSH_HOME=home-100`、
profile `ssid-dev`、CDP 9222、web 19488）；探针 `ssid-plugins-dev/node_modules/probe-rule` 经
`profiles/ssid-dev/cordis.patch.yml` 的一条 `insert` 挂到 `agent/pre-step`。
**四次请求逐字相同**：「你拉取一下 dsh-anatomy 的最新代码，仓库在 `H:\MaxNull\WorkStation\dsh-anatomy`」。

| # | 上下文 | 隔离环境的用户技能 | 探针第 2 步判定 | 模型行为 |
|---|---|---|---|---|
| 1 | 短（新会话） | **0 个** | `skill=false` → 注入提醒 | 「没有匹配「拉取/同步仓库」的现成技能——`dsh-upstream-watch`…、`ssid-pre-push-checks`…都不对口」→ 直接 git |
| 2 | 短 | 0 个（提醒带候选清单） | `skill=false` | 「用户点名的是「拉取」，**对应 `mxy-git-pull`**」→ 调用 → `skill "mxy-git-pull" is unknown` → 说明原因后继续 |
| 3 | 短 | **17 个**（补种自 `~/.dsh/skills`） | **`skill=true`** | **自己调用 `mxy-git-pull`** 并按其流程完成 |
| 4 | **长（175k）** | 17 个 | **`skill=true`** | **自己调用 `mxy-git-pull`**，按 skill 的硬约束中止（沙箱拒绝写 `.git`），并用只读 `git ls-remote` 独立核实远程无新提交 |

**读数**：

- **实验 1 里模型「没找到对口技能」是准确的判断** —— 那时隔离环境的技能列表里确实没有 `mxy-git-pull`
  （`home-100/skills` 不存在）。我最初把它读成「它漏掉了完全对口的技能」，**那个结论是错的**（见 §四）。
- **决定变量是技能可用性**：无技能 → 不调用（1、2）；有技能 → 第 2 步就调用（3、4）。
- **上下文长度没有造成差异**：175k 的会话（实验 4）里，探针在第 38 轮的第 1 步仍是 `skill=false`、
  第 2 步即 `skill=true`；同一次运行里 allostasis 报 `drift=chinese`，**说明它确实是长上下文**。
- 实验 2 的附带读数：**候选清单让模型一次锁定了正确的技能名**（此前它只列举了两个不相干的）。
  但实验 3/4 显示技能可用时它自己就能找到 —— 所以 `candidates` 的价值**仍未被证实**（见 §五）。

## 三、口径复核：11.76% 是怎么来的

原判据（`docs/调研/scripts/measure-4.mjs:43`、`extract-named-rounds.mjs:18`，两张表相同）：

```js
const TRIGGERS = [/提交|commit|推送/i, /日报|周报/, /设计文档|设计方案|写方案|原型/,
  /代码审查|review|审查/, /拉取|pull|同步代码/i, /整理代码|加注释/, /更新文档|更新 ?AGENTS|同步文档/i,
  /pptx|ppt|幻灯片|演示/, /做成图片|发群里|导出 ?PDF|做成 ?PDF/i, /架构图|活点地图|链路图/,
  /剧本杀/, /台账|判据|能发吗|能交付/]
```

**只要用户消息出现过其中任一词，就算「点名了该技能」** —— 不看语义。抽样（同口径重跑得到的
229 条清单，读前 300 行）看到的典型分母：

- 「我看过了，整体内容没问题，两个优化点：**ppt** 首页头像只有头了…」（反馈）
- 「这个 **ppt** 的演讲者就是尹文凯本人，你在文字里写『尹文凯找到了』会不会很奇怪」（提问）
- 「还有一份报告错误的**提交**到了 mac 打包分支，你看一下」（查询）
- 「我已发布 dsh-skills 插件，修复 skill **审查**的结果」（陈述）

这些轮次不调用 skill 是**正确**的，但它们都在分母里。

**严口径**（`.tmp/strict-named-rounds.mjs`，结构条件：短于 40 字 + 无疑问/表态词 + 呈指令形态）：

| 口径 | 点名轮次 | 调用 | 调用率 |
|---|---|---|---|
| 粗（原关键词表，分母上界） | 229 | 20 | **8.7%** |
| 严（结构条件，分母下界） | 35 | 13 | **37.1%** |

严口径仍有 2–3 条误收（如「好，我也推荐找队员来做，你做设计和审查」是讨论分工、「审查一遍设计」
的对象不是代码），修正后约 **32 轮 / 13 调用 ≈ 40%**。

**所以：真实调用率约 40%，漏用约 60%** —— 仍然不是小数，但比原口径暗示的「88% 漏用」
小得多。原数字应读作**上界**（分母上界 → 调用率下界）。

## 四、形态分析：那 22 条漏用到底是什么

对严口径下 22 条未调用的轮次，统计**该轮实际用了什么工具**：

| 形态 | 条数 |
|---|---|
| ① 自己用 `pwsh` 跑了 git 命令 | **21** |
| ② 有工具动作但不是 git | 1 |
| ③ 整轮没有任何工具调用 | **0** |

**没有一条是「什么都没做」。** 逐条追一个样本（`session-fabc21b2-…-d1ec93b247c4`，turn 70）：

```
【用户】先只提交，等 ssid dev 环境准备好测试完成后再推送和发布
  [工具 1-4] pwsh × 4（检查 build 目录 / dev-home / 插件 / profile-template/vendor）
  [工具 5]   validate_dsh_ui · 「提交已就位 · dev 环境待更新」→「提交完成，未推送」
```

**它手搓 git 提交了，而且正确执行了「先只提交」的约束**（明确回报「未推送」）。
所以这一类既不是「想不起来用 skill」，也不是「没做」：

> **它是「自己有做法、做完了、只是没走项目既有的 skill 流程」。**

**这同时解释了四次实验为什么抓不到漏用**：那四次是**单一明确任务**（新会话、只这一件事），
模型从零起步，会先去技能目录里找；而真实漏用发生在**多轮混合任务**里 —— 它已经铺开了自己的
路线，用户在中途插一句「提交」，它就**延续既有路线**，不会为此切到 skill。
**差别在任务形态，不在上下文长度**（后者是我先前的假设，数据不支持）。

### 4.1 更正

[验证实验 1](2026-10-15-旁观助手-验证实验1-提醒有效性.md) §3.2 写「它漏掉了完全对口的
`mxy-git-pull`」——**该结论作废**。真相是那个技能当时不在隔离环境的技能列表里（`home-100/skills`
不存在），模型说「没有匹配的现成技能」是**准确的**。我当时在「第一跳数据」上下了结论，没有核实
技能是否真的可用 —— 这与同日 `memory-auditor` 那次误判（只看一跳链接就断定「两侧不共享」）是
**同一个错型**。

## 五、对设计的影响

1. **判据不能是「本轮没调用 skill」。**
   「它手搓完成了」与「它没做」在观测上完全一样（都是没调 skill），但只有后者需要救；而实测里
   **前者是 21/22**。按现探针的判据上线，绝大多数提醒会打在一个**已经把事情做完**的模型身上。

2. **判据要成立，前提是那个 skill 携带「增量规范」。**
   提醒的价值只能是「让它用上 skill 里的规范」。若 skill 只是把同样的 git 命令包装一遍，提醒
   就没有意义。因此设计前需要逐条审目标 skill：**它比手搓多出来的东西是什么**
   （例：`mxy-commit-review` 的提交前审查清单、`mxy-git-pull` 的拉取总结格式）。
   这是新出现的前置工作，方向文档里没有。

3. **`candidates` 字段的处境：留着，但价值待验。**
   实验 2 显示它能让模型一次锁定正确技能名；实验 3/4 显示技能可用时模型自己也能找到 —— 所以
   在那个条件下它无用。但真实漏用发生在**多轮混合任务**里（模型注意力在别处），候选清单可能
   恰好是把注意力拉回来的手段。**要验它，得在「多轮混合任务 + 技能可用」的条件下重做实验**，
   而不是在单任务条件下。

4. **第一条判据（交付类动作）方向仍然对。**
   22 条漏用里绝大多数是「提交 / 推送 / 发布」，与 schema 草案选的第一个用例一致；只是它的
   **判据形态**要按第 1、2 点重写。

## 六、边界与未决

1. **严口径是结构判据，不是人工全量标注。** 22 条是机械筛出来的，我人工读过其中一部分（有 2–3 条
   误收）；要更硬的结论需要对 229 条逐条标注。
2. **四次实验的样本极小**（每臂 n=1），只能作方向性读数；其中实验 3、4 都有沙箱噪声介入
   （会话工作区在 `Documents\deepseek-harness\default-workspace`，目标仓库在 H 盘别处）。
3. **`--min-size` 参数在本机脚本里有瑕疵**：`.tmp/strict-named-rounds.mjs` 的默认值传参写成
   `Number(argv[argv.indexOf('--min-size') + 1] || 300_000)`，未传参时会取到 `argv[0]` 得到 `NaN`，
   实际**没有做体积过滤**。两个脚本最终落在同一批 108 个会话 / 229 轮上，**数字不受影响**，
   但下次要跑应显式传 `--min-size`。
4. **未决**：那次「多轮混合任务里它延续自己的路线」是**假设**（由 21/22 的形态与样本 1 支持），
   尚未用受控实验证伪 —— 它决定 §五第 3 点那个实验该怎么设计。
