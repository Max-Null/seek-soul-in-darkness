## 1. 总纲：机械质量门禁胜过散文约定

`2026-06-11-quality-gates.md` · 被后续多篇引用为 "the whole quality story is mechanical gates"

### 他们遇到的事

这个代码库**主要由编码 agent 开发**。早期出过一次事故：类型检查不通过的测试被提交了——因为 vitest 不做类型检查，而这个问题是被人工评审发现的。换句话说，靠的是运气和人的注意力。

### 判断

每一条**可机械检查**的 `AGENTS.md` 承诺，都必须配一条能非零退出的命令。分工是：CI 跑穷尽集，Git hooks 只把延迟预算留给廉价的本地缺陷。

### 凭什么这么判断

> Agents follow enforced gates far more reliably than prose conventions, and "a lot of work" is not a cost argument when agents do the labor.

三句话，三件事：

1. **规范的对象是 agent，不是人**——agent 服从机械强制远比服从散文约定可靠。这不是在说人自觉性差，是在说 agent 的服从模型就是这样。
2. **"工作量大"不构成成本论据**——因为干活的是 agent。这句话直接否决了"写门禁太费事所以算了"这种想法。
3. 因此真正的筛选标准不是"值不值得写脚本"，而是**"这条约定能不能被机械判定"**。

### 他们承认的代价

原文明写了两条，没有藏：

- 门禁本身是**需要维护的代码**，配置变更要像普通改动一样被评审
- **100% 覆盖率压力会催生没有断言的测试**——对冲手段是变异测试（当时还在提案阶段）

### 被否决的方案

这篇写于格式确立之前，末尾有一行显式豁免注释：`<!-- agent-note-format: alternatives-not-recorded (pre-format Agent Note) -->`。**没有 Alternatives 段这件事本身被记录在案，而不是静默缺失。**

## 2. 双语文档配对门禁

`2026-07-02-bilingual-docs-and-pairing-gate.md`

### 他们遇到的事

文档语料要被公司内外的人**和 agent**用中英双语阅读。靠人工维护第二语言、没有任何机制，就是翻译腐烂的标准剧本：一侧前进了，另一侧静默地说着假话，而且没有任何门禁会发现。

原文给这类问题的定性很干脆：*"The repo's standing answer to invariants of this kind is to encode them as a mechanical check"*——**这类不变量的标准答案，就是把它编码成机械检查。**

### 判断

一对文档 = 三个兄弟文件：英文 `foo.md`、中文 `foo.zh.md`、一致性记录 `foo.i18n.yaml`。

关键设计：

- **两侧地位平等，没有"原文"**——可以先写中文再翻英文，也可以反过来。约束只有一条：两侧必须说同一件事，且**配对整体合并**（两种语言加记录，从不单独一个）
- 记录里存**两侧的 git blob 哈希**（截至上次确认一致的状态）
- 重录要点名确认配对（批量重录是显式的 `--write --all`）
- 清单文件**只包含显式排除项**
- **全语料一个要求**：一篇文档从创建起就要求完整配对，没有 per-file 过渡态、没有日期截止线、没有 README 专属类别

### 凭什么这么判断

**为什么记录 blob 哈希而不是 commit 哈希**（他们明确参考并否决了 MDN 的 `l10n.sourceCommit` 模型）：

> a same-PR edit has no commit hash yet, so the MDN model cannot express "consistent as of the state this PR introduces", and verifying it requires git history instead of file content.

同一个 PR 里的编辑还没有 commit 哈希；而且验证要查 git 历史，而不是读文件内容。**核心判断：验证应当基于内容，不基于历史。**

**为什么重录必须显式点名**：*"confirming consistency is an explicit, visible act in the PR"*——确认一致必须是一个可见的动作，而不是顺手批量刷过去。

**为什么清单只列排除项**：*"so no requirement can bypass discovery and receive a weaker check"*——不能让任何条目绕过发现流程、从而获得更弱的检查。**绕过必须在结构上不可能。**

### 他们承认的代价

> When the two sides disagree, no mechanical rule picks a winner — the PR review does. That is the price of equal authority, accepted deliberately.

两侧冲突时，**没有机械规则能判定谁对，由 PR 评审决定**。这是"对等权威"的定价，**刻意接受**——因为另一条路（指定一种语言为原文）会禁掉中文优先撰写。

另一条代价：每对多一个文件。但因为记录是机器写的（`--write`），成本是**目录噪声，不是维护工作量**；换来的是"谁在何时确认过一致"可以从 yaml 的 git blame 直接回答。

### 被否决的方案（6 个）

| 方案 | 否决理由 |
|---|---|
| 英文为原文 + 在翻译文件里存指纹（单向 EN→ZH） | 团队要中文优先撰写、双语对等权威，单向模型表达不了这一点。（**但 blob 哈希机制被保留**，只是从"文件内"挪到了 sidecar） |
| locale 目录（`docs/en/` + `docs/zh/`，K8s/ECharts 模式） | 本仓库没有把 locale 映射到路由的文档站框架；移动所有英文文件会搅动全部交叉引用；链接检查需要路径映射逻辑而不能原样工作 |
| 独立翻译仓库（PingCAP `docs`/`docs-cn` 模式） | 对独立发布节奏的文档产品是对的，对 monorepo 自己的文档是过度设计；而且**把翻译放到了本仓库门禁触及范围之外** |
| 单文件交错双语 | 每条 diff 翻倍；破坏"一段一行"的 diff 工效；**局部不一致变得不可见** |
| commit 哈希记录（MDN 模型） | 同 PR 编辑还没有 commit 哈希 |
| 比较两侧的 git 时间戳（不存记录） | 纯格式编辑会**假阳**；无关编辑之后提交的对应文件会**假阴**——**内容同一性是唯一有意义的信号** |

### 顺带：一段业界先例调研

这篇里有一段很值得学的做法——他们在决定前调研了业界：

- **中文大厂的惯例**是配对的同后缀文件（ant-design `index.zh-CN.md`、arco-design、ShardingSphere 的 387 对 `.cn.md`/`.en.md`）——**但没有任何一个仓库在 CI 里强制配对或一致性**，全靠评审
- **一致性自动化反而在中国之外**：MDN 的 `l10n.sourceCommit`、Vue 的 Ryu-Cho（上游提交监视器，为过时翻译开 issue/PR）、K8s 的本地化漂移脚本、微软 Azure 的 co-op-translator
- **他们的设计是两者的合成**：中文生态的文件布局 + 哈希配对门禁 + 用 agent 工作流替代 bot 服务

## 3. 文档分层与字数预算

`2026-07-04-doc-tiers-and-budgets.md`

### 他们遇到的事

常设文档在积累重复的规则、复述事故经过、重复包地图、过时的 Agent Note 摘要——**尽管当时已经有写作指导**。

原文对原因的判断只有一句：*"Because review alone did not prevent that growth, the repository needed a mechanical budget alongside its documentation taxonomy."*——**因为评审不足以阻止增长。**

### 判断

- **结构跟随文档树**：一份文档拥有自己主题的细节，只总结直接子项的用途、职责和高层行为，并链接到更深的拥有者
- **一个事实一个家**（one home per fact）：禁止在自己的层级之外复述
- **窄而硬的预算门禁**：受预算的文件若**缺失也判失败**，这样重命名不能静默地让它的预算成为孤儿
- 范围**刻意**只覆盖容易膨胀的常设文档（各级 `AGENTS.md`、`architecture.md`、`packages/README.md` 及其接收被驱逐内容的策略文档）。**参考文档、Agent Note、完整的包 README 不设预算——因为穷尽式的事实可以很长**
- **天花板是棘轮式的**：已达标的文档保留至少 5% 余量、上限随之下调；超标的文档上限被冻结、阻止继续增长直到达标；**提高天花板需要显式的 PR 理由**

### 凭什么这么判断

**为什么不要"只靠 skill + 评审纪律"**：

> the accretion above happened while the current-state rule and reviewer attention already existed; a prose rule with no mechanical backstop demonstrably does not hold here

积累**就是在规则和评审注意力都在场的时候发生的**。散文规则没有机械兜底，在这里被证明不成立。

**为什么不要"覆盖所有文档的宽泛门禁"**（这条极重要）：

> a blanket ceiling punishes exactly the right kind of long doc (a feature matrix or type catalog where every row is a fact) and generates per-file override churn that trains contributors to rubber-stamp raises.

一刀切的天花板**恰好惩罚了正确的长文档**（特性矩阵、类型目录，每一行都是事实），并产生逐文件覆盖的翻腾，**最终训练出贡献者橡皮图章式地批准提高上限**。——错误的门禁会训练坏行为，这比没有门禁更糟。

**为什么字数这个粗糙代理可以被接受**：

> Word count is a crude proxy accepted deliberately: it cannot judge quality, but it forces the relocation decision at exactly the moment content is being added, which is when the author has the context to place it correctly.

字数**不能判断质量**，但它**恰好在内容被添加的那一刻**逼出"该放哪"的决定——而那一刻正是作者最清楚上下文的时候。**门禁的价值在强制决策的时机，不在度量的精度。**

### 被否决的方案（4 个）

| 方案 | 否决理由 |
|---|---|
| 只要 skill + 评审纪律，不要门禁 | 积累就发生在规则与评审都在场的时候；没有机械兜底的散文规则在这里被证明不成立 |
| 覆盖所有完整文档的宽泛门禁 | 惩罚正确的长文档；逐文件覆盖的翻腾训练出橡皮图章式批准 |
| 每个文档入口各写一套新手教程 | 重复的设置步骤会在命令顺序、首个成果、产品身份上漂移 |
| 把标准放进 skill 里 | **契约住文档、工作流住 skill**；打包进 `SKILL.md` 的标准，对**不调用该 skill 就编辑文档的 agent 不可见** |

## 4. 并行 pre-push 门禁

`2026-07-06-parallel-pre-push-gates.md` · 这就是 `run-gates.ts` 的出生证明

### 他们遇到的事

聚合任务（如文档同步）掩盖了长的**顺序链**，而链上的成员其实是只读且互相独立的。而在 workflow YAML 里复制这些叶子清单，等于给未来的脚本变更留下**多处漂移点**；串行跑包发布检查，则让一道门禁的耗时与包数量成正比。

### 判断（数据化的调度设计）

- `run-gates.ts` 拥有被 CI、`doc-sync`、按需的 `check:all` 共用的**有界调度器**
- 在启动任何子进程**之前**，拒绝空图或有歧义的依赖图
- `needs` 边：前置必须**通过**，否则跳过依赖方
- `after` 边：只等前置**以任意结果结算**，然后仍允许后继运行
- `allowFailure`：仍报告结果，但不让聚合失败
- 默认**缓冲**可归因输出；只有声明了 `streamOutput` 的长协调者实时透传
- 环境变量供不同资源规格的机器调整并发

### 凭什么这么判断——看 6 条否决理由

| 被否决的方案 | 否决理由 |
|---|---|
| 保持聚合任务串行 | 墙钟时间等于独立检查之和，还重复了命令包装器的启动开销 |
| 每个叶子门禁声明一个 CI job | 并行度最大，但重复 checkout/setup/install 开销，且**在 YAML 里复制了调度器清单** |
| 在 shell 脚本里后台跑子命令 | 能并行，但**丢失逐门计时、确定性的失败分组和直接的信号处理** |
| 每个门禁都继承 stdio | 进度立刻可见，但互相独立的门禁输出被交错，且**调度器的可归因输出记录被丢弃** |
| 每个包声明一个 `publint` job | 并行度最大，但产生**手工维护的包清单**，包一变就漂移 |
| `publint` 无界并发 | 只在小仓库上减少耗时，代价是赌进程数、内存压力、tarball 创建和日志可读性 |

**把 6 条否决理由放在一起看，会发现它们是同一个模式的 6 个变体**：每个方案都换来了某种即时好处，但代价要么是"**产生第二份需要同步的东西**"（YAML 清单、包清单），要么是"**丢失可归因性**"（计时、分组、输出归属）。理解了这个模式，后面再看他们的任何编排设计都能预判。

### 他们承认的代价

用"慢的那条依赖链"替代"独立门禁之和"，代价是**一个自定义调度器 + 一份显式的 mode 清单**。选定的长协调者则用跨门顺序和缓冲日志，换即时诊断。

## 5. 移除 Knip（反面案例）

`2026-08-19-remove-knip.md` · **什么时候该删掉一个门禁**

### 他们遇到的事

Knip 从静态源码图推导未使用的文件、导出和依赖。但本仓库还做这些事：从包清单和配置加载 Cordis 插件、把 Typert face 生成进 `lib/`、拆分 Host/Client 程序、声明只被生成代码或运行期加载的代码消费的依赖。

结果是：**为了让受支持的路径通过扫描，不得不维护一套 workspace 专属的入口清单和忽略依赖例外**。包和测试布局一变，就得维护那个"可执行图的第二份近似"。

### 判断

Knip 不再作为仓库依赖或质量门禁存在。仓库**不设**仓库级的未使用代码静态检查。

### 凭什么这么判断

这是整篇最关键的一段——他们不是凭"这工具不好用"删的，而是做了**覆盖分析**：

> The repository already has narrower checks for the failures it treats as release contracts: TypeScript and Oxlint validate source imports, workspace constraints validate manifests, `verify-optional-dependency-imports` validates optional imports, `verify-runtime-closure` validates runtime dependencies, `verify-client-packages` validates Client packaging, and publint validates published packages. The generic unused-code result is advisory, while its exceptions are required maintenance.

拆开是三个判断：

1. **那些失败模式已经被 6 道更窄的检查覆盖了**——一个泛化工具提供的信息，绝大部分是冗余的
2. **泛化结果是参考性的（advisory），而它的例外清单是必须维护的**——收益是软的，成本是硬的
3. 例外清单的存在，让**普通的包变更依赖于一个不能代表组装后应用的源码图**

### 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 保留 Knip 和它的例外清单 | 保住了宽泛的参考信号，但每个受支持的动态/生成路径都需要配置，而这些配置**重述了清单、构建配置和包专属检查已经拥有的事实** |

### 他们承认的代价

他们明确放弃了自动的宽泛未使用代码/依赖报告；评审和简化工作必须**针对真实的加载路径**证明删除是安全的。并且给未来的检查定了门槛：

> A future unused-code check must understand manifest-driven Cordis loading, generated outputs, and the Host/Client split **without a per-workspace ignore inventory**.

未来若要重新引入未使用代码检查，**必须理解清单驱动的 Cordis 加载、生成产物和 Host/Client 拆分，且不需要 per-workspace 忽略清单**。最后留下了那句判断：

> a dependency with no source import is not dead-code evidence by itself.

**一个没有源码导入的依赖，本身不构成死代码的证据。**

## 这批的共同判断标准

跨 5 篇提炼，按我判断的重要性排序：

**① 可机械判定的不变量必须编码成检查，散文规则不作数。**
依据是两处独立印证：总纲的立场，以及预算门禁的"积累就发生在规则和评审注意力都在场的时候"。这是整套体系的地基。

**② 代价的真正来源不是写脚本，是维护"第二份真相"。**
`remove-knip` 的例外清单、`parallel-gates` 拒绝的 YAML 清单与包清单、`doc-budgets` 拒绝的逐文件覆盖——**三种不同的场景，同一个否决理由**。判断标准：任何要求你维护第二份清单的方案，都要重新审视它带来的收益是否值得。

**③ 验证基于内容，不基于历史。**
双语门禁同时否决了 commit 哈希和时间戳：前者在同 PR 场景下无法表达，后者既会假阳又会假阴。**内容同一性是唯一有意义的信号。**

**④ 确认动作必须显式、可见。**
重录要点名、批量要显式开关；豁免要留痕（连"这篇没写 Alternatives"都用注释标了出来）。**看不见的确认等于没确认。**

**⑤ 不接受过渡态。**
全语料一个要求，没有 per-file rollout、没有日期截止线、没有类别特例。过渡态是永久泄漏的开始。

**⑥ 绕过必须在结构上不可能。**
只列排除项，不列包含项——"不能让任何条目绕过发现流程而获得更弱的检查"。

**⑦ 错误的门禁会训练坏行为。**
一刀切的天花板"训练贡献者橡皮图章式地批准提高上限"。这条是对"我们加个检查吧"的**最强反驳**：门禁设计错了，比没有门禁更糟。

**⑧ 门禁的价值在强制决策的时机，不在度量精度。**
字数不能判断质量，但它恰好在内容被添加的那一刻逼出迁移决策——那是作者最清楚该放哪的时刻。

**⑨ 删门禁和加门禁一样需要记录，且门槛更高。**
`remove-knip` 给出了删除的三个条件：失败模式已被更窄的检查覆盖、泛化结果只是参考性而例外是硬维护成本、例外清单使普通变更依赖一份失真的图。
