## 1. 浏览器 GIF 保留单一证据链

`2026-08-08-browser-gif-evidence-chain.md` · **Problem 段写得极好，值得整段记住**

### 他们遇到的事

一个浏览器演示的分镜（storyboard）可以**包含各自都为真的截图，却不能证明一次真实的执行**。他们列了四种具体的失效：

- **复用全局应用状态**，会把旧的设置或会话带进来
- 捕获自动化会**意外地把来自不同模型运行的帧组合在一起**
- **聊天记录可以展示一次成功的回退，却不暴露导致它的那次工具拒绝**
- 模糊的可访问名称匹配会接受**提示词回显**或后代文本，而不是预期的结果

还有两条发布边界：

- 产品默认可能打开一个**自动化无法驱动的原生操作系统界面**；而用 mock 或测试钩子替换它，意味着 **GIF 不再展示生产路径**
- **一次成功的上传或 push，并不证明上传的资产在评审路径上可达且完整**，也不证明 GitHub 把 PR 的 Markdown 认作图片

### 判断：一个分镜 = 一条证据链

核心原则一句话：**一个分镜就是一条证据链，钉在确切的 PR head 上。**

- 构建前要求**干净的工作树**，并记录那个 commit SHA
- 每次运行使用**全新的** `DSH_HOME`、`DSH_AGENTS_HOME`、工作区、会话和隔离的浏览器状态
- **每个发布的帧都来自同一次服务器 + 模型驱动的场景运行**
- 失败的一次捕获**整场丢弃、从全新的根重来**，**绝不与另一次运行拼接**
- 浏览器自动化**等待唯一的、确切语义的状态**
- 当主张涉及工具调用、拒绝或恢复时，分镜必须包含一个**细节帧或轨迹帧**：指明是哪个工具、展示其状态或稳定错误码、并展示下游结果
- **最终编码的 GIF 才是验证主体**——查看器动不了它时，要**从那个 GIF 里解码代表帧**，而不是拿源截图当等价证据
- 原生生产界面**只能通过正常的应用配置**、用一个官方可被浏览器驱动的生产后端来替换，且**这个覆盖要标注在 GIF 旁边**
- **fixture、mock 传输、合成事件、测试专用钩子，都不构成真实生产主张的证据**

### 发布阶段要再验一次边界

他们不信任"上传成功"这件事，而是把发布拆成可验证的几步：

- 首选 `gh --attach`（v2.99.0+、仅 github.com、上限 10 MB）：body 文件引用本地 GIF 路径 → 命令上传**已验证的产物**并**就地重写那个引用** → 然后**活体 body 必须显示重写后的 URL，且该 URL 必须返回 `200` 和 `image/gif`**
- 改动 PR body **之前**，活体 head 必须**仍等于**记录的 head；编辑**之后**再检查一次，必须**仍在该记录值上**
- GitHub 的 Markdown 渲染器**单独**必须产出预期的图片

### 凭什么这么判断

| 被否决的方案 | 否决理由 |
|---|---|
| 当可见状态"看起来等价"时，允许不同运行的帧混用 | **视觉相似性不确立共享状态、因果顺序或单次场景执行。** 重录要再花一轮真实成本，但**保住了分镜所主张的东西** |
| 用聊天记录作为"工具恢复"的充分证明 | 最终答案证明任务完成了，但它**可以隐藏：哪个工具运行了、失败是否是结构化的、模型是否从该失败中恢复** |
| 用 fixture 或测试钩子替换不可访问的原生 UI | 那**是通过改变被观察的产品路径**来让自动化更容易。通过正常配置选择官方生产后端，**让被执行的实现保持真实**，并让更窄的模式**显式** |
| 相信一次成功的上传或 push | 上传或 push **只证明 GitHub 接受了那些字节**，不证明 body 引用指向了上传的资产，也不证明 Markdown 渲染了图片 |

### 他们承认的代价

- 工作流要花额外的暂存状态；**捕获失败后可能要重复一轮真实模型**
- 通常要多加一个细节帧，外加一串发布检查（活体 head 与 body 重读、Markdown 渲染、上传 URL 抓取）
- **无头录制能用的生产后端比交互式桌面少**，而每一个被选中的后端**都要标注在 GIF 旁边**

最后一条是"诚实边界"的又一例：**能力受限这件事被写在产物旁边，而不是瞒着。**

## 2. 证据驱动的性能优化

`2026-09-06-evidence-driven-performance-skill.md`

### 他们遇到的事

两件具体的事：

1. 性能工作**会改进一个孤立的阶段，同时把成本搬到另一个阶段、保留更多数据、或者跳过必需的行为**
2. **历史 PR 描述会保留被放弃的实现和估算**——所以照着它们表面上的解决方案做，**可能恢复一个已被拒绝的设计**，而不是解决当前的瓶颈

### 判断

把宽泛的性能调查导向**有界的、可测量的用户路径**，并组合：

- 聚焦的归因 + **独立计时**的后端与浏览器端点
- 合成的工作负载分布
- **可比较的**冷/热与保留内存条件
- **针对收紧预算的负对照**（negative controls）

一条容易被忽略但很关键：**工作流要求独立于计时的行为证据**。模型可见日志、持久代际与发布规则、流顺序、取消、释放**仍然是义务**——性能优化不能成为删掉它们的理由。

以及两条边界：

- **授权的私有语料检查只产出聚合的工作负载灵感**；提交的输入和发布的产物**只含合成材料**
- 优化 PR 携带它**更紧的预算**；而前面一层基准可以保护已测量的基线，并**保持可独立合并**

### 他们怎么处理"历史证据"（这段最有教育意义）

表格开头先声明三点：

> These are **author-reported historical measurements, not benchmarks rerun for this workflow**. **Final merged diffs and owning source take precedence over original PR descriptions.** The rejected intermediate proposal is retained **only to explain why identity registries are not a general prescription**.

1. 这些是**作者自报的历史测量，不是为这个工作流重跑的基准**
2. **最终合并的 diff 和拥有它的源码，优先于原始的 PR 描述**
3. 被否决的中间提案**保留下来，只为解释"为什么身份注册表不是一条通用处方"**

然后表格里每一行都给一个 "Reusable lesson"，而且**诚实标注哪些数字是估算而非测量**（例如 "The 10,000-node timing table is **estimated, not browser measurement**"）。还专门保留了一行 **closed unmerged** 的 PR，并写明"**没有当前的所有权证据就不要复活它**"。

### 凭什么这么判断

| 被否决的方案 | 否决理由 |
|---|---|
| **先优化可疑代码，再测量** | 局部复杂度**不能识别主导的用户成本**，也**无法建立改进或回归保护** |
| **把历史上的加速当作可复用的处方** | 表示法、所有权和生命周期要求**会变**。**历史证据产生假设；当前生产路径和新鲜测量决定一个改动是否适用** |
| **只用微基准，或只用端到端计时** | 孤立的阶段会**漏掉被搬走的成本**，而聚合计时**无法定位原因**。两者都需要，在适合所选问题的范围内 |

第 2 条是本批最重要的一句：**历史证据产生假设，不构成处方。**

### 他们承认的代价

- 这个 skill **不增加任何运行时行为、基准实现或新的 CI 政策**；它的验证只是文档/链接一致性与 skill 元数据
- **每个未来的优化，都在自己的拥有者处提供可执行的测量和功能证据**
- **有限的场景/修复范围，防止一个宽泛的性能请求变成一次无关的架构重写**

最后一条值得单独记：**限定范围本身就是一种防御**——防止任务从"优化 X"蔓延成"重写架构"。

## 3. 统一的 GitHub 标签分类

`2026-08-08-unified-github-label-taxonomy.md`

### 他们遇到的事

PR 标签实际在回答**两个独立的问题**：这次改动做的是**哪一类工作**，以及它**实质影响了哪些持久的仓库领域**。

两个失效模式：

- **混合这两个维度**，或保留同义的普通标签与命名空间标签，会让**查询变得有歧义**
- 而**一个封闭的领域清单，会强迫新领域进入不准确的类别**

### 判断

- 每个开放的或已合并的 PR：**恰好一个**规范的 `kind/*`，**至少一个**实质影响的 `area/*`
- **从未合并就关闭的 PR，保留迁移过来的历史分配，但不会获得被臆造的缺失分类**
- kind 集合**封闭且互斥**；kind 记录**主导意图**——附带的测试、文档、清理、依赖移动，**不覆盖** feature 或 bug fix
- **保留（reserve）统一化过程中移除的每一个别名**（`kind/bug`、`feature`、`docs`…），理由很精准：*"防止一个过时的同义词被重新创建为一个看起来无关的操作标签"*
- area 集合**刻意可扩展**：当没有现存的描述能**诚实地**覆盖一个持久且可复用的领域时，**agent 可以不经单独批准就创建**一个 `area/<lowercase-kebab-case>`；但**不得**为一个 PR、一个偶然路径、一个临时项目、一个状态、或一个人/团队创建。应用后要**向请求者报告新标签和理由**

最后一条附了一个很硬的约束：**仅仅为了避免一次有正当理由的新增，而复用一个不准确的 area，是不可接受的。**

### 凭什么这么判断（9 个被否决方案，挑最利的几条）

| 方案 | 否决理由 |
|---|---|
| **一个未区分的标签集合** | **一个标签的存在，不会证明"意图"和"语义范围"都被考虑过** |
| **从包或路径推导 area** | **area 描述跨包边界的语义影响，而变更路径包含偶然的测试、文档和支持文件** |
| **宽泛的实现标签替代产品或工程主题** | **一个具体能力不仅仅是它的工具、界面、文件系统或进程实现** |
| **在 Issue 上加 kind** | 原生 Issue Type 已经拥有那个分类；**重复它作为标签会产生漂移** |
| **只靠评论来做 Issue 执行** | **一条评论保留无效元数据并要求人工清理，即使唯一有效的结果就是移除。** 生命周期直接应用那个移除，只为它**无法推断**的选择保留评论 |
| **每个 PR 恰好一个 area** | 连贯的改动可以实质影响多个独立的 API 或行为，**丢掉次要 area 会隐藏受影响范围** |

第 5 条是本批的另一颗珍珠：**"评论而不修复"被否决，因为它保留了无效状态并要求人工清理。** 这与第 01 批的"不接受过渡态"是同一条原则的不同侧面——**知道该怎么修却不修，只是把成本推给未来的人力**。

### 他们承认的代价

- 维护者必须**读改动和活的标签描述**，而不是从标题前缀或路径**推断分类**
- **活的目录、这份理由、以及政策执行，必须在 kind 或某个不明显的 area 边界变化时一起移动**
- 分类法的迁移**带有明确的历史回填与验证成本**

## 这批的共同判断标准

**① 相似性不构成同一性。**
这是本批的核心。"看起来等价"有四种典型伪装：**视觉相似**（不同运行的帧）、**结果相似**（聊天记录显示成功但隐藏了失败路径）、**来源相似**（历史加速看起来是现成答案）、**名称相似**（用宽泛标签替代语义分类）。每一次他们的判断都是：**回到"这个主张到底需要什么"**。

**② 历史证据产生假设，不构成处方。**
性能篇的原话。配套的两个操作：**合并后的 diff 优先于 PR 描述**（因为描述里留着被放弃的设计），**被否决的提案要保留但只为解释边界**。

**③ 要验到"评审者真正使用的那条路径"。**
GIF 篇不满足于"push 成功"，而是要**重读活体 body、用 Markdown API 渲染、抓取上传后的 URL**——因为那才是评审者实际看的东西。**验证的终点应当是消费点，不是产出点。**

**④ 不确定的地方要标注，不要补齐。**
三篇三次出现：性能篇标注"哪些是估算不是测量"；标签篇**不发明缺失的分类**（未合并关闭的 PR 就保留历史分配）；GIF 篇把"这个后端是替代品"标在 GIF 旁边。这是第 02 批"诚实的空白胜过编造的理由"的第二次现身——**它显然是一贯立场，不是偶然**。

**⑤ 知道该怎么修就直接修，别评论。**
"只评论不修复"被否决的理由是：它保留无效状态并要求人工清理。**把一个可自动完成的修复降级成一条提示，是把自己的成本转给未来的某个人。**

**⑥ 限定范围本身就是防御。**
性能篇明确说"有限的场景/修复范围，防止一个宽泛的性能请求变成一次无关的架构重写"。**边界不只是为了省事，是为了防止任务变质。**

**⑦ 验证手段不能改变被验证的行为。**
用 fixture 替换不可访问的原生 UI 被否决，因为**那通过改变被观察的产品路径来让自动化更容易**。这是观察者效应在工程规范里的版本：**凡是让"验证更容易"的改动，都要先问它有没有改变被验证的东西。**
