# 插件样式被连带删除的机制与修复（2026-09-14）

> 日期：2026-09-14
> 状态：已完成（机制定位 + 两处修复 + 复现复测）
> 决策人：MaxNull
> 关联：`2026-09-14-插件中心405诊断记录.md`（同期的注入类故障）、`SSiD开发手册.md` §7 常见坑、工作区铁律 2.0（DSH 源码只引用不改）

## Problem

用户报告「操作 ssid dev 之后悬浮球样式就坏」：`<div id="ssid-toolbar">` 与悬浮球元素都在，但 `style[data-dsh-quick-toolbar]`、`style[data-dsh-quick-toolbar-toolbar]` 两个标签都不在 DOM 里，刷新页面即恢复。同期还报告「只显示收藏」按钮遮挡导航条列表——展开与收起都遮挡。

两件事都属于**注入型 UI 的生命周期**：一个是样式被别人删掉，一个是自己的样式位置压住了内容。排查先排除浏览器与 CSP 因素（dev 的 CDP 现场里两个 style 标签都在、19 条 `#ssid-toolbar` 规则生效），随后在 DSH 源码里定位到一条 client 模块系统的样式记账链路。

## Decision

### D1 根因：裸注入的 `<style>` 会被别的模块认领，随它的一次 HMR 重载被删

链路三步，全部有代码出处：

1. 插件手动 `document.createElement('style')` + `head.appendChild`，标签只带自有属性（`data-dsh-quick-toolbar` 这类），**没有 `data-plugin`**。
2. DSH 的 client 模块系统在**任何模块 materialize 时**做一次认领——`packages/client/modules/src/client/system.ts:42-52` 的 `claimStyles(id)`：对 `document.querySelectorAll('style:not([data-plugin])')` 逐个 `setAttribute('data-plugin', id)`，并把 `data-plugin-css ?? id` 记进该模块的 `record.styles`。
3. 该模块被 HMR 重载时，`packages/client/hmr/src/client/index.ts:86-91` 的 `removeOwnedStyles(id)` 在 `entry.refresh()`（`:130-137`）**之前**按 `el.getAttribute('data-plugin') === id` 逐字匹配删除。

于是：我们的样式标签被某个模块认领 → 那个模块重载一次即被删；`<div id="ssid-toolbar">` 不是 style，既不认领也不删 → **元素留存、样式消失**。再叠加插件的防重守卫（`__dshQuickToolbarInstalled`）让重建的 fiber 直接 return、不再补注 → 只能刷新恢复。

**这解释了用户观察到的规律**「你操作 ssid dev 样式之后就会这样」：每次把插件 bundle 同步进 profile 都会触发该插件的 HMR 重载；web 端同源受害，因为 dev 与 web 共用 profile 里的同一批插件文件。

**复现（修复前）**：向 profile 里的 chat-rail bundle 追加一行注释触发重载——第一次重载后三个 style（两个 quick-toolbar + 一个 chat-rail）的 `data-plugin` 全部变成 `@max-null/dsh-chat-rail`；第二次重载后 quick-toolbar 的两个 style 消失、`#ssid-toolbar` 规则数 0、元素 `position` 从 `fixed` 退化为 `static`；刷新后全部恢复。

### D2 修复：给样式标签一个独立于模块 id 的 `data-plugin` 值

`dsh-quick-toolbar` 用 `dsh-quick-toolbar-styles`，`dsh-chat-rail` 用 `dsh-chat-rail-hide-official`。属性非空即退出 `claimStyles` 的认领集合；值与任何模块 id 都不相等，`removeOwnedStyles` 也不会命中它——**既不进别人的账，也不随本模块的进出被清掉**。

**复测（修复后）**：同样连续两次重载 chat-rail，两个 style 的归属与 19 条 `#ssid-toolbar` 规则完全不变。

### D3 「只显示收藏」遮挡：header 必须在流内，不能是 sticky

`favToggle` 原是 `position:sticky`，滚动时必然覆盖滑到它下面的条目——实测任意滚动位置都有 2 个条目与它相交，与用户截图里 `#104` 被压住一致；折叠态由 `activeIndex` 的居中滚动驱动，同样会盖住条目。

改为：rail 自身不再滚动（`overflow:hidden`），条目放进独立的 `.crl_list` 容器承担滚动，header 留在流内。`activeIndex` 的居中滚动改作用于 `.crl_list`，并给 `.crl_list` 设 `position:relative`，使 `item.offsetTop` 相对它计算。

**验证（116 条真实长列表）**：展开态 280px、`.crl_list` 为 `overflow-y:auto`（scrollHeight 3712 / clientHeight 366）、header 底边 229 ≤ 列表顶边 235；滚到顶部 / 40% / 底部三次，**可见条目与 header 的相交数均为 0**（折叠态同样 0）。

### D4 测量纪律：CDP 所连窗口未聚焦时，过渡时钟是冻结的

排查中一度把 rail 展开态宽度读成 36px（真实 280px），并据此得出过错误结论。原因：Chromium 对未聚焦/未绘制的窗口冻结 CSS 过渡与 rAF——`getComputedStyle().width` 始终返回过渡的起始值，`el.getAnimations()` 里 `width` 的 `CSSTransition` 永远 `running`；此时连 `style.setProperty('width','280px','important')` 都读不回新值。

**纪律**：几何测量前先 `Emulation.setFocusEmulationEnabled({ enabled: true })`；但开启后 `Input.dispatchMouseEvent` 的 hover 可能不再触发 React 的 mouseenter——**先在未开启时 hover 展开，再开焦点模拟让过渡跑完**，是已验证可行的顺序。判据：`el.getAnimations()` 里过渡恒为 `running` 即时钟已冻结。同类现象见此前 `behavior:'smooth'` 滚动不推进（需 `'auto'` 兜底）。

### D5 逐处普查：自制插件里只有三处是裸注入，其余一处属第三方

按同一判据（注入的 `<style>` 是否带 `data-plugin`）逐处普查全部自制插件，结论与最初按「注入位置」列出的候选清单不同：候选 13 处里有 10 处本就带 `data-plugin`（`tag.dataset.plugin` 或 `setAttribute('data-plugin', …)`）。最初只用 `createElement('style')` / `head.appendChild` 定位注入位置、未核实归属标记，清单因而虚高。真正需要加固的只有三处，均已修复：

| 插件 | 注入点 | 归属值 |
| --- | --- | --- |
| dsh-quick-toolbar | `src/client.ts` 基础样式与工具栏样式（两处） | `dsh-quick-toolbar-styles` |
| dsh-chat-rail | `src/client/index.tsx` 屏蔽官方 TurnNavigator 的样式 | `dsh-chat-rail-hide-official` |

**现场实证**：修复后 dev 页面的「待认领池」只剩一条带 `data-plugin-css` 而无 `data-plugin` 的标签，属于第三方插件 `ds-harness-remote`。该问题作者已修复——issue #52（2026-09-07 报告，同日关闭）给出同一机制与 jsdom 对照实验，上游 `packages/plugin/src/client.ts:2384` 现为 `style.dataset.plugin = clientModuleId`，自 0.4.12 起发布。本机两个 profile 的 `ds-harness-remote` 已由 0.4.10 升到 0.4.13（声明 + `pnpm install`），dev 实测：该样式标签带 `data-plugin="ds-harness-remote"`，**待认领池为 0**。

判据固化：**任何 `<style>` 注入都必须带 `data-plugin`**；自制插件取一个独立于模块 id 的稳定值，官方 CSS 注入模板那种「真实模块 id + `data-plugin-css` 幂等键」的写法同样安全，前提是注入会在模块重载后重跑。

## Alternatives considered

- **改 DSH 源码**（让 `claimStyles` 跳过非本模块注入的标签，或去掉认领机制）：**否决**。违反工作区铁律 2.0（DSH 源码只引用不改），且只对 dev 生效、对装版无效，会让两个环境跑行为不同的实现——405 排查已经因此绕过一圈。
- **用真实模块 id 作 `data-plugin` + 幂等补注**（DSH 官方 CSS 注入模板的做法，见 `packages/client/tsdown.client.ts:43` 的 `querySelector('style[data-plugin-css=…]') === null` 判断）：**可行但多一个时序依赖**。官方模板的注入发生在模块工厂执行期（materialize 时必然重跑），而本插件的注入在 `apply` 里，且被防重守卫挡在后面——要让它在重载后重新注入，必须先把注入挪到守卫之前。独立值方案不需要这个改动，故选后者。代价是样式标签不参与本模块 HMR 的清理，重载自身时旧标签会留存——由幂等检查（chat-rail 主样式已有的 `data-plugin-css` 判据）与守卫保证不重复注入。
- **把「只显示收藏」移到 rail 之外**（如导航条上方的独立按钮）：**否决**——用户明确要求「移到导航条面板内，与 header 一致」。
- **用 `position:absolute` + `padding-top` 给 header 占位**：等价但更绕，折叠与展开两态要各算一次占位；独立滚动容器一次解决两态。

## Consequences

- 这两个插件的样式不再因别人的重载而丢失；按同一判据普查，自制插件里只有这三处曾是裸注入（见 D5），其余插件本就带归属标记。第三方 `ds-harness-remote` 的同类缺陷已随上游 0.4.12+ 修复，本机升级到 0.4.13 后待认领池归零——**没有留下需要对外沟通的事项**。
- 新增判据进手册 §7：任何 `<style>` 注入必须带 `data-plugin`，值不等于模块 id；CDP 几何测量前先开焦点模拟。
- 修复只落在我们自己的插件源码（`max-null-plugins/`）与 profile 里的构建产物，DSH 源码未改动。
- 复现与复测方法可复用：改 profile 里某个插件的 `lib/client.js` 内容触发 HMR（watch 比对 `mtimeMs` + `size`，但只在内容 hash 变化时才发 `rebuilt` 帧），连续两次即可观察「第一次认领、第二次删除」。
