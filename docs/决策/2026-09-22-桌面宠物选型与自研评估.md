## 一、起因

用户希望 SSiD 带一只「DS 鲸鱼娘」桌面宠物。需求原话拆成五条：**Q 版鲸鱼娘形象**；**不在 SSiD 窗口内、可置顶**；**实时显示 agent 在干什么**；**会话完成等时刻用声音 + 动作提示**（替代系统通知）；**喂食等常见互动，最好结合 token 用量或余额**；**SSiD 最小化时仍能显示状态**。

## 三、MerZlin 在 SSiD 下的实测结论

### 3.1 架构：与 DSH 只有单向文件联系

它是 **PyInstaller 打包的 Python + PySide6 程序**，自带运行时；不是 DSH 插件、不是 Electron、也不是 SSiD 的子进程（实测父进程为启动它的 shell，与 SSiD 的 electron 零交集）。与 DSH 的唯一联系是**只读 glob** `%APPDATA%\dsh-pet-bridge\dsh-*.jsonl`，该文件由装在 DSH 里的桥接插件 `@dsh-pet/bridge` 写入。

### 3.2 「它不支持 SSiD」是误解

`DshMonitor` 读端只做「桥目录增量 glob」，不关心 DSH 形态；`install_bridge()` 的 docstring 是「一键安装到**所有真实存在的 dsh profile**」（扫 `$DSH_HOME/profiles/*`，只过滤空目录，**没有 web/headless 白名单**）。实测在 SSiD 上点开关后，插件被装进 `ssid` 与 `ssid-dev` 两个 profile。

日志里那个 `[DSH STATE]` 有**两副面孔**，实测中都出现过：桥目录没有活跃实例时它显示 `offline` —— 那是**服务探测通道**（找 3080 或配置端口，供「启动 Harness」菜单与余额查询用），SSiD 用动态端口所以探不到；一旦桥目录出现某个实例的 `dsh-{pid}.jsonl`，它就切换成真实状态（实测 `idle → working → thinking → success`）。**前者认不出 SSiD，后者与 SSiD 无关** —— 不要把 `offline` 读成「不支持 SSiD」，那只是探测通道探不到端口。

### 3.3 端到端联动已验证

正式实例重启内核后，桥文件 `dsh-{内核pid}.jsonl` 实时记录会话活动；桌宠侧出现：

```
Agent 监视器 [dsh] 已启动
播放联动音效 event=start agent=dsh path=...\assets\sounds\agent\start.wav
[DSH STATE] idle -> working -> thinking -> success
```

气泡（「主人，DSH正在运行正在跑命令」）、音效、状态跟踪三条链路全部工作。**SSiD 不需要任何改造**。

### 3.4 两个上游缺陷（v4.2.0）

| 缺陷 | 现象 | 规避 |
|---|---|---|
| `AgentLinkManager` 懒加载 | 监视器只在「展开 Agent 联动菜单」或「关闭设置对话框」时装配，**每次重启桌宠后都要手动点一次开关**（main 分支已修、未发版） | 每次重启后点一次；或等上游发版 |
| 全屏检测误判 | 微信/QQ 等自绘窗口（无系统标题栏）被判定为「真全屏」，桌宠反复隐藏/显示 | 关闭「全屏时自动隐藏」 |

另观察到一个未定性的现象：**状态事件密到同一毫秒内切换 3 次**（`working -> thinking -> working -> thinking`），而动画始终停在随机池、未切「抱笔记本」。原因是状态抖动淹没换帧节流，还是联动链的动画分支另有条件，**尚未验证**。

## 四、体积评估

### 4.1 MerZlin 的体积构成（解压后 317.8 MB）

| 组成 | 大小 | 性质 |
|---|---|---|
| PySide6（Qt 运行时） | 112.9 MB | 框架税 —— 因为它是 Python 程序 |
| imageio_ffmpeg | 83.6 MB | 单个静态 ffmpeg 二进制，只为解 WebM |
| assets | 69.9 MB | WebM 51.9 MB（106 段）+ 彩蛋图 15.8 MB |
| PIL | 12.8 MB | 主动识屏用 |
| Python + DLL | ~24 MB | python311.dll、OpenSSL 等 |
| 主程序 exe | 9.1 MB | 业务代码本体 |

发布物：安装包 142 MB / 便携 zip 173.5 MB。

### 4.2 自研可用 Electron 省掉前两项

**「用 Electron 播 WebM 透明动画」已被验证过两次**：MerZlin 自己的 README 写明「桌面模式（Electron=Chromium）直接透明播放 webm」；而它的上游 PC2005-cloud/dsh-pet **本来就是 web 插件形态，一直在浏览器里直接播这些 WebM**。所以 ffmpeg 与 Qt 都不是必需品。

| | 集成 MerZlin | 自研（Electron 窗口） |
|---|---|---|
| 运行时 | 113 MB | **0**（复用思灵的 Electron） |
| 视频解码 | 84 MB | **0**（Chromium 原生解 WebM alpha） |
| 其它运行时 | 37 MB | ~0 |
| 动画素材 | 52 MB | 52 MB |
| **总计** | **~318 MB** | **~52 MB** |

对 360 MB 的思灵安装包而言：集成 → ~500 MB，自研 → ~382 MB。素材还可再压（彩蛋图 15.8 MB 可不收；WebM 按 106 段平均 490 KB/段，降分辨率或码率后砍到 20–30 MB 是常规操作），**自研净增量可压到 ~25 MB**。

### 4.3 素材来源：链是现成的

MerZlin 的 README 有一节「素材生成教学（从零制作动画素材）」，但**它只有 856 字符、只写了 ①（绿幕提示词的硬性规范）**，②素材生成链与③插件都没有内容 —— 那一节自己指向了上游：「本项目动画素材**沿用参考项目** PC2005-cloud/dsh-pet 的三件套流程…任何人 clone **参考仓库**都可以从零生成」。**管线确实在上游，而且完整可跑**：

| 环节 | 现成资产 | 量级 |
|---|---|---|
| ① 提示词配方 | `prompts/桌面宠物 10 秒动作提示词.md` | **291 KB**：绿幕规范（`#00FF00`、无阴影杂物、人物头顶 20% / 脚底 85% / 左右 25%·75%、禁止平移、首尾帧闭环、道具「无→有→无」、按秒分解）逐动作写明 |
| ① 生成绿幕视频 | 无（需 AI 视频工具：豆包/可灵/Runway，参考项目素材由豆包生成） | **唯一的大头**：每动作一段 10 秒 |
| ② 素材链 | `scripts/` 11 个脚本 | **约 58 KB**：`watermark_step01` → `chroma_step02` → `normalize_step03` → `encode_thumbs` / `encode_preview_gifs`，另有 `check_alpha` / `fill_nn` / `make_mask_black`，以及 macOS 的 HEVC alpha 编码（`.sh` + `.swift`）与 PR 手工抠像导入（`pr_import_step02`） |
| ③ 打包成宠物 | 目录 + 命名约定（`video/<动作名>.mp4`） | 无黑魔法 |

**四步链**：`step01 原始视频 → crop/chroma（抠像）→ step02 透明 810×720 → normalize（归一化）→ step03 母版 1200×1200 → encode → step04 播放变体 360×360`（step04 为最终产物）。关键实现：抠像用 **HSV 色相判定**（只认绿色方向，蓝/白/红永不误抠 —— 注释里写明 chromakey 的 YUV 色度距离与 RGB 色差阈值都会误伤彩色），转码 **VP9 + alpha + CRF32**。

**结论**：「复刻生成管线」这件事基本不成立 —— **链已经写好且量级很小**。自研真正需要投入的只有**拿 AI 生成绿幕视频**这一段，且可按需分批（先做核心 15–20 个动作即可起步，其余慢慢添）。

**授权状况（已核实）**：上游 `PC2005-cloud/dsh-pet` 是 **MIT**（`Copyright (c) 2026 PC2005-cloud`）—— 脚本与提示词配方的借鉴无碍；MerZlin 本体亦 MIT，但 `shenshen` 角色形象的上游归属仍建议单独确认。**仓库已克隆存档**在 `references/_ref-dsh-desk-pet/dsh-pet-upstream/`（`scripts/` 55.6 KB + `prompts/` 284 KB；其中 `dsh-pet/` 目录 126 MB 是插件成品含运行时，自研不需要；`.git` 129 MB 可删）。

**命名提醒**：动作名直接就是文件名（`video/吃白饭.mp4`），自研的动作清单**最好一开始就定好命名**，后期改名要连带改代码里的映射。

## 五、功能取舍

**砍掉的判据是「纯复杂度」而不是「趣味性」** —— 玩法类功能（抛掷物理、回旋、边缘探头、撞飞彩蛋、喂食成长）**代码成本小、包体成本为零**（纯逻辑 + 调用已有动画），是桌宠存在的理由，应保留。

| 功能块 | 自研要不要 | 依据 |
|---|---|---|
| DSH 状态联动 | ✅ 必留 | 核心需求 |
| 主动识屏 | ✅ 留 | 体积 **0**（Electron 自带 `desktopCapturer`，不用 PIL） |
| 待办提醒 | ✅ 留 | 体积 0 + 小 |
| 弹弓/抛掷/回旋/探头/撞飞彩蛋 | ✅ 留 | 体积 0 + 小～中，趣味性 |
| 喂食/成长/亲密度 | ✅ 留 | 体积 0 + 小 |
| 余额查询 | ✅ 留 | 便宜，需求原话提过 |
| 主题 / DPI / 多屏适配 | ✅ 留 | 体积为零，不做很难看 |
| **Claude / Cursor / OpenCode 适配** | ❌ 砍 | 三套事件源与解析，与 SSiD 无关 |
| **菜单编排系统** | ❌ 砍 | 一千多行，不需要用户重排菜单 |
| 多开 / 小肥鱼 | ⏳ 待定 | 体积 0 + 中（多窗协调与共享解码） |

**别砍过头的三项**（属「能不能用」而非「好不好玩」）：长时运行的内存稳定（MerZlin 为它做过专项治理，如每段动画永久持帧 1.76 MB 的坑）、多屏与 DPI 变化、崩溃与异常恢复。这三块恰是 MerZlin 文档写得最厚的部分 —— 砍功能省下的人力，多半刚好要用来重踩这三遍。

**趣味功能的真实成本在「调手感」**：抛掷的重力/摩擦/恢复系数、动画切换的顿挫、点击反馈的跟手程度。MerZlin 把物理参数全做成配置项（`gravity`/`restitution`/`groundFriction`/`throwPower`）就是为了反复微调，这部分需预留调试时间。

## 六、架构建议

MerZlin 必须走「**桥接插件写 jsonl → 桌宠 tail 读**」的中转，因为它是外部 Python 程序、进不了 DSH 进程。**自研不需要这一层**：桌宠可以是「**一个 DSH 插件（直接订阅事件）+ 一个 Electron 窗口（由壳创建）**」。

省下的不只是桥接代码，还有：

- jsonl 事件协议（含六态映射、事件名白名单）
- `link:` 依赖解析（就是下文 7.1 那个把内核搞崩的坑）
- v4.2.0 的懒加载缺陷（自己的代码没有这个问题）
- 桥接插件的装配与卸载流程

**进程启动必须由壳（主进程）负责**，不能由内核插件 spawn —— 见 7.2。

### 第一版建议范围

压到六件事：透明置顶窗、素材播放、直接订阅 DSH 事件、拖拽/点击/右键/托盘、一个只有开关键与位置记忆的设置页、素材。

四个来源各取所长，**源码都已在本地**（`references/_ref-dsh-desk-pet/` 存原型产物，两个桌宠的解包/克隆在 `.pet-test/merzlin/`、`.pet-test/asahimoon/`）。

| 来源 | 借鉴什么 |
|---|---|
| **AsahiMoon/dsh-desktop-pet** | **架构同形，首选参考**。核心约 5500 行：`main.js` 1555（窗口/托盘/穿透/位置持久化/角色扫描）、`pet.js` 2033（帧播放器/状态机/交互）、`index.mjs` 1224（DSH 插件半区读 agent 事件）、`config.mjs` 90（schemastery 配置 schema）、`preload.js` 89（安全桥）。窗口配方已实测：`transparent + frame:false + resizable:false + skipTaskbar + alwaysOnTop + hasShadow:false + backgroundColor:'#00000000'`。**附一条它踩过的坑**：Electron 的 `skipTaskbar` 会**静默失败**（任务栏仍出现默认图标的按钮），必须用 koffi 调 Win32 强设 `WS_EX_TOOLWINDOW` 并在每次 show 时重设——这也是它依赖 koffi 的原因。另有 6 个 smoke 脚本（菜单/穿透/待机/拖拽/打盹）可作测试方法参考 |

| **PC2005-cloud/dsh-pet** | **浏览器播 WebM 的原型**（自研形态的现成验证样本）+ pet pack 格式（用户自行添加宠物种类） |

| | PNG 精灵条（AsahiMoon 式） | WebM（MerZlin 式） |
|---|---|---|

### PC2005 的 Electron helper：四个我们没踩到的坑

`dsh-pet/runtime/electron-helper/`（约 150 KB）是「把 web 桌宠搬上桌面」的完整实现，其注释记着实测结论，自研可直接受益：

| 坑 | 现象 | 解法 |
|---|---|---|
| **全屏透明置顶窗触发 Windows DWM 视频合成黑屏** | 铺满整个工作区的透明置顶分层窗口，会让浏览器里任何正在播放的视频（B 站/本地文件）**画面变黑、声音继续**，悬停/点击桌宠都触发。实验结论：**窗口不全屏就不黑** | 窗口取「**宠物包围盒 + 四周外扩余量**」（为气泡/弹窗预留空间），宠物移动时 renderer **逐帧上报 bounds**、主进程 `setContentBounds` 让窗口跟随 —— 既绕开黑屏又最小化合成开销 |
| **`setIgnoreMouseEvents` 的 forward 钩子在 Windows 会静默失效** | 「回调超时被系统摘掉、或被其它软件的钩子干扰」，而整窗穿透的判定链**只有一个入口**；失效后**没有任何退路**：光标悬浮不触发、拖不动、点击与右键全无反应 | 把「按真实光标位置决定要不要可交互」抽成**不 require electron 的纯函数**（可被 node:test 直接单测），主进程侧 **60 ms 轮询光标 + 调该函数 + 翻转窗口**，作为穿透的**兜底通道** |
| **EPIPE 弹框**（issue #56） | 主进程的 stdout/stderr 是宿主给的管道，宿主一退出读端就消失，**下一次写即 EPIPE**，而「Electron 默认处理器只会弹框且不退出」 | 加「宿主存活」守卫（管道守卫 + 宿主 PID 探测），宿主没了就自己退。（本次原型脚本也撞过同一个 EPIPE 弹窗，属同一已知问题） |
| **渲染端访问宿主 HTTP 被令牌闸门拦** | DSH Desktop 2.0.3+ 的浏览器访问闸门会拦**无令牌裸 HTTP** | 注册自定义 scheme `dsh-pet-bridge://`，主进程 `protocol.handle` 收到渲染端请求后经 **stdin/stdout JSON 行协议**转发宿主，宿主用与 HTTP 路由同一份 `handlePetRoute` 应答 |

**它还把状态机语义写成了规格**（`events.js`），可直接作为自研的行为定义：

- **气泡驻留**：`thinking` / `working` / `result` / `waiting`（「事情还没完」）**常驻直到状态切走**；`success` / `error`（「这事结束了」）**10 秒自动收起**；`state=null`（空闲或回合被打断）收起气泡回待机。
- **动画循环**：进行中的档位**循环播**（`switchTo once=false`），终态档位**播一遍回 idle 链**。

**穿透的坐标细节**：`pointer-target.js` 用 **DIP** 统一坐标系（`win.getBounds()` 与 `screen.getCursorScreenPoint()` 同为 DIP，可直接比较），命中区是画布坐标下的硬编码 `HIT_BOX = {x0:200, y0:50, x1:440, y1:335}`（画布 640×360），并有守卫测试钉住它与 `src/shared/constants.ts` 同步。

### 它的 shared 层：纯计算、可单测、双端共用

`src/shared/` 是本项目最值得学的工程方法 —— **所有几何与物理都是纯计算（无 DOM / 无 rAF / 无 ref），浏览器 overlay 与桌面 helper 共用同一份**，以保证两侧手感严格一致。

- **`physics.ts`（491 行）** —— 拖拽抛掷：弹簧跟手 + 甩抛 + 重力反弹。可调参数（重力/弹性/地面摩擦）来自配置顶层 `physics` 段，文件内的常量只是**默认值来源**。关键取值：`SPRING_K = 200`（刚度，越大越跟手）、`SPRING_C = 30`（阻尼，**ζ ≈ 1.06 过阻尼、不 overshoot**）、`TRAIL_KEEP_MS = 200`（轨迹保留窗口）、`RELEASE_WINDOW_MS = 150`（初速估算窗口）、`RELEASE_STALE_MS = 150`（**松手前停顿超过它就判「温柔放下」，不带残余速度 —— 即使之前甩过**）。注释注明**参数移植自 dsh-pet-indesktop 的 `physics.py`**（即 MerZlin 与 PC2005 的物理是同一套取值）。
- **`motion.ts`** —— 移动几何与角落定位：移动规划归一化为视口比例，px 换算交由调用方；目标越出视口边缘（含边距）时返回 `null`。
- **`displays.ts` / `pickers.ts` / `balance.ts` / `whisper.ts` / `work-status.ts`** —— 多显示器几何、动作选取、余额、碎碎念、工作状态判定，同样纯计算。

**`host/helper-process.ts`（482 行）** 是宿主侧的进程管理器，把上面那个 Electron helper 拉起来并守护：

- **依赖 `@electron/get` + `@electron-internal/extract-zip`** —— 插件会**自己下载 Electron** 来跑 helper 窗口（这也是 `dsh-pet` 在 npm 上带这两个依赖的原因）。
- **协议**：宿主 ↔ helper 之间是一条 **stdin/stdout JSON 行协议**，行统一前缀 `dsh-pet-bridge:` 以与普通日志区分（main.js 的 console 输出也走 stdout）。
- **素材不走管道**：宿主只返回**文件绝对路径**，由 main.js 自行读盘应答（webm/字体/光标都不把二进制过管道）。
- **职责**：解析 Electron 可执行文件 → 子进程拉起 `electron-helper/main.js` → 守护协议通道 → **异常退出自动重启**。
- 注释补充了闸门的准确行为：**DSH Desktop 2.0.3+ 会给「插件自拉的独立进程」的裸 HTTP 请求回 403**。

## 七、踩坑记录

### 7.1 插件装配的 link 依赖（导致内核启动失败）

MerZlin 的 `install_bridge()` 往每个 profile 写入 `"@dsh-pet/bridge": "link:H:/.../merzlin/_internal/integrations/dsh-pet-bridge"`。那条路径从插件目录一路到 `H:\` 都没有 `node_modules`，Node 解析 ESM 裸包名（`import '@deepseek-ai/dsh-llm'`）必然失败 → 整棵插件树加载失败 → 内核起不来、白屏「思灵启动失败」。

**修复**：在插件目录建 `node_modules` junction 指向 `profiles/ssid/node_modules`。

**规则**：装第三方插件前必须 `node -e "import('file:///<入口>')"` 实测解析；让用户重启/关停任何 DSH 实例之前，先自己验证目标 profile 能 boot。

**误导提示**：启动失败时壳会兜底提示「设置 DSH_CHECKOUT 指向 DeepSeek Harness 仓库」—— 那是通用文案，与依赖解析失败无关，不要顺着它排查。

### 7.2 进程树清理（桌宠"莫名退出"）

DSH 的 subprocess 层带 **local process-tree provider**，内核重启会清理整棵进程树。用会话内 `Start-Process` 拉起的桌宠（父进程 = 会话内 pwsh）会在思灵重启时被一起带走，日志停在那一刻且无任何错误痕迹 —— 当时误判为崩溃。

**规则**：长期存活的外部程序一律用**脱离进程树**的方式启动 —— WMI（`Invoke-CimMethod -ClassName Win32_Process -MethodName Create`，父进程为 WmiPrvSE）或 `explorer.exe` 代理或计划任务。
