## 1. 移除生成的 Agent Note 索引

`2026-07-19-remove-generated-agent-note-index.md`

### 他们遇到的事

他们曾经提交一个生成的 Agent Note 索引进仓库。两个问题：

**① 它复制了已经存在的事实。** 每个文件的**生命周期/类别路径、文件名日期和 H1** 已经编码了这些信息——索引只是把它们再抄一遍。

**② 它是个可预测的合并热点。**

> Every branch that adds, moves, or renames an otherwise unrelated Agent Note rewrites the same generated file.

**每一个"添加、移动或重命名一个本来无关的 Agent Note"的分支，都会重写同一个生成文件。** 换句话说：一个跟你的改动毫无关系的文件，每次都要在你的 diff 里出现。

而且这个集中式时序列表**在树导航和仓库搜索之外，几乎不增加发现价值**——但它的生成器、渲染器、命令和新鲜度检查**仍然是维护负担**。

### 判断

- **生命周期/类别文件系统树就是 Agent Note 的清单**
- README 保持为**精选的入口点与契约**
- 发现工作交给**普通的树导航和仓库搜索**
- 门禁**拒绝**旧的家目录和根 `INDEX.md`；它**不渲染、也不做新鲜度检查**

### 凭什么这么判断

| 方案 | 否决理由 |
|---|---|
| 保留提交的生成索引，用"重新生成"来解决冲突 | **重新生成让冲突解决变得机械，但不能阻止无关分支修改同一个产物，也不减少它制造的评审噪声** |
| 提供一个不提交的按需索引命令 | 避免了提交冲突，**但为一个已经由树导航和仓库搜索服务的发现路径，保留了一个渲染器和一条命令** |
| 恢复手工维护的索引 | **同样的共享文件争用，外加生成方式本来避开的完整性与顺序错误** |

第 3 条尤其利落：**手工索引 = 原有的争用 + 一批新的错误类型。**

### 他们承认的代价

读者**失去了一个单独的时序页面**，改用生命周期/类别树或仓库搜索。

## 2. 冻结低未来价值的 Agent Note

`2026-07-26-frozen-agent-note-archive.md`

### 他们遇到的事

implemented Agent Note 被当作**当前决策记录**来维护，于是活跃语料里的**每一条路径、符号、默认值、翻译、代码围栏、包引用和出站链接，都是一项持续义务**。

当理由能指导未来工作时，这个成本是正当的。但对**已关闭的 UI 细节、小修复、被取代的实现机制、或当前权威在别处的过程历史**，就不正当了。

而两个显而易见的出路都不行：

- **删掉每一个低价值的 implemented 记录** → 会抹掉有用的历史证据
- **保留每一个被拒绝的提案** → 保留了那些**既不合理也无教益**的想法

他们要的是一条**保留边界**，能区分"活跃指导"与"冻结历史"，**而又不把归档变成另一个维护层级**。

### 判断（保留规则写得极精细）

- **只有 implemented 笔记能被归档**；proposed 笔记**永不进入归档**（一个过时的提案变成 rejected）
- 归档条件：已发布的决策**已完成**，且它的**理由、替代方案、后果、负面保证和重新引入条件**都不太可能指导未来工作
- **不论年龄或字数，以下保持活跃**：基础边界、持久与线路语义、安全规则、**反复出现的设计诱惑**、**未解决的重新引入条件**
- **rejected 笔记只在它能防止"一个诱人且有意义的错误"时保留**，否则作为完整三件套删除
- 归档变更**只允许四种编辑**：重定位、插入 `Archived: YYYY-MM-DD` 元数据行、相应的 sidecar 重录、机械的入站链接修复
- 根 `.rgignore` **把归档从"遍历父目录的搜索"里排除**（历史查询要显式点名归档目录）
- **归档后三件套永久冻结**：**不因重命名包、变化的行为、翻译标准、格式规则、断裂的出站链接或后来的文档契约而更新**
- 门禁**验证指向归档文件的链接**，但**从不把归档文件当作链接源**
- `verify-archived-agent-notes` 用**路径 + SHA-256 内容哈希**把每个产物封存进一个**只追加的清单**；`--write` 模式**先证明每个现有封印未变**，才追加新归档的产物
- **所有其他文档门禁排除归档源**——这样"它们演变的标准不能产生编辑历史的压力"
- **supersession 检查在写新笔记时进行，而不是推迟到以后的语料清理**

### 凭什么这么判断（7 个被否决方案，取最锋利的）

| 方案 | 否决理由 |
|---|---|
| **删掉每一个离开活跃语料的笔记** | 一个 implemented 记录可以**前向指导价值低，却仍提供关于一个已关闭决策的有用历史证据**。**内容封存的归档保留了那个证据，而不假装它仍然是当前的** |
| **把归档笔记留在默认的搜索结果里** | **归档事实按设计就可能过时，并且可能靠词汇匹配压过当前结果** |
| **把 supersession 清理推迟到周期性语料审计** | **替代笔记的作者拥有关于所有权和重叠的最新鲜证据。** 推迟会留下冗余的活跃权威，并让以后的分类更贵 |
| **也归档 rejected 或 proposed 笔记** | 归档状态的意思是"已实现的历史决策"。**一个过时的提案需要一次明确的拒绝；而一个没有护栏价值的拒绝需要删除，而不是第二个低价值的存放区** |
| **继续对归档笔记适用所有文档门禁** | 后来的格式、翻译、代码、包或链接规则**会要求重写那个历史快照** |
| **允许事实刷新，只冻结理由** | **那重新制造了活跃语料的判断和翻译负担，并让"哪些分句是历史的"变得不清楚** |

第 4 条对"归档"这个动作的语义界定值得记住：**归档 = "已实现的历史决策"，所以它不能用来处理其他状态的废弃物。** 每一种废弃有它自己的正确出口——过时提案 → 明确拒绝；无价值拒绝 → 删除。

### 他们承认的代价

- 活跃语料变成"**一组预期会影响未来工作的决策**"
- 写一篇新笔记现在包含一次**有范围的 supersession 检查**
- **归档事实和出站链接可以按设计就是过时的**——所以读者和 agent **必须把活跃代码与文档当权威，只把归档笔记作为历史引用**

最后一条是**把"存档会腐坏"这件事正当化并明写出来**，而不是假装存档还能保持新鲜。

## 3. 包锚定的子系统页面

`2026-08-03-package-anchored-subsystem-pages.md`

### 他们遇到的事

子系统目录的前页曾用一条 **spine-vs-seam 规则**划定范围：**一个类型是 "core" 的，如果循环在每一轮都持有、派生、流式传输或记录它。**

这条规则的问题在于——**它选的是类型，不是包**。随着文件夹长到四十多页：

- **前页变成了一个跨包的大杂烩**：LLM 对话词汇坐在 agent 契约之上
- 创建/所有权词汇（`AgentHandle`、`CreateAgentOptions`…）**在整个文件夹里哪儿都没被记录**，因为生成器把它们豁免到了一个包 README
- **读者无法从"这个类型住在哪里"预测哪个页面记录它**

同时，包组 README **没有共同形状**——有的带分节表格，有的夹着设计散文，有的拖着本该属于子系统页面的段落。

### 判断

- 每个 `docs/subsystems/` 页面**锚定到声明它词汇的那个包或包组**，**页面成员资格跟随仓库布局**
- 仓库范围的类型模式（`…Map → derived-union`、branded ids）**留在一个显式框定的收尾章节**里，而不是与包内容交错
- **每个被生成的签名引用到的类型，都必须在文件夹里的某处可解析**——所有权词汇从生成器的 `TYPE_LINK_EXEMPTIONS` 移进了 `LINK_MAP → core.md`，于是**豁免被保留给真正的服务本地或 vendor 形态**
- **每个被粘贴的声明只有一个家**
- 每个 `packages/<group>/README.md` 对是一个**薄入口点，形状统一**：why-first 引言段 + 一张包表（Package / Role / ctx key）+ 结尾指向所属子系统页面
- **承载实质内容、超出该形状的散文，重定位到所属子系统页面，而不是被删除**
- 门禁拒绝：缺失的组 README、**既没有读者可见的直接链接也没有显式豁免的组**、空白或孤立的豁免、**"已豁免的组后来又获得了链接"**、以及所指页面缺失的链接

### 凭什么这么判断

| 方案 | 否决理由 |
|---|---|
| 保持 spine-vs-subsystem 范围规则 | **它按类型回答"这个类型是不是 core？"——这就是为什么前页积累了来自四个包的类型，却漏掉了 `packages/core/agent` 公共 API 的一半。按仓库布局的可预测性胜出** |
| 一个扁平的单一文档目录 | 原笔记里已被否决；**增长到四十一页确认了那个判决** |
| 只在包 README 里记录所有权词汇（豁免的现状） | 这让 `AgentHandle` 和创建/恢复选项**对那个自称"类型参考"的文件夹不可见** |

第 1 条的否决理由是一次很干净的自我修正：**规则问错了维度**（问"类型重不重要"，而不是"类型住在哪个包"），于是既收进了不该收的，又漏掉了该收的。结论只有五个字：**可预测性胜出。**

### 他们承认的代价

- 每个包组**必须让它的子系统拥有者、或者一个有理由的缺席，变得可评审**（不能只是"没有"）
- `verify-type-equiv` 的 1:1 清单要求每个粘贴单一归属——**重复的 `SessionEvent` 粘贴被删掉了**

## 对索引里跨批模式的验证

第 06 批的选题目的之一就是**交叉验证**，结果是两条得到强力印证：

### ✅ 模式 B：拒绝"第二份真相"——**强验证**

第 1 篇是这条模式的完美例证，而且理由比我之前记录的更完整：

- 索引**复制了**路径、日期、H1 已经编码的事实（第二份真相）
- 而且它还是个**合并热点**——无关分支每次都要重写它

这里补上了我之前没意识到的一个维度：**第二份真相的代价不只是"要同步"，还包括"它会把无关的改动拖进同一份文件里"。** 争用与漂移是两种不同的成本。

### ✅ 模式 A：诚实的空白胜过补齐——**强验证，且更彻底**

第 2 篇把这条立场推到了制度层面：

> A content-sealed archive preserves that evidence **without pretending it remains current**.

**内容封存的归档保留那个证据，而不假装它仍然是当前的。**

它甚至把"存档会腐坏"**正当化并写进规范**：归档笔记**不因重命名包、变化的行为、翻译标准、格式规则、断裂的出站链接而更新**。这不是疏忽，是设计。

### 🆕 新增一条模式：可预测性战胜精确性（第 3 篇）

一条更精确的规则（spine-vs-seam）输给了一条更粗糙但可预测的规则（按仓库布局）。原因不是精确性不好，而是**精确的规则需要每次判断，而判断会漏**——它漏掉了半个公共 API，同时收进了四个包的类型。

**当一个规则要求"逐例判断重要性"时，它就已经在制造漏洞了。**

### 🆕 新增一条模式：冻结 = 放弃更新它的义务

归档笔记与其他文档门禁**完全脱钩**，理由是"它们演变的标准不能产生编辑历史的压力"。

**冻结一个东西，意味着明确划掉它未来的维护义务**——否则"冻结"只是名义上的，实际负担照旧。

## 这批的共同判断标准

**① 一份事实只该有一个家，而且那个家要可预测。**
索引复制路径与日期（第 1 篇）、类型该跟着包走而不是跟着"重要性"走（第 3 篇）、每个粘贴声明只有一个家（第 3 篇）——三个不同层面上的同一个要求。

**② 第二份真相有两种成本，漂移只是其中之一。**
另一种是**争用**：它会把你无关的改动拖进同一份文件。评估任何"再维护一份清单"的方案时，两种成本都要算。

**③ 冻结要真的冻结，包括放弃维护义务。**
归档笔记**不跟随重命名、格式规则、翻译标准更新**，且**被所有文档门禁排除在外**。否则"历史"会持续产生新的工作量，而它已经不再提供价值。

**④ 归档与删除的语义不能混。**
归档 = "已实现的历史决策"。所以过时的提案要**明确拒绝**，没价值的拒绝要**删除**，而**不是找第二个低价值存放区**。

**⑤ 用可预测性换精确性，通常是划算的。**
要求"逐例判断重要性"的规则，会在两个方向同时出错：收进不该收的，漏掉该收的。
