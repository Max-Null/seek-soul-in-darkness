# 插件中心 0.2.1 发布与 SSiD 归档覆盖机制复盘（2026-08-22）

## 背景

dsh-plugin-center 0.2.1（AI 推荐修复：Message 契约 / dsh-market spec 修正 / spec+stars / maxTokens 2000 / failure 详情）在本轮发布。期间暴露了三个 SSiD 部署机制的坑，均有真实现场证据。

## 一、思灵启动时用安装目录归档覆盖 profile（版本回退根因）

**现象**：临时部署 0.2.1 到 profile（node_modules 手工覆盖）后，重启思灵，插件中心面板回到 0.1.7。

**机制**（`shell/main.mjs` ensureProfile）：
```
deployNeeded = !hasModules || (archiveVer !== null && profileVer !== archiveVer)
```
- 归档 = 安装目录 `resources/dsh-runtime.tar.gz`（NSIS 打包时内置）
- 每次启动比对「归档内 .runtime-version」与「profile/.runtime-version」
- **不一致 → 解压归档覆盖 profile 整个 node_modules**（含手工部署的版本）
- 覆盖后 .runtime-version 写回归档值，下次启动 skip

**教训**：对 profile 的临时部署只对「.runtime-version 与归档一致」的启动有效；任何触发部署的启动都会把 profile 打回归档内容。**验证新版本必须同步替换安装目录归档**，或直接走正式流程（发布 → prepare-runtime → 替换归档）。

**本轮 hack**：直接解压安装目录归档 → 替换其中 `node_modules/@max-null/dsh-plugin-center` 为本地构建 → 重打包（tar -czf，保持 `./` 顶层结构）→ 替换安装目录归档（原归档备份 `.bak-0622`）→ profile .runtime-version 改一个不匹配值触发部署。**注意：pnpm 锁文件机制会覆盖此类 hack（见二）**，hack 只适合临时验证，最终必须发布。

## 二、pnpm add 重建 node_modules，按锁文件恢复包版本

**现象**：hack 归档部署 0.2.1 后，用户点安装 EAC（`pnpm add -w github:zouyuxuan122/Deepseek-Harness-EAC`）→ 插件中心版本回到 0.1.7。

**机制**：`pnpm add` 解析依赖图 → 更新 pnpm-lock.yaml（EAC 带 148 个传递依赖，日志 `Packages: +148 -61`）→ **按新锁文件重新生成 node_modules 全部链接**。锁文件里 plugin-center 锁的是 0.1.7（依赖声明 `^0.1.7`、0.2.1 未发布），relink 时从 store 恢复 0.1.7，手工 hack 的内容被冲掉。

**教训**：**任何对 node_modules 的文件级覆盖都是临时的**——只要锁文件/依赖声明还是旧版本，任何 `pnpm add/install` 都会恢复。新版本想稳定存在：发布 npm → 更新依赖声明 → pnpm install（锁文件锁定新版本）。

**附带发现**：`pnpm add github:owner/repo`（git 依赖）在本机实测可用（Deepseek-Harness-EAC 0.0.0 安装成功，GitHub 网络慢约 1.5 分钟；SSiD 运行时若 node-pty 等被占用会 EPERM，需先关思灵）。

## 三、package.json 带 UTF-8 BOM 导致 kernel 启动失败

**现象**：部署 0.2.1（工作区 package.json 被外部工具写入时带上 BOM）后，思灵启动报：
```
SyntaxError: Unexpected token '﻿', "﻿{ "n"... is not valid JSON
at loadProfile (kernel.bundle.mjs:5702)
```
DSH kernel 的 `JSON.parse` 不剥离 BOM（Node ESM 会剥离，但 JSON.parse 不会）。

**教训**：npm 包内的 package.json 严禁 BOM。发布前检查（`[System.IO.File]::ReadAllBytes` 前 3 字节 EF BB BF）。本轮已修复工作区 package.json（去除 BOM + 修复 description 历史乱码 `鈥?` → `—`）。

## 四、prepare-runtime 的 node/pnpm 路径漂移

**现象**：重跑 prepare-runtime 报「缺少 Node」/「缺少 pnpm 11.x」。

**原因**：脚本硬编码 `D:\Program Files\nvm\v22.22.2\node.exe`（nvm 目录已移除），且 pnpm 只找 `dirname(node)/node_modules/pnpm/bin/pnpm.cjs`（系统 node 安装目录没有 pnpm）。

**修复**（commit ec7e769）：
- node 候选追加 PATH 上的 `node.exe`
- pnpm 候选追加 `%APPDATA%\npm\node_modules\pnpm\bin\pnpm.cjs`

## 结论

1. 验证新版本：临时部署只对「.runtime-version 与归档一致」的启动有效；可靠路径是发布 → prepare-runtime → 替换安装目录归档 → 重启自动部署
2. 发布后必须同步：依赖声明（profile-template）→ 锁文件（pnpm install）→ 归档（prepare-runtime）→ 安装目录归档
3. npm 包 JSON 文件禁 BOM；pnpm 锁文件是 node_modules 的唯一事实来源
