# guardian 写链兜底与内核级验证

> 2026-09-18 · 状态：**插件侧已改并实测**；内核侧与上游 issue 见 §五
> 起因：远端拉下来的 `docs/排查/2026-09-17-DSH内核崩溃退出-排查记录.md` 里那两处插件缺陷
> 关联：该排查记录（现场与探针）· `docs/排查/2026-09-18-上游issue草稿-原子写rename无重试.md`（上游诉求）

## 一、背景

那份排查记录把一条链查清并复现了：Windows 上进程外软件会瞬时持有刚写好的文件，`rename` 覆盖目标返回 `EPERM`；`@max-null/dsh-guardian` 的写链没有 `catch`（`writeChain` 一旦 rejected 就**保持** rejected），事件入口又用 `void this.handleEvent(...)` 丢弃了返回的 promise —— Node 把未处理的 rejection 当致命错误，于是**一次状态落盘失败终止了整个内核进程**，带走全部会话。

处置现状（2026-09-18 核查）：内核侧与插件侧**都没动过**，环境侧也没配白名单；`docs/排查/` 下四份上游 issue 草稿里没有这一篇。也就是"定位完成、零处置"。

## 二、决策（插件侧两处）

1. **写链自愈**：`flushSession` / `flushQueue` 各加 `.catch`，失败被吞掉并记录，`writeChain` 始终可用。理由是 guardian 的状态（断言计数、审查队列）都是**可重建的提示性状态**，落盘失败的正确后果是「丢一次本次更新」，不是让链毒化、更不是终止承载全部会话的进程。
2. **事件入口兜底**：监听器改为 `void this.handleEventSafely(...)`，后者用 `try/catch` 包住 `handleEvent`。这样任何失败都不会逃逸为未处理的 rejection。
3. **诊断走 stderr，不走 `ctx.logger`**。这是实现期的一个实测结论：cordis 的日志默认阈值是 1（只放行 error/info），`warn`(2) **连它的内存 buffer 都进不去**，也没有 exporter 往文件写 —— 用 `ctx.logger.warn` 等于静默吞掉。宿主侧 stderr 才是落地的：SSiD 壳把内核子进程的 stderr 落进 `~/.ssid/kernel-child.log`。同类先例是 `dsh-ssid-pwsh-retry`。

## 三、实现

`max-null-plugins/dsh-guardian/src/engine.ts`：

| 位置 | 改动 |
|---|---|
| 字段 | 新增 `failureCount`（累计吞掉的失败次数，进日志便于判断"偶发"还是"持续"） |
| `bindSessionEvents()` | 从 `[Service.init]` 抽出注册逻辑，监听器改指 `handleEventSafely` |
| `handleEventSafely()`（新） | `try/catch` 包住 `handleEvent` |
| `absorbFailure(scope, error)`（新） | 计数 + 落一行 stderr：`[guardian] <环节>（累计 N 次，本次更新已丢弃）：<message>`；stderr 不可写时静默 |
| `flushSession` / `flushQueue` | 补 `.catch` |

## 四、验证（三层）

**L1 单测**（`tests/engine-resilience.spec.ts`，4 项，随 `npm test` 共 31 项全绿）：注入会抛的假 KvUnit，断言 `flushSession` / `flushQueue` 不 reject、`writeChain` 保持可用（换回可用单元后写入仍真的执行）、连续失败逐次累计、以及经 `ctx.emit` 进入也不产生未处理 rejection。

**L2 构建与运行实体**：`npm run typecheck` 通过；`npm run build` 后只 `engine.js` / `engine.d.ts` 与运行实体有差异（其余 10 个文件哈希本就相同，说明没有漂移），同步后 SHA256 一致。

**L3 内核级故障注入**（`shell/scripts/verify-guardian-absorb.mjs`，隔离实例里跑真实内核）：

```
[verify] 内核 boot ok，port=49390
[verify] 对照组（无故障）写入完成 → guardian.json 存在=true
[verify] 故障注入成立：裸写入抛 EPERM EPERM: operation not permitted, rename '…\.tmp' -> '…\guardian.json'
[verify] 实验组（撞锁）flushSession 正常返回 → 写链兜底生效
[verify] 事件入口（内部抛错）正常返回 → handleEventSafely 兜底生效
[verify] 释放句柄后再次写入成功 → writeChain 未被毒化
[verify] 内核仍存活：HTTP 401
```

诊断行也确实落地（这条是关键——它证明"记录"没有变成静默）：

```
[guardian] 会话状态落盘失败（累计 1 次，本次更新已丢弃）：EPERM: operation not permitted, rename '…'
[guardian] 事件处理失败（累计 2 次，本次更新已丢弃）：Cannot read properties of null (reading 'name')
```

这份脚本的价值在于**故障是真的**：它用一个 `FileShare.None` 的独占句柄注入锁，并先绕过兜底裸写一次自证会抛 EPERM（否则"没出错"可能只是因为没撞上锁）。注入方式与 09-17 排查记录里的探针同源，报错堆栈同形。

## 五、边界与后续

- **内核侧未修**：`@deepseek-ai/dsh-storage-json` 的 `writeAtomic` 仍无重试（0.1.5-rc.2）。写上游 issue 时发现 `packages/util/atomic-write` **已经实现了**同一件事（`EACCES`/`EBUSY`/`EPERM`，20ms 起翻倍到 200ms，上限 8 次），而 storage-json 自己重写了一份同样的协议却漏了这层 —— 诉求因此从"请发明退避"变成"隔壁两个目录外就有现成的"。草稿见 `docs/排查/2026-09-18-上游issue草稿-原子写rename无重试.md`。
- **兜底只降后果，不除触发源**：任何其它消费 `storages/` 且没有自兜底的插件，仍持有那条致命路径。
- **交付状态**：`0.2.1` 已发布（commit `ed8b964` + tag `v0.2.1` 已推 GitHub，npm latest = 0.2.1）。两处 pin（`profiles/ssid` + `profiles/web`）已改到 0.2.1，`pnpm install --lockfile-only` 重算 lock（specifier 与 integrity 都对上发布包），实体按「先删目录再复制」更新后**逐文件 15/15 与发布包哈希一致**——`ssid` 侧那支 `engine.js` 与手工铺入时同哈希（`A77159DED25D`），即**跑的就是正式发布版**，不是"手工铺入的近似物"。
- **不再是"窗口期"**：pin / lock / 实体三者对齐之后，此后任何 `pnpm install` 都不会退回旧版（`profiles/web` 原先停在未兜底的 0.2.0，是唯一的例外面，现已收口）。**两处都要重启才生效**——内核与 web 端当前内存里跑的还是旧代码。
