# 官方桌面端壳层扩展点盘点（2026-09-25）

盘点对象：`deepseek-harness` 仓库 tag `dsh-v0.1.7-rc.2` 的 `apps/desktop`（61 文件 6673 行）与 `apps/desktop-host`（6 文件 1672 行）。全程只读。

目的：回答三个决定性问题，据此重算「二次开发官方壳到 SSiD」的账。前置实测见 `2026-09-25-官方桌面端承载思灵插件实测.md`。

## 结论速览

| 问题 | 答案 | 影响 |
| --- | --- | --- |
| ① Host↔Shell 的 private IPC 可扩展吗 | **是**，一条 9 种消息的 discriminated union + 两个 `switch` | 加一类消息约 10 行，无向后兼容负担 |
| ② `apps/desktop-host` 能挂插件吗 | **能，官方自己就在挂** | Host 侧能力可以用现成范式追加，不必改架构 |
| ③ 品牌位有非硬编码入口吗 | **没有，但只有一处** | `electron-builder-config.mjs:109` 的 `productName`，改一行 |

## ① Host↔Shell 的 IPC 协议

`apps/desktop/src/host-process.ts` 里 `DesktopHostEvent` 是一个 discriminated union，**9 种消息**：

- Host → Shell：`ready`（url + injections）、`fatal`（message + diagnostic）、`platform-session`（session）、`shutdown-complete`、`update-tasks`（响应）、`quit-inspection`（响应）
- Shell → Host：`shutdown`、`update-tasks`（`action: inspect | lock | unlock`）、`quit-inspection`

收发两侧各是一处分支（`host-process.ts:57-85` 与 `:212-218`；Host 侧对应 `apps/desktop-host/src/index.ts:59-90`）。

**协议是版本化的**：`apps/desktop/src/host-protocol.ts` 全文只有 4 行——

```ts
/** Lifecycle protocol generation recorded in Desktop release metadata. */
export const DESKTOP_HOST_PROTOCOL_VERSION = 4 as const
```

这个版本号写在 Desktop 发布元数据里、启动时校验，用于保证壳与 Host 配套。**但 README 的 Release identity 决策明确写着「Electron 与 `@deepseek-ai/dsh` 永远同版本」**——壳与 Host 永远一起发布、一起升级，因此**这条协议没有跨版本向后兼容的负担**：加消息就是加消息，不需要版本协商与 schema 校验。

## ② Host 的扩展范式

`apps/desktop-host/src/index.ts` 全文 122 行，主干是一段 `runProfile`：

```ts
const application = runProfile({
  environment: loadLayeredEnv('dsh'),
  profile: 'desktop',
  resolvedProfile: { profile, installAnchor },
  patchFiles: [],
  args: ['--no-open', '--port', '19387'],
  ...packageManager,
})
...
const { ctx } = await application          // ← 标准 cordis ctx
control.updateTasks = installDesktopUpdateTaskControl(ctx)
control.quitInspection = installDesktopQuitInspection(ctx)
await ctx.plugin(desktopOffice, {...})     // ← 官方自己挂了一个插件
installPlatformSessionPublisher(ctx, (session) => process.send?.({ type: 'platform-session', session }))
```

**官方在这里演示了四种扩展写法，全都是「拿 ctx 注入能力」**：

1. **挂插件**：`await ctx.plugin(desktopOffice, {...})`（`index.ts:95`）
2. **订阅服务流并外发**：`platform-session.ts`（全文 36 行）——
   `ctx.inject(['deepseekAccount'], (accountCtx) => accountCtx.effect(() => { for await (const _ of account.watch(signal)) publish(...) }))`
3. **挂 HTTP 中间件**：`update-tasks.ts:34` 的 `ctx.on('connection/request', async (_req, res, next) => {...})`——**官方 Host 自己就在拦 HTTP 请求**
4. **注册生命周期**：`ctx.effect(() => () => { stopped = true })`

**推论**：Host 侧加能力不需要动架构，只要再写一个 `installXxx(ctx, publish)`。而且 `ctx` 就是 profile 插件树跑在上面的那个 ctx——**profile 里的插件与 Host 的额外注入共享同一个 cordis 上下文**。

## ③ 品牌位与 profile 名

- `apps/desktop/src` 里**没有** `app.setName`、**没有** `productName`；`app.name` 只在 3 处被**读取**（`crash-report.ts:109`、`main.ts:111`、`main.ts:925`）
- 唯一的品牌写入点是打包配置：`apps/desktop/scripts/electron-builder-config.mjs:109` 的 `productName: 'DeepSeek Harness'`（同处还有 `protocols[].name`）
- `appId` 反而是**必须由环境变量提供**的（`resolveDesktopAppId(env)` 强制要求 reverse-DNS 格式）
- profile 名 `desktop` 硬编码在 **2 处**：`apps/desktop/src/paths.ts:19`（profile 与 lock 路径）与 `apps/desktop-host/src/index.ts:27`（`profile: 'desktop'`）；但 profile **目录路径**是 Shell 通过 `argv[3]` 传给 Host 的，所以「换个 home 就换个 profile」不难

## 把「Windows 通知」搬进 fork 的官方壳：落地估算

思灵现方案（`shell/main.mjs:1530-1636`，约 106 行）由三部分组成：`readNotifyConfig()` 读 `~/.ssid/notify.json`、`maybeNotify(scene, title, body)`（含 `win.isFocused()` 抑制与 PowerShell 音效）、三条事件源（`session/event` 的 `turn/end` / `approval/asked`，以及 `userQuestions.ask` 包装）。

搬到官方壳等价改动：

| 文件 | 改动 | 估算 |
| --- | --- | --- |
| `apps/desktop-host/src/` 新增 `notify-publisher.ts` | 照 `platform-session.ts` 写：`ctx.inject(['sessions'|'userQuestions'], …)` + `ctx.on('session/event', …)` + `publish()` | 30–40 行 |
| `apps/desktop/src/host-process.ts` | union 加成员 + 收/发各一个分支 | ~10 行 |
| `apps/desktop/src/main.ts` | 通知投递（`Notification` + 失焦抑制 + 音效 + 配置读取） | ~40 行 |
| 配置读写 | 沿用共享文件，或复用现有 HTTP | ~30 行 |

**合计约 120 行、3 个文件。** 属于接线级改动——它跨进程，但没跨架构。

**注意一个差异**：思灵壳在**同进程模式**下由壳直接 `kernel.ctx.on('session/event')`（`main.mjs:1605`），这是自建壳独有的便利；官方桌面端固定子进程架构，必须走 IPC。反过来，官方在 Host 侧订阅会话事件的能力**并不比我们弱**——只是出口是 IPC 而非直接函数调用。

## 两次判断修正（记录演进，避免复述错误结论）

1. 第一次（写实测记录时）：判断搬迁是「接线而不是重写」——**对托盘/快捷键/标题栏成立，对通知系统不成立**，因为通知要拿到会话事件流与服务句柄，跨了进程。
2. 第二次（本次盘点）：判断「要改协议，是重写级」——**过重了**。协议就是一条 `switch`，且官方壳与 Host 永远同版本发布、无向后兼容负担，所以加一类消息约 10 行。正确定性是：**接线级改动，只是跨越了进程边界**。

## 重算的账

| 维度 | 自建壳（现状） | fork 官方壳 |
| --- | --- | --- |
| 每轮升级的核心成本 | `kernel.ts` 的 boot / patch 管理 / appReady（本轮 7 项工作里占 1 项） | 跟随 `apps/desktop`（6673 行 + tests）+ `desktop-host`（1672 行）的结构与协议变化 |
| 加一个原生能力 | 同进程，几十行，随时加 | 跨进程，约 120 行 / 3 文件，顺着官方范式写 |
| 品牌定制 | 完全自主 | `productName` 一行 + 图标资源 |
| 多 profile / 多开 | 隔离三件套，已验证 | 改 `paths.ts` + `index.ts` 两处 |
| 省下的 | — | runtime resolution、profile 准备与校验、内置 pnpm、崩溃恢复、自动更新、打包签名链 |
| 新增的风险 | — | 官方自更新指向官方 feed；发布门槛升至 EV 签名 / notarize；跟随上游 |

**盘点改变的核心认识**：官方 Host 的扩展范式（`installXxx(ctx)`）干净且已自用，fork 之后加东西是**顺着写**而不是**逆着改**。真正的长期成本不在「加能力」，而在「跟上游的 UI 与生命周期决策」——尤其当我们想要的形态（自绘标题栏、splash、遮罩、完全不同的界面语言）与官方的形态不同时，这部分差异每次上游调整都要重新处理。
