## 2. 破坏性变更：一条，但它是硬失败

**`dsh-persona` 的配置字段由 `text` 改为 `prefix`（required）。** 这不是 rc.2 引入的，`0.1.5-rc.1` 与 rc.2 相同；rc.2 相对 rc.1 在 `packages/preset/` 下**只改了 package.json 的版本号**（persona 源码零差异）。

实测（不是读文档推断的）：

- `dsh-persona@0.1.2-rc.1`：`Config = { text: string; complete?; includeRuntimeContext? }`
- `dsh-persona@0.1.5-rc.2`：`Config = { prefix: z.string().required(); suffix: z.string().default(''); complete?; includeRuntimeContext? }`
- 用 rc.2 实体 + 真 schemastery 3.18.2 跑校验：`{ text: '…' }` → **`$.prefix missing required value`**；`{ prefix: '…' }` → 通过。

同时 `dsh-system-prompt` 把 persona 段从单个 `deployment:persona` 拆成 `deployment:persona-prefix` / `deployment:persona-suffix`，并新增导出 `PERSONA_PREFIX_SECTION` / `PERSONA_SUFFIX_SECTION`。**内核包族必须整体升**：rc.2 的 `dsh-persona` 配 rc.1 的 `dsh-system-prompt` 会在 ESM 链接期直接报 `does not provide an export named 'PERSONA_PREFIX_SECTION'`（已实测）。

→ SSiD 的动作：`presets/ssid-double-star/agent.cordis.yml` 的 `config.text` 改 `config.prefix`（两处副本，见 §4）。

**没有补 `suffix`（刻意）**：rc.2 里 `suffix` 默认 `''`，而 `dsh-persona` 在 agent preset 内会**遮蔽整个 deployment persona**。rc.1 的模块文档与 rc.2 逐字相同（"Mounted inside an agent preset it shadows the deployment persona for that one session"），所以双星 persona 本来就从不包含官方那句 `Your working directory is {{cwd}}.`——升级前后一致，补 suffix 反而是引入新行为。

## 3. 顺带发现：preset 不在归档同步链内

`prepare-runtime.mjs` 只把 `skills/` 纳入指纹与归档（`walkVendor(skillsDir, 'skills')`），`kernel.ts` 的 `syncPresetSkills` 也只同步技能；`agentPresetsRoot` 指向的 `apps/cli/config/agent-presets` 在两个版本里都只有 `examples/`（`scanRoot` 对不存在的根返回 `[]`，静默忽略，不报错——这条"死路径"不是缺陷但也没用）。

结论：**`presets/ssid-double-star/` 是手工部署的**——仓库副本（版本管理）+ `~/.dsh/.agent-presets/ssid-double-star/`（DSH 实际读取）。改 preset 必须两处同时改，且**不在任何归档/升级自动路径上**。任何 preset 字段变更都会漏掉其中一处而静默生效失败。

## 8. 顺带结论：封存分支 `feat/connection-fetch-routes` 可以启用，但不在本轮合

`dsh-capture` 的分支（`37fa8e9`，`inject: ['webServer','webRuntime'] → ['connection']`，路由迁到 `ctx.connection.fetch`）**只在 0.1.5+ 成立**——rc.1 的 connection 自身 `inject ['webServer','credentials']` 且内部经 `ctx.webServer.register`，是 webServer 的语义包装层，不是 carrier-neutral。

rc.2 侧已逐条核实，分支代码与类型**精确对齐**：

- `ctx.connection.fetch.register({ path, methods, requestBody, fetch })`——分支用的 `requestBody: 'buffered'` 正是 rc.2 的必填字段（`'buffered' | 'streaming'`）。
- 路径必须在 `/api` 之下（rc.2 测试断言 `path: '/outside'` → `toThrow('invalid exact Fetch route')`）；分支用 `/api/ssid/screenshot/{get,set,trigger}` ✓。
- `methods` 不可为空、不可重复（同测试文件断言）；分支三条各为 `['POST']` ✓。
- 同一 path 被多路由认领会 `toThrow('already registered')`；分支三个不同后缀 ✓。
- rc.2 里 connection **不再静态 inject webServer**，改为 `ctx.inject(['webServer'], …)` 可选——无 webServer 时 Fetch 注册表仍在，与分支前提一致。

**但本轮不合**，两个理由：

1. 该分支**混入了与路由无关的截图改名**（`docs/shots/*-1.png` → `shot/中文名.png`，`package.json` 的 `files` 同步改成 `shot`）——与本仓库规范（截图落 `docs/shots/`）冲突，合规部分需要分离。
2. 分支的验证环境是 `0.1.5-alpha.2`（其自身提交信息如此声明）。rc.2 的**接口签名已核对一致**，但**行为**验证（typecheck + 无壳环境下的 GET 200 / TRIGGER 503 / 未知方法 404）应在 rc.2 上重做。

→ 建议下一轮：先拆掉截图改名、在 rc.2 环境跑一遍验证，再决定合入与发布（插件发布走 npm，F2A 由用户执行）。

## 9. 真机验证：rc.2 的实际破坏性影响（2026-09-12 补记）

SSiD dev（源码模式）在 rc.2 上跑通。过程中确认了两类**与清单预测不同**的事实。

### 9.1 插件要跟着改：`dsh-pocket` 必须升到 2.10.6

boot 时插件树加载失败：

```
failed to apply loader entry dsh-pocket: cannot get property "webServer" without inject
  at client-connection/src/rpc-host.ts:179  ← rpc.handle() 内部访问 owner.webServer
  at dsh-pocket/lib/web-rpc.js:39 installPocketRpc
```

根因是 **`client-connection` 的 inject 在 0.1.5 收缩**（rc.1 为 `['webServer','credentials']`，0.1.5 改为只 `['credentials']`）。关键在于 `rpc.handle` 的 owner 是 **connection 实例自己的 ctx**（`rpc-host.ts` 的 `get rpc()` 里 `const owner = this.ctx`），而非调用方插件的 ctx；owner 只声明了 `credentials`，所以 `owner.webServer.register(route)` 必抛。

**归因更正（2026-09-13）**：原文写成「SSiD 恰好是无 webServer 的宿主」，这是错的。实测证据：SSiD 组合树里 `webserver` 行启用（`--dump-config` 可见），内核端口在监听且 HTTP 401；profile 的 `cordis.patch.yml` 只 insert 了 MCP，没有禁用该行。也就是说 **SSiD 有 webServer，但 connection 实例的 ctx 没有它的权限**——报错的是 ctx 权限，不是宿主能力。真正没有 webServer 的宿主是 DSH 官方桌面壳（`desktop.cordis.patch.yml` 显式 `webserver: disabled: true`）。这一区分影响判断：在 SSiD 上，`connection.fetch.register`（本仓库 dsh-capture 的改造方向）与 `rpc.handle` 走的是同一个 webServer 挂载点，改造的价值在于去掉对 webServer 的依赖（适配官方壳/headless），而**不是**修 SSiD 上的既有故障。

**`dsh-pocket@2.10.6` 是官方适配版**（其 `lib/web-rpc.js` 头部注释逐字写明了这个坑），`inject` 改为 `['connection','webServer']`，并优先自行把路由挂到 webServer 上、失败才回退 `rpc.handle`。SSiD 的 webServer 是正常提供的（`bootKernel ok port=` 就是它），所以优先路径成立。已按**双处声明**升级（`profile-template/package.json` + ssid profile），实体 2.10.6。

**这条是清单遗漏的**：清单把 connection 变化列为"能力变化（方案 B 的关键）"，但**没预判它会让既有第三方插件在无 webServer 宿主下直接崩**。凡是用 `ctx.connection.rpc.handle` 注册通道的插件都要按此模式适配。

### 9.2 dev 源码模式的三个依赖口子（与 rc.2 无关，但升级时才会暴露）

`kernel.ts:374` 的规则是：dev 裸跑时若 `$DSH_CHECKOUT` 未设且 profile 有部署闭包，**理应走闭包**；但 SSiD 的 tsx 会用 `shell/tsconfig.json` 的 paths 把内核包解析到 checkout 源码——于是实际加载的是源码，闭包被旁路。源码模式因此需要 checkout 自身完整可用：

1. **paths 要跟得上内核加包**（本次补 57 条，289→347）——`subprocess/src` 在 rc.2 新增 `@deepseek-ai/dsh-http-proxy` 导入即触发。
2. **checkout 必须完整 `pnpm install`**——它此前从未装过（`zod`、`mime-types`、`@deepseek-ai/node-addon-system` 全缺）。
3. **dist 型包必须有 `lib/` 构建产物**——22 个包缺（须跑 `pnpm run build`；`node-addon-system` 的 `lib/` 单独构建亦可）。

### 9.3 一条排查教训

「启动失败」有两次根本不是内核问题，而是 **单实例锁被占用**：打包版思灵（`AppData\Local\Programs\ssid-shell\思灵.exe`）一直在后台运行，dev 实例起来后立刻 `single-instance lock FAILED -> quit`。判断启动失败前**先确认锁的持有者**，别把「被拒绝启动」当成「启动后崩溃」。
