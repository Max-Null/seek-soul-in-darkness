## 1. Web 样式系统

`2026-07-19-web-styling-system.md`

### 他们遇到的事

两句话，但把前提说尽了：

> The GUI **has no designer supply**; styles are written by an agent and reviewed. **Without a machine-checkable token system and coding rules**, colors/radii/motion drift as literals across components, and dark mode grows into conditional branches scattered inside components.

**GUI 没有设计师供给**；样式由 agent 写、由人评审。**如果没有机器可检查的 token 系统和编码规则**，颜色/圆角/动效就会作为字面量在组件之间漂移，而暗色模式会长成**散落在组件内部的条件分支**。

### 判断：五条框架规则

1. **视觉基线 = 与 Chat 前端对齐**。每个值来自一次 Chat 前端调研（品牌蓝、灰阶、气泡几何、阴影层级…）；**偏差允许，但必须先记录在偏差表里**
2. **两层 token，不是三层**。基线仓库用 static→alias→specific 三层；**在他们的规模上压缩成两层**——"直接持有真实值的语义层 + 少量组件专属槽位"
3. **字号与间距不做 token 化**。字号在组件里写 px，且**总是搭配行高**（16/24、14/22、12/18）；间距用 4 的倍数；**token 化只覆盖颜色/圆角/动效/字体栈/阴影**
4. **边框与交互态用透明度方案**。理由很实用：`rgba(...)` **叠加在任何高度背景上都成立**，于是**不需要引入新的实色灰**
5. **暗色模式只发生在 token 表里**——**组件 CSS 里零主题选择器**。当某个非 token 值确实必须随主题变化时，走"**CSS 变量桥**"：组件定义局部变量，主题块只覆盖那个变量

### 一条为 agent 设计的规范形态

> The spec is maintained as a **review checklist** (12 items): each item is a decidable "**see X, reject**" — **not a style suggestion** — and **writing styles and reviewing styles share the same table**.

三个要点叠在一起：

- 每一项都写成**可判定的拒绝**，不是风格建议
- **写和评审共用同一张表**（作者的自我检查与评审者的检查是同一次动作）
- 规范带**操作清单**：新增组件怎么做、加 token 怎么做（先加表行 → 再改两个 CSS 块 → 才在组件里引用）、偏离基线怎么做（**先记偏差表再落代码**）

### 分工：RFC 与活文档

| 内容 | 家 |
|---|---|
| 五条框架规则、工程约束、"为什么两层"、"为什么字号不 token 化" | **本 RFC——改它需要一份新的取代 RFC** |
| 每个 token 的权威值、视觉基线常量、12 条编码规则、偏差记录 | 活文档，随实现演进 |

**判断性的内容（为什么）冻结在 RFC，事实性的内容（值）放在活文档。** 改事实是日常，改判断要重新走一次决策。

### 凭什么这么判断

| 方案 | 否决理由 |
|---|---|
| **token 化字号/间距** | 基线仓库**证明了不 token 化也能收敛**（配对行高的纪律替代了它）；而**一个膨胀的 token 表会稀释颜色 token 的权威性** |
| **暗色模式用 `prefers-color-scheme` 或组件内分支** | 属性选择器的**整表覆盖让组件保持无知觉**；系统偏好以后可以叠加到开关上，而不触碰 token 机制 |

第 1 条里那句值得单记：**表越大，表里每一项的权威越弱。** 他们宁可少收一点，也不稀释已经收进表里的东西。

### 他们承认的代价

- 字号/间距**依赖纪律而非 token**（配对行高 + 4 的倍数）
- **任何框架变更都需要一份取代 RFC**

## 2. CI 故障切换运行手册

`2026-07-26-ci-failover-runbook.md`

### 他们遇到的事：一个完美的死锁

三个必需的 Linux worker job 跑在托管的企业 32 核池上。当企业池退化时——

> When the enterprise pools degrade — jobs queue indefinitely or the enterprise labels vanish — **every open pull request becomes unmergeable**, and **the ordinary recovery of merging a fix is itself deadlocked behind the very required checks that cannot run**.

**每一个开着的 PR 都变得不可合并；而"合并一个修复"这个常规恢复手段本身，被那些跑不起来的必需检查死锁住了。**

修复 CI 的改动要走 CI，而 CI 挂了。**这正是"常规出路恰好被故障本身封死"的经典形态。**

### 判断

**范围：两个独立开关，每个平台一个。** `DSH_CI_FAILOVER_LINUX` 恢复企业 Linux 池故障；`DSH_CI_FAILOVER_WINDOWS` 恢复托管 Windows 池故障。**一个平台的故障不必重定向另一个平台的 job。**

关键性质：

> Each switch is **writer-manageable repository state, not a merge**, so it works while checks are red.

**每个开关都是 writer 可管理的仓库状态，不是一次合并，所以它在检查是红的时候也能工作。**

### 他们凭什么敢把它交给 writer 级权限（这段是权限推理的范本）

GitHub 允许任何有写权限的协作者管理仓库变量，所以这不是 admin-only。他们的回应：

> In this repository's trust model that is **not an escalation**: the runner groups admit all workflows of this private, fork-disabled repository, so **any writer could already reach the VMs by pushing a branch workflow**. **The boundary against untrusted code is repository membership; the variables only route work for members.**

**对不可信代码的边界是仓库成员资格，而变量只是为成员路由工作。** 换句话说：这个开关没有创造任何新能力，它只是让已有的能力便宜了一点。

### 三条附带的诚实设计

**① Dependabot 例外。** 两个开关的自托管腿**刻意排除 `dependabot[bot]`**：在自托管故障切换下，Dependabot PR **保持排队等待托管池，而不是在常驻 VM 上执行依赖提供的代码**。

而且明确写了期望行为：**一个在故障期间保持排队的 Dependabot PR 是预期行为，不是切换失败。**

**② 自建池的容量描述不许美化。** `vm-backup` 是**一个共享 VM 上的多个 runner 实例**：

> Registrations share its CPU, memory, and disk; **their count is not a count of independent machines.**

**它们的数量不是独立机器的数量。** 同段还写着"额外注册只增加调度槽位，不增加机器资源"。

**③ 一条实测教训写进了规范。** 把 runner 组钉到 master-ref workflow **与这个故障切换不兼容**——因为故障切换 job 是 `pull_request` 运行、从 PR merge ref 评估的，master 钉住的组会让它们**保持排队**：

> (observed live on 2026-07-27; the group was widened to all workflows of this repository to unblock the switch)

**更严格的 runner 侧策略，代价是 PR 故障切换。**

### 凭什么这么判断

| 方案 | 否决理由 |
|---|---|
| **合并一个 workflow 变更来切换池** | **促成这个开关的故障状态，恰恰是没有任何 PR 能合并的状态——那些必需的检查正是失败的那些。** 仓库变量是 writer 可管理状态，重跑即生效、无需合并 |
| **让自建池永远留在必需路径里** | **那是拿托管池的可用性换了自建 VM 的可用性，等于移动了单点故障，而不是增加了一个回退。** 按平台拆分意味着一个平台的故障不会重定向另一个平台 |

第 2 条是一个可以复用的判据：**"把 A 换成 B" 不是冗余，只有"A 或 B 都能用"才是。**

### 他们承认的代价

- **每个平台要维护第二套 runner 拓扑**，而且自托管的并发与缓存分支必须**与托管腿保持同步**
- **只有完成的 verdict 才算就绪证据**——一个被取消的、或仅仅被排入的运行**不是就绪证明**
- 按平台拆开关**多了一个要管理的变量**，但把每个开关的影响范围**限制在单一平台的 job 上**

## 3. 发布的依赖面与有界的 peer 中继

`2026-08-26-published-dependency-faces.md`

### 他们遇到的事

一个包可能同时包含**浏览器 bundle、Host 入口、共享 TS 声明和 Cordis 注入元数据**。把所有这些关系都编码成必需的 npm peer，导致发布的 CLI **安装变得昂贵**：npm 会自动安装 peer，并且沿着深层的、收敛的 peer 路径**反复评估放置位置**。

关键判断：**改范围、或者把 peer 变成可选，都没有消除那个遍历。** ——问题不在"范围写得不合适"，在"关系被放错了区段"。

而且两类关系的归属本就不同：**选择 Client 构建输入的是"发布的 profile"**，而**Host 值导入是由 Node 从导入包处加载的**。

### 判断：三档分类 + 一道硬闸

每个 Host 运行时导出被归入三档之一，**只能归入一档**：

| 分类 | 含义 | 结果 |
|---|---|---|
| `duplicateSafePackages` | 该包的值是无状态的、结构可识别的、或通过版本化互操作描述符存储 | 整包作为**普通依赖** |
| `safeHostDependencyExports` | 包的其余导出无法作同样保证，但**列出的这些可以** | 仅列出的导出作为普通依赖 |
| `peerRequiredHostExports` | **构造函数身份或模块状态必须共享**的导出 | **整条包边**保持 peer + dev |

然后是那道硬闸：

> An unclassified Host runtime export is a policy violation that **blocks all `--fix` writes**... Once source safety passes, `--fix` performs only the section and range changes implied by the classification.

**未分类的运行时导出是政策违规，阻塞所有 `--fix` 写入。** 只有源头安全通过之后，`--fix` 才执行分类所蕴含的区段与范围变更。

**自动修复拒绝在存在未分类项时动手**——因为此时任何自动写入都是在**猜测**。这与第 05 批"tag 是 commit 指针不是发布证明"是同一种谨慎：**工具只做它有证据做的事。**

诊断形态也值得记：

> An unclassified runtime import reports **one clickable `path:line:column` diagnostic per imported export.**

**每个被导入的导出，一条可点击的 `path:line:column` 诊断。** 而且验证器**读源文件，所以它在干净树上运行**——不需要先构建。

### 凭什么这么判断

| 方案 | 否决理由 |
|---|---|
| 保持内部关系为 peer | npm 必须沿着收敛的祖先路径放置和验证每个必需 peer——**即使所有内部版本都兼容，也会重现报告过的安装时故障** |
| 用 `"./client"` 导出作为 Client 面的名册 | 一个包可以发布面向 Client 的类型或浏览器 API，**却不贡献动态加载的行**；选择它会**把迁移扩大到无关的 Host 包**。`dsh.client` 标识动态行，`packages/client/` 目录独立覆盖静态输入 |
| 展平每个 Host 包 | 消除了更多 peer 工作，**但把迁移扩大到那些个别基准结果微不足道的包**。显式列表**保留剩余的 peer 契约，直到测量证明另一个条目正当** |
| 把每个 Client 相关声明移到仅开发 | 双面包的 Host 值导入**仍然是真实的 Node 加载**；省略它们**会让包依赖于某个 profile 的偶然提升** |
| 在 CI 里强制墙钟阈值 | **resolver 时间随机器负载和元数据完成顺序变化。确定性的 manifest 分类属于 CI；计时留给维护者基准** |

**"直到测量证明另一个条目正当"** 与第 07 批"趁爆炸半径小的时候换"是同一套纪律：**不做没有测量支撑的扩大。**

### 他们承认的代价

- **把一个公开的类型-only 关系移到 `devDependencies`，意味着一个独立 TypeScript 消费者在消费那个声明时必须安装被引用的类型包。** 发布的 profile 安装完整族；**支持独立组装的消费者将需要一个不同的政策**
- **元数据-only 基准是诊断证据，不是发布时的性能承诺**

第 1 条是主动写出"这个决定的受益者之外还有受损者"——**代价不只作用于自己，也作用于下游消费者，他们说清楚了。**

## 这批的共同判断标准

**① 规范要写成"可判定的拒绝"，不是风格建议。**
12 项检查表的每一项都是"看到 X，拒绝"。**判断标准：一个人读完这条规范，能不能在不咨询作者的情况下得出唯一结论？**

**② 写的人与评审的人共用同一张表。**
自我检查与评审检查是同一次动作——**这消除了"规范知道但没执行"的空间**（第 02 批"十九个文件展示了单靠约定能达成什么"的正面解法）。

**③ 约束要在被约束者无知觉的情况下生效。**
暗色模式靠属性选择器的**整表覆盖**，于是**组件里零主题选择器**。**好的约束不需要被约束者配合。**

**④ 表越大，表里每一项的权威越弱。**
他们拒绝 token 化字号与间距，理由是**膨胀的表会稀释颜色 token 的权威性**。**约束的范围应该由"它能守住多少"决定，不是由"它能覆盖多少"决定。**

**⑤ 越界的机制不能走那条被阻塞的路径。**
CI 那篇的决定性论证：把切换做成"一次合并"是错的，**因为需要切换的时刻，正是合并被阻塞的时刻**。
**判据：设计应急机制时，先问它依赖的通道在故障时是否还通。**

**⑥ 冗余 ≠ 替换。**
"让自建池永远在必需路径里"被否决，因为**那是用 B 的可用性换 A 的可用性——移动了单点故障，没有增加回退**。

**⑦ 自动修复必须在信息不足时拒绝动手。**
未分类导出阻塞所有 `--fix` 写入。**工具只做它有证据做的事**——证据不足时的"尽力而为"，等于用一个更强的语气说出一个更弱的判断。

**⑧ 诊断要可直接定位。**
每个未分类导出给一条**可点击的 `path:line:column`**。这是第 01 批"每条违规自带 文件:行"的又一次落地。
