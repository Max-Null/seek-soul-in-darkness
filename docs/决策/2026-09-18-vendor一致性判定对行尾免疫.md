# vendor 一致性判定：对行尾码免疫

> 状态：**已执行**（`lib/vendor-fingerprint.mjs` 已改，`scripts/check-vendor-sync.spec.mjs` 四条自测已入库；手册 §7 坑 #36）
> 关联：手册 §10（内置专属插件规范：源 → 三处 vendor 逐文件一致）· `docs/决策/2026-09-10-SSiD-check-rules骨架建议.md`（比对面与指纹的原始设计）

## 一、起因

v0.3.3 发版前置的七门守卫里，`check-vendor-sync` 报 **6 处「内容漂移」**：

```text
✗ dsh-ssid-panels/.npmignore          src 与 web / ssid 内容漂移
✗ dsh-ssid-env/cordis.patch.yml       src 与 ssid 内容漂移
✗ dsh-ssid-env/lib/index.mjs          src 与 ssid 内容漂移
✗ dsh-ssid-env/package.json           src 与 ssid 内容漂移
✗ dsh-ssid-env/tests/contract.test.mjs src 与 ssid 内容漂移
```

而手册 §10 把「四份逐文件指纹一致」写成硬性要求，`sync-vendor --apply` 又是标准处置——两条一起意味着**发布前必须先把门修绿**。

## 二、定位：差异只有行尾码，且是结构性的

按四份（src / tpl / web / ssid）逐文件复核，用两个独立口径互相印证：

1. **归一化后取指纹**：把 CRLF 折成 LF 再算哈希，四份**完全相同**。
2. **逐字节明细**：`dsh-ssid-env/lib/index.mjs` 的 src 与 tpl 为 `CRLF=73 LF=0 bytes=3225`，web/ssid 为 `CRLF=0 LF=73 bytes=3152`——差的 73 字节正好等于 73 个行尾。

**谁写成了 LF**：不靠猜，看两个副本的落盘痕迹——`~/.dsh/profiles/ssid/vendor/dsh-ssid-env/lib/index.mjs` 与 `~/.dsh/profiles/ssid/node_modules/@max-null/dsh-ssid-env/lib/index.mjs` 的**字节数与时间戳完全相同**（3152 B、同为 2026-09-17 02:32:58）。而 `sync-vendor.mjs` 用的是 `fs.copyFileSync`，只会保留源侧字节。因此把行尾归一成 LF 的只可能是 **pnpm 物化那一步**（`file:./vendor/<pkg>` 依赖的实体是 pnpm 写出来的，不是直接复制）。

根因于是很清楚：源与 `profile-template` 是 **git 检出**（本仓库 `core.autocrlf=true`，仓库内存 LF、检出为 CRLF），profile 侧是 **pnpm 物化**（LF）。两者在 Windows 上**必然不同**，除非有人手工去改 pnpm 的行为。

## 三、两条处置路径

| 路径 | 代价 | 结论 |
|---|---|---|
| 每次发版前 `sync-vendor --apply` 把 profile 刷回 CRLF | 下一轮 `pnpm install`（含 `prepare-runtime` 第 4 步的完整 install）又把差异造回来 → 每轮都修、每轮都复发 | **不采纳**：修不干净，且把「真漂移」淹没在假信号里 |
| 指纹对**行尾码**免疫，其余逐字节 | 源侧行尾被手工改写而内容不变时不再报漂移 | **采纳** |

判定语义的实现落在 `lib/vendor-fingerprint.mjs`（验证与同步**共用**同一实现，避免「验证说通过、同步完仍不一致」）：

```js
export function normalizeEol(buf) {
  if (buf.includes(0)) return buf;
  const text = buf.toString('utf8');
  if (text.includes('\uFFFD')) return buf;   // 非法 UTF-8 序列 → 按二进制处理
  return Buffer.from(text.replace(/\r\n?/g, '\n'), 'utf8');
}
```

- **只对可解码 UTF-8 文本生效**：含 NUL 或非法 UTF-8 序列的缓冲区原样参与哈希——`.node`、图片、zstd 会话日志等二进制不做文本解释。
- **归一的不只是 CRLF**：孤立 `CR`（旧 Mac 行尾）一并折成 LF。
- **其余一律照旧**：内容改动、末尾换行增删、行内空白差异**仍然报漂移**（由 `check-vendor-sync.spec.mjs` 第三条自测守住）。

**为什么不走「让 tpl 也用 LF」这条路**：`core.autocrlf=true` 下工作树的 bytes 由 git 决定，改 `.gitattributes` 会让每个检出者拿到不同形态、且要重写已提交的 blob；而归档由 tpl 直接复制，它带 CRLF 进包并不影响插件运行。行尾既不影响 JS/YAML 语义，也不是任何人手工物化的意图，**它不是内容**。

## 四、代价与副作用

- **代价（有意接受）**：源侧行尾被手工改写、内容不变时，门不再报。行尾对插件运行无影响，用这一点换一条**能长期维持**的门是划算的。
- **`sync-vendor` 的行为随之变化**：dry-run 从 5 处假差异回到「全部一致」——同步与验证同源，这是设计上的一致，不是掩盖。
- **`.runtime-version` 的 vendor 清单指纹不受影响**：`prepare-runtime` 用的是「相对路径 + 文件大小」，与本次改动无关（行尾差异仍会体现为体积差，行为未变）。

## 五、同批处理的第二处假红

`check-profile-sync` 报 `dsh-context` **A(template)=0.53.3 / B(dev profile)=0.53.1**。这是方向明确的「B 落后于 A」——dev profile 落后，按 §4 第 6 条处置：改 profile 声明 + `pnpm install` 对齐（`Packages: +1 -71`，改后 66 项声明逐项在 `node_modules` 在位、33 项 bundles 全在）。
