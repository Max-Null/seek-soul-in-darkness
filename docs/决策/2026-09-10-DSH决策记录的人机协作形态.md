## 一、Agent Note 是什么

来源：`.agents/notes/README.md`（125 行，制度的正式文件）

它对自身的定性在开头第一段：

> 一份 **Agent Note** 记录一个影响本代码库的决策或提案——**其中的"为什么"和"我们放弃了什么"，即代码与文档承载不了的那些部分**。

三个关键设计：

**① 路径就是状态。** 格式为 `{生命周期}/{类别}/日期-主题.md`，两轴都编码在路径里：

| 生命周期 | 含义 |
|---|---|
| `proposed/` | 实施前经过评审的提案，尚未建成 |
| `implemented/` | 决策已交付。记录决定了什么、否决了什么，**并随实际交付物保持最新**（只更新事实——路径、名字、结构——不更新决策本身） |
| `rejected/` | 提案被审议并拒绝。**只在它的理由能阻止一个诱人且有意义的错误时才保留**，否则整组删除 |

| 类别（共 6 个，封闭集合） | 覆盖范围 |
|---|---|
| `feature` | 面向用户或模型的新能力 |
| `bug-fix` | 修正缺陷，或补上事故复盘暴露的缺口 |
| `simplification` | 移除代码、行为或表面积，而不新增能力 |
| `architecture` | 关于**已交付源码**的结构决策 |
| `process` | 代码**周边**的工具、政策、工作流（门禁、包管理器、vendoring），不是运行时行为 |
| `testing` | 测试基础设施与策略 |

**② 强制的 `## Alternatives considered`。** 每一篇都必须有这一节，且：

> **决策若没有记下它击败了什么，就会招致"重新打官司"——而那正是 Agent Note 存在要防止的失败。**

**③ 正文骨架按生命周期固定**（`implemented/` 是 `Problem → Decision → Alternatives considered → Consequences`），由门禁强制；`Proposal`、`Plan`、`Acceptance criteria` 这类提案期标题**在 implemented 里被门禁拒绝**。

## 二、谁执笔、谁评审、谁授权

`.agents/notes/AGENTS.md` 第 3 行是直接答案：

> Agent Notes are effectively **RFCs written by agents**（Agent Note 本质上是由 agent 撰写的 RFC）。

三种角色在材料里都能定位：

| 角色 | 依据 |
|---|---|
| **agent：执笔与执行** | 上句；`process/2026-06-11-quality-gates.md`：本代码库**主要由编码 agent 开发** |
| **人：评审者** | `process/2026-08-09-committed-artifact-citations.md` 记录了"**大型设计与评审会话**"会留下 **reviewer rulings（评审者裁决）**；`README.md`：由**评审**强制执行"非平凡变更必须写 Note"这条语义边界 |
| **人：项目所有者** | `process/2026-07-30-generated-third-party-notices.md`：**项目所有者单独授权**分发某个 SDK 的每一个官方版本 |

第三种最值得注意——**那是机器拿不到的信息**：开源合规要求披露某份依赖，这件事"不是工程必须，是开源必须"，而授权只能由人给出。

还有一处能说明协作的严格程度。`proposed/process/2026-07-13-human-review-skill-maintenance.md` 描述了一个**双评审者流程**，它把每条反馈的作者分成三类：**`human-authored`（人写的）/ `forwarded-automation`（agent 转发机器发现的）/ `unclear`（无法判定）**，然后：

> 从"已被修复的机器人发现"里学习 —— **否决：来源契约是人的评审反馈**。作者类型在分析之前就被过滤。

**他们只从人的反馈里学习，并明确过滤掉 agent 转发的内容。** 人和 agent 在这里不是可互换的两种劳动力。

## 三、关键判据：什么时候**不该**用机器判定

这回答了前一批末尾"我没有答案"的那个问题——**判据就在这条规则里**。

`README.md` 要求：**每个非平凡变更必须在同一个 PR 里添加或更新至少一个 Agent Note**。但这条规则**没有门禁**：

> **评审强制这条语义边界。没有任何自动门禁试图把一个 diff 分类为平凡或非平凡**，所以这条政策不增加门禁阶段或运行时。

被否决的对照方案给出了完整理由（`archived/process/2026-07-19-require-agent-notes-for-non-trivial-changes.md`）：

> **加一道 CI 的 diff 分类门禁。** 一个机械检查**无法可靠判断一个语义变更是否平凡**，而另一道门禁会增加运行时，**并招致误报或表面合规（superficial compliance）**。

拆开是两条理由，缺一不可：

1. **能力上不可靠**：机械检查无法可靠判断"语义上是否平凡"
2. **代价上不划算**：多一道门禁增加运行时，而且会招致**误报**与**表面合规**

**"表面合规"（superficial compliance）** 这个词是新的，它比"误报"更精确：**一道不可靠的门禁不会让人去解决它想解决的问题，而是让人学会迎合它。**

这和第一批读到的"一刀切天花板会**训练贡献者橡皮图章式地批准提高上限**"，是同一失败模式的两种表述。

### 由此修正第 4 档与第 6 档的区别

我此前说"两者都不强制，所以没找到判据"——**这个框定本身是错的**。它们的区别不在"强不强制"，而在**机器是否具备可靠的判定能力**：

| 档位 | 机器的判定能力 | 处置 | 为什么 |
|---|---|---|---|
| **参考性（advisory）** | **不可靠**，但**跑起来仍有参考价值** | 跑，但不阻塞合并 | 例：Knip 的未使用代码扫描——泛化会误伤动态加载与生成代码，但宽泛信号本身有参考价值 |
| **由评审负责（review-owned）** | **不可靠**，且**跑起来只有害处** | **不跑** | 例："这个 diff 是否平凡"——跑起来会招致表面合规，且增加运行时 |

**判据是：当机器的判定不可靠时，跑这道检查还有没有剩余价值？有则降级为参考性；没有且会招致表面合规，就交给评审。**

你关于"脚本失效会静默通过"的那条洞察，恰好是这道题的另一面：**不可靠的判定有两种危害——静默通过（漏），和表面合规（把注意力从真问题引开）。** 后者更隐蔽，因为它会让人以为自己合规了。

## 四、"脚本静默失效"在被防御的名单上

你指出"脚本也要有适用环境，外部条件变了会使脚本失效，进而静默通过"。这不是多虑——**它是一个被专门命名的失效模式，且有一整类防御对应**：

| 防御 | 出处 |
|---|---|
| **拒绝缩窄的语料** | `scripts/verify-client-ui-i18n.ts`：*"discovery narrowed to N source file(s); expected at least M"*；对应决策 `architecture/2026-08-23-locale-owned-client-ui-copy.md`："**Discovery refuses a narrowed corpus**" |
| **空语料直接失败** | `scripts/verify-cordis-config.ts`：包自身配置扫描为空 → 报错；fixture 数量为零 → 报错 |
| **明写覆盖缺口** | `process/2026-08-09-committed-artifact-citations.md`：*"**Coverage gap**: no gate rejects a new ordinal citation — review owns the rule."* |
| **声明不声称什么** | `architecture/2026-08-04-configuration-source-ownership.md`：门禁*"makes no repository-wide claim about `process.env` access"* |

**结论：他们防的不只是"脚本判错"，而是"脚本因为环境变了、扫描面缩了，然后静默地报绿"。** 这在他们那里是一整类防御，不是边角问题。

## 六、附：这次会话本身也是同构的

你指出"我们的这次会话不也是一次 Agent Note 吗，你在执笔不是吗"——**结构上确实高度吻合**。

这 15 批笔记的每一篇，用的骨架正好是 `implemented/` 的规定骨架：

| Agent Note 的规定骨架 | 本系列笔记的对应小节 |
|---|---|
| `## Problem` | 「他们遇到的事」 |
| `## Decision` | 「判断」 |
| `## Alternatives considered` | 「被否决的方案」 |
| `## Consequences` | 「他们承认的代价」 |

而本次会话的过程，也与那套流程同构：**你提出判断 → 我去取证（读源码与决策记录）→ 落盘 → 你复核并提出修正**。

**但有三处实质差别，值得记下来：**

1. **读者不同，所以形态不同。** DSH 的 Agent Note 写给"将来要改动这块代码的人或 agent"；本系列笔记写给"想学这套判断方法的人"。前者为**行动**服务，后者为**理解**服务——所以笔记保留了大量的"他们凭什么这么判断"，而 Agent Note 本身不需要解释自己的方法论。

2. **我们缺少 supersession 检查（取代关系检查）。** `README.md` 要求写一篇新 Note 时必须检索活跃树中覆盖同一决策的旧 Note，并分类完全取代或部分取代。我在写这 15 批时**没有做这件事**——我不知道它们是否与 SSiD 已有的学习笔记重复或冲突。

3. **我们的产物没有状态字段。** Agent Note 的 `Status:` 行与文件夹互为校验（门禁会交叉检查），而本系列笔记是"一次性写就"的——它们不会随 SSiD 的实践演进被更新。**如果以后要拿它们当规范用，这会成为问题。**
