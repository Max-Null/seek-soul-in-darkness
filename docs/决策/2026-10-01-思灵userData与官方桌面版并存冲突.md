# 思灵与官方 DSH 桌面版并存冲突：userData 该由思灵让出

> 记录时间 2026-10-01 · 内核基准 `0.1.7-rc.2`（装版 1.1.4） · 官方端基准 `0.2.0-rc.2`
> 证据取自本机装版实例与 `.dsh-desktop-test/install`（官方桌面版）
> **状态：代码已交付，实机验证待真实场景。** 实现是 `apps/desktop/src/ssid/user-data.ts`（含目标不可用时保持默认的兜底），在 `main.ts` 里接在 `app.setAppLogsPath()` 之前；类型检查、构建、纯逻辑验证（13/13）均已通过，真实双击场景的验证待做。`docs/SSiD开发手册.md` 的对应增补与之一并做。

## 现象

思灵运行时，官方 DSH 桌面版启动不起来——双击后进程直接退出，界面上没有任何提示。

## 成因：两者的 `app.name` 相同，因而派生同一个 userData

| | 官方 DSH 桌面版 | 思灵 |
|---|---|---|
| `package.json` 的 `name` | `@deepseek-ai/dsh-desktop` | 同（刻意保持） |
| 默认 userData | `%APPDATA%\@deepseek-ai\dsh-desktop` | 同一个目录 |
| 单实例锁 | `<userData>\lockfile` | 同一个文件 |

Electron 由 `app.name` 派生默认 userData 目录，单实例锁就落在该目录下。先启动的一方占住锁，另一方启动即退出——**表现为「打不开」，实际是被锁挡掉**。

官方版身份直接取自它自己的 `app.asar`：`name = @deepseek-ai/dsh-desktop`、`version = 0.2.0-rc.2`。

## 当年为什么保持 `app.name` 不变

`apps/desktop/src/ssid/product.ts` 写明两条理由：

1. 改名会丢现有配置（Electron 由 `app.name` 派生 userData）；
2. dev 下它的值是包名，与打包后的 `productName` 不一致，会把包名漏给用户看。

两条今天的状态：

1. **「会漏包名」已不成立** —— 凡是要显示给人的名字都取自 `SSID_PRODUCT_NAME`（`'思灵'`），不再读 `app.name`；`SSID_PRODUCT_NAME` 与打包 `productName` 必须同名，由 `scripts/electron-builder-config.mjs` 保证。
2. **「改名会丢配置」量下来比听起来轻** —— 见下一节。

## 代价量化：userData 里究竟有什么

实测 `%APPDATA%\@deepseek-ai\dsh-desktop`：

| 内容 | 体积 | 换目录的后果 |
|---|---|---|
| `Code Cache` / `Cache` / `GPUCache` / `Dawn*Cache` | 约 37 MB | 纯缓存，自动重建 |
| `Network`（含 Cookies） | 57 KB | 平台会话 cookie；grant 本身在 DSH_HOME 的 `.credentials.yaml` |
| `Local Storage` | 127 KB | 渲染进程的界面状态 |
| `Preferences` / `Local State` | 76 KB | Chromium 偏好与加密密钥 |
| `lockfile` | 0 B | 冲突的唯一实际原因 |

**DSH 自己的状态不在这里**：配置、profile、会话根、插件状态都在 `DSH_HOME`（默认 `~/.dsh`）。这个目录里只有 Chromium 侧的东西，其中大头是缓存。

## 决策

**只改 userData 路径，不动 `app.name`**：在壳里用 `app.setPath('userData', <思灵自有目录>)` 把 userData 指到自己的位置。

理由：

- 冲突的实际来源只有 userData 路径这一个；锁随它走，路径独立即锁独立。
- `app.name` 还被另外三处读——crash-report 的上报标识、client-metadata、macOS 菜单 label——改它的影响面比改路径大。
- 改路径之后，官方版回到它本该占用的默认目录，思灵退出该目录，**方向是占用方让位**，不是让官方版绕道。

**这次改动不解决 dev 与装版之间的互斥**：dev 跑的是同一份 `main.ts`，`setPath` 同样生效，于是 dev 与装版仍落在同一个自定义目录、仍共用锁。两者并行依旧要靠 `--user-data-dir` 等参数（见 `SSiD开发手册` §3.1 / §3.3 与铁律 2.2）。若要让 dev 与装版也天然分家，需另加 `app.isPackaged` 分流，那是独立的一次改动。

## 配套：一次性迁移

首次启动时若检测到老目录（`%APPDATA%\@deepseek-ai\dsh-desktop`）仍存在，把 `Local Storage`、`Preferences`、`Local State`、`Network` 复制到新目录一次。缓存目录不必搬——重建成本为零。

## 未验证：剩下一项

**真实双击场景下能否起来。** 换目录后平台登录态即便失效也可重新登录，不构成阻塞（用户 2026-10-01 明确）。

已由实测澄清的三点：

- **调用时机**已落地：`applySsidUserData(app)` 接在 `app.setAppLogsPath()` 之前，构建产物与运行日志都确认它在 `whenReady` 之前执行。
- **dev 路径不需要特别处理**：`scripts/dev.ts` 本就传 `--user-data-dir=…\development\electron-user-data`，判据命中 false、原样保留 —— 隔离实例不受影响，这正是设计意图。
- **dev 也验不了让位本身**（2026-10-02 实测）：工作区根带 `Low Mandatory Level:(OI)(CI)(NW)`，标签继承到工作区里每个 exe，从工作区启动的 `electron.exe` 因此是 Low IL —— 写 Medium 的 `%APPDATA%` 必然 `EPERM: operation not permitted, mkdir '…\AppData\Roaming\ssid-shell'`，让位随之走兜底分支。`icacls` 对照：工作区 exe 为 `Low (I)(NW)`，装版 `%LOCALAPPDATA%\Programs\ssid-shell\思灵.exe` 无 Low 标签。**这一项只能在装版上验证**，在 dev 上空耗只会得到假阴性。
  同一次运行也是兜底分支的首次现场触发：目标目录建不出来时它保持了官方默认目录，应用照常启动。

**兜底**：目标目录若不可建可写，保持官方默认目录并告警。这条来自一次真实失败：目标目录建不出来时，Chromium 连 `lockfile` 都创建不了（`process_singleton_win.cc` `Lock file can not be created`），应用直接起不来 —— 那比与官方版冲突更糟。

## 备选方案与取舍

| 方案 | 效果 | 代价 |
|---|---|---|
| 改 `app.name` | 与官方版不再冲突 | 影响 crash-report / client-metadata / macOS 菜单 label；dev 与打包不一致 |
| **改 userData 路径（选中）** | 与官方版不再冲突 | 需要一次性迁移；dev 与装版仍互斥 |
| 官方版加 `--user-data-dir` | 能否隔离**未验证**（先前的否证已作废，见下节） | 即便可行，也让占用方继续占着本该属于官方的默认目录 |
| 维持现状 | — | 两者不能并存 |

## 官方版能否用 `--user-data-dir` 隔离：未验证

一度记作「官方版拒绝该参数」，**该结论已作废**。那次测试的启动环境带毒（见下节），`electron.exe` 退化成纯 Node，任何 Chromium 开关都会报 `bad option` —— 把「参数被拒」当成官方版的属性，是把测试环境的缺陷读成了被测对象的行为。

同源的还有 `SSID-CHANGES.md` 里「两个实例共用同一个单实例锁目录（`--user-data-dir` 没能绕开它）」那条：它同样可能只踩了这个坑，**不宜再当作「该参数无效」的依据**。

目前能确证的只有一件 —— 官方 0.2.0-rc.2 的 `lib/main.js` 里 `setPath` 出现 **0 次**（实测 grep），即它自己不改 userData。它接不接受 `--user-data-dir`，**要在干净环境里重测才算数**。

**这不影响本决策**：思灵让位不依赖官方版能否被隔离。

## 坑：在装版的 pwsh 里启动 Electron 应用会带毒

装版的 subprocess runner 就是 `思灵.exe`（Electron 当 Node 用），由它派生的 pwsh 因此继承 `ELECTRON_RUN_AS_NODE=1`。带着它启动 `electron.exe`，Electron 退化为纯 Node：

```
electron.exe: bad option: --remote-debugging-port=9222
electron.exe: bad option: --user-data-dir=H:\...\development\electron-user-data
exit code 9
```

**判据**：`--remote-debugging-port` 是 dev 实例一直在用的参数，连它也被拒 —— 那就不是「某个版本不收某个参数」，而是启动环境有问题。识别方法：

```powershell
Get-ChildItem env: | Where-Object { $_.Name -like 'ELECTRON*' }
```

**在装版的 pwsh 里做任何 Electron 启动测试前，先 `Remove-Item Env:ELECTRON_RUN_AS_NODE`。**

## 锁失败的表现

`apps/desktop/src/single-instance.ts` 全文 26 行，锁失败时只做一件事：

```ts
if (!application.requestSingleInstanceLock()) {
  application.quit()
  return false
}
```

不写日志、不提示 —— 界面上就是「双击没反应」。排查这类「打不开」时，先看 userData 下的 `lockfile` 被谁占着。

## 补充（2026-10-02 凌晨查实）：真正的风险在 DSH_HOME，不在 userData

**症状**：跑过一次官方 dsh-desktop 后，思灵侧大量会话掉进「未分组」。

**根因链**：

1. 思灵的**会话根**早已隔离 —— 壳注入 `SSID_SESSION_ISOLATED_ROOT`，profile 的 `cordis.patch.yml:119` 用 `!!js` 读它，指向 `<DSH_HOME>\sessions-ssid`；
2. 但**会话分组名单 `workspace.json` 住在 `<DSH_HOME>/storages/` 下，这一层没隔离**；
3. 官方 dsh-desktop 用**同一个 `DSH_HOME`**、读的是**共享根 `sessions`** —— 它看不到隔离根里的会话，**重写名单时把它们挤掉**。

**证据**：

- `workspace.json.bak-2026-09-17T16-15-04`（DSH 自带备份）：合计登记 **297**、WorkStation **145**；2026-10-02 实测 **131 / 21**。
- 当前名单里**混着一个共享根会话**（`session-c9979ffc` → `sessions/--H-MaxNull-WorkStation--`），而其余登记项都在 `sessions-ssid` —— **自相矛盾，证明写它的是另一个实例**。
- 参照：`session_projcache`（92 MB）自 9/7 未动；`memory.json`（220 KB）10-01 23:24 仍在写。

**因此「共存」是四件事，不是一件**：

| # | 要件 | 状态 |
|---|---|---|
| ① | 单实例锁（userData 让位） | 本文上半部分：代码已写、**未验证** |
| ② | storages / DSH_HOME 隔离 | 本节新增：方案已定、**代码未写** |
| ③ | 端口 | 已天然错开：思灵 19388 / 官方 19387 |
| ④ | 全局热键 | 思灵注册了（`SSID_NOTIFY_CONFIG` / `SSID_SCREENSHOT_CONFIG`），官方版是否注册**未查** |

**② 的落点（未实施）**：思灵独立 `DSH_HOME`（壳在启动早期设该环境变量），同时把 `SSID_SESSION_ISOLATED_ROOT` 继续指向原 `…\.dsh\sessions-ssid` —— 于是几百个会话目录**一个都不用搬**，真正要迁的只有 profile 与 storages。

**动手前必须先验的两条前提**：

1. `DSH_HOME` 能否在壳启动时设定，并**早于** profile patch 的 `!!js` 求值；
2. `memory.json` 走 storage 服务还是 dsh-memory 自拼路径 —— 决定它是否也在这条隔离里。

**版本落点**：①②④ 一起进 **1.1.6**。1.1.5（2026-10-01 23:57 出包）只含 0.2.0 内核升级，不含本文任何共存改动；本机在查证时装的仍是 1.1.4（安装目录 mtime 2026-09-30 02:21:18，与 1.1.4 出包时间吻合；其 asar 内 `lib/main.js` 为 616510 字节）。
