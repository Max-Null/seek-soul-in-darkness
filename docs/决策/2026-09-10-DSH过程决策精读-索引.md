## 跨批模式（本索引最有价值的部分）

单独一篇里的结论可能像是偶然的谨慎；**同一个立场在多批里反复出现，才是可以依赖的判断标准**。目前识别出 5 个跨批模式：

### 模式 A：诚实的空白胜过补齐（出现 9 次）**← 已稳固为默认习惯，10 批出现最强形态**

不一致、缺失、不确定的地方，**标注出来，而不是补一个看起来合理的东西**。

| 出处 | 具体表现 |
|---|---|
| 02 批 ⑦ | 无法重建 alternatives 的旧笔记，永久保留一行"此处不可重建"的注释，而不是补一段像样的理由 |
| 02 批（格式强制） | 连"这篇没写 Alternatives"都用 HTML 注释显式标出，而不是静默缺失 |
| 04 批 ④ | 性能表里明写"这个数字是估算，不是浏览器测量"；未合并就关闭的 PR **不发明缺失的分类** |
| 05 批 ⑥ | "字节可重现性是假设，不是测量"——并给出行动指令：**在第一次可能被重跑的发布之前先测它** |
| **06 批（归档）** | **归档"保留那个证据，而不假装它仍然是当前的"**；归档笔记**按设计就可能过时**，不随重命名/格式/翻译/链接规则更新 |
| **07 批（pnpm）** | **主动公开不利于自己的数据**：性能表三个格子对 pnpm 不利，并附上"我们的测试环境让那个本来可能成立的优势无法显现"的解释；结论改成"**理由是生态对齐和安全，不是速度**" |

**07 批给出了这条立场的一个新形态**：前几次是"标注缺失"，这次是"**公开一个削弱自己结论的证据**"。

| **08 批（依赖分类）** | **未分类的运行时导出阻塞所有 `--fix` 写入**——"只有源头安全通过之后，`--fix` 才执行分类所蕴含的区段与范围变更"。**信息不足时拒绝猜一个分类**，而不是"尽力而为" |

**08 批给出了另一个新形态**：不是"标注缺失"，也不是"公开证据"，而是**工具在信息不足时拒绝动手**。证据不够时"尽力而为"，等于用一个更强的语气说出一个更弱的判断。

| **10 批（配对合并）** | **最强形态**：Git 合并驱动的启动器**能算出一个干净的文本合并结果，却仍然返回冲突**——因为那个结果没经过驱动的校验（六 blob 哈希、语言切换器、结构签名）。**主动放弃一个看似可用的答案，只因为它没被验证过** |

**四批四个形态**：标注缺失（02/04/05/06）→ 公开不利证据（07）→ 信息不足时拒绝动手（08）→ **放弃未经验证的可用答案（10）**。**方向一致，强度递增。**

| **11 批（Model Experience）** | **把不稳定的部分排除出契约**："稳定的契约是**增长形态**，不是数值"——精确 token 数依赖 tokenizer／序列化／配置／运行时数据，**它不稳定，所以不进契约**；契约退到"能被稳定判定的那一层"。同篇还有这条模式的**反面用法**："**无约束的缺席，在'审计过的零'和'忘记写文档'之间是模糊的**"——空白可以是诚实的，但必须是被标注过的空白 |
| **12 批（自托管演练）** | **"选择器测试不声称复现那些构建"**、"本地调度测试不声称原生运行时执行"（11 批同款）——**每篇末尾都在划定自己验证能力的边界**。这已成固定收尾：**不声称验证不了的东西** |

### 模式 B（09 批修正）：能消除的第二份真相就消除；不能消除的，让同步自动化

前 5 次都是"拒绝"，第 6 次却是"接受"——**09 批接受了一个生成文件（`THIRD_PARTY_NOTICES.md`），而它同样是派生出来的第二份拷贝**。同性质的东西结论相反，边界正好由三问划定：

| 判据 | 生成索引（❌拒绝） | 第三方声明（✅接受） |
|---|---|---|
| **① 它是必需的吗？** | 否，只是发现路径的一种便利 | 是，开源合规**要求**这份披露存在 |
| **② 源变化时能自动重生成吗？** | — | **是**："Freshness is **maintained**, not merely enforced" |
| **③ 校验能搭现成的车吗？** | — | **是**：断言放进测试泳道本来就在跑的 spec，零新门进程、零调度槽位、零 CI 步骤 |

**三问都否，就该考虑消除它；都满足，就该接受它并把同步自动化。**

| 出处 | 判断 |
|---|---|
| 01 批 ② | ❌ Knip 的例外清单（重述了清单、构建配置、包专属检查已有的事实） |
| 01 批（编排器） | ❌ YAML 里的门禁清单、手工维护的包清单 |
| 03 批（评审状态） | ❌ 定时对账器（事件流之外的第二套真相） |
| 05 批（npm） | ❌ `vendor/published.json` 账本——"**tag 反正必须存在，所以它没有引入状态的第二份拷贝**" |
| 06 批（索引） | ❌ 生成的 Agent Note 索引——复制了路径、日期、H1，而且是个**合并热点** |
| **09 批（notices）** | ✅ 生成的第三方声明——三问全满足 |

**两种成本**：第二份真相的代价不止"要同步"（漂移），还有**争用**——无关分支每次都要重写同一份文件。

**被否决的对照方案说明了关键所在**：把校验做成一个专门的 `doc-sync` 门，它"**唯一的失败模式，是在一个贡献者推完无关的依赖升级几分钟后，告诉他去重跑生成器**"——**把同步成本推给一个人**。这个方案输在第三问上。

**11 批补了一条更根本的论据**：拒绝"从源码生成中央上下文目录"的理由不止"会漂移"，还有——**AST 能找到注册，但推断不出语义条件**（历史保留、输出截断、父子可见性、辅助模型边界）。
**当源信息不足以生成正确的副本时，这个副本的问题不是"需要维护"，而是"不可能正确"。**

### 模式 C：别把不同的事混成一种状态（出现 6 次）**← 10 批出现危险形态**

| 出处 | 被拆开的两种 |
|---|---|
| 03 批 ③ | 交接（谁拥有下一步）vs 判定（GitHub 认为可合并） |
| 04 批（标签） | 意图（kind）vs 语义范围（area） |
| 05 批 ① | 未满足的合并条件 vs 评估失败（`pending` vs `error`） |
| 05 批 ② | 没有那个版本 vs 有但内容不同（重跑 vs 未升版本的改动） |
| **10 批（依赖区段）** | **分发浏览器代码 vs 让安装器下载同名包**——同一个 `devDependencies`，回答"要不要下载"与"要不要披露"是两个问题 |
| **10 批（CI 条件）** | **失败聚合 vs 资源清理 vs 被取消运行的簿记**——三种不同的义务 |
| **11 批（Model Experience）** | **"不使前缀失效" vs "保证缓存命中"**——前者是这个包能承诺的，后者只有 provider 能承诺。一句话划清责任边界 |
| **12 批（分区覆盖）** | **阈值所有权属于合并后的报告**——"每个分区有意只看到套件的一部分，会报告假未覆盖文件"。**一个有意不完整的部分，不能对自己作整体判定** |
| **14 批（Windows job）** | **"阻塞 / 红色可见但不阻塞 / 忽略"是三种处置**——`windows-coverage` 缺席于聚合 `needs`，所以它的阈值失败"**保持红色且可见，而不延迟必需的裁决**"。**把三种压成两种必然损失信息** |

**危险形态（10 批点明）**：**success-only 的聚合"能把失败的依赖藏在一个被跳过的必需检查后面"**。
**混淆状态时，错误的方向是"把失败显示成通过"**——这比漏报更危险，因为漏报至少还能被发现，而假通过会一路走到底。

**判据**：当一个字段名（`devDependencies`、`always()`）开始承担第二个问题时，**错误就藏在两个问题的差集里**。

### 模式 D：验证到消费点，而不是产出点（出现 4 次）**← 12 批给出新强度**

| 出处 | 表现 |
|---|---|
| 01 批（门禁） | 门禁必须有退出码契约；`verify-deploy-rename.mjs` 那种"只打印不退出"的形状无法挂到任何自动化上 |
| 04 批 ③ | GIF 发布不满足于"push 成功"，要重读活体 body、用 Markdown API 渲染、抓取上传 URL 确认 `200 image/gif`——**那才是评审者实际看的东西** |
| 07 批（GUI 测试） | **"fixture 全绿不算完成，真链路也必须通过"**——**fixture 短路掉的正是链路运载链，而两个经验确认的 bug 都藏在那里** |
| **12 批（分区覆盖）** | **"未完成运行不是增加并发的证据"**、"反复重启会抹掉唯一的证据"——**把"什么算证据"推进到了"证据的形成条件"**：不仅要求"我看到的是真的"，还要求"**我看到的时候，条件没有被我的观察行为破坏**" |
| **13 批（串行参考）** | **"调度和验证共享实现假设"**——所以需要一条**不共享假设的独立路径**（串行聚合）作完整性预言机。**同一实现既调度又验证时，它的错误会同时骗过两边** |

**通用问法**：这个验证手段**短路掉了什么**？被短路的那一段，就是故障的藏身处。
**12 批的追加问法**：**我这次的观察行为，会不会破坏我正在观察的那个东西？**
**13 批的追加问法**：**承担验证的那条路径，和被验证的对象共享实现吗？**

### 🆕 模式 F：可预测性战胜精确性（06 批新增，出现 1 次）

| 出处 | 表现 |
|---|---|
| 06 批（子系统页面） | 一条更**精确**的规则（"这个类型在每一轮都被循环持有/派生/流式/记录"）输给了一条更**粗糙但可预测**的规则（按仓库布局）。原因不是精确性不好，而是**要求"逐例判断重要性"的规则会在两个方向同时出错：收进不该收的，漏掉该收的**——它漏掉了半个公共 API，同时收进了四个包的类型 |

**判据**：当一个规则要求"逐例判断重要性"时，它已经在制造漏洞了。

### 🆕 模式 G：冻结 = 明确放弃更新义务（06 批新增，出现 1 次）

| 出处 | 表现 |
|---|---|
| 06 批（归档） | 归档笔记**被所有其他文档门禁排除**，理由是"它们演变的标准不能产生编辑历史的压力"；且**不随重命名包、变化的行为、翻译标准、格式规则、断裂链接更新** |

**判据**：只冻结内容而不划掉维护义务，等于没冻结——历史会持续产生工作量，而它已经不再提供价值。

### 🆕 模式 H：让工具的错误成为防线（07 批新增，出现 1 次）

| 出处 | 表现 |
|---|---|
| 07 批（pnpm） | **刻意不加** `node-linker=hoisted` / `shamefully-hoist` 逃生舱——非扁平的 `node_modules` 会让**幻影依赖大声失败**，而"这对于一个整个质量故事都是机械门禁的仓库是一个 *feature*" |

**判据**：选工具时问的不是"它的报错会不会烦到我"，而是"**它的报错恰好是我需要的那个信号吗**"。

### 🆕 模式 I：越界的机制不能走那条被阻塞的路径（08 批新增，出现 1 次）

| 出处 | 表现 |
|---|---|
| 08 批（CI 故障切换） | 有意的困境：企业池挂了 → **所有 PR 不可合并** → **"合并一个修复"这个常规恢复手段也被封死**。所以切换机制被设计成**仓库变量**而非一次合并——"**它在检查是红的时候也能工作**" |

**判据**：设计应急机制时先问——**它依赖的通道，在它要应对的那种故障里还通吗？**

### 一条张力（值得持续追踪）

01 批的标准是"**可机械判定的不变量必须编码成检查**"，但 02 批第 3 篇**主动不机械化**（术语是无界自然语言，硬上会误伤合法散文）。
