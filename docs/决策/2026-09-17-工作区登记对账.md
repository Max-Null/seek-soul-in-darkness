# 工作区登记对账：不指望上游自愈，自己补一次并留一把工具

> 状态：**已处置**（脚本 + 手册条目）· 2026-09-17
> 关联：`docs/排查/2026-09-17-多实例共用storages.md`（同一个根因家族）·
> 手册 §7 坑 #34 · `shell/scripts/heal-workspace-registry.mjs`

## 一、现象

侧栏工作区分组里的会话比实际少。用户是在会话「掉出 WorkStation 分组」时发现的，此前记在排查文档里的口径是「142/235 个会话未登记」——**那个数字是错的**，见 §四的排查纪律。

## 二、根因：官方那套自动归位只跑一次

`WorkspaceRegistry.bootstrap()`（`deepseek-harness/packages/workspace/workspace/src/index.ts:425-507`）是一段完整的对账逻辑：把历史会话按 cwd 分组，给没有工作区的 cwd **新建**工作区，给已有工作区把未登记的会话**前置**合并进去。它本该是「登记丢了也能自己长回来」的兜底。

但它被这一行挡在门外（同文件 `:127-130`）：

```ts
if (!this.state.initialized) {
  …
  await this.bootstrap(headers)
```

`global.initialized` 一旦为 `true`，`bootstrap()` **永不再跑**。本机的 `workspace.json` 早就是 `initialized: true`（我在 state 里读到了），于是：

- 平时那条「创建会话即登记」的写入（`entity.ts:146` 的 `attachSession`）是**唯一**的登记入口；
- 它一旦因多实例共用 `storages/` 互相覆盖而丢失（`docs/排查/2026-09-17-多实例共用storages.md`），就**再没有任何兜底**——会话文件完好无损，只是永远不进分组。

这也修正了排查文档里的一个说法：「2026-08-22 起停止登记」是现象而非机制，真正的原因是这条链没有自愈能力。

## 三、处置

新增 `shell/scripts/heal-workspace-registry.mjs`，规则照 `bootstrap()` 写，保持一致：

| 规则 | 取值 |
|---|---|
| 归位依据 | 会话日志首帧 header 的 `cwd`（**不是**目录名，见 §四） |
| 匹配 | cwd 归一化后与工作区 `path` 相等（Windows 大小写不敏感、去尾随分隔符） |
| 合并方式 | 未登记者**前置**（与 `bootstrap()` 一致），只加不删 |
| 跳过 | 已归档的 id；已被别的工作区登记的 id（一个会话只属于一个工作区） |
| `--new-workspaces` | 为没有工作区的 cwd 新建；跳过临时目录、跳过目录不存在的 cwd |
| 安全性 | 默认 dry-run；`--apply` 才写，并在同目录留 `.bak-<时间戳>` |

**为什么是手动脚本而不是自动对账**：`bootstrap()` 只在首启跑，正是为了不覆盖用户对分组的整理（UI 里有「从工作区移除」这类动作）。每次启动都自动对账会把用户刻意移出的会话重新塞回去——那是拿一个 bug 换另一个。所以这把工具留给人按需跑。

**必须在实例停止时跑**：运行中的实例持有内存态的整份登记，会把自己的版本写回，覆盖脚本的改动。

## 四、验证

dry-run（`--new-workspaces`）实测：

| 工作区 | 现有登记 | 待补 | 登记指向已消失的会话 |
|---|---|---|---|
| `H:\MaxNull\WorkStation` | 29 | **91** | 1 |
| `C:\Users\MaxNull\.dsh\profiles\ssid` | 13 | **45** | 2 |
| `C:\Users\MaxNull\.dsh\profiles\web` | 3 | 9 | 0 |
| `H:\MaxNull\台本` | 1 | 8 | 1 |
| `H:\MaxNull\WorkStation\deepseek-harness` | 42 | 1 | 0 |
| `H:\MaxNull\WorkStation\seek-soul-in-darkness` | 9 | 0 | 0 |
| `H:\MaxNull\WorkStation\test` | 2 | 0 | 0 |
| ＋新建 `…\seek-soul-in-darkness\shell` | — | 11 | — |
| **合计** | 99 | **165** | 4 |

跳过：临时目录 3 个（18 条评估会话）、目录不存在的笔误 cwd 1 个（`C:\MaxNull\WorkStation`，漏了盘符）。

首次 dry-run 报的是 **174**，差的 9 条是去重——同一个会话同时躺在两个会话根里，扫描会把它收两遍（见下）。

### 写回前先在副本上演练

停机窗口里没有第二次机会，所以先在一份副本上把 `--apply` 跑通：把 `workspace.json` 复制到临时 `DSH_HOME`，用目录联接（junction）把两个会话根挂进去，跑 `--apply --new-workspaces`，再按 `validateStoredState` 的约束核对结果——`workspaceIds` 覆盖全部条目且无重复、path 不重复、sessionIds 不跨工作区重复、字段类型与 `workspaceDomainSpec` 一致。**这一步抓到两个真问题**：

1. **同一会话会在登记里出现两次**：它同时存在于 `sessions-ssid` 与 `sessions`（会话根隔离时整体复制过），扫描把同一个 id 收了两遍。改为按 id 去重，这就是 174 → 165 的来源。若不修，侧栏会把同一个会话显示两次。
2. **脚本因此补了一道具名自检**：写回前若 `workspaceIds` 与条目不一致就拒绝写。DSH 启动时 `validateStoredState`（`index.ts:512-526`）会为「order 缺条目」直接抛错——写坏了不是显示异常，而是 **SSiD 起不来**。

演练在副本上进行，真实 `workspace.json` 全程未被触碰（演练后复核：条目数仍为 7、字节数与时间戳不变）。

### 实跑（2026-09-17 23:41，实例运行中）

按上面的判断，这一步**没有停机**：`workspace.json` 只在工作区变动时才写（上次写是当天 04:34，之后 18 小时没动），所以运行中写回是安全的，前提是写回到重启之间不发生「新建会话 / 删除会话 / 跨分组移动 / 新建工作区」这类动作。

| 项 | 结果 |
|---|---|
| 写回 | 165 条补入，8 个工作区；文件 11,888 → 20,472 字节；备份 `workspace.json.bak-2026-09-17T15-41-08-453Z` |
| 写回后自检 | `workspaceIds` 覆盖全部条目且无重复、path 不重复、sessionIds 不跨工作区重复、字段类型合规 |
| 重启后 | 登记**原样保留**（264 条；文件时间戳仍停在写回那一刻——DSH 只读没写） |
| 最强证据 | **SSiD 正常启动**：`validateStoredState` 在启动路径上，写坏了起不来 |

登记分布（重启后实测）：`WorkStation` 29→120、`profiles/ssid` 13→58、`profiles/web` 3→12、`台本` 1→9、`deepseek-harness` 42→43、新建 `shell` 11。

### 两条排查纪律（这次都踩过）

- **认 header 里的 `id`，不要用目录名当键**。会话目录名有的带 `session-` 前缀、有的不带；我第一版脚本用目录名做键，于是大批会话匹配不上，得出「登记 99 条里 83 条对不上、142/235 未登记」的**错误结论**。改用 header 的 `id` 重扫后完全反转：登记其实大体健康——`deepseek-harness` 42 条全在、`seek-soul-in-darkness` 9 条全在、`test` 2 条全在，缺失集中在两个活跃工作区。**统计脚本错了，比没有统计更危险**，因为它会导向错误的修复方案。
- **先问「我算的是哪个集合」**。`sessions-ssid`（237 条）与 `sessions`（286 条）两个根有**大量重复 id**（会话根隔离时整体复制过），并集只有 333 条。算「未登记数」时用并集还是各自，会差出一倍。

## 五、边界

- **它不修「运行时又丢了一条」**。脚本只补执行那一刻的存量；下一个会话期若再被覆盖，还得再跑。真正的根治在运行时那条登记路径（上游），或让 SSiD 在启动前自动对账——后者因 §三 说的理由没有采纳。
- **登记里指向已消失会话的 id 不清理**（本次 4 条）。`bootstrap()` 也不删；可见性由 DSH 自己的过滤负责，删它属于额外风险。
- **不覆盖工作区标题与顺序**：只动 `sessionIds`，`title`/`createdAt`/`workspaceIds` 顺序保持原样（新建工作区例外，按 `newestAt` 降序追加）。
