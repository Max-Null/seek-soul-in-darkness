# 请求扩展准备失败：一条「临时本地插件条目」打死实例的全部模型请求（2026-10-02）

> 状态：**已修复**（2026-10-02；本机运行时恢复 + 发版基准对齐 + seed 自愈 + 新机械门，证据见 §七）
> 关联：手册 §7 坑 #66 · 坑 #42（本地 `link:` 与依赖解析）、#31（条目配置打死整棵插件树）、#40（模板改了运行时不会自己跟上）；`docs/决策/2026-09-17-工作区登记对账.md`（那条临时插件的由来）
> 影响面：本机 **profile `ssid` 的全部实例**（SSiD 桌面版，以及任何加载该 profile 的实例）在 **15:43:22 → 15:53:51** 之间的**每一次模型请求 100% 失败**；同一时段 profile `desktop`（DSH 官方桌面实例）完全正常，用户据此误以为"只有某个会话坏了"

## 一、Problem

用户报障：SSiD 窗口里**每一轮**都停在

```
本轮运行失败
DeepSeek request extension preparation failed
```

- `本轮运行失败` 是客户端对 `turn/end { reason: { kind: 'error' } }` 的文案（`packages/client/ui-chat/src/client/locale.ts` 的 `message.turnError`），紧随其后那行才是错误正文。
- 失败**不在网络、不在模型、不在密钥**：从 `request/header` 落盘到 `finish: error` 只隔 **17–27 ms**，HTTP 请求根本没发出去（`sessions-ssid/…/session.v4.jsonl.zstd` 里 `assistant/attempt` 的 finish 时间戳可逐帧复算）。
- 触发面是**整个 profile**：新建的会话第 1 步就炸（`session-251e343b` turn 1 step 1），标题生成那条旁路请求同样炸（`session/title-llm-request` 之后紧跟 `finish: error`）。

## 二、根因与机制

一句话：**profile 补丁里插入了一条指向本地文件的插件条目，而该文件向上找到的最近 `package.json`（就是 profile 根那份）声明了 `name` 却没有 `version`；负责给每次 DeepSeek 请求收集插件包清单的 provider 对"有 name 无 version"是硬失败，于是每一次请求在建链阶段就抛错。**

四段机制链（每段都有确定的抛出点）：

| # | 环节 | 位置 | 事实 |
|---|---|---|---|
| 1 | 请求扩展准备失败被包成 `REQUEST_EXTENSION` | `packages/llm/llm-deepseek/src/adapter.ts:628-637` | `prepareExtensions()` 抛任何错 → `LlmError('DeepSeek request extension preparation failed', 'REQUEST_EXTENSION')` |
| 2 | 任一 provider 抛错 ⇒ 整次请求失败 | `packages/llm/deepseek-llm-api-extensions/src/index.ts:108-129` | `prepare()` 并发跑**所有**已注册 provider，`Promise.all` 拒绝即整体拒绝；没有"跳过坏 provider"的降级 |
| 3 | 真凶 provider：每次都解析活跃条目的包身份 | `packages/llm/plugin-package-inventory-deepseek/src/index.ts:196-204`（注册）、`:157-185`（收集） | `dsh_plugin_packages` 字段：`activeEntries(ctx.loader)` → `resolver.resolve(entry)` |
| 4 | **硬失败点** | 同上 `:62-70` + `:111-131` | `identityFromManifest(path, allowAnonymous)`：`allowAnonymous=false`（裸包名）要求 name+version 都非空；`allowAnonymous=true`（本地文件模块）**只在 name 缺失时放行**——name 有、version 无 ⇒ `throw new Error('… must declare non-empty name and version')` |

第 4 段的分支走向由条目 `name` 的形态决定：

```
barePackageName('C:/Users/MaxNull/.dsh/profiles/ssid/tmp-ws-fix.mjs')
  → specifier.includes(':') → undefined        // 不是裸包名
isAbsolute(…) → true                            // 走本地文件分支
moduleUrl = pathToFileURL(…)                    // file: 协议
manifest = nearestManifest('…\profiles\ssid\tmp-ws-fix.mjs')
  → 自 dirname 逐级向上找 package.json
  → 命中 …\profiles\ssid\package.json           // ← 就是它
identityFromManifest(manifest, allowAnonymous=true)
  → name === 'dsh-profile-ssid'（有）
  → version === undefined（无）
  → THROW
```

离线复算（与内核同款逻辑，逐条照抄 `:111-131` 的分支）实测输出：

```
barePackageName = undefined
nearestManifest = C:\Users\MaxNull\.dsh\profiles\ssid\package.json
name= "dsh-profile-ssid"  version= undefined
RESULT: THROW -> …\profiles\ssid\package.json must declare non-empty name and version
```

而 `profiles/ssid/package.json` 的形状来自官方 `initProfile`（`packages/boot/app-boot/src/profile.ts`）：`{ name, private, dependencies, dsh.profile.bundles }`——**官方骨架本来就不写 `version`**，本机 6 个 profile（ssid / web / desktop / headless / assistant-probe / rc1-clean）**全部缺**。所以这不是"某个文件被改坏了"，而是**骨架与 provider 预期的错配**，只要有本地文件条目落进 profile 目录就会显形。

## 四、Decision

分三层，**先恢复、再治本、最后上机械门**：

### 第一层：立即恢复（一次性，已执行）

1. `~/.dsh/profiles/ssid/cordis.patch.yml`：删除临时条目（9 行，含注释块），保留 `storage-json` 为末条目；改前备份 `cordis.patch.yml.bak-<时间戳>`。
2. 删除 `~/.dsh/profiles/ssid/tmp-ws-fix.mjs`（其一次性修复在 15:43:22 已完成：`ws-fix.log` 三条 attach OK，`storages-ssid/workspace.json` 15:46:06 已落盘）。
3. 依赖 Loader 的配置热加载（15:43:22 已实测会热加载），**不重启任何实例**；`ws-fix.log` 之后不再出现 `apply called` 即证明条目已卸载。

### 第二层：治本 —— 让 profile 根 manifest 恒有非空 `version`

触发条件里唯一**由我们掌握**的变量，是"profile 根 manifest 缺 version"。三处一起收：

| 落点 | 动作 | 为什么是这里 |
|---|---|---|
| `ssid-desktop/apps/desktop/src/ssid/profile-seed.ts` 的 `mergeProfileManifest()` | 合并时**只在缺失时补** `version`（`'0.0.0'`），已有值一律不动 | seed 每次启动都跑、对所有用户生效，是**唯一能自愈**的落点；"只补不覆盖"保住既有的"用户层优先"语义 |
| `~/.dsh/profiles/ssid/package.json`、`~/.dsh/profiles/web/package.json` | 本机一次性补齐 `version` | 与 seed 的效果等价，但不必等下一次启动；web 侧是本机的 web 开发环境，由同一批脚本维护 |
| `shell/profile-template/package.json` | 补 `version` | 发版基准是"照着抄的范本"，范本不带这个字段，下一个人就会再抄一份缺字段的 manifest |

**不改的**：DSH 源码（铁律 2.0）。`identityFromManifest` 的判定在官方内核里，装版内核还随包进 `app.asar/dsh/`——改源码既违规又追不上上游。

### 第三层：机械门 —— 让"没人会报警"变成"门会报警"

本次真正的教训不是"写错一行 YAML"，而是**整条链路沉默**：YAML 合法、插件正常激活、日志无异常、报错文案指向"DeepSeek 请求"（把人往网络/密钥方向带），而唯一能解释它的规则（provider 对 manifest 的硬要求）不在任何门里。

新增 `shell/scripts/check-profile-manifest.mjs` 并纳入 `check:rules`：

1. **受管 profile 根 manifest 必须声明非空 `version`** —— `shell/profile-template/package.json` + 受管 profile（`check-rules.manifest.json` 的 `profiles` 白名单 + `web`）。这条直接钉住本次的根因，**零依赖、结构化 JSON 解析**。
2. **补丁里以本地文件路径插入的条目**，其 `nearestManifest` 命中的 manifest 必须带非空 `version` —— 钉住**机制**而不是钉住那一个文件：未来只要有人再往任何 profile 插一条 `name: <路径>/x.mjs`，门会点名它落在哪份 manifest 下、缺哪个字段。
3. 配自测（`check-profile-manifest.spec.mjs`，沿用 `check-bom.spec.mjs` 的注入式自测范式：`SSID_PROFILE_MANIFEST_ROOTS` 指定临时目录，**测的是门本体而不是副本**）。

## 五、Alternatives considered（备选与不采纳理由）

| 备选 | 不采纳的理由 |
|---|---|
| 改 DSH 源码让 `identityFromManifest` 对"有 name 无 version"宽容（降级为排除） | 违反工作区铁律 2.0（`deepseek-harness/`、`dsh-web-runtime/`、asar 里的内核只引用不改）；且装版内核随包进 asar，改 checkout 也改不到用户机上，反而制造"dev 正常 / 装版坏"的不可信对照。**改为记入"待提上游"**（见 §六） |
| 只删临时条目，不动 manifest（治标） | 触发条件只被移走一次：下一次任何人再写 `tmp-*.mjs`（这类一次性修复脚本是常见手法）就会原样复现，且症状同样误导。本次事故就是"上一个人写 tmp 脚本时没人报警" |
| 关掉 `dsh_plugin_packages`（`config.enabled=false`） | 用绕过代替修复：牺牲官方请求侧的插件包清单能力（上游靠它做插件包溯源），而且**只要有人再打开它，坑立刻回来**；config 层的开关也不会让任何人知道原因 |
| seed 里改成"写死 manifest"（整体重写） | 会覆盖用户层（`dependencies` 里用户自装的插件、用户改过的版本），与既有的"只增不覆盖"语义冲突，风险远大于收益 |
| 把 `version` 加到 `check-rules.manifest.json` 的 `hardScopes` 里当文本检查 | `hardScopes` 只做"旧名残留为零"的文本/结构化比对，语义不匹配；且它管的是命名，不是字段存在性。宁可新写一门，也不把两种判定塞进同一个门 |
| 只在手册里加一条坑、靠人记住 | 无机械保障。手册 §7 已记 65 条坑，其中多条（#30/#37/#40）的复盘结论都是"规则写在注释/列表里，不会自动扩散"——本条的处置按同一结论做成门 |

## 六、Consequences

- **对运行时是惰性的**：给 profile manifest 多加一个 `version` 字段不改变内核行为——`readProfileManifest` 只读 `name`/`dependencies`/`dsh`，而同款形态的 `createRuntimeProjectMetadata()` 自己就在写 `version: '0.0.0'`（`project-manager.ts:137-143`）。
- **"只补不覆盖"保住了用户层语义**：用户或插件中心写进 manifest 的既有 `version` 不会被 seed 改写；既有单测"幂等：第二次调用逐字节不变""用户层优先：已有的链接与声明都不动"仍成立（这两条 fixture 里骨架缺 version，需按新语义补一条断言：**缺失则补、已有则不动**）。
- **门的覆盖边界要写明**：只管 `profile-template` + 受管 profile（`ssid`/`web`）。DSH 官方自建的 profile（`desktop`/`headless` 等）不在管辖——它们由官方 `initProfile` 生成，本次事故未波及；将来若要管，判据是"这个 profile 会不会被插入本地文件条目"。
- **上游那处"语义不一致"：不提（2026-10-02 用户判断）**。`identityFromManifest` 的 `allowAnonymous` 分支放行"完全匿名"的本地模块，却对"有 name 无 version"硬失败 —— 用户认为这更可能是**官方有意做的社区规范化**（要求自称成包的模块把身份写全），两种待遇对应两类东西（真正的临时模块 vs 自称成包的模块），**不是缺陷**。本工作区不改源码，**此待办关闭**（与 §五 的第一条备选同源）。
- **保留的临时性**：`gap` 期间被"杀掉"的那次工作区登记修复**已经完成**（登记数 25→28 并已落盘），不需要重做；本文不改变它。

### 回退与未做

- **回退**：`cordis.patch.yml.bak-2026-10-02T07-53-51-031Z` 覆盖回原文件即可（不建议——会把报错带回来）；两份 profile manifest 的 `.bak-versionfix` 同目录可回退。
