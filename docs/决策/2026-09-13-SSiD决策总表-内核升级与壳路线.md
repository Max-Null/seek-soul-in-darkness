# SSiD 内核升级决策总表（0.1.2-rc.1 → 0.1.5-rc.2）

> 日期：2026-09-13
> 状态：已决策
> 决策人：MaxNull
> 配套：`2026-09-12-SSiD内核升级-0.1.5-rc.2.md`（执行记录与证据）、`SSiD内核升级报告-0.1.5-rc.2.html`（全景报告）

> 本篇是四段模板的第二个应用。与执行记录的分工：**执行记录回答「发生了什么」，本篇回答「定了什么、排除了什么、为什么」**。
> 用户的原始要求：*「不止记录要做什么，也要记录不要做什么，更要记录为什么这样决策」*——所以 `Alternatives considered` 一节是本篇的主体，不是附录。

## Problem

本轮内核升级牵出的决策超出了「升个版本」的范围：它同时暴露了一处**工作区级**的资源冲突（共享 checkout）、三处**被内核逼出**的适配、以及若干**跨轮次才能定**的路线选择（换不换桌面壳、做不做签名、移不移内核进程）。

这些决策如果只留在对话里，下次会被重新讨论一遍；只看执行记录又会缺「为什么没走另一条路」。需要一份能让人**独立复盘**的落盘：选项、否决理由、以及**生效条件**（"现在不做"和"永远不做"必须区分开）。

## Decision

### D1 升级目标取 `0.1.5-rc.2`（而非核对清单写的 rc.1）｜**已执行**

核对清单（2026-09-10 版）写的是 rc.1，但执行时 npm `next` 已是 rc.2（rc.1 停在 `latest`）。实测二者对本轮**唯一的破坏性变更完全一致**（`packages/preset/` 下 rc.1→rc.2 只改 package.json 版本号），故取更新者。

### D2 共享 checkout 加红线 + web 版内核隔离｜**已执行**

`deepseek-harness/` 同时是 web 版与 SSiD 的内核来源（web profile 不带内核闭包）。对它做 `git checkout` / `pnpm install` / `pnpm run build` 会**连带影响运行中的 web 宿主**——本轮实际发生了：web 版被连带升级后崩溃。

处置：为 web 版建独立副本 `dsh-web-runtime/` + `启动-DSH-Web.bat`（设 `DSH_CHECKOUT` 指向副本）；约束写进工作区 `AGENTS.md` 铁律 2.1 与手册 §5.0 第 0 条。

### D3 隔离走「独立副本 + 各自启动入口」，**不用**用户级 `DSH_CHECKOUT`｜**已执行**

用户级环境变量会同时改变 SSiD 的内核解析，把问题从"web 被动升级"变成"两边都指向同一个 checkout"，更乱。

### D4 插件适配：`dsh-pocket` 2.10.3 → 2.10.6｜**已执行（分发面待同步）**

`client-connection` 在 0.1.5 把 inject 收缩为 `['credentials']`，而 `rpc.handle` 的 owner 是 **connection 自己的 ctx**（`get rpc()` 里 `const owner = this.ctx`）——不是宿主能力问题。2.10.6 的 `inject` 含 `webServer` 并优先自行挂载路由，是官方适配写法。

### D5 版本号显示改为「实际加载的内核模块」｜**已执行**

标题栏读 `installAnchor`（部署闭包），而 dev 下 tsx 的 paths 让模块实际从 checkout 源码加载——两者不一致时显示"没升级"，与实际相反。改为 `import.meta.resolve` 走与运行时相同的解析链读取实体版本，`installAnchor` 降为兜底。

### D6 内核升级必须同步的「口子」写进手册 §5.0 / §5.5｜**已执行**

preset 手工部署（两副本）、persona 字段跨版本会变、tsconfig paths 手写清单、dev 源码模式要求 checkout 自身完整（paths / install / `lib/` 三条件）、以及"先确认单实例锁持有者"的排查纪律。

### D7 **不切换**到 DSH 官方桌面壳（当前时机不成熟）｜**已决策，条件性搁置**

**触发条件（满足其一即重评）**：官方桌面端出现正式发版或 CI 构建；或 SSiD 需要"无端口 + 最小 IPC 暴露"这一整套安全姿态；或自研壳的维护成本超过迁移成本。

### D8 **不**自己做代码签名证书（非商业用途）｜**已决策**

不签名也能运行，仅首次启动有系统提示。成本：Windows OV 约 $200–400/年（EV 需企业资质）、macOS 需 Apple Developer $99/年。**触发条件**：出现对外分发计划。

### D9 **不**降级内核｜**永久排除**

DSH 会话格式已是 v3 且**无降级路径**（源码只有 v0→v1→v2→v3 迁移器，错误文案写死 `ships no upgrade path for it`）。旧内核读 v3 日志会让已有会话**永久打不开**——「出问题就回退内核」在 SSiD 上不成立。

### D10 **不**急于处理 webserver 债务，但记下硬边界｜**已决策**

全家桶有 15 个插件用 `webServer`。走"无 webServer 宿主"路线时 HTTP 路由可迁到 `connection.fetch.register`，但 **WebSocket 无替代通道**（`registerUpgrade` 是 HTTP upgrade；Electron `protocol.handle` 只处理 Request→Response）。**下一步不是动壳，而是先看 better-sidebar 上游是否提供非 WebSocket 方案。**

### D11 **不**顺带引入 `workflow` / `ralph` 工具面｜**已决策**

DSH 0.1.5 提供这些 `tool-*` 行，但 SSiD 的委派体系是自研四角色（灵犀/明镜/巧匠/明瞳）。顺带引入等于同时暴露两套委派概念，需单独评估——不在本轮范围。

### D12 **不**改壳的进程模型以外的通信机制｜**已决策**

D7/D10 相关。保留 `webServer` 与现有壳↔页面通道（标题栏/托盘/截图/主题同步）。

### D13 dsh-capture 路由迁移：分支保留、**暂不合入**｜**已决策**

分支 `feat/connection-fetch-routes-clean`（`54f75ec`）已就绪并验证（typecheck + build + 8 项 rc.2 契约核对），但经 §D10 的归因更正后**对当前 SSiD 收益为零**（SSiD 有 webServer，新旧写法走同一挂载点）。价值是为无 webServer 宿主铺路。

## Alternatives considered

| 决策 | 被否决的备选 | 否决理由 |
|---|---|---|
| D1 | 按清单升 rc.1 | 清单写于 rc.2 发布前；rc.2 更新且改动集一致，选新不选旧。清单的版本号属**过期信息**，不是承诺。 |
| D1 | 升到 `0.1.5-alpha.2`（更新的 alpha 通道） | alpha 通道无回归验证，且清单针对 rc 段整理；rc 已是官方候选发布。 |
| D2 | **直接切主 checkout**（本轮实际做法） | 正是事故成因。checkout 是**共享资源**，SSiD 单方面切版本会连带升级 web。 |
| D2 | 让 web 版也带内核闭包（彻底不依赖源码） | 改造面大（web profile 由官方模板生成，无归档机制），且收益与"独立副本"相同。列为将来可选。 |
| D3 | 用户级环境变量 `DSH_CHECKOUT` 指向独立副本 | 会同时改变 SSiD 的内核解析——把"web 被动升级"换成"两边都读同一个 checkout"，更难排查。隔离必须**分入口**。 |
| D3 | 改 OpenCode 启动器配置注入环境变量 | 启动器是闭源桌面应用，未找到可注入环境变量的配置点；脚本入口是等效且可控的做法。 |
| D4 | 回退到 rc.1 内核（让旧插件继续工作） | 违反 D9：v3 会话不可降级。**这条路在物理上就堵死**，不是取舍问题。 |
| D4 | 临时禁用 `dsh-pocket` 让 boot 通过 | 治标；且插件是用户常用功能。上游已有官方适配版（2.10.6，其源码注释逐字写明了这个坑），没有理由不用。 |
| D5 | 只改 `installAnchor` 的取值（让 dev 指向源码） | 会破坏 `healProfilesModuleFallback` / `loadProfile` 的锚点语义——那两个 API 依赖锚点找 bundle 物理目录。显示层的问题应在显示层解决。 |
| D5 | 版本号显示两个值（闭包版 + 源码版） | 标题栏空间有限，且用户需要的是"在跑什么"这一个事实。来源标注（source/bundled）已能区分。 |
| D5 | 不动它（用户能看到 About 页详情） | 显示与实际相反会**系统性误导排查**——用户第一反应就是"升级没生效"，本轮已实际发生。 |
| D7 | 立刻切官方桌面壳 | ①官方从未发布过安装包（12 个 release 资产数全为 0）；②无任何 CI 构建（`.github/workflows` 20 个文件 grep `desktop` 零命中）、`private: true`、无兼容承诺——"把维护交给官方"这个收益**不存在**；③官方壳显式禁用 `webserver`，15 个插件要改造；④壳↔页面交互（标题栏/托盘/截图/主题）在官方模型下无对应物，要重建；⑤协议号 `DESKTOP_HOST_PROTOCOL_VERSION` 是内部号、overlay 的 patch 行 id 未命中只 warn 不报错，上游改名会**静默失效**。 |
| D7 | 在 SSiD 仓库 fork 官方壳 | 同 D7 的②③④，且额外背上 fork 漂移。 |
| D7 | 用官方壳但保留自研 webServer 与交互通道 | 与官方壳的进程/通信模型冲突（官方是子进程 + 分帧字节管道 + `dsh-app://` 协议），等于只借了打包配置，收益最小而改造最大。 |
| D8 | 立即买证书 | 非商业用途，收益（消除首次启动提示）不抵成本。且与"用哪个壳"无关——**签名不可借用**，官方签名绑定其构建者证书，改代码重打包后原签名即失效。 |
| D8 | 借官方签名 | 同上，物理上不可能。且官方根本没有已签名的安装包可借。 |
| D9 | 保留"回退内核"作为兜底方案 | 会让已有会话永久不可读。兜底方案必须是**前向**的（修当前版本），不能是后向的。 |
| D10 | 现在就把 15 个插件迁到 `connection.fetch.register` | 对当前 SSiD 收益为零（有 webServer，同一挂载点）；且 WebSocket 那 3 条**无解**，迁一半反而留下不一致状态。 |
| D10 | 把 webServer 从"宿主提供"改成"插件自持" | 每个插件自建 HTTP 服务会引入端口管理、认证、生命周期等一整套问题，比现状差。 |
| D11 | 顺手启用 Workflow/Ralph | 两套委派概念并存会让用户与模型都难以判断该用哪个；且其价值未在 SSiD 场景验证。 |
| D13 | 直接合入 main 并发布 0.3.1 | 收益为零的改动不值得单独发一版（npm 发布是 F2A，用户手动执行，更不该为此打扰）。 |
| D13 | 删除该分支 | 它验证过、可合入，且是 D10/D7 路线的现成起点；删了将来要重做。 |

**D14 内核移出 Electron 主进程：分两阶段，第一阶段已完成（2026-09-13 续）**

原列在"未闭合项"的第 3 条，本轮推进了核心部分。**阶段一（已完成并验证）**：

- `shell/kernel-child.ts`：把内核跑在独立 Node 子进程里，经 Node IPC 上报 `port/url/dshVersion`、转发通知用的会话事件（`turn/start`、`turn/end`、`approval/asked`）、响应 `shutdown`，并在父进程 IPC 断开时自我了结（不留孤儿占端口）。跑在标准 Node 里，因此不再需要 `module-resolution.ts` 那套 `registerHooks` 绕行。
- `shell/host-process.mjs`：主进程侧 spawn、等 ready（带超时）、事件回调、优雅关闭（15s 超时后强杀）。
- **实测**（从 `shell/` 跑）：子进程成功 boot 内核，`dshVersion = 0.1.5-rc.2`、端口在监听、HTTP 401（就绪）、空闲期无事件转发、关闭后端口释放。typecheck 0 错（`kernel-child.ts` 原先不在 `tsconfig.include` 里，已补——否则这个文件根本没被类型检查过）；单测 50/50。

**为什么不用官方那套分帧字节管道**：官方 `host-protocol.ts` 的 fd3/fd4 帧协议是为了让窗口走 `dsh-app://` 自定义协议、**彻底不要端口**。SSiD 的内核本来就监听 127.0.0.1 随机端口、BrowserWindow 直接 loadURL，所以只需传出端口与生命周期——引入那套协议等于凭空多维护一个协议而无收益。

**阶段二（未做）**：

| # | 项 | 说明 |
|---|---|---|
| 1 | `main.mjs` 切换 + `SSID_KERNEL_CHILD=1` 开关 | 开关式集成（默认仍同进程），便于灰度与回退 |
| 2 | **反向能力通道** | `restart` / `update` / `screenshot` 是闭包、无法跨进程传递；不补则子进程模式下「设置页重启按钮 / 在线更新 / 快捷截图」失效。这是阶段二的主体工作 |
| 3 | `turn/start` 的 time 字段 | 子进程转发里缺内核的 `event.time`，用时暂按主进程本地时钟估算；补上才能与同进程模式完全一致 |
| 4 | `session/event` 的类型正确写法 | 该事件声明为 `this: Scoped<Session>`，根 ctx 不满足；当前用受控断言（依据 `main.mjs:1286` 同款调用已在生产运行数月），应下沉到 session 作用域（cordis 未导出该类型名，需另找路径） |
| 5 | 打包链路 | `kernel-child` 需要 bundle（打包版用内置 `node.exe` 跑 bundle，dev 用 `tsx` 跑 TS），并确认 electron-builder 的 `extraResources` 带上它 |

## 附：本轮新增/更新的规则与坑

| 位置 | 内容 |
|---|---|
| 手册 §7 坑 14 | **YAML block mapping 不能加尾逗号** —— 该文件是 block 风格，条目不带逗号；批量切版脚本惯性加逗号会让 `pnpm install` 直接报 `bad indentation of a mapping entry`。且改完必须用真解析器验语法，正则自检挡不住 |

| 手册 §7 坑 16 | `prepare-runtime.mjs` 第 4.5 步会把 vendor 根的 `README.md` 当插件目录复制（产物里出现 0 字节的 `@max-null/README.md`） |
| 工作区 `AGENTS.md` 铁律 2.1 | 共享 checkout 是红线；隔离走独立副本 + 各自启动入口；不用用户级 `DSH_CHECKOUT`；降级内核不是选项 |
| 手册 §5.5 | dev 源码模式的三个条件（paths / 完整 install / `lib/` 产物）+ 单实例锁排查纪律 |

**本篇的自我限制**：所有"实测"结论均附可复现命令或文件行号；「推断」在正文显式标注。本轮共发生 3 处**我自己的判断错误**（切共享 checkout 未告知、假设 SSiD 无 webServer、检查器未校准就下结论），全部已在执行记录中留痕——保留它们的理由与保留正确结论相同：**复盘时最有价值的是错误路径，不是成功路径。**
