# 0.2.0 升级遗留：两处插件降级项

> 记录时间 2026-09-29 · 内核基准 `0.2.0-rc.1` · 证据取自 `.ssid-iso-test/logs/` 下 dev 实例的日志
> **两个插件都是第三方**（在 `third-party-plugins/`，不在我们的 `max-null-plugins/`）—— 修复要走 PR 或等作者。

## 共同前提：两者的 peer 都还停在 `0.1.x`

| 插件 | 版本 | 上游 | 内核 peer |
|---|---|---|---|
| `dsh-sidebar-qa` | 1.0.2 | `ChenRuoT/dsh-sidebar-qa` | `dsh-client-locale=^0.1.0-rc.8`、`dsh-client-ui-primitives=>=0.1.2-alpha.2` |
| `dsh-dream-skin` | 9.14.2 | `RevolutionLA/dsh-dream-skin` | 6 条全 `^0.1.0-rc.x`，另依赖**已消亡**的 `@deepseek-ai/dsh-client-runtime` |

`^0.1.x` 对 `0.2.0-rc.1` 判定 false（caret 上界是下一个 minor），所以**它们现在纯靠 profile 的 `compatibility.json` 豁免在 0.2.0 下运行**。豁免按**精确版本**匹配 —— **作者一发新版，豁免就失效，插件会被静默跳过**（不进 fiber 图、界面上不报错）。

## 一、`dsh-sidebar-qa`：设置项在 0.2.0 下不可编辑

**现象**（每次启动一行 info）：

```
[dsh-sidebar-qa] this host offers no settings namespace registration (dsh-settings ≥ 0.1.7 derives editable fields from the plugin Config instead); the sidebarqa namespace is skipped and defaults are used
```

**这不是 bug，是刻意的降级。** 插件**按结构**（而非按版本）做能力探测，探测不到 `register` 就返回一个带类型的拒绝、继续跑默认值。它的注释写明了迁移该落在哪：

> A future migration that keeps the settings page alive on 0.1.7+ (declare a volatile `Config`, then address the form by entry id) would land here; the guard is what makes that additive instead of a behavior cliff.

**成因**：`dsh-settings` 从 `0.1.7-alpha.1` 起删掉了 `SettingsProvider.register(ns, schema)`，服务改名 `SettingsForms` —— 可编辑字段改由插件导出的 `Config` schema（volatile 字段）派生，`describe` / `update` 按 **profile entry id** 寻址，不再是插件自选的命名空间。**没有兼容入口**。

**影响**：`sidebarqa` 的设置项在该内核下不可编辑，一律取默认值；`/sidebarqa/api` 的 config 路由返回准确的拒绝，而不是假数据。

**修复路径**（插件注释自己给的）：声明 volatile `Config`，再按 entry id 寻址表单。落点是 `src/settings-face.ts`。

**若我们提 PR，有两个坑必须避开**（`third-party-plugins/DSH-better-sidebar/AGENTS.md` §3.1 第 1 条记着）：

- 必须用 **DSH 自己的 schemastery**（`@deepseek-ai/schemastery`）——用公开的 `schemastery` 包会**静默丢弃**每一次改设置：写入报成功、revision 也涨，但有效值永远不变。
- `.volatile()` 走 `extra()`，**返回副本而非原地修改** —— `for (const f of ...) f.volatile()` 会把标记丢掉，必须收集返回值。

**旁证**：日志里紧跟着还有一句 `this DSH has no right sidebar …`，**那不是降级** —— 它是启动早期的服务探测噪声，同一份日志随后就有 `[dsh-sidebar-qa] registered 2 tabs in DSH's own right sidebar`。别把它当成第二个问题。

## 二、`dsh-dream-skin`：CSS 类名漂移，material refinements 失效

**现象**（启动后一条 warn）：

```
[dsh-dream-skin] host class names drifted — these material refinements are inactive on this DSH build (harmless, cosmetic only):
  .bqrRRG_card | .lXshSW_root,
  ._7yHdaG_panel | .uV2eYG_root |
  .nArs4W_panel, .nArs4W_pane, .nArs4W_paneContent, .nArs4W_workbench, .nArs4W_explorerBody |
  .hHd-Xa_root .hHd-Xa_footArea, .hHd-Xa_root .hHd-Xa_settingsArea, .hHd-Xa_root .hHd-Xa_footerActions |
  .qDHVXG_fade
```

**成因**：DSH 的样式用 **CSS Module 哈希类名**（`.bqrRRG_card` 这种），上游每次构建都可能变。插件靠这些类名做材质注入，漂移后选择器匹配不上。

**影响**：**纯外观** —— 插件自己标注 `harmless, cosmetic only`。

**⚠️ 清单会增长，别只看一次日志**：两次运行拿到的清单**不同** —— 01:30 那次有 `.qDHVXG_fade` 而没有 `.nArs4W_*`；02:03 那次有 `.nArs4W_*`。说明插件是**遇到一个记一个**，取决于当时打开了哪些界面。要拿全清单得覆盖各种界面状态多跑几轮。

**修复方向**（推测，需与作者确认）：改用**稳定锚点** —— DSH 的约定是 `data-slot` / `aria-label`（工作区铁律 8 与手册 §9「样式一致」对我们自己的插件也是这条要求）。

**⚠️ 限制**：该仓库里**没有 `src/`**（`git ls-tree -r --name-only HEAD` 顶层只有 `lib/`、`docs/`、`tests/`、`scripts/`、`wallpapers/`），所以改法只能从它的 `docs/` 与打包产物 `lib/client.js` 里推，无法直接定位到源码行。

## 优先级建议

| 项 | 优先级 | 理由 |
|---|---|---|
| 两者的 **peer 范围** | **高** | 不改就一直在豁免上跑，作者一发新版就静默掉；而且这是**发布前必须处理**的（`profile-template` 要记最终版本） |
| `sidebar-qa` 设置项 | 中 | 真实功能缺口（设置不可改），但有准确降级、不影响主流程 |
| `dream-skin` 类名漂移 | 低 | 纯外观，插件自己判定无害 |
