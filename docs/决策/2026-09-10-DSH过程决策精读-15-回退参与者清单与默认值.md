## 1. 实测的 PR preview runner 尺寸

`2026-09-06-preview-hosted-runner-sizing.md`

### 他们遇到的事

一个容易被忽略的计费机制，写在 Problem 的第一句：

> **A lower per-minute runner price does not guarantee lower job cost because GitHub rounds each job upward to whole minutes.**

**更低的每分钟 runner 价格，不保证更低的每 job 成本——因为 GitHub 把每个 job 向上取整到整分钟。**

于是"换更便宜的 runner"这个直觉需要实测，而不是按单价推算。

### 测量结果

| Runner | 冷 / 热 job 秒 | 取整分钟 | 每个 USD | 工作区秒（冷/热） | preview 秒（冷/热） |
|---|---:|---:|---:|---:|---:|
| standard, 2 vCPU | 202 / 203 | **4** | **0.024** | 138.92 / 147.21 | 12.65 / 12.94 |
| larger, 4 vCPU | 177 / 162 | 3 | 0.036 | 124.21 / 114.86 | 10.77 / 9.88 |
| larger, 8 vCPU | 154 / 154 | 3 | 0.066 | 110.51 / 110.77 | 9.20 / 9.21 |
| larger, 16 vCPU | 124 / 125 | 3 | 0.126 | 90.57 / 84.99 | 7.62 / 7.33 |

结论：**标准版比 16 核便宜 80.95%、比 4 核便宜 33.33%**，代价是**比 16 核多 78 秒**。

注意那个"取整分钟"列：标准版 202 秒取整成 **4 分钟**，而 16 核 124 秒取整成 3 分钟——**时间只差 78 秒，价格差 5.25 倍**。他们的判断是：**"Preview 构建不足以证明那个 16 核溢价值得"**（对一个以成本为焦点的决策）。

### 凭什么这么判断

| 方案 | 否决理由 |
|---|---|
| 保持 16 核 | 最短的实测 job，**但每个样本多花 $0.102 换 78 秒的改进** |
| 选 4 核或 8 核 | 两者都成功并缩短构建，**但它们取整后的样本成本超过标准 Ubuntu**；4 核保留更多 RAM/磁盘余量**如果未来工作负载耗尽标准容量**——**而这样的改变需要新的测量** |
| 移到自托管 | **被范围否决**：preview 留在 GitHub CI |

第 3 条的措辞值得记：**"Rejected by scope"** ——不是"做不到"，是**"这超出本决策的范围"**。**范围本身可以是一个否决理由，而且要说清是范围而不是能力。**

### 一段罕见的"诚实到过头"的边界说明

- **标准版暴露 2 vCPU / 7.75 GiB RAM**，工作区最大进程 RSS 是 2.86 / 2.76 GiB，preview 是 0.76 / 0.74 GiB，都没有 OOM 或超时。但紧接着：

  > **GNU time RSS is not simultaneous process-tree memory.** These samples establish **successful execution, not a permanent memory guarantee**.

  **GNU time 的 RSS 不是同时的进程树内存**；这些样本确立**成功执行，不是永久的内存保证**。
- **比较固定了源码、锁文件、命令和运行时版本，但没有固定物理 CPU 或镜像发布**：标准版和 4 核用镜像 `20260831.293.1`，8 核和 16 核用 `20260823.283.1`；**CPU 在 AMD EPYC 9V74/7763 与 Intel Xeon 8370C/8573C 之间变化**。
- **"每个缓存状态一个样本，测量的是所提供的标签，不是隔离的 CPU 伸缩或统计可重复性。"**
- 关于把生产 job 的开销加进来："**那是一个预测，不是实测的标准 runner 发布结果**"

### 他们承认的代价

- **用大约 78 秒的采样构建延迟，换取更低的计算成本**
- **"不从这个单一实验外推任何小时或月度的节省。"**
- **临时的基准工作流和它的安全测试不在最终树里；实验提交和链接的 run 保留了方法和证据**——**临时物清理掉，方法与证据留下。**

## 2. Windows Python 运行时 CI 回退到托管

`2026-09-06-python-runtime-windows-hosted.md` · **一份完整的失败迁移记录，这类记录很少见**

### 他们遇到的事：带时间线的失败复现

之前一次迁移（PR #3629）把 Windows x64 目标路由到自托管池。结果：

> The shared `dsh-win-ci` pool **did not make the lane more reliable**.

随后是一份精确到分钟的记录（全部 UTC，每个 run 都执行了那个 07:56 合并起生效的选择器）：

| 时间 | 结果 |
|---|---|
| **09:12** | 在 `dsh-win-ci-16` 上，installed-wheel 冒烟**通过**（PR #3640 的 commit `ca3ffe95`） |
| **10:06** | 在 `dsh-win-ci-21` 上**失败**（PR #3337） |
| **10:46** | 在 `dsh-win-ci-04` 上**失败**（PR #3640 的最终 head `c5ba873f`）——`smoke_sdk_profile_plugin` 的打包 `dsh plugin add` **子进程无输出地退出**，而**同一次运行的 Linux 和 macOS cell 都通过了** |
| **11:29** | 一次 job 重跑**重复了同样的静默死亡** |

还有一句点出根因的话：

> The migration proposal (#3629) remained **`proposed`** because its **throughput and shared-load acceptance criteria were never measured**.

**那份迁移提案一直停留在 `proposed` 状态——因为它的吞吐量与共享负载验收标准从未被测量。** 换句话说：**没有测量验收标准，就上线了。**

### 判断：完整回退

- Windows x64 目标**总是使用它的托管 `matrix.runner`**，配标准工具链、pnpm 缓存恢复和 pkg 缓存
- **failover 选择器、job 私有 Python setup 步骤、自托管依赖安装与 post-step 清理、私有 setup 脚本、以及那个路由 spec 全部被移除**

### 凭什么这么判断

| 方案 | 否决理由 |
|---|---|
| 保持 failover 路由 | **共享池在一天内重复了同样的静默子进程死亡两次，而迁移清单的吞吐量验收仍然开着；而且让一条正确性泳道经过 failover 状态，会把它耦合到一个无关的池故障开关** |
| **修复共享池** | **留给池运维者**：观察到的失败是"子进程无输出地死亡"，**不是缺少镜像前置条件——而同一个镜像服务于原生 Windows failover job** |
| 在托管镜像上保留 job 私有工具链 | **私有 uv/Python 下载的存在是为了避免改动一个常驻共享宿主；一次性托管镜像已经提供了迁移前泳道使用的已注册 Python 3.10 工具链** |

第 1 条后半句是一个通用判据：**不要把"正确性泳道"接到"故障切换开关"上**——那会让一次无关的池故障影响到正确性信号的可用性。

第 2 条也很干净：**"这不是池配错了，是池本身不可靠"**——承认问题归属不在自己这边，**然后把决策（回退）和自己的处置（不修池）分开**。

### 一段"给未来重试者的前置条件"

Consequences 的最后一部分列出了**四条必须重新建立的约束**：

1. **setup-python 的 Windows 安装器会移除匹配的 machine/current-user 记录并为所有用户安装**——**私有 toolcache 不能隔离那个注册表状态**
2. **每个构建缓存和临时测试根必须 job 自有，用复制导入而不是共享存储链接**
3. **清理必须在成功、失败和取消时都运行**，带有界的 Windows 文件系统重试
4. **只有 Windows x64 目标是可移植的——Linux 目标的 manylinux 检查需要 Docker**

并且定下门槛：**"未来的一次自托管尝试必须在实际池上重新验证吞吐量和失败可复现性，在任何路由变更之前。"**

**一次失败的迁移，留下的不是"别再试了"，而是一份"要再试的话，先满足这些"。**

## 3. Blacksmith 作为 CI 池的故障切换腿

`2026-09-09-blacksmith-failover-leg.md`

### 他们遇到的事

第三方 runner 供应商的**迁移向导建议整体替换仓库的 `runs-on` 标签**。这在默认状态下不可接受，理由写得很完整：

> it **breaks the workflow contract specs**, **distorts benchmark and performance-budget measurements**, and **moves trust-boundary jobs without a decision record**

**它破坏工作流契约 spec、扭曲基准与性能预算测量，并在没有决策记录的情况下移动信任边界 job。** ——三个不同层面的理由，**没有一个是"我们不信任第三方"这种态度**。

### 判断：一个显式开关 + 一份参与者清单

`blacksmith` 作为一个**新值**加入两个 failover 变量。**只在设置期间花钱，所以它是显式的故障或实验选择，永远不是默认。**

真正的工作量在**参与者清单**上——这份清单是这篇的核心价值：

**参与的**：三个企业 Linux worker、`node-compat` 腿、`all-checks-passed` 裁决、四个 Windows 泳道、`expected-filenames`、sandbox bwrap 腿、两个手动基准矩阵。

**不参与的（保持自己的 runner）**，按理由分类：

| 类别 | 例子 |
|---|---|
| 被工作流 spec 钉在托管 runner 上 | `node-24-bench`、`python-sdk`、master Wine 门、`release-publish`、Cloudflare preview、加权审批对 |
| **持有凭据** | real-API e2e 泳道、issue App-token job、npm 与 PyPI 发布器 |
| **需要 Blacksmith 缺少的宿主能力** | Landlock 腿与其打包验证、Seatbelt 腿、linux-arm64 单 exe 腿 |
| **release 形态的链** | npm/PyPI 发布器、node-addon-system release 链、Pages 部署——**因为它们的产物喂养已发布的 registry 输出** |

以及两处"有理由的不动"：

- **python-runtime 构建器完全保持托管**：它的调用者**传入真实 API 凭据**，它的 macOS/arm64 腿需要 GitHub 的镜像，**而它的 wheel 输出喂养 PyPI 发布链**
- **release 演练 job 保持变更前的路由不变**：它们**只携带既有的 `selfhosted` 分支，所以在 `blacksmith` 下回落到托管默认值，且不获得 `blacksmith` 分支**——**没做的事也写明**

还有一处与第 08 批呼应的细节：**blacksmith 分支不携带 Dependabot 排除**，因为**"Blacksmith runner 是短暂的，所以让 Dependabot 留在托管池的那个'常驻 VM'理由不适用"**。**同一个排除规则，在前提下失效时自动不适用——而这件事被写出来。**

### 凭什么这么判断

| 方案 | 否决理由 |
|---|---|
| 整体采用迁移向导 | **破坏工作流契约 spec、改变基准语义与性能预算校准，并作为默认把持有凭据和信任边界的 job 移到第三方基础设施上** |
| 保持自建池作为唯一 failover 目标 | **它们是一个有界的备用；Blacksmith 为"舰队本身即退化资源"的故障与实验情形增加弹性容量** |

### 一次精确到触发条件的故障归因

试验暴露了一个 `verify-md-wrap` 在 Blacksmith 上失败的问题。归因写得非常克制：

> The trigger is **the lstat-probe of a path beneath a matched symlink**, **not `**` over symlinked trees in general**: the other `globSync` `**` call sites that scan symlink-bearing trees **stayed green on the same run and needed no change**.

**触发条件是"lstat-probe 一个已匹配 symlink 之下的路径"，而不是"`**` 扫过含 symlink 的树"**——证据是：**同一次运行里，其他扫描含 symlink 树的 `globSync` 调用点保持绿色，无需改动。**

**用"同类情况里哪些没出问题"来收窄故障条件**，比笼统地说"某个模式有问题"精确得多。

### 他们承认的代价（含未验证项的标注）

- **blacksmith 腿保持休眠直到值被设置**，只在真实故障或显式实验期间被演练
- **Blacksmith 把它的 runner 注册为 self-hosted，所以在该值下 `node-compat` 腿会真实执行它们的 toolcache 与隔离验证步骤**（而非跳过）
- **基准矩阵的 8 和 32 vCPU 标签不在试验范围内，是按已实测的 4/16 vCPU 标签的命名对称推定的；首次使用前请用一次手动 dispatch 确认**
- **Landlock、Seatbelt 和 linux-arm64 的排除仍基于更早迁移尝试的散文式 dispatch 实测，记录为已知缺口**；试验按设计无法触发这几条腿

最后两条是"哪些已验证、哪些是推定、哪些是已知缺口"的三分法——**而且每一项都说清了验证手段的局限**。

## 这批的共同判断标准

**① 先弄清度量机制，再比较方案。**
取舍整到整分钟的机制让"价格 5.25 倍差距"对应"时间只差 78 秒"。**度量是离散的，直觉上的比例关系就不成立。**

**② 不从单一实验外推。**
"不从这个单一实验外推任何小时或月度的节省。""每个缓存状态一个样本，测量的是所提供的标签，**不是隔离的 CPU 伸缩或统计可重复性**。"

**③ 失败的迁移要完整记录，包括根因。**
时间线精确到分钟、失败现象（**子进程无输出地退出，而同 run 的 Linux/macOS cell 通过**）、以及那个真正的根因：**"验收标准从未被测量，提案一直停在 proposed"。**

**④ 回退时，给未来的重试者留下前置条件。**
四条约束（注册表状态无法被私有 toolcache 隔离、缓存必须 job 自有且用复制导入、清理必须在成功/失败/取消时都跑、只有 Windows x64 可移植），加上门槛：**"必须在实际池上重新验证吞吐量与失败可复现性，在任何路由变更之前。"**

**⑤ 变更要列参与者清单，逐个点名。**
谁参与、谁不参与、**为什么**不参与（凭据 / 宿主能力 / 产物喂养发布链 / 工作流 spec 钉住）。**"谁不受影响"和"为什么不受影响"是同一份清单的两半。**

**⑥ "没做的事"也要写明。**
"release 演练 job 保持变更前的路由不变……**不获得 `blacksmith` 分支**。" **沉默会被读成"忘了"，而不是"决定不做"。**

**⑦ 整体替换作为默认不可接受。**
三条理由都不是态度：**破坏工作流契约 spec、扭曲基准测量、移动信任边界 job 而无决策记录。**

**⑧ 用"同类里哪些没出问题"来收窄故障条件。**
"触发条件是 probe 一个已匹配 symlink 之下的路径，**不是 `**` 扫过含 symlink 的树**"——依据是**同 run 里其他同类调用点保持绿色**。

**⑨ 范围可以是一个否决理由，但要说清是范围而不是能力。**
"移到自托管——**被范围否决**。"

**⑩ 临时物清理掉，方法与证据留下。**
"临时的基准工作流和它的安全测试不在最终树里；**实验提交和链接的 run 保留了方法和证据**。"
