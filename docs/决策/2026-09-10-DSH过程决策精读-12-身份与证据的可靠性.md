## 1. 自托管上的可信发布演练

`2026-09-06-release-rehearsal-selfhosted.md`

### 他们遇到的事

两句话把取舍摆平：

> Dependency-layout and release-pack rehearsals **consume hosted Linux minutes without requiring npm or API credentials**. Moving arbitrary pull-request code or credentialed publication onto a persistent shared host would **weaken isolation**; reusing a checkout without cleaning would also **weaken the packed-payload proof**.

演练消耗托管的 Linux 分钟数，**却不需要 npm 或 API 凭据**——所以有省钱空间。但两个风险也明确：**把任意 PR 代码或有凭据的发布搬到常驻共享主机上会削弱隔离**；**复用一次没清理的 checkout 会削弱打包载荷的证明**。

### 判断：窄的、显式的信任边界

选择器要求**规范仓库**和**非 Dependabot 的 actor**，然后**只接受 master 推送、或同仓库非 fork 且作者不是 Dependabot 的 PR**。

**手动 dispatch 总是选择 `ubuntu-24.04`**——所有其他被拒绝的上下文也一样。这条对应被否决的方案：

> Allowing manual dispatch on arbitrary refs gives a maintainer action **broader persistent-host access than the explicit event trust rule**.

**手动 dispatch 跑在任意 ref 上，会给一个维护者动作比"显式的事件信任规则"更宽泛的常驻主机访问权。**

另有一个刻意的耦合被写明：**发布演练与主 CI 共享同一个 Linux 开关**——"启用或禁用它**同时路由两种工作负载，而不是独立地路由发布**。" 他们选择让开关语义简单，代价是两者联动。

### 三条清理与隔离的设计

**① 临时目录要落在"即使进程被杀也会被清理"的地方。**

`TMPDIR` 指向 `runner.temp`：

> so temporary npm consumers stay **outside the checkout but inside runner cleanup** even when **a killed process cannot execute `finally`**

**临时 npm 消费者待在 checkout 之外、但在 runner 清理之内——即使一个被杀死的进程无法执行 `finally`。** **按"finally 不会被执行"来设计清理位置**，而不是假设它总会被执行。

**② checkout 必须显式清理未跟踪与被忽略的输出。**

它在**不可变安装和既有构建之前**清理。理由在别处点明：

> a warm pnpm store **cannot substitute workspace links or stale build output for a tarball payload**

**一个热的 pnpm store 不能替代 workspace links、也不能替代陈旧的构建输出去充当 tarball 载荷。** ——**打包验证的完整性依赖于"补丁没有被别的东西悄悄填充"**。

**③ 打包安装验证器在 checkout 之外建全新消费者**，用 npm 安装 tarball、**移除继承的 Node 解析钩子**、并在 `finally` 里删除。

**移除继承的解析钩子**这一条很关键：**否则验证器可能解到仓库里的源码，而不是 tarball 里的内容**——那就是"你以为在验证 A，实际在验证 B"。

### 关于负控与边界的两句话

测试跑负控：**fork、Dependabot、其他仓库、非 master 推送、dispatch、缺失 PR 数据、禁用的开关**。

边界声明：

> Real release-build and packed-install execution **remains the PR CI verification owner**; selector tests **do not claim to reproduce those builds**.

**选择器测试不声称复现那些构建。** 与第 11 批"本地调度测试不声称原生运行时执行"是同一条。

### 他们承认的代价

- **这是操作者选择的后备，不是自动的 runner 健康检测，也不是对已排队 job 的故障切换**
- 共享 VM **仍然会与其他可信 job 争用**
- **没有 workflow 供应主机包，也不改变全局主机配置**（**"谁能改主机"被明确留在 workflow 之外**）

## 2. job 内分区覆盖

`2026-08-18-in-job-partitioned-coverage.md`

### 他们遇到的事

**原生 Windows 覆盖是完整 PR 清单里最长的反馈路径。** 具体症状：

- 把插桩套件保持在**一个单 worker 的 Vitest 进程**里，避免了更大进程池下出现的 **worker 丢失和 Node 24 CJS lexer 失败**
- **但一次失败可能要超过十四分钟才出现**，而且门 runner **在完成前一直扣着子进程输出**

两条硬约束同时压着：

1. **优化必须保留每一个测试和合并后的逐文件 100% 阈值**
2. **必须留在既有的 coverage job 内**——拆到多个 workflow job 会给必需拓扑**增加 checkout、安装、制品传输和一个 merge job**

### 判断：一个 job 内多个单 worker 进程

- 本地 `test:coverage` **仍然是一次 Vitest 调用**（本地保持简单）
- CI 固定 `DSH_COVERAGE_PARTITIONS=4`
- **没有基于经过时间的触发器会在运行进行中改变这个数**
- 协调器用**最小堆按最长处理时间优先（LPT）**分配文件——"**这样重量级的子进程绑定套件会分散开，而不是堆在路径哈希把它们扔进去的那个分片里**"
- 每个分区收到**临时 Vitest 配置**，include 是它自己的文件列表（**命令行传文件超过了 Windows CreateProcess 限制**）
- **空分区在任何子进程启动之前就被拒绝**
- **最重的分区最先启动**，让它的裁决最早落地
- **分区模式在每个子进程里抑制阈值和覆盖率报告器**，每个进程写一个 blob 报告

而裁决的唯一归属是：

> The coordinator waits for every child, validates that the blob directory contains **exactly** the expected files, and then runs **one** `vitest --merge-reports ... --coverage`. **Only that merged command applies the repository's per-file thresholds, so a partition is never judged against an intentionally partial inventory.**

**只有合并后的那一次命令应用逐文件阈值——所以一个分区永远不会被用一份有意不完整的清单来评判。**

被否决的对照方案说得更直白：

| 方案 | 否决理由 |
|---|---|
| **在每个分区里独立应用阈值** | **每个分区有意只看到套件的一部分，会报告假未覆盖文件。阈值所有权属于合并后的报告** |

### 三个"让证据可用"的设计

**① 失败也要留下可合并的证据。**

> A normal failed test **still emits a blob through `--coverage.reportOnFailure`**, allowing the merge to report the complete coverage state before the coordinator returns failure.

**一个正常的失败测试仍然发出 blob**，让合并能报告**完整的**覆盖状态，**然后**协调器返回失败。**失败不等于放弃完整性。**

**② 具体失败要与最终诊断放在一起。**

协调器保留每个子进程**一个有界的 64 KiB 合并尾部**；当子进程不成功地结算时，它打印 spawn 错误/退出码/信号，**并在验证完整 blob 集之前重复那个尾部**——"**把具体的 Vitest 失败与最终的分区诊断放在一起**"。

**③ 清理要防链接陷阱。**

**协调器只移除它自有的覆盖树，并把一个链接形状的路径 unlink 而不是递归跟随它。**

### 本批最锋利的一句：关于"什么时候才有资格调参"

> **Future tuning starts from completed runs at one fixed configuration. Slow progress alone never raises partition count or outer concurrency, because repeated restarts would erase the only evidence needed to choose a stable setting.**

**未来的调优从一个固定配置的已完成运行开始。仅仅"进展缓慢"永远不会提高分区数或外层并发——因为反复重启会抹掉"选择稳定设置"所需要的唯一证据。**

配套的一句同样干脆：

> These values come from completed runs or fixed capacity bounds; **an unfinished run crossing an arbitrary elapsed-time mark is not evidence for increasing concurrency.**

**一个跨过某个任意经过时间标记的未完成运行，不是增加并发的证据。**

**这两句合起来是一条通用的反模式警告：在没有稳定基线时调参，会破坏调参本身所依赖的证据。**

### 他们承认的代价

- 覆盖**为每个分区付一次 Vitest 启动/配置成本，加上一次报告合并成本**
- **分区输出可能交错**，但分区起始标签和 Vitest 文件身份保留了归因
- Windows 用四分区**保留独立进程隔离并与 Linux 对齐，代价是更长的单 job 覆盖墙钟时间**——"这个取舍被接受，以减少高自托管并发下的 vitest worker 启动失败"
- 性能数字带着口径说明："**那些值比较的是分区延迟，不是当前的峰值**"

## 3. 按文件路径识别审批工作流

`2026-09-10-approval-review-workflow-identity.md` · 短小精悍

### 他们遇到的事

> GitHub can populate a workflow run's `name` with its **expanded `run-name`**.

GitHub **会用展开后的 `run-name` 去填充 workflow run 的 `name`**。审批评审工作流在那个标题里包含了 PR 号，于是**把 `workflow_run.name` 与静态工作流名比较，会在刷新审批状态之前拒绝掉有效的评审事件**。

### 判断

审批发布器**通过它确切的 `workflow_run.path` 识别评审事件工作流**。此外还要求：一个成功的 `pull_request_review` 运行、**从 `display_title` 解析 PR 号**、校验任何提供的 PR 关联、**并在评估审批之前比较当前 PR head 与被评审的 head**。

最后那条是防止"用旧的评审结论为新的提交背书"——**审批必须绑定到它实际评审的那个 head**。

### 凭什么这么判断

| 方案 | 否决理由 |
|---|---|
| **接受一个名称前缀** | **一个显示名不标识工作流文件；另一个工作流可以使用同样的标题** |
| **移除带编号的运行标题** | **该标题在 GitHub 返回空 `pull_requests` 数组时提供 PR 号**；移除它需要一个不同的交接机制 |

第 1 条是身份判定的通则：**显示名是给人看的，它可以被任何同名的东西复用；标识符才是身份。**

### 他们承认的代价

- **运行标题展开不再阻止审批刷新，而一个意外的工作流文件仍然失败校验**（正确方向上的严格）
- **移动评审事件工作流需要更新发布器的预期路径**——**把路径当身份，就要承担路径变化的维护成本**

## 这批的共同判断标准

**① 身份用标识符，不用显示名。**
"一个显示名不标识工作流文件；另一个工作流可以使用同样的标题。" **显示名是给人看的，可被复用；路径/ID 才是身份。**

**② 信任边界要窄，而且要显式到可枚举。**
"规范仓库 + 非 Dependabot actor + 只接受 master 推送或同仓库非 fork PR"——**边界由具体条件组成，不由"我们信任自己人"这种态度组成**。手动 dispatch 被排除在自托管之外，因为它绕过了事件信任规则。

**③ 清理要按"finally 不会被执行"来设计。**
`TMPDIR` 指向 `runner.temp`，为的是**即使进程被杀、`finally` 没跑，临时物仍在清理范围内**。

**④ 验证必须确保它在验证你以为的那个东西。**
"移除继承的 Node 解析钩子"、"checkout 显式清理未跟踪与被忽略的输出"、"一个热的 pnpm store 不能替代 tarball 载荷"——**三处都在防"验证器解到了别的东西"**。

**⑤ 只有稳定配置下的已完成运行，才构成调参的证据。**
"仅仅进展缓慢永远不会提高并发，因为反复重启会抹掉唯一的证据。" **在基线不稳时调参，会破坏调参所依赖的证据本身。**

**⑥ 判定的归属必须唯一。**
"阈值所有权属于合并后的报告"——**一个有意不完整的部分，不能对自己作整体判定**。

**⑦ 失败时也要留下完整证据。**
失败测试**仍然发出 blob**，让合并报告完整状态之后才返回失败。**"失败"和"证据残缺"是两件事，不要用一个掩盖另一个。**

**⑧ 优化不该改变拓扑。**
"必须留在既有 job 内"——拆 job 会带来 checkout、安装、制品传输和 merge job。**在既有结构内解决问题，优先于为问题改变结构。**
