# 思灵 0.4.0 → 1.0.0 切换清单（含回滚）

**适用场景**：把本机正在运行的**自建壳版思灵 0.4.0** 换成 **fork 版 1.0.0**。
**性质**：这会**替换掉当前正在使用的思灵**（两者 appId 相同，NSIS 视为同一程序的升级）。
**写这份清单的时间**：2026-09-27，1.0.0 的安装包刚打包完成、隔离环境首启验证通过。
**实测更新**：同日下午在一台**已装 0.4.0** 的机器上走完了真实升级路径 —— 结论见「一之二、实测记录」，清单正文已按实测结论修订。

---

## 一、为什么不能「直接装」

`seedSsidProfile` 的契约（源码注释原文）：

> **幂等**：链接已存在就跳过；`bundles` 与 `dependencies` 只补缺失项。
> **profile 里已有的一切（用户自装插件、用户自己的 bundle、用户改过的声明）都不动。**

这条保护了用户的手工改动，**但也保护上一代的库存**。当前 profile 的实际构成：

| 项 | 现在 |
|---|---|
| 依赖总数 | 69（61 个版本号 + **7 个 `file:./vendor/…`** + 1 个 `link:`） |
| `vendor/` | 8 条目（0.4.0 时代拷进去的副本） |
| `node_modules/` | 490 条目（自建壳时代 `pnpm install` 的实体） |

**后果（已实测）**：直接装 1.0.0，启动**立刻崩**：

```
Error: desktop welcome: Web RPC failed
    at settingsAndReference (app.asar/lib/main.js:9823)
    at openInitialWindow     (app.asar/lib/main.js:13838)
```

失败在「欢迎页读设置」这一步。`welcome-backend.ts` 里 `Web RPC failed`（L59）与 `Web request failed`（L55）是两个不同分支 —— 我们中的是前者，说明 **HTTP 通了、Host 进程起来了**，是后端处理 `settings/describe` 这个 RPC 时返回了业务错误：旧插件在 0.1.7 内核下加载失败，settings 服务因此不可用，而欢迎页一上来就要读它。

**解法（已验证有效）**：升级前**把 profile 改名**，让 fork 版从零建一份。

## 一之二、实测记录（2026-09-27，一台已装 0.4.0 的机器）

| 尝试 | 动作 | 结果 |
|---|---|---|
| 第 1 次 | 直接装 1.0.0（profile 不动） | **崩** —— `desktop welcome: Web RPC failed` |
| 第 2 次 | 点对话框上的「Restart」 | **崩在同一处**（同调用栈，仅 PID 不同） |
| 第 3 次 | **改名 profile 后重启** | **正常** —— 窗口标题 `思灵  DSH 1.0.0`，界面完整 |

改名后启动日志里的关键一行：

```
ssid: plugin set: linked=584 kept=0 missing=0 bundlesAdded=32
```

**`kept=0`** 是关键 —— 全新 profile 下**一个旧条目都没保留**，584 个包全部建成指向随包插件集的新链接。这组数字与本机隔离环境首启时**完全一致**。

**由此确认**：

- **旧 profile 是崩溃的根因**（原假设成立）
- **「升级前改名 profile」是必要步骤**，不是可选项
- **NSIS 的装/卸/覆盖本身正常** —— 它成功覆盖了 0.4.0，并沿用了其安装目录（`%LOCALAPPDATA%\Programs\ssid-shell`，因为新版的 `allowToChangeInstallationDirectory: false`）
- **「Restart」按钮解决不了这个问题** —— 它不碰 profile，所以重启多少次都一样

## 二、前置准备（升级前）

### 1. 备份 profile —— 改名，不是删除

```powershell
# 关闭思灵之后再做（见步骤 5）。改名而非删除，旧的那份完整保留。
Rename-Item 'C:\Users\MaxNull\.dsh\profiles\ssid' 'ssid.backup-0.4.0'
```

**这一步同时化解了两个风险**：① 插件集不换代；② 万一安装器动了 profile（已查证不会，见附录），你也不会有损失。

### 2. 记下要补回的自装插件

按 `check-rules.manifest.json` 的登记，只有**两个**是本机增量、需要升级后补回：

| 插件 | 来源 | 备注 |
|---|---|---|
| `dsh-plugin-zhihu-search` | `github:klarkxy/zhihu-search` | 你从 GitHub 自装的第三方插件 |
| `@dsh-pet/bridge` | `link:H:/MaxNull/WorkStation/.pet-test/merzlin/_internal/integrations/dsh-pet-bridge` | 桌宠的 `install_bridge()` 写的运行时依赖 |

> 除此之外若你还记得装过别的，一并记下。这两条是 manifest 里有登记的，可能不全。

### 3. 确认回滚材料在手

```powershell
# 0.4.0 的安装包就在本机，回滚时用它
Test-Path 'H:\MaxNull\WorkStation\seek-soul-in-darkness\shell\dist-electron\ssid-shell-setup-0.4.0.exe'
```

### 4. 会话**不需要备份**

DSH 的迁移契约是「may add a version-named successor but **never move, overwrite, or delete committed generations**」。当前会话是 `session.v3.jsonl.zstd`，迁移会产出 v4 **新文件**，v3 原文件保留 —— 回滚后 0.4.0 读的还是它自己那代。

（若要更保险，把 `C:\Users\MaxNull\.dsh\sessions-ssid` 整个复制一份即可，约 300 个文件、体积不大。）

## 三、切换

### 5. 退出思灵

**当前会断** —— 这个会话就跑在 0.4.0 里。退出前先确认没在跑别的任务。

### 6. 装 1.0.0

```powershell
# 双击或命令行都可以
H:\MaxNull\WorkStation\.ssid-build\checkout\apps\desktop\.desktop-build\targets\win-x64\unsigned-artifacts\ssid-1.0.0-win-x64-unsigned.exe
```

未签名构建，Windows SmartScreen 会拦一下 —— 选「仍要运行」。

### 7. 启动思灵

首启会跑 `seedSsidProfile`：在 `~/.dsh/profiles/ssid/` 下建 `node_modules` 目录链接（junction）指向安装目录里的随包插件集，并补齐 `dsh.profile.bundles`。

## 四、验收判据

逐条对照，**任何一条不符就先别往里灌工作数据**：

| # | 判据 | 怎么看 |
|---|---|---|
| 1 | 窗口标题是 **`思灵`** | 崩溃时标题会变成「应用无法启动或已意外停止」 |
| 2 | Host 端口 **19388** 在监听 | `Get-NetTCPConnection -LocalPort 19388 -State Listen` |
| 3 | 没有 crash 日志 | `~/.ssid/` 或 userData 下无 `crash-*.log` |
| 4 | **profile 是新形态** | `~/.dsh/profiles/ssid/package.json` 里应是 **`link:`** 形式、**不是 `file:./vendor/`** |
| 5 | **`node_modules` 是指向安装目录的 junction** | 顶层条目数应为 **336** 上下（随包插件集规模），不是 490 |
| 6 | `bundles` 是 **34 项** | `(Get-Content ~/.dsh/profiles/ssid/package.json -Raw \| ConvertFrom-Json).dsh.profile.bundles.Count` |
| 7 | 插件集里 `dsh-node-appearance` 是 **0.6.0** | `…/node_modules/@max-null/dsh-node-appearance/package.json` 的 `version` 与 `dsh.client.inject`（应为 `…ui-plugin-manager`） |

**第 4~7 条是这次切换的核心** —— 它们区分「换了程序」和「程序与插件都换了」。

## 五、回滚

四步，每一步都可逆：

```powershell
# 1) 卸载 1.0.0（控制面板，或安装目录下的 Uninstall）
# 2) 装回 0.4.0
#    H:\MaxNull\WorkStation\seek-soul-in-darkness\shell\dist-electron\ssid-shell-setup-0.4.0.exe
# 3) 把 profile 改回来
Remove-Item 'C:\Users\MaxNull\.dsh\profiles\ssid' -Recurse -Force   # 删掉 fork 版建的那份
Rename-Item 'C:\Users\MaxNull\.dsh\profiles\ssid.backup-0.4.0' 'ssid'
# 4) 启动 0.4.0，确认能读到升级前的会话
```

**回滚的两条边界**：

- **能退回升级那一刻的对话状态** —— v3 文件没被动过。
- **退回后，在 1.0.0 上聊的内容读不到** —— 那些进了 v4 世代，0.1.5 内核不读 v4。这是「降级无支持」的必然，不是故障。

## 附录：安装器会不会动 profile —— 已查证，不会

三条独立证据：

1. **`installer/uninstall.nsh` 首行注释**：
   `; Electron user data and updater downloads leave with the application; the Harness home is never touched.`
2. **`$UnHome`（读自 `DSH_HOME`）是「拒绝删除」名单的成员**，不是删除目标。
   `uninstall-data.h` 注释：`The helper refuses unsafe roots, the installation and the Harness home, and never descends into reparse points.`
   实际删除目标只有 `$APPDATA\思灵`、`$APPDATA\<包名>` 与 `$LOCALAPPDATA\<updater 缓存>`。
3. **升级路径跳过整个数据清理**：`un.CleanData` 开头就是 `${If} ${isUpdated} / Return`，另有 `/KEEP_APP_DATA` 参数用于换目录安装的场景。

另外本机 `DSH_HOME` 在**用户级与机器级都未设置**（只有思灵运行时设的进程级值），卸载时 `$UnHome` 取不到值。

**结论**：安装器不碰 profile。把 profile 改名仍然值得做 —— 它解决的是「插件集换代」，顺带让这件事的风险归零。
