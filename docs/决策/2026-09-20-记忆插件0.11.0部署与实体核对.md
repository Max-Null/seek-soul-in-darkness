# dsh-memory 0.11.0 部署：四层核对

> 状态：**已执行**（三处 pin、两个实体、两份 lockfile 全部 0.11.0，内容逐字节一致；提交 `bc58520` 已推送；`check:rules` 7 门全绿）
> 关联：`check-profile-sync` 门 · `docs/决策/2026-09-18-vendor一致性判定对行尾免疫.md`（同类：一致性判定口径）· 待建第 8 门 `check-entity-sync`

## 一、起因

dsh-memory 0.11.0 需要把两个运行时 profile 与发版基准对齐。此前发布被 npm registry 维护窗口挡住（`status.npmjs.org` 的 indicator 为 `maintenance`），最终于 `2026-09-19T18:01:31Z`（本地 09-20 02:01:31）发布成功。

**起始状态本身是不一致的**：

| 层 | ssid | web | template |
|---|---|---|---|
| pin（声明） | 0.10.0 | 0.10.0 | 0.10.0 |
| 实体（已装） | **0.11.0** | 0.10.0 | — |

ssid 实体**领先于所有 pin**。原因是它由本地工作区手动拷贝进 profile —— 当时 npm 上还没有 0.11.0，无法通过包管理器获得。

## 二、四层核对模型

单一「版本号」不足以判定一致。本次把一致性拆成四层，逐层都要过：

| 层 | 位置 | 判定 |
|---|---|---|
| **pin（声明）** | `<profile>/package.json` 的 `dependencies` | 三个文件应相同 |
| **lockfile（锁定）** | `<profile>/pnpm-lock.yaml` | 应与 pin 的解析结果一致 |
| **实体（已装）** | `<profile>/node_modules/<pkg>/package.json` 的 `version` | 应与 pin 相同 |
| **内容（指纹）** | 实体目录逐文件 SHA256 | 同一个包在不同 profile 的实体应逐字节相同 |

**第四层不是前三层的推论，是独立的判据**：本次实测中 ssid 与 web 的实体**版本号都是 0.11.0**（前三层全过），但 `README.md` 不同 —— 版本号完全看不出这一处。

## 三、实测数据

### 3.1 发布后最终状态

| 层 | ssid | web | template |
|---|---|---|---|
| pin | 0.11.0 | 0.11.0 | 0.11.0 |
| lockfile | 0.11.0 | 0.11.0 | — |
| 实体 | 0.11.0 | 0.11.0 | — |
| 内容 | 33 文件 · README `1A04984D828B22CD` | 33 文件 · README `1A04984D828B22CD` | — |

### 3.2 内容比对发现的缺口

ssid 实体 33 个文件里 **32 个一致，`README.md` 一处不同**：

| 文件 | SHA256 前 16 位 | 大小 | 来源 |
|---|---|---|---|
| 本地仓库 `README.md` | `1A04984D828B22CD` | 14249 | git 工作树（提交 `df2dbad`） |
| web 实体 `README.md` | `1A04984D828B22CD` | 14249 | 刚由 `pnpm install` 从 npm 装出 |
| ssid 实体 `README.md` | `F188443C419CAB03` | 13415 | **手动拷贝，落后一个版本** |

**判定方向的依据**：web 实体刚由包管理器装出，它就是 npm 上的真身；它与本地仓库逐字节相同 → **npm 上的 0.11.0 确实包含 `df2dbad`**。因此落后的是 ssid 侧，不是 npm 侧。

### 3.3 门禁发现的第二个缺口

`check-profile-sync` 门报 **`@max-null/dsh-guardian` A(template)=0.2.0 / B(运行时)=0.2.1**。查证：npm 上 0.2.1 已发布（版本列表 `0.1.0 / 0.2.0 / 0.2.1`）、ssid/web 的 pin 与实体均为 0.2.1、本地源码亦为 0.2.1 —— **只有发版基准落后**。

这属于该门判据里的「B 超前于 A」：**下次从 template 构建归档会把 guardian 降回 0.2.0**。

## 四、处置

| 缺口 | 处置 | 理由 |
|---|---|---|
| ssid 实体 `README.md` 落后 | 用本地仓库的 `README.md` 覆盖该文件 | 只差一个文件，不动 `node_modules` 结构；下次 `pnpm install` 按 pin 重新物化时自然一致 |
| ssid lockfile 停在 0.10.0 | `pnpm install --lockfile-only` | **只重写 lockfile、不碰 `node_modules`**，规避 SSiD 运行中占用 node-pty 导致的 `ERR_PNPM_EPERM` |
| 三处 pin 停在 0.10.0 | node 脚本改（正则锚定，命中数必须恰为 1 才写） | 铁律 5：JSON 一律 node 写，防 BOM |
| template 的 guardian 落后 | 一并改为 0.2.1 | 与 dsh-memory 同性质，合并为一次提交 |

**`--lockfile-only` 的安全性验证**：改前备份，改后 `Compare-Object` 显示**差异 10 行、全部是 dsh-memory 的 0.10.0→0.11.0**（总行数 14085 不变，无其它依赖被顺带升级）；实体复核仍是 33 文件、README `1A04984D` —— 确认没有触碰 `node_modules`。

**明确没做的事**：没有在 ssid profile 跑完整 `pnpm install`。SSiD 实例正在运行且**承载着操作会话**，这违反铁律 2「不弑主体」；`--lockfile-only` 已足以让 pin 与 lockfile 对齐，而实体本就已经是 0.11.0。

## 五、为什么需要第 8 门

现有 7 门**覆盖不到实体层**：

- `check-profile-sync` 只比 **profile 与 template 的声明**（即 pin 层）。
- 它**抓到了 guardian 那一处**（说明现有门在有效工作），但抓不到「pin 与实体不一致」（ssid 起始状态 pin=0.10.0 / 实体=0.11.0），也抓不到「版本相同、内容不同」（`README.md` 那一处)。

建议新增 `check-entity-sync`，两条判定：

1. **版本三方一致**（对每个 profile 的 `@max-null/*` 依赖）：declared（`package.json`）/ locked（`pnpm-lock.yaml`）/ installed（`node_modules/<pkg>/package.json`）。
2. **跨 profile 内容一致**：同一个包在多个 profile 的实体逐文件 SHA256 比对。

第 1 条能抓到本次的起始状态与中途状态；**只有第 2 条能抓到 `README.md` 那一处** —— 它是本次唯一被人工发现、而版本号完全看不出来的缺口。

**判据**：手动拷贝绕过包管理器，一定会留下看不见的缺口。这次是 `README.md`，下次可能是 `dist/`。
