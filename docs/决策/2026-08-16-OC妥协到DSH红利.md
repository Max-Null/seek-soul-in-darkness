## 三个「根问题」的提炼

这 10 条妥协，往上归结为 OC 的三个根问题，而 DSH 各有一套原生答案：

| OC 根问题 | 具体表现 | DSH 答案 |
|---|---|---|
| **① 事件/接口贫瘠** | 事件不全、task 阻塞、配置不热更新、serve 能力未接 | 事件溯源会话日志 + 非阻塞 subagent + settings 热重载 |
| **② 提示词模拟底层能力** | Plan Mode、行为前门都用 prompt 硬撑 | 原生 plan-mode + section/context 分层 |
| **③ 扩展点与引擎强耦合** | 记忆/agent 模型都长在 OC 专有 API 上 | 通用 capability seam（llm/section/context/storage/subagent） |

### 根因再挖一层：上下文有没有「固定 vs 变化」的标识

「提示词模拟底层能力」出问题的根子，不在「prompt 太长」，而在 OC 的上下文是**无结构的文本流**——哪些固定、哪些变化没有标识，LLM 只能靠语义猜。DSH 把它做成了两个结构化 seam：

- `systemPrompt.section()` = **固定**（每轮稳定，前缀缓存安全，section 名 + order 标识）
- `systemPrompt.context()` = **变化**（每轮动态，runtime snapshot，context 名标识）

这正是「缓存前缀稳定纪律」的来源（稳定记忆进 section、动态记忆进 context），也是 plan-mode 能做「底层切换」而非「贴纸条」的原因——模式是结构化状态（`plan/mode` + `plan:policy` + `exit_plan_mode` 工具），不是让 LLM 猜的文本。

## 结论

**这些妥协不是瑕疵，是 fractal 在 OC 框架内"用技巧换能力"的代价。** 换到 DSH，这些技巧大多可以删掉，换成原生能力——这就是迁移最实在的红利，也是「不 fork、只插件」能成立的底气：DSH 的 seam 已经把这些坑填平了。
