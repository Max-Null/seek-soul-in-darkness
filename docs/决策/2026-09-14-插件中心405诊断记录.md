# 插件中心 405 诊断记录（2026-09-14）

> 状态：**根因已定位**（v0.3.0 安装包内冻结的是内联旧内核，`--external` 修复从未进包）
> 关联：`docs/插件开发规范.md`、`check-loader-external` 门、v0.3.0 装机验证

本记录的目的是**防止重复推断**：下面「已被推翻的假设」一节的每一条都花掉了实际轮次，
看到现象时先读它，不要重走。

## 一、现象

安装 v0.3.0 后：

- 插件中心不可用：`POST /plugin-center/*` → **405 Method Not Allowed**
- MCP 面板空白（显示「未配置 MCP server」，而 profile 里实际有 2 个）
- 侧栏底栏不可用
- 浏览器控制台：`Failed to load resource: the server responded with a status of 405`

## 二、已确认的事实（均有实验支撑）

### 2.1 实验矩阵：405 只在 bundle 形态出现

| 内核形态 | 进程模式 | `/plugin-center/listInstalled` |
|---|---|---|
| `.ts`（tsx 转译） | 同进程 | 401 ✓ |
| `.ts`（tsx 转译） | 子进程 | 401 ✓ |
| bundle（esbuild） | 同进程 | 405 ✗ |
| bundle（esbuild） | 子进程 | 405 ✗ |

**同一个 profile、同一个闭包、同一台机器**，只改内核形态与进程模式。
→ 与「是否子进程」「cwd」「`--port 0`」全都无关。

### 2.2 部分插件正常，坏的是特定一类

| 插件 | 注册路由的方式 | bundle 形态下 |
|---|---|---|
| `dsh-wechat` | 日志显示已挂载（提供 `/wechat/qr`） | ✓ 正常 |
| `@max-null/dsh-ssid-panels` | `ctx.webServer.register` | ✓ 正常 |
| `@max-null/dsh-plugin-center` | `ctx.connection.rpc.handle` | ✗ 405 |
| `ds-harness-remote` | `ctx.connection.rpc.handle` | ✗ 405 |

→ **不是「第三方插件全挂了」**，而是「走 `connection.rpc` 的那一类挂了」。

### 2.3 对照实验：同一批插件版本，web 版正常

web 版（3080，隔离内核 `dsh-web-runtime`）与思灵用**同一内核版本、同一批插件版本**
（plugin-center 0.2.19、ds-harness-remote 0.4.10）：

| 路径（POST） | web 3080 | 思灵 58858 |
|---|---|---|
| `/api` | 401 | 401 |
| `/plugin-center/listInstalled` | **401** | **405** |
| `/api/plugin-center/listInstalled` | 401 | 401 |

→ 差异在**启动路径**（官方 `dsh web` vs `kernel.ts` 自己 boot），不在插件版本。

## 三、已被推翻的假设（不要重复走）

| 假设 | 推翻方式 |
|---|---|
| `--port 0` 让 webServer 就绪变晚、插件撞上窗口 | dev 实例同样用 `--port 0`，三个路径全 401 |
| `spawn` 的 cwd 指向 `resources/` 导致 | harness 用两种 cwd（`shell/` 与 `resources/`）分别启动，都 405 |
| bundle 内联 DSH 产生两份 Loader peer | 当时结论是「改成 external 后 405 依旧」——**该结论已作废**。external 的构建产物从未进过安装包（见第六节），被替换的对照物是旧产物 |
| peerDeps 下限未对齐当前内核 | 与运行无关；且 semver 覆盖判断表明 `^0.1.0-rc.6` 本就覆盖 `0.1.5-rc.2` |
| 「`/api` 返回 401 证明 connection 路由已注册」 | **这是推理陷阱**：401 也可能来自 `web-app` 的信任栅栏，它对所有路径都返回 401 |

最后一条尤其要记：它一度让我以为「`connection` 已就绪」，从而把注意力引到错误方向。

## 四、缩小后的真问题

`packages/client/connection/src/rpc-host.ts`：

```js
private register(owner, channel, handler) {
  const route = { kind: 'prefix', path: channel, handler: async (req, res) => { ... } }
  const webCtx = this.webServerCtx
  if (webCtx === undefined) {
    throw new Error(`connection: cannot register RPC channel ${JSON.stringify(channel)} before the webServer scope attaches`)
  }
  return owner.effect(() => webCtx.webServer.register(route), ...)
}
```

而 `webServerCtx` 只在 `connection` 的 `inject(['webServer'])` 回调里 attach
（`packages/client/connection/src/index.ts:119-121`）：

```js
ctx.inject(['webServer'], (webCtx) => {
  connection.attachWebServer(webCtx)
  ...
  webCtx.effect(() => webCtx.webServer.register(route), 'client-connection: /api route')
})
```

**若该回调没执行、或执行得比插件注册晚，channel 就不存在** —— 症状正是 404/405
（裸路径落到静态 fallback）。

`plugin-center` 的 `PluginCenterRpc` 只 `inject ['pluginCenter', 'connection']`，
**不 inject `webServer`**，所以它可能在 `webServer` 就绪之前就注册。

## 五、探针实测（续一）：机制正常，服务也都注册了

在 `kernel-child.ts` 的 `main()` 里 boot 之后加了一段临时探针（结果写进子进程日志）。
两个形态的输出**逐行相同**：

```
ssid: [probe] webServer=true connection=true rpc=true
ssid: [probe] connection.rpc.handle 成功 —— webServerCtx 已 attach
ssid: [probe] ctx.get('pluginCenter')    = true
ssid: [probe] ctx.get('pluginCenterRpc') = true
ssid: [probe] ctx.get('loader')          = true
ssid: [probe] ctx.get('apiProxy')        = false
ssid: [probe] ctx.get('remote')          = false
ssid: [probe] cordis 服务表（230 个）
```

### 这推翻了「卡在插件 apply」这一整条推断

`pluginCenterRpc` **在两边都是 `true`**。所以：

- 注册机制是好的（`connection.rpc.handle` 主动调用成功，`webServerCtx` 已 attach）
- `plugin-center` 的 engine 与 Rpc **都注册成功了**
- 不是 Cordis 的 `await ctx.plugin()` 时序问题，不是注入未唤醒

（本节早先写的 `pluginCenterRpc = false` 是**错的**，已按实测更正。当时据它推出的
「卡在 `PluginCenterRpc` 的 apply」随之作废。）

**服务都在、路由却没生效** —— 这个组合把方向指向「注册进了哪一份 webServer /
Loader 实例」，也就是下一节查实的东西。

## 六、根因（2026-09-14 续二）：装的不是那份内核

前面几轮一直在「机制」里找原因。偏差出在被测对象上 —— **装进系统的内核不是
修好的那一份**。

两个形态实际跑的东西（进程命令行实测）：

| | 内核进程命令行 | 加载的代码 |
|---|---|---|
| 装版 | `Programs\ssid-shell\resources\node\node.exe …\resources\kernel-child.bundle.mjs` | 263 KB 内联产物 |
| dev | `shell\node_modules\electron\dist\electron.exe --import tsx/esm …\shell\kernel-child.ts` | `kernel.ts` 源码 |

dev 走 tsx 直跑源码，`import '@deepseek-ai/*'` 由 Node 的 ESM 解析到 profile 的
`node_modules`，与插件**共用同一份** Cordis Loader；而装版那份 263 KB 产物把整个
DSH 闭包内联进了内核，于是内核一份 Loader、profile 一份 Loader，
`ctx.connection.rpc.handle` 注册的路由落进内核看不见的那一份 → 405。

### 证据链

1. 重跑构建脚本产出的是**外置版**：`esbuild … --external:@deepseek-ai/*` →
   `kernel-child.bundle.mjs` 23.3 KB、`applyEntryPatches` 不存在。
   即构建脚本本身是对的，产物却不对 → 说明进包的**不是**这次构建的产物。
2. 安装目录 `AppData\Local\Programs\ssid-shell\resources\kernel-child.bundle.mjs`：
   263,232 字节、含内联 `applyEntryPatches`。
3. 该 263 KB 产物与 `shell\dist-electron\win-unpacked\resources\` 下那份
   **逐字节相同**（SHA256 `8FE21D4B…`），且早于 `d0548e2` → 这就是 00:27 打进去的那份。
4. `kernel-child.bundle.mjs` **不被 git 跟踪**，靠 `extraResources` 从仓库根直接进包。
   所以 `d0548e2` 只改了「怎么打包」，没有改动「已经打好、等着被打包的那个产物」——
   产物是构建出来的，而这次打包沿用了上一次构建遗留的旧文件。

于是「改成 external 后 405 依旧」（第三节那条）**是错的**：当时被对照的其实是内联旧产物，
external 产物一次都没真正上过场。

### 本轮实际修复

`npm run pack`（`bundle-kernel` → `bundle-kernel-child` → `electron-builder`），
让它重新构建产物再进包；随后重装并复验。

### 防复发

构建产物不进 git 是**有意**的（避免二进制/生成物入版本库），所以不能靠「提交产物」
解决。可机械检查的部分应当进打包流程：`check-loader-external` 门目前只扫仓库根的
bundle，**没有覆盖 `dist-electron` 与安装目录** —— 这是漏洞所在。

## 七、附带成果（本次已落地，独立成立）

- `check-loader-external` 门 + 8 例自测：bundle 不得内联 DSH。该门现在**绿灯**。
- `kernel.ts` 的 DSH 导入改为动态 + resolver 提前。**它没有修好 405**（见第三节），
  但「bundle 内联 DSH」违反 DSH 官方规则这件事本身要修 —— 官方原话见
  `docs/插件开发规范.md` 第一节。
