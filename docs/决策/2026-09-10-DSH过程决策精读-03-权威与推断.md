## 1. 评审状态的事件驱动

`2026-08-10-event-directed-pr-review-status.md`

### 他们遇到的事

Issue Project 的状态记录的是**"谁拥有下一步"**——这是一个交接（handoff）语义。

但 GitHub 给出的聚合评审状态回答的是另一个问题：**"GitHub 是否认为这个 PR 可合并"**。它无法表达交接，有一个具体的反例：

> an earlier `CHANGES_REQUESTED` review can remain effective after the author fixes the code and requests review again

**一个更早的"请求修改"评审，在作者修完代码并重新请求评审之后，仍然保持生效。** 于是聚合状态说"被阻塞"，而现实中球已经踢回评审者那边了。

第二个问题：单调（只前进）的投影**无法**在评审者请求修改时，把一个自动化拥有的 Issue 从 `In review` 退回 `In progress`。

### 判断

把评审 webhook 当作**命令**来处理，而不是当作状态快照：

- `pull_request.review_requested`（**包括重复请求**）→ 目标状态 `In review`
- `pull_request_review.submitted` → 目标状态 `In progress`，**仅当** `review.state` 是 `changes_requested`
- submitted 事件**仍然必要**，因为**评审者可以在没有更早的评审请求事件的情况下直接请求修改**
- approved 和 commented 的提交**运行它们的生命周期 job 但什么也不做**（从不触达 Project token 那一步）
- dismissed（被驳回的）评审**不订阅**

然后是最关键的不对称设计：

- 普通订阅的 PR 事件保持**只前进**——可以把 `Inbox`/`Backlog`/`Ready` 移到 `In progress`，但**不能把 `In review` 往回移**
- 而 changes-requested 命令**只有在**目标 Project 的最新状态事件是由配置的生命周期 actor 写下的时候，才能把 `In review` 往回移
- **人类或未知的最新 actor，保留当前状态**

### 一份"不做什么"的清单

这篇花了整整一段列举它**不做**的事，这在这批材料里很罕见，值得单独记住：

不改变终态、不为没有 Project 状态的 Issue 添加状态、不依赖 PR 元数据的有效性、不查询 `reviewDecision`、不重建评审轮次、不从 Issue 反查 pull request、**不运行定时的对账器**。

最后一条尤其值得注意：**不加一个定时对账器来兜底**。对账器看似稳妥，实则引入了一个"与事件流并行的第二套真相"——正是第 01 批判断标准②要拒绝的东西。

### 凭什么这么判断

| 被否决的方案 | 否决理由 |
|---|---|
| 从 `reviewDecision` 或重建的评审轮次推导状态 | GitHub 的聚合**在重复评审请求之后可能仍停留在 `CHANGES_REQUESTED`**；而一个轮次 reducer 会引入**超出两个显式交接**的评审者语义和顺序语义 |
| 保持只前进的投影 | 单调推进保护了后续状态，但**让 Issue 停在 `In review`，而作者正在实现被请求的修改** |
| **无条件**应用每一个评审命令 | 这是最小的处理器，但它**让自动化覆盖人类拥有的 Project 状态**——所以"最新目标 Project 状态的 actor"成为唯一那道后退转换的守卫 |
| 恢复 `ready_for_review` 或加一个防抖队列 | ready 状态**不携带任何评审交接**；而多一个队列**增加延迟和控制面状态，却不改变任何一个命令** |

第 3 条的对照最有教育意义：**"最简单的实现"和"正确的实现"在这里正好相反**——无条件应用是代码最短的写法，但它跨越了一条所有权边界。

### 他们承认的代价

坦诚得不寻常，原文列了三条：

- 重复的评审请求会把自动化管理的 Issue 移到 `In review`，**即使 GitHub 仍报告一个更早的阻塞评审**
- 投影保持事件驱动，**不会修复一个从未运行的事件**
- **重放一个旧的 workflow run 可以重放它当时的旧命令**；而且 ProjectV2 **仍然不提供**"读取最新状态"与"变更"之间的原子 compare-and-swap

也就是说：存在竞态，他们用"逐 PR 的 workflow 并发"和"人类所有权守卫"**减少**了竞态，但**没有引入持久的生命周期状态**去根除它。这个取舍是明写的。

## 2. 原生 stack 与可选 rebase

`2026-08-02-native-github-stacks-and-optional-rebases.md`

### 他们遇到的事

一个只由 base 分支表示的依赖 PR 链，**没有官方的 stack 身份**。落地这样一条链需要手工一次合并一个 PR、保留中间分支、给每个子 PR 重定目标，然后**重建这条链是否还活着**。

而 GitHub 的原生 stacked-PR 特性把这些都接了过去：携带顺序、对**每一层**应用 trunk 规则和 CI、自己拥有自底向上的合并和重定向。

同时出现了第二条线索：**一刀切禁止重写已评审分支**，会把官方的 `gh stack` 同步工作流也排除掉（它的级联 rebase 会更新每一层并用 lease 保护发布）。而如果只在 stack 之外应用那条禁令，又会**给独立 PR 和 stack PR 两套不一致的历史选择**。

### 判断

- 每个同仓库、两个及以上依赖 PR 的链，**落地前必须使用 GitHub 官方的 stack 对象**
- **活的** `PullRequest.stack` 和 `stackEntry.position` 字段是权威
- 单作者的非 stack 链**自动**链接（`gh stack link`，自底向上）；**混合作者或作者不可用需要用户确认**
- **缺少原生支持、跨 fork 链 → 硬停**
- 已存在于冲突 stack、或官方顺序与分支拓扑不一致 → **需要用户指示**才能解散或重建
- "落地 stack" 合并**完整的**官方 stack；部分落地**必须**指定一个显式的边界 PR
- **绝不回退**到逐 PR 的 `gh pr merge` 加手工重定目标

历史改写方面：

- **merge-forward 和 rebase 都允许**作为刷新历史的手段，**包括评审之后**
- 远程历史重写必须用**精确的 lease**或受 lease 保护的 push 路径，**远端移动就中止**；**裸 `--force` 禁止**
- `gh stack sync` 是一个**显式例外**：因为它把 fetch、级联 rebase、push 当作一个操作，所以**每一个被重写的层都要在之后立刻验证，且任何受影响的 PR 在证据通过前都不得合并**
- 任何重写后的 push 之后，**重新审计**：当前 heads、未解决的评审线程、批准、可合并性、检查——因为**更早的 commit OID 和内联锚点可能已经过时**

### 凭什么这么判断

| 被否决的方案 | 否决理由 |
|---|---|
| 保持分支链作为唯一的 stack 表示 | 保留了手工流程，但**给不了 GitHub 一个 stack 对象**去展示顺序、在每一层强制 trunk 规则、或原子地合并一个范围 |
| 采用原生 stack，但禁止其评审后的 rebase 命令 | 保持 commit OID 稳定，但**在 stack 处于活跃评审时禁用了官方同步路径**，并让独立 PR 落在**另一套政策**下 |
| 要求每个 PR 刷新都 rebase | 线性历史有用，但**合并检查点仍是有效选择**——当"保留已完成的冲突解决及其恢复点"比"紧凑历史"更重要时 |
| 自动解散冲突的 stack | 会让**本地分支推断覆盖共享的 GitHub 元数据**，还可能打扰被请求链**之外**的 PR 或作者 |

### 一条贯穿的边界：谁的元数据

把四种"需要用户确认"的场景排在一起看——混合作者、冲突 stack、顺序与拓扑不符、部分落地——会发现它们共享同一个性质：**这些是共享的元数据，不是本地状态**。

于是自动化的边界就清楚了：**本地能确定的事自动做，涉及共享元数据或链外影响的事，必须留给人类。** 这与第 1 篇的"人类拥有权守卫"是同一条原则的两种应用。

### 他们承认的代价

- 重写 push 会使 commit 哈希、批准或评论锚点失效，**所以每次重写 push 都带着一次活的评审与检查审计**
- `gh stack sync` **可能短暂地发布本地证据尚在等待的代码**；受影响的 PR 保持禁止合并直到同步后验证通过
- merge-forward 仍然可用并保留已完成的检查点，**代价是额外的合并提交**

## 3. 依赖优于手搓

`2026-07-26-dependencies-over-hand-rolling.md` · **本批最重要的一篇**

### 他们遇到的事

harness 手搓了大量成熟外部包已经提供的基础设施。其中**有一部分是刻意的**（vendored Cordis、孪生 LLM 适配器、schemastery 作为配置 schema 标准）——但他们诚实地指出，**更多的部分是从一个从未被说出口的"避免新依赖"反射中积累出来的**：

> the repo-wide external dependency list stayed tiny while packages grew their own SSE parsers, protocol framers, retry loops, and glob matchers

仓库范围的外部依赖列表保持极小，而各个包长出了自己的 **SSE 解析器、协议分帧器、重试循环、glob 匹配器**。

然后是整篇的题眼，也是我在这 94 篇里读到的最重要的一句：

> Nothing in `AGENTS.md` actually stated a dependency policy, so agents inferred one from the existing pattern, and the inferred rule ("don't add deps") is stricter than anyone decided.

**`AGENTS.md` 里没有任何地方陈述过依赖政策，所以 agent 从既有模式中推断出了一条——而推断出的规则（"别加依赖"）比任何人实际决定的都严格。**

他们对这个现象的命名是：**默认运行的"非我发明"（Not Invented Here）谬误**。每一个手搓的成熟库克隆，都是我们自己要测试、写文档、评审、调试的代码，**却一点也拿不到生态积累的边界情况修复**。

### 判断

- 引入外部依赖是**合法的简化**，不是政策例外
- 当维护良好的包（或引擎底线之上的 Node 内置模块）覆盖了手搓的面，**替换手搓代码是首选方向**
- 但受**与其他简化相同的证据标准**约束：交换必须**真正缩小我们所拥有的东西**（代码、测试、契约面），**而不是把复杂度搬到一个 wrapper 后面**

新依赖的四条门槛：

| 门槛 | 判断内容 |
|---|---|
| **净删除** | 依赖替换的是**真实的、已拥有的代码**（实现 + 专用测试 + 文档），不是假设的未来代码。**只增加能力的依赖是特性决策，不是简化** |
| **健康度** | 活跃维护、广泛使用、传递依赖足迹合理。**一个微小的无人维护的包，是用我们的代码换了别人的废弃代码** |
| **边界契合** | 包的语义要覆盖我们**实际**的契约；**我们仍然围着它手搓的剩余语义要算作这次交换的负分** |
| **不是已定的接缝** | schemastery、vendored Cordis、`@earendil-works` 孪生等已记录在 implemented Agent Note 里的决策**不因本政策重开**；一个要瓦解已记录设计的交换，**需要击败那个已记录的理由，而不只是引用本笔记** |

还顺手澄清了一处被误读的规则：`packages/util/` 的"零依赖"宪章描述的是那个组的**导出**纪律（util 包保持不含 harness 依赖，这样任何组都能依赖它们），**并不禁止外部包**。一个 util 包如果它的全部工作都被维护良好的外部包做得更好，**应该被依赖替换，而不是为了宪章而保留**。

### 凭什么这么判断

| 被否决的方案 | 否决理由 |
|---|---|
| 保持隐式的"不加新依赖"文化 | **它从来不是一条被记录的决定**；而它的成本是具体的——手搓的协议与解析代码重复了久经沙场的库，**抬高了逐文件覆盖率负担**，并**拖慢每一个必须重新推导"生态早已修好"的边界情况的评审者** |
| 一份获批包的硬白名单 | 仓库处于发布前、依赖集很小；**逐 PR 的证据门槛（净删除、健康、契合）加评审，把判断留在有上下文的地方**，而不是建立一个本身就需要维护的常设委员会制品 |
| 像 Cordis 那样 vendor 每个新依赖 | vendor 是留给**我们必须打补丁或对抗上游翻腾而钉住**的包；广泛套用它**会重建依赖本来要卸下的维护负担** |

第 2 条否决理由里那句"**把判断留在有上下文的地方**"值得记住——他们宁可逐 PR 付证据成本，也不要一个"本身需要维护的常设制品"。

### 他们承认的代价

- 依赖列表会增长，随之而来的是**供应链面**；而本政策**让那个供应链提案变得更紧迫**（原文就用"more urgent"）
- 根 `AGENTS.md` 只放一行规则，**理由和门槛由这篇笔记承担**

## 这批的共同判断标准

**① 当推断与权威冲突时，权威胜。**
三篇的三个版本：聚合状态 vs 交接事件（**选事件**）、本地分支推断 vs 共享元数据（**选共享元数据**）、从现状推断的模式 vs 写下的决定（**选写下的决定**）。

**② 而权威不存在时，必须显式建立它。**
第 3 篇证明：**沉默不是中立**。政策不写下来，就会被从现状中推断出来一条——而且**推断出来的总是比你想的严格**。这大概是"把规范写下来"最有力的论证，比"便于查阅"这种理由强得多。

**③ 状态要表达交接，不要表达判定。**
"谁拥有下一步"是交接，能驱动行为；"GitHub 认为可合并"是判定，会在具体反例上说谎。**选状态时先问：它是用来驱动谁的下一步动作的？**

**④ 自动化的边界由"谁拥有这份元数据"划定。**
第 1 篇的人类所有权守卫、第 2 篇的四类"需要用户确认"，是同一条原则：**本地能确定的事自动做；共享元数据或影响链外的事留给人类。**

**⑤ 重写历史必须带租约，且事后重新审计。**
精确 lease 或受 lease 保护的路径，远端移动就中止；裸 `--force` 禁止。而且因为 commit OID、批准和评论锚点会失效，**每次重写 push 都要重新审计评审、批准、检查、可合并性**。

**⑥ 不做的事也要列出来。**
第 1 篇那段"不重建评审轮次、不查询 reviewDecision、不加定时对账器"，价值不低于决策本身——**它划出了"这条命令管到哪为止"**。定时对账器尤其典型：它看似稳妥，实则是事件流之外的第二套真相。

**⑦ 交换必须真正缩小我们所拥有的。**
"净删除"这条门槛针对的是一个常见伪装：**把复杂度藏到 wrapper 后面**，看起来代码变短了，实际什么都没减少。"我们仍然围着它手搓的剩余语义要算负分"是同一个判断的延伸。
