# 2026-09-07 升级部署覆盖用户层修复（插件/MCP 丢失 + 无法启动）

> 现象报告（用户 v0.2.0 覆盖安装后）：① 用户自装插件与新版 DSH 不兼容，新版 SSiD 安装后无法启动；② 用户自装 MCP 消失——MCP 程序本体还在，但注册信息被覆盖。
> 结论：两个 bug 同根因（部署零保留覆盖用户层），另附一条「部署失败→无闭包锚点→运行时定位崩溃」的失效链与本机遗留的「陈旧 pending 回滚炸弹」。

## 1. 机制确认（代码 + 本机现场证据）

- `main.mjs deployRuntime`（v0.1.3+）：归档顶层 = profile 根内容，部署 = `node_modules` 整体替换 + **其余条目（package.json / cordis.patch.yml / pnpm-lock.yaml / vendor/…）逐个「rmSync + rename」覆盖**——没有合并，用户自装插件声明、用户 patch（MCP 注册）零保留。
- DSH 的 MCP 注册渠道 = profile 根 `cordis.patch.yml` 的 insert 条目（dsh-skill-mcp-center / 插件中心都编辑它）；DSH 无全局 MCP（2026-08-24 方案文档同款结论）。
- 本机现场（开发机即用户机器，dev 与安装版共用 `~/.dsh/profiles/ssid`）：
  - 今晚 21:53 安装版启动日志：`runtime deploy needed (archive=0.2.0-…e13b24f3 profile=0.2.0-…86e1fb66) → runtime deployed`；
  - 部署后 `cordis.patch.yml` = 模板原文（仅 mcp-playwright）；`package.json` deps = 模板+内核族；
  - 用户曾装插件（`@huanlin/dsh-plugin-better-sidebar-plugin-office`、`dsh-web-preview-panel`）仅存在于各 `package.json.pre-*`/`.bak-*` 备份，node_modules 实体已消失；
  - **`~/.ssid/pending-plugin-updates/index.json` 残留 8-28 的 `dsh-sidebar-qa@0.4.2`**：kernel `applyPendingPluginUpdates` 每次 boot 前 `pnpm add -w dsh-sidebar-qa@0.4.2`——一旦某次成功就把 0.5.0（rc.1 兼容）降回 0.4.2（rc.2 时代）→ `Failed to load plugins` 白屏。当前实体仍是 0.5.0（消费一直失败），但雷一直挂着。
- 无法启动链（ssid.log 实锤）：`runtime deploy failed: EPERM … .deploy.old`（旧实例/杀软占用 + 首次 `rmSync` 残留清理无防御）→ isUpgrade 走「继续用旧环境启动」→ 旧 profile 无闭包锚点（源码模式残留）→ `Error: 无法定位 DeepSeek Harness 运行时` → 崩溃。用户观察到「直接打不开」，且「没装插件时覆盖安装正常」——因为旧插件增大 node_modules 占用与部署失败概率，且失败后环境完整性差。

## 3. 设计取舍

- **MCP 自动合并、插件不自动重装**：MCP 条目是纯配置（无版本/兼容风险）→ 合并保留；插件声明层丢失后自动重装 = 把「旧版插件 × 新内核」的白屏风险直接灌回 → 只进报告，引导用户从插件中心装兼容版。
- **合并失败保模板**：任何异常返回模板原文（绝不写坏 profile patch），仅日志。
- 用户「disable 了出厂条目（如 mcp-playwright）」的偏好：合并规则以出厂模板为准（disable 同 id 不保留）——出厂基线恢复优先，文档记录此边界。

## 8. 补充（2026-09-07 深夜）：0.2.1 修复失效实证——insert 子条目级漏网（v0.2.2 修复）

- **用户实证**：另一台电脑 0.2.1 安装版覆盖 0.2.0 后，用户自装 MCP **仍全部丢失**（0.2.1 已含 92446d5 的护栏与 main.mjs/lib 修复——不是没带代码）。
- **根因（复现实锤）**：用户 MCP 是被**追加进既有 `- insert:` 列表的第三个子条目**（面板/插件中心的标准做法，顶层仍是同一个 insert 块）。第一版 mergeUserPatch 只做**顶层条目级**对比：旧 patch 的 insert 块整体 id=第一个子条目（mcp-playwright）→ 与模板同 id → 整块判定「模板已有」→ **用户子条目被丢弃**（复现：merged=0、mcp-user-custom 丢失）。只有「独立顶层 insert 块」形态（形态 B）能保住（复现 merged=1 保留）。
- **修复**（lib/profile-merge.mjs `mergeUserPatch` 重写）：**子条目级**对比——把模板与旧 patch 的 insert 块都 `splitChildEntries` 到子条目（`- <key>:` 形态判定，**排除 args/env 里的 `- !!js`/`- '字符串'` 列表项**——首次实现把 args 当子条目导致虚高合并 4 条）；用户新增子条目并入模板 insert 块尾部；非 insert 顶层条目维持原逻辑；任何异常保模板。单测 15/15（新增「追加子条目」与「模板无 insert」两用例）+ typecheck + round-trip（单块、子条目序 [playwright, codegraph, user]、无 BOM）全绿。
- **现状处置**：用户那台电脑的 MCP 注册已被 0.2.1 覆盖，但 0.2.1 部署时**快照已拍**——`~/.ssid/profile-backups/<旧指纹>-<ts>/cordis.patch.yml` 含升级前原始 patch（用户 MCP 条目可对照找回，面板重加）；自动保留从 0.2.2 起生效。
- **教训**：patch 合并的粒度必须到「insert 块内子条目」级；测试必须用**真实模板形态**（多子条目 + args 表达式/字符串）而不是理想化样例。

### 8.1 对抗审查（2026-09-07 深夜，修复后自查）

- **P1 真 bug（已修）**：`mergeUserPatch` 未剥离 **UTF-8 BOM**——旧 patch 若被编辑器写成带 BOM（首行即 `- insert:`、无头注释）→ `\uFEFF- insert:` 被条目切分误判为非条目行 → 整块（含用户 MCP）再次全丢。修复：入口 `replace(/^\uFEFF/, '')`（oldText + templateText）。
- **P2 边界（已确认安全，记录）**：① 模板有多个 insert 块时用户子条目并入**最后一个**块（当前模板仅 1 块）；② 子条目判定 `- <key>:` 不约束缩进层级——若未来某插件 config 含「数组对象带 id 字段」的嵌套结构会被误切（当前 mcp-client config 全为标量/列表，无此形态）；③ 模板顶层若出现 disable 条目，其子行 id 会进入 tmplChildIds（暂无此形态）。
- 对抗用例（+3，共 18）：BOM 头无注释旧 patch、多用户 MCP 子条目顺序、用户子条目内 args `!!js`/字符串完整保留。全套：18/18 + typecheck + 真实 v0.2.0→v0.2.1 复现（两形态均保留）+ round-trip（单块、序 [playwright, codegraph, user]、无 BOM）。
