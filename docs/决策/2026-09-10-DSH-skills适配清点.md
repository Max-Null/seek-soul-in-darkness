## 一、先说一个结构性发现：skill 是"技能包"，不是单个文件

调查前的认知是"12 个 skill = 12 个 SKILL.md"。实际是 **12 个技能包，共 2956 行**：

**这本身是设计要点**：`SKILL.md` 保持精简（45–172 行）以便随时加载，重材料外置按需读取。`dsh-doc` 里有一句把它说透了：

## 三、小改即可用（3 个）

### 1. `dsh-ci-test-reliability`（131 + 60 行）

**这是 12 个里通用性最高的。** 它解决的问题是"测试在真实 CI 拓扑下才暴露的失效"，而这些问题与仓库规模无关。

**通用判据（几乎可原样保留）**：

- **执行拓扑四层模型**：同一 Vitest 文件内 → 不同 worker 进程 → 同一 job 内的独立进程 → 共享主机的不同 job。"除非当前配置证明不然，**假设这些层会重叠**"
- **"进程隔离不隔离主机的端口、可预测文件系统路径、外部服务、数据库、socket 或继承的子进程。"**
- **"不要因为一个 fixture 缺隔离就把整个套件串行化。"**（"顺序化一个 Vitest 块无法保护主机资源免受另一个文件、进程、job 或 runner 的干扰"）
- **用资源所有者的分配器，而不是"先检查可用、稍后再占"**：网络用 `listen(0)` 读回分配到的地址；**绝不要扫描空闲端口然后稍后绑定**
- **进程全局状态清单**：`process.env`、`cwd`、假计时器、locale 与时区、模块 mock、注册表、console 钩子、`globalThis`、全局 `fetch` 拦截——**都当作独占可变资源**；变更时"捕获原值是缺失还是存在 → 恢复那个确切状态 → 立即注册恢复 → 最小作用域 `try/finally` → 保留 `afterEach` 兜底"
- **平台自有语义 4 条**（Windows 特有）：mtime 精度不足、环境变量名大小写不敏感、文件句柄异步释放（需要"按实测争用规模定大小的有界重试"）、无 POSIX 权限与信号语义
- **超时预算**："`describe` 或 case 超时会**覆盖** runner 的 `--testTimeout` 而不是让位"；**"提升测试预算时要一起提升 hook 预算"**（否则"只提升 case 预算会把一次争用失败挪进 `afterEach`"）
- **"固定的 sleep 不是 setup 完成或清理结算的证据。"** 等显式就绪事件/握手/状态转移/自有 promise/可外部观察的条件；**"超时只用来界定等待，绝不用作让断言成立的条件"**
- **释放干净**："调用 `abort()`、`close()` 或 `kill()` 而不等待自有的完成信号，是**不完整的拆除**"
- **拒绝掩盖式修复（7 条）**：加超时而不指明等待的状态、加重试、全部串行、吞掉错误、弱化断言、归一化不稳定行为、清理前加 sleep
- **而"恢复预算不是掩盖"**：把套件提升到它本来就有的 lane 预算，或"按 runner 上实测的争用规模定有界重试"，都是"**命名了等待的工作并归还了 lane 已授予的量**"
- **"只做诊断的请求保持只读：报告原因与证据，除非用户同时要求修复。"**

**需要适配的**：`docs/testing.md`、`docs/defensive-patterns.md`、`snapshots/AGENTS.md` 这些 DSH 文档引用；以及 `references/ci-flake-diagnosis.md`（60 行，绑 DSH 的 CI 拓扑）。

### 2. `dsh-trim-cot-leakage`（45 + 327 行）

**直接对应你的待办 #8（CoT 泄漏探针）**，而且它比第 02 批我读到的决策记录更完整——**决策记录给了原理，这个 skill 给了可操作分类**。

**核心判据只有一句**（"The one test"）：

> 对每一段可疑文字问：**一个在 HEAD 处、无法访问任何会话记录、PR 讨论或未提交草稿的读者，能否解析每一个引用、核实每一条主张？** 若不能，就用仓库视角重述仍成立的事实并删掉其余部分。

**8 类泄漏**（每类都有具体模式）：失效的设计会话引用、Stack/PR 视角、变更叙事与版本戳、评审编排、面向评审者的自我辩护、重述与推导记录、模糊措辞与规划残留、撰写语言滑落。

**9 条 keep 规则**（**这一节是防过度清理的关键**）：issue 引用、Agent Note 里的已合并 PR 引用、抑制理由、反事实现在时、**带 `measured` 的实测边界**（"provenance 词 `measured` 是承重的"）、运行时旧/新状态、note 变更史段落里的历史阶段名、**按设计在仓库外解析的外部引用**（RFC 章节号、Figma 帧名）、项目声音与体裁形式。

**工作流 5 步**，其中第 2 步是你待办 #8 要的方法：**先只读审计，跑召回探针（带 `--hidden`），每条探针在信任其输出之前，用一个已知正例和一个近似负例校准，然后逐条语义判断**——并且"**探针不是定义**：原始清除的每一轮评审都发现了探针漏掉的情况，所以在没有模式在手的情况下，也去读范围内最密集的文字"。

**需要适配的**：DSH 专有路径（`docs/AGENTS.md#writing-rules`、`verify-type-equiv`、`verify-translation-pairing`）、`references/recall-batteries.md`（52 行，探针清单要按 SSiD 的词汇重写）、`references/examples.md`（275 行，示例要换成 SSiD 的）。

### 3. `dsh-prose-standard`（81 + 142 行）

**文字判据通用，本体只需小改。**

**核心**："**写够以保住契约，然后移除推理记录、重复和装饰。**"

**"保住完整命题"一节是精华**——编辑前先识别段落里的每个命题，逐项保留：行为者与动作 / 条件、时机与顺序 / 情态（必须、可以、绝不）/ **负面保证与例外** / 归属、副作用、失败模式与后果。配套两句硬话：

- **"字数更少本身不是改进。"**
- **"不要为了满足删除目标而制造编辑。"**

**"按文字位置要求的覆盖"一节（11 类）**是最可直接移植的部分：公开 JSDoc / 内部注释 / 模块注释 / 测试 / 教程 / README / Agent Note / 事故复盘 / **skills 与 agent 指令** / 示例与配置注释 / 提示词与可见字符串 / 诊断信息——**每类都写明"该有什么"和"该删什么"**。

**Borderline 的定义值得抄**："只有当**至少两个版本都满足完整命题规则、但交换了被接受的原则**，且本 skill 不解决这个权衡时，才算 borderline。**一个只有单一保命题答案的改写不是 borderline。**"

**互动模式还给出了知识沉淀机制**：用户决定后，"**把原则和版本提炼进 examples，不带 PR 历史或评审叙述**"。← **这正是你说的"知识沉淀"，而且是它写明的做法。**

**需要适配的**：`vendor/` 与 `archived/` 排除（SSiD 无此结构）、`verify-client-ui-i18n`（无此门禁）、`adding-a-package.md`（无此文档）。

## 四、需适配（4 个）

### 4. `dsh-code-review`（52 行）

**"Manual checks"那 16 条是全篇价值所在**，且绝大多数与仓库规模无关：

- **意图与接口契约**：追踪每个变更接口的两侧
- **生命周期与并发**：异步 setup、回调、进程、拆除——"检查发布前的竞态、await 期间的取消、独立错误上报、回调包含、重入前的归属、完整的 detach 清理、静默拆除"
- **能力与消费者匹配**：追踪每一个当前消费者；**反向也要查**——"一个通用服务上的新公开方法，若唯一调用者是一个内部消费者，那是**不必要的 API 扩张**"
- **范围、归属与必要性**：把每个抽象、状态机、选项、防御性拷贝映射到它的当前契约、生产消费者与归属方
- **配置与公开选择**：问"每个默认值、公开操作集、格式有什么当前消费者证据或先例支持"；**"当证据缺失时，要求一个显式选择或显式推迟"**
- **模型视角**：检查模型实际收到的提示词、工具 schema、结果与诊断
- **执行路径**：跟踪每条拒绝路径到真正执行它的操作
- **界限覆盖最终操作**：定位完整产物的所有者，**探测极小与精确边界**
- **真实入口路径**：测试要走真实 Loader/bin/worker
- **测试强度**："断言在预期的回归上失败，并验证外部状态、日志、事件或释放，**而不是复述实现或相信 agent 的报告**"
- **"覆盖率是必要的，但不是场景正确的证据。"**
- 报告部分：**"把阻塞项与建议分开，并**省略已被绿色门禁强制的问题**"**，以及**"收到评审时，逐条核实，用技术理由修复或反驳，不要表演式同意"**

**需要适配的**：`Sources of truth` 那 8 个链接全部指向 DSH 文档；`Blocking requirements` 里 #3（subsystems/type-equiv）、#4（Cordis 注册）、#5（invariant companions）、#7（locale 文案）是 DSH 专有；`change-scope` 脚本不存在。

### 5. `dsh-find-simplifications`（157 行）

**判据通用、流程专用。**

**"什么算强候选"9 条**（可原样用于 SSiD）：

- 公开方法/事件/配置项/注册表通知/helper/包/持久事件/测试产物**没有生产消费者**
- 只有测试或文档是消费者，而它们钉住的行为**不承重**
- 两种表示**镜像同一个事实**
- 一个接缝有每个实现都必须支持、但**没有消费者使用**的方法
- 独立包只为测试/demo/支持代码存在
- 特性实现的是**投机性通用**
- 不变量/回滚路径/期望输出集/特例测试**只为保护一个未使用的 API 而存在**
- 手搓代码重实现了成熟外部包或 Node 内置已经提供的
- **简化后的行为可以略有不同，但新行为仍然合理且更易解释**

配套的反例同样重要：**"薄弱候选不足以写 Agent Note"**——删一个错字、跑一次 `knip`、移除一个有意记录的后端/适配器、**"无调用点证据地说'这看起来复杂'"**。

**"消费者三分类"是可复用的判据**：生产语料（`src`、运行时脚本、loader/config 路径）/ 非生产语料（测试、README/docs、Agent Note、快照、生成的期望输出、注释）/ **歧义语料（可能是产品冒烟路径的示例和脚本——分类前先查用法）**。

**"拒绝或降级一个候选"4 条**：存在生产调用者（那就是特性决策而非清理）/**API 由一个已实现的 Agent Note 或一个来之不易的防御模式明确论证过，而新证据没有击败那个理由**/移除会迫使无关翻腾而不真正减少公开 API/想法正确但太小（**那就加一个有针对性标签的 TODO**）。

**需要适配的**：`.agents/notes/` 制度、DSH 的包结构、`rg` 工作流细节、"Coalesce Superseded Agent Notes"整节（依赖待办 #7）。

### 6. `dsh-pre-push-checks`（128 行）

**判据通用**："选取**覆盖即将推送或被刚推送 diff 的最小测试与检查**，而不是反射式地跑全仓库套件"。

**通用条款**：

- **"除了钩子，不存在通用的本地基线。"** 每个行为变更需要"**能因它的回归而失败的最窄可用测试**"
- **"不要仅仅因为接下来要 commit 或 push 就手工重跑一个已经通过的检查。"**
- **"测试选择与覆盖率选择是两回事。"**
- **"不要推送并指望 CI 表现不同。"**
- 失败时的四条证据纪律：记录确切命令/失败测试/平台特定不匹配 → 确认相关的非平台证据 → **优先修跨平台不确定性** → 只有用户明确要求才绕过本地钩子，并报告究竟什么失败了、为什么期望 CI 不同
- 历史重写保护：`--force-with-lease=<branch>:<observed-oid>`，"**裸 `--force` 永远不允许**"
- 一条很实用的诊断：`gh pr checks` 报 "no checks reported" 且 `total_count: 0` 时，**那不是基础设施问题，是 PR 处于冲突状态**——"GitHub 在 PR 为 `CONFLICTING`/`DIRTY` 时不创建 `pull_request` 工作流运行"，而"空提交、`--allow-empty` 推送、draft/ready 切换、revert-and-restore 弹跳都会让 `total_count` 保持 0，并增加垃圾历史"

**需要适配的**：`change-scope` 脚本、8 类变更对应的具体 pnpm 命令、snapshot 目录规则、`gh stack` 相关整节。

### 7. `dsh-speed-up-perf`（91 行）

**测量纪律通用，基础设施专用。**

**测量卡片（7 字段，实施前必填）**是全篇最有价值的形式：用户操作 / 工作负载 / 入口路径 / 时钟 / 内存 / 判定 / 行为。

**通用判据（可直接用）**：

- **"一个可疑的循环、未使用的缓存，或一个大文件，本身不是瓶颈的证据。"**
- **"变化独立成本驱动量：字节、持久事件、紧凑记录、原始增量、轮次、工具、子项、可见 DOM 节点是不同的量。"**
- **"不要在不检查它压的是什么用户操作的情况下，把大批量微小的相同消息称为'真实的'。"**
- **"绝不让 fixture setup 偷偷预热一个冷场景。"**
- **"一个解析后丢弃的基线，与经过验证的保留历史不可比。"**
- **"不要为了让回归通过而放宽预算或挑选幸运的一次运行。"**
- **"不要仅为测量而新增生产导出，也不要把算法复制进一个'基准实现'。"**
- **"推迟不是删除"**，视口高亮不是完全虚拟化
- **"一个宽到让回归通过的阈值不是保护；一个低于已核实噪声底的预算也不可靠。"**
- **"不要静默截断历史、跳过工具结果、禁用不变量，或为了达到一个数字而改变生命周期语义。"**
- **"当收益在端到端处消失、典型工作负载实质回归、复杂度超过小收益、或取消/保留/持久性无法被解释和测试时，拒绝这个优化。"**
- **"不要仅仅因为报告来自 bot 就驳回它。"**
- 结果汇总格式：**工作负载 → 前后绝对值与比率 → 端点与内存语义 → 行为证据 → 负对照 → 实际执行的检查 → 排除项**，并**分开陈述作者自报的历史数字、新的本地测量与 CI 证据**

**需要适配的**：`benchmarks/AGENTS.md`、既有 benchmark lane、CI 性能门禁——**SSiD 没有这套基础设施**。判据可以先归档，等有性能需求时再建。

## 八、两个需要你决定的点

1. **落点结构与命名**：DSH 用 `.agents/skills/<name>/SKILL.md` + `references/`。SSiD 要不要照这个结构？如果照，名字前缀该用什么（DSH 用 `dsh-`，我们大概用 `ssid-`）？

2. **适配的产品是什么**：是产出**可直接放进 SSiD 的 skill 文件**，还是先产出**逐个 skill 的"适配说明"**（列出它依赖 DSH 的哪些前提、在 SSiD 该怎么改）？

   我倾向后者——因为按第 12 批学到的"**软技能**"（`dsh-prose-standard` 自称的 *"It is guidance, not a script"*），适配的价值恰恰在那些**判断依据**上，而不是让文件长得像。先有说明、再生成文件，也便于你逐条复核。
