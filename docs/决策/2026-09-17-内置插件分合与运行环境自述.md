# 内置插件分合与运行环境自述

> 状态：**已执行**（`dsh-ssid-env` 已入库并接入链路；分合结论已入手册 §10）
> 关联：手册 §10（内置专属插件规范）· `docs/决策/2026-09-15-pwsh-spawn-EPERM-重试插件决定.md`（同类的内置适配插件先例）

## 一、起因

模型无法从会话内判断自己跑在 SSiD 还是裸 DSH web 里。两者的界面同为 DSH Web GUI，但 profile、插件集合、会话根与配置层都不同；两侧同时运行时尤其容易混。2026-09-17 的调查中因此反复绕路——查宿主进程、查 Playwright MCP 配置、查会话根，每一步都要先确认「我在哪」。

SSiD 侧需要一份**运行环境自述**：像 `dsh-chinese-thinking` 那样注入一条提示词，让模型直接知道自己在 SSiD 内，并给出**可自行复核**的判据。

## 二、决策

**一、新增内置插件 `@max-null/dsh-ssid-env`**，贡献一条固定的 `systemPrompt` 段落。

- **动态而非硬编码**：只有探测到内核在 boot 前写入的 `SSID_PROFILE_DIR` 才注入，探测不到就保持沉默。装到非 SSiD 环境时不会说谎——自述说错比没有更糟。
- **判据可复核**：文本带上宿主进程链、profile 目录、会话根，模型可据此自行验证，不必盲信。
- **`order = -95`**：排在部署 persona 与 `dsh-chinese-thinking`（-90）之前——先知道「我在哪」，其余指令都在这个前提下读。

**二、内置插件保持「一个适配面一个插件」，不合并。**

## 三、备选方案与不采纳的理由

| 备选 | 不采纳的理由 |
|---|---|
| 三个小适配合并成一个「SSiD 适配包」 | 合并能省的成本已被工具吸收，代价却无法自动化（见下） |
| 四个全并成一个（含 `dsh-ssid-panels`） | 面板是 TypeScript 工程（22 文件 / 975 KB，含 `src/`、`client/index.tsx`、tsdown 构建、tests、docs），与三个手写 mjs 的小适配（合计 30 KB）性质不同；并进来会让适配包变成杂物袋，改一行重试逻辑也要重建整个 TS 包 |
| 用 profile 的 patch 层注入（不建插件） | 那是本机私有配置，不进 SSiD 产品；且 patch 改 `system-prompt` 需要 `!!js` 表达式读环境变量，不如插件干净 |

**「合并能省的成本已被工具吸收」的实测依据**：2026-09-17 加 `dsh-ssid-env` 的全部人工动作是——manifest 加一段 JSON → `node scripts/sync-vendor.mjs --apply` → `node scripts/check-vendor-sync.mjs`。全程没有手工复制第二个文件，门禁自动覆盖新包。

**合并的代价无法自动化**：

- **独立演进 / 单独回滚**：现在每个适配面可单独禁用
- **故障隔离**：一个坏不带倒其他
- **加载顺序**：`dsh-ssid-pwsh-retry` 必须挂在 `bundles` 末尾——Cordis 的 waterfall 用 `cbs.shift()` 逐个消耗监听器、`next()` 不可重放，只有链尾包装器重新 `next()` 才会真正 dispatch；合并后顺序由包的位置决定，可能静默改变重试语义

**重新评估的触发条件**：小适配插件 ≥ 5 个，或它们开始互相共享状态与生命周期。

## 四、实现

新增 `plugins/dsh-ssid-env/`（3 文件：`package.json` + `lib/index.mjs` + `cordis.patch.yml`），接入链路四步：

1. `shell/scripts/check-rules.manifest.json` 登记（`mode: "full"`）
2. `sync:vendor --apply` 铺两处 vendor（tpl + ssid；**web 未纳入**，与 `dsh-ssid-pwsh-retry` 同款）
3. 双处声明：`shell/profile-template/package.json` 与 `~/.dsh/profiles/ssid/package.json` 的 `dependencies` + `dsh.profile.bundles`（bundles 31 → 32）
4. 安装实体：`~/.dsh/profiles/ssid/node_modules/@max-null/dsh-ssid-env`

## 五、验证

- `check:vendor-sync`：`dsh-ssid-env（full）src=3 tpl=3 ssid=3`；341 个受检、0 违规
- `check:profile-sync`：0 违规
- `check:rules`：**7 门全绿**
- **运行效果待重启观测**：SSiD 的启动路径没有 patch watcher（`watchUserPatches` 只挂在 `apps/cli/src/profile-boot.ts:393`，`shell/kernel.ts` 未调用），新增插件必须重启才加载

## 六、副作用与遗留

- **顺手修复的既有漂移**：`dsh-ssid-panels` 的 `.npmignore`（tpl 侧缺）与 `release-notes.md`（ssid 侧落后一小时）——已用 `sync:vendor --apply` 对齐，`check-vendor-sync` 复验通过。
- **手工铺入的安装实体只在「归档未更新」的窗口期生效**：实例运行中不能 `pnpm install`（Windows 下会锁 node-pty 报 EPERM），所以本次直接复制了一份到 `~/.dsh/profiles/ssid/node_modules/@max-null/dsh-ssid-env`——**只为让这次重启就能加载**。**正式形态由归档部署保证**：template 已双处声明，`prepare-runtime` 构建归档时会带上该包，下次部署整体覆盖 profile node_modules 时它即成为权威版本，不需要额外的 lockfile 收编动作。
- **未涉及**：README 截图门槛不适用于 `dsh-ssid-env`（无界面元素）。
