## 1. 串行跨平台 CI 参考

`2026-07-21-serial-cross-platform-ci-reference.md`

### 他们遇到的事（三个递进的问题）

**① 必需检查不该是唯一的完整性预言机。**

> a defect in their gate inventory or dependency graph could **omit work while the required aggregate stays green**

**门清单或依赖图里的一个缺陷，可能漏掉工作，而必需的聚合仍然全绿。**

**② 把时间目标编码成超时，会制造一个独立的失败模式。**

> Hosted-runner startup and performance vary, so **a correct gate can be cancelled at the target boundary before it emits useful diagnostics**.

**托管 runner 的启动和性能会变化，所以一个正确的门可能在目标边界处被取消——还没发出有用的诊断。** 于是他们划开两个目标：**性能目标需要按 GitHub 时间戳测量，而正确性需要足够的时间去完成。**

**③ 评审者需要一个更简单问题的直接答案**：当仓库完整的聚合在**没有矩阵选择、没有分片变量、没有并发门**的情况下跑在每个操作系统上，会发生什么？

### 判断：一个独立的、串行的、可见的参考

- **PR 和 master 推送被赋予互补的责任**：PR 跑 Linux/native Windows/Node 兼容/Python 检查，**master 推送拿三套 Python 运行时载体和 Wine**
- master 上活跃的是**串行 standby** 引用，它们是"**持续重新证明故障切换目标的 hot-standby 演练**"
- 每个参考 job 跑 `check:ci` **不带任何分片选择器**，`DSH_GATE_CONCURRENCY=1` 让聚合**一次执行一个就绪的门**
- **"独立 job 定义刻意保持它们简短的 checkout、运行时 setup 和不可变安装序列可见，而不是把操作系统藏在矩阵或可复用 workflow 后面"**

### 凭什么这么判断

| 方案 | 否决理由 |
|---|---|
| **设每个超时等于它的延迟目标** | **调度方差会取消正确的工作，并压制诊断回归所需的证据** |
| **只信任并发的主清单** | **调度和验证共享实现假设；一个串行聚合是独立的完整性检查** |
| 每个 PR 都跑串行参考 | 它们重复完整的跨平台聚合，并给每个变更加 macOS 工作 |
| 每个 PR 都跑真实内核沙箱矩阵 | 它的四个状态**不参与分支保护**，而重复安装、Landlock 构建、macOS 单元对等**消耗 runner 容量却不改变合并裁决** |
| 用一个操作系统矩阵 | **三个具名 job 让参考面可见，而不需要另一个选择机制** |
| 在更大的 runner 上跑串行参考 | **必需 CI 和它的独立参考都必须在组织自有池无法分配 job 时仍可运行** |

第 2 条是本篇的核心判断：**"调度和验证共享实现假设"**——同一个实现既调度又验证时，它的错误会同时骗过两边。**所以需要一个走不同实现路径的独立检查。**

第 6 条是另一条通用原则：**正确性路径必须能在没有"仓库外部的 runner 配置"的情况下运行。**

### 三处平台正确性的处理

**① 平台所有权要显式。**

`terminal-bash` 支持 Linux 和 macOS，**因此它在 POSIX 上拥有它的单元与逐文件覆盖契约，而不是加载一个拒绝 `win32` 的后端**——**Windows 运行仍然执行每一个可移植包**，但**不声称覆盖一个它加载不了的后端**。

**② 可移植 fixture 要真的可移植。**

通过 `node:path` 推导原生路径；**用与生产相同的原生 realpath 实现**比较规范身份；**使用在每个主机上都合法的文件名**。

**③ 别名归一化要按最长优先。**

ACP snapshot 运行把生成 cwd 的两种拼写都传给归一化器，**"它按最长优先替换别名，这样 Windows 的短路径和长路径不能搅动共享 fixture"**。

### macOS 上的一处"遏制而不是移除"

> Node 24 on macOS arm64 has **aborted in its CJS lexer from a worker thread**; **the process boundary contains that external runtime failure without removing any test from the aggregate**, while Linux and Windows retain the lower-overhead thread pool.

**进程边界遏制了那个外部运行时故障，而不从聚合里移除任何测试。** 用结构隔离一个无法修复的外部缺陷，**而不是把它从检查范围里删掉**。

同段还列了三处"仓库自有的竞态在它们的观察边界处修复"：dev bundle 轮询**先暂存**再发布重扫、缺失 bundle **保持 dirty 直到成功的内容哈希**、真实 PTY fixture **在运行时组装同步 token**（"**这样交互式 shell 的输入回显不能满足一个子进程就绪等待**"）。

### 他们承认的代价

- **工作流包含重复的 setup 步骤**，master 参考可能比优化的 PR 路径长得多——**"那个重复是刻意的"**：评审者能检查每个操作系统的完整命令，而不用解析矩阵或并发调度器
- **参考可能暴露优化的阻塞集还不声称支持的平台故障**——而定性很关键：

  > Such a failure is **evidence about current cross-platform behavior** rather than a reason to **weaken or silently skip** the aggregate.

  **这样一个失败是关于当前跨平台行为的证据，而不是削弱或静默跳过聚合的理由。**
- **只对真实主机内核或打包 Landlock 安装可见的回归，可以在 master 报告之前合并**——"那个合并后检测窗口被接受，以换取从每个 PR 移除四个非阻塞 job；**默认分支保留完整的信号**"
- **移除严格时长超时，意味着延迟回归是被观察到而不是被自动取消**——因此**托管测量必须伴随性能变更**

## 2. 重定向 Node 编译缓存到数据卷

`2026-08-28-ci-node-compile-cache-data-disk.md`

### 他们遇到的事：一份带数字的现场勘查

自托管 Linux CI VM（**一台主机上 32 个 runner 实例**）**耗尽了根分区的 inode 容量**。机制链查得很清楚：

- pnpm 11.7.0 **在它的入口里启用缓存**（`bin/pnpm.mjs` 里的 `module.enableCompileCache?.()`），**每次调用都启用**
- TypeScript 在 `tsc`/`tsserver` 里也这么做
- **vitest 转发该 API 但不自己启用它**
- 每一次这样的调用都把序列化的 V8 字节码缓存写到 `os.tmpdir()/node-compile-cache`

实测（2026-08-28）：**697,389 个 inode 和 9.2 GB，其中 34,110 个文件年轻于 1 小时**。

> the cache **grows on every CI run and is never cleaned**, so the root partition's 3,276,800 inodes **trend toward exhaustion** even after the `dsh-*` residue is controlled

**缓存在每次 CI 运行时增长且永不被清理，所以根分区的 327 万 inode 趋向耗尽**——即使在另一处残留被控制之后。

### 判断：结构性修复，而不是清理

把 `NODE_COMPILE_CACHE` 重定向到每 runner 的数据卷临时目录（`/data_local`，1 TB，约 1% inode 使用）。**重定向是一个紧接 `actions/checkout` 的步骤，把变量写进 `$GITHUB_ENV`**，于是泳道里每个后续步骤都继承它。

### 三个"为什么不用更简单的做法"

**① 为什么不直接禁用编译缓存？**

> `NODE_DISABLE_COMPILE_CACHE=1` would stop root-partition growth immediately but **forfeit the startup speedup on every run**, and the cache is a **legitimately useful Node feature**. **Redirecting preserves the benefit while moving the cost off the constrained partition.**

**会立即停止增长，但每次运行都放弃启动加速。重定向保留了收益，同时把成本移出受限分区。** ——**"关掉它"永远是能立刻让指标变好的选项，代价是丢掉一个本来正当的功能。**

**② 为什么不把 `node-compile-cache` 加进残留清扫？**

> the CI sweep targets **test residue**; the compile cache is **a cache, not residue**. **Deleting it every run would discard the speedup the cache exists to provide.** Redirecting is **the structural fix**.

**清扫针对的是测试残留，而编译缓存是缓存，不是残留。每次运行删除它会丢弃缓存存在的意义。** 这是本批最好的一个区分：**"混乱"和"缓存"看起来都是"占地方的东西"，但前者的正确处置是删除，后者是搬家。**

**③ 为什么必须注入到 `$GITHUB_ENV`，而不是 job 级 env？**

两个具体的技术事实：**`runner` 上下文在 job 级 `env` 里不可用**（求值为空字符串，会**静默地**把缓存留在根分区）；而只在门步骤加 step 级 env **会让更早的 pnpm 调用继续写根分区**。

于是校验里有一条**位置断言**：`ci-workflow.spec.ts` 断言每个 Linux 泳道在 `pnpm/action-setup` **之前**注入该变量——**"位置断言会在注入移到第一次 pnpm 调用之后时失败"**。

**"在正确的位置做"属于被测试的契约，而不只是实现细节。**

### 一处经过实测的"静默降级是可接受的"

受限子进程（bwrap/Landlock）如果沙箱不授予 `runner.temp` 路径，**会继承变量但静默跳过缓存**。他们在 VM 上验证了行为差异：

> with `NODE_COMPILE_CACHE` pointing at an ungranted path inside bwrap, **`node` runs normally (exit 0)**, **unlike `mkdtemp` which fails hard** with a read-only filesystem error. The compile cache is **best-effort by design**; a failed write is **a cache miss, not a crash**.

**在 bwrap 里指向一个未授权路径时，`node` 正常运行（exit 0），而不像 `mkdtemp` 那样以只读文件系统错误硬失败。** 由此判定：**编译缓存按设计是尽力而为的，一次失败的写入是缓存未命中，不是崩溃。**

**先实测行为，再决定这个失败是否可接受**——而不是先假设再辩护。

### 他们承认的代价（Bought / Cost 格式）

- **Bought**：编译缓存不再消耗根分区 inode；**没有丢掉缓存的启动收益**
- **Cost**：缓存在 `runner.temp` 里累积，**而 runner 在 job 之间不清空它**——但在数据卷上（约 1% inode）**那无害**（**代价被量化，然后判定无害**）
- **Cost**：受限子进程跳过缓存，**"这是缓存未命中，不是失败，且符合 Node 的尽力而为契约"**
- **Cost**：**本地开发保持默认的 `os.tmpdir()` 位置**——CI 与本地不同，且被写出来

## 3. Playwright 视频捕获连续演示

`2026-09-08-playwright-video-gif.md`

### 他们遇到的事

第 04 批读过 GIF 证据链，现在补上视频模式。问题一句话：

> A screenshot storyboard **omits intermediate animation frames** and can miss short-lived progress indicators. **Increasing the encoded GIF frame rate cannot recover motion absent from its source images.**

**截图分镜省略了中间动画帧**；而**提高编码 GIF 的帧率，无法恢复它的源图像里没有的运动**。

**插值补不出信息。** 输出采样率再高，源里没有的东西也不会出现——**所以正确的做法是提高源采样率（改用连续录制），而不是提高输出帧率。**

### 判断与其他

- **浏览器控制工作流优先**；当它暴露 `recordVideo` 时，**在同一个受控上下文里**捕获中间帧；否则截图
- **视口与录制尺寸显式匹配，避免 Playwright 默认缩放到 800×800**
- 编码器接受视频或截图目录；视频输入**选一个连续区间、应用声明的播放倍率、延长最后一帧**
- **模式不当的选项和无效区间会失败**（fail-loud）
- **"失败的录制不能为一次成功的运行贡献帧"**（第 04 批那条纪律的延续）

### 一条划清"演示"与"证据"的规则

> The original video remains available for review; **trimming and speed never establish model response latency.**

**原始视频保持可评审；裁剪和加速永远不确立模型响应延迟。**

**一旦你改变了时间轴，这个产物就不能再被当作时间证据。** 用它做演示可以，用它证明"模型响应很快"不行——**因为加速这个动作本身改变了被声明的那个量。**

### 凭什么这么判断

| 方案 | 否决理由 |
|---|---|
| 只提高编码帧率 | **重复稀疏的截图不会捕获额外的运动**（截图仍对显式状态保持、请求的分镜和无视频支持的工作流有用） |
| 安装一个单独的录制器，或捕获桌面 | **仓库已经声明了 Playwright。** 另一个驱动增加 setup 和版本管理；**桌面捕获会包含无关窗口和个人状态** |

第 2 条里那个理由值得记：**"桌面捕获会包含无关窗口和个人状态"**——**扩大捕获范围会把别人的隐私捎带进来**。

### 他们承认的代价

- **连续录制保留中间状态，所以评审者必须检查选定区间是否有敏感内容与可读性**——**新能力带来了新的评审义务**，而不是"更真实所以更省事"
- 原始视频消耗额外暂存存储；**上下文关闭是成功录制的一部分，不是可选的清理**
- **编码器的本地测试调用真实 ffmpeg 和 ffprobe**，需要媒体前置条件并**被显式运行；仓库 CI 不供应这些媒体二进制**

最后那条又是"不声称验证不了的东西"：**这些测试不在 CI 里跑，就明说不在 CI 里跑。**

## 对索引里跨批模式的印证

**模式 D（证据要成立）——"独立预言机"是一个新维度。**

"调度和验证共享实现假设"——**如果一个检查与被检查的对象共享实现，它的通过不能独立地支持任何结论。** 这是"证据"要求的又一次升级：不只是"验到消费点"，还要"**用一条不共享假设的路径去验**"。

**模式 A——"不声称验证不了的东西"再次出现（两处）。**

"仓库 CI 不供应这些媒体二进制"（本地测试不在 CI 跑，就说明）；"本地开发保持默认位置"（CI 与本地不同，就写出）。

**模式 C——"演示"与"证据"的区分。**

"裁剪和加速永远不确立模型响应延迟"：**同一个产物的不同用法，其证明力不同；改变了时间轴，就不能再主张时间结论。**

## 这批的共同判断标准

**① 独立检查不能与被检查对象共享实现假设。**
"调度和验证共享实现假设；一个串行聚合是独立的完整性检查。" **同一个实现既调度又验证时，它的错误会同时骗过两边。**

**② 超时不是性能目标的正确表达。**
"调度方差会取消正确的工作，并压制诊断回归所需的证据。" **用取消来表达"太慢了"，会让你同时失去"慢在哪"的证据。**

**③ 区分"混乱"与"缓存"。**
两者看起来都是"占地方的东西"，但**前者的正确处置是删除，后者是搬家**。"每次运行删除它会丢弃它存在的意义。"

**④ 结构性修复优先于周期清理。**
重定向 vs 清扫、搬到为它定尺寸的卷 vs 定期删——**当增长是某个东西的正常行为时，问题在"它长在哪"，不在"它长了"。**

**⑤ 插值补不出信息，要提高源采样率。**
"提高编码帧率无法恢复源图像里没有的运动。" **输出端的任何加工，都不能让输入端不存在的信息出现。**

**⑥ 一旦改变时间轴，就不能再主张时间结论。**
"裁剪和加速永远不确立模型响应延迟。" **编辑手段与被声明的量相冲突时，产物的证明力归属要重新划定。**

**⑦ 让参考面可见，值得付出重复的代价。**
"那个重复是刻意的：评审者可以检查每个操作系统的完整命令，而不需要解析矩阵或并发调度器。"

**⑧ "在正确的位置做"属于契约，不只是实现细节。**
位置断言：**注入必须发生在第一次 pnpm 调用之前，否则整个目的落空**——所以测试断言的是位置。

**⑨ 代价要量化，然后判定它可不可接受。**
"缓存在 `runner.temp` 里累积，runner 不清空它——但在数据卷上（约 1% inode）那无害。"**先量，再判，而不是含糊地说"影响很小"。**

**⑩ 新增能力带来新增义务。**
"连续录制保留中间状态，**所以评审者必须检查选定区间是否有敏感内容与可读性**。" **能力变强时，责任清单同步变长。**
