## 1. 生成的第三方声明

`2026-07-30-generated-third-party-notices.md` · **本批最重要的一篇**

### 他们遇到的事

开源要求披露依赖及其许可证。这个披露必须同时满足三件事：

1. **完整**
2. **随依赖变化保持真实**
3. **说出读者能行动的东西**——哪些包最终会出现在用户机器上，哪些只用于构建和测试

然后一句判决：

> A hand-written inventory answers **none of those durably**. Roughly a hundred rows... **drift silently the moment a package is added, removed, or relicensed, and nothing would notice.**

手写清单一条都做不到。大约一百行名字与许可证字符串，**一旦有包被添加、移除或改许可就会静默漂移，而没有任何东西会注意到。**

### 判断：把"新鲜度"设计成被维护，而不是被检查

这是本篇最有价值的设计，也是对模式 B 的一个正面解法：

> **Freshness is maintained, not merely enforced.** A pre-commit job regenerates the file and stages it **whenever a generator input is staged**... so **an unrelated dependency edit never has to come back and rerun a generator**.

**在生成器的任一输入被暂存时，pre-commit job 重新生成并暂存该文件。** 输入清单包括：任何 manifest、workspace 声明、根锁文件、`vendor/README.md`、`pyproject.toml`、生成器本身、以及持有构建期 pin 的脚本。

于是**一次无关的依赖编辑永远不必回头重跑生成器**——文件在提交的那一刻就已经是对的。

而**校验**则搭了现成的车：提交后的字节在 `gen-third-party-notices.spec.ts` 里被断言，**而测试泳道本来就会跑它**：

> the check adds **no gate process, no scheduler slot, and no separate CI step**

**不增加门进程、不增加调度槽位、不增加独立 CI 步骤。**

对比一下他们否决的那个方案就明白这个设计的分量：

> its only failure mode is telling a contributor, **minutes after they pushed an unrelated dependency bump**, to go rerun a generator

**它唯一的失败模式，是在一个贡献者推完一个无关的依赖升级几分钟后，告诉他"去重跑一下生成器"。**

### 一个被接受、而不是被绕过的缺口

> lefthook inspects only files present on disk, so **deleting** a manifest runs no job

lefthook **只看磁盘上存在的文件**，所以**删除**一个 manifest 不会触发任何 job。他们试过补救——重建暂存文件列表以包含删除——**不行**，因为 lefthook 无论如何都会用工作树过滤那个列表。

于是他们**接受这个缺口并指定兜底**：断言正是为这种情况存在的。**"接受并指定兜底"不同于"忽略"**——差别在于缺口被写下来了。

### 三条关键的内容判断

**① 只披露直接依赖。** 完整传递闭包（几千个包）**已经带精确版本记录在锁文件里**：

> re-materializing either as prose would be a **second, worse copy**

**把它们重新物化成散文，会是第二份、更差的拷贝。** 文件改为指向锁文件和 `pnpm licenses list` 渲染器。

**② 分层跟随"分发"，不跟随 manifest 区段。**

这是本篇的技术核心，也是他们明确推翻的一个"机械上简单"的做法：

| 规则 | 结果 |
|---|---|
| 按 manifest 区段分层（`dependencies` vs `devDependencies`） | **机械上简单，在真实数据上两个方向都错** |
| 按"从已发布装配的可达性"分层 | 层更紧，**但把 MCP 客户端和 OpenTelemetry 导出器判为仅开发——即使用户运行已安装的仓库时可以挂载它们** |

实际规则：运行时库 = `dependencies` 或 `optionalDependencies` **且不在 `DEV_ONLY_AREAS` 里**；**被发布的 tsdown 和 Vite 配置解析的浏览器输入也算运行时，即使它们在 `devDependencies` 里**；而**测试支持的依赖不会仅因为它的 manifest 写着 `dependencies` 就发布**。

最关键的一条：**运行时层刻意覆盖每一个可挂载的插件**，不只是默认装配加载的那些——因为**源码执行可以从用户的 `cordis.yml` 挂载任何插件包**。原文由此给出错误方向判断：

> **Under-disclosure is the costly direction for a legal notice.**

**对一份法律声明来说，披露不足才是代价高昂的那个方向。**

**③ 各处 fail-loud 的清单。**

- manifest 集合**从根 `pnpm-workspace.yaml` 声明的成员派生**——"**一个新的成员区域在被声明的那天就被读到，而不是等到有人记得扩展列表的那天**"
- **一个包若既不在 store 也不在 link farm 里解析，就大声失败，而不是发出一个空单元格**
- **许可证不在许可列表上的运行时依赖是硬错误**：*"发布 copyleft 是一个分发决定，不是一张重新生成的表可以静默吸收的东西"*
- vendored 包与 `vendor/README.md` 交叉核对，**任何一个不是 MIT 就被拒绝**
- `patchedDependencies` 列在运行时表下——因为 **pnpm 在安装时应用那些补丁，发布的产物携带修改过的副本，而补丁文件就是"改了什么"的记录**

### 一段极精细的授权设计（Claude SDK）

项目所有者单独授权分发官方 `@anthropic-ai/claude-agent-sdk`。生成器把它表示为**一个精确的直接包身份例外，而不是一次许可证宽松化覆盖**：

- `SEE LICENSE IN README.md` 这类**仍然是非宽松分类**
- **每一个无关的非宽松运行时仍然 fail closed**
- 当 SDK 存在时，生成器读它已安装的 manifest、**拒绝官方 SDK 载荷前缀之外的可选身份**、验证已安装宿主载荷的身份/版本/声明许可字段
- 版本、声明许可和载荷集变化**不需要新的身份授权**，但**仍然需要常规的依赖、锁文件、兼容性、条款和 notices 评审**

被否决的两个替代形状：

| 方案 | 否决理由 |
|---|---|
| 把 Claude SDK 条款当作宽松 | **错述上游声明** |
| 加一个可复用的非宽松允许列表 | **让一个无关的运行时继承它从未被授予的授权** |

### 测试要钉住"静默遗漏路径"

> It also pins the parsers against the shapes that would otherwise **drop a package without a word**... **Each of those is a silent-omission path, which is the failure mode a disclosure file cannot afford.**

被钉住的形态包括：`vendor/README.md` 表格不再覆盖某个 vendored 目录、带 extras 的 requirement（`"httpx[http2]"`）、完全没有版本的 requirement、作者命名的 `[dependency-groups]` 表、**一个不在任何硬编码列表里的 workspace 成员区域**。

测试还钉住了**促成这条规则的那两种情况**：一个测试支持包的 `dependencies` 条目、一个没有应用挂载的插件包。

### 他们承认的代价

- 依赖编辑现在**把重新生成的文件带进同一个提交**；贡献者在触碰 manifest 的提交上付**大约一秒**，其他提交上不付
- **禁用钩子提交会把成本推迟到一次指名命令的测试泳道失败**
- 生成器**需要已安装的树**，比纯源码生成器重；**新包若有不可用的发布元数据，需要一条 `OVERRIDES` 条目，而不是静默渲染空白许可证**——两个失败都**大声且指名补救方法**

## 2. worktree 局部的 Lefthook

`2026-07-27-worktree-local-lefthook.md`

### 他们遇到的事

每次 `pnpm install` 跑根的 `postinstall`，它调用 `lefthook install --force`。问题是：

> Linked Git worktrees otherwise **share the common repository's default hooks directory**, so **an install in any worktree can rewrite hooks used by every other worktree**.

**链接的 Git worktree 共享公共仓库的默认 hooks 目录，所以在任何一个 worktree 里安装，都能重写其他每一个 worktree 正在用的 hooks。**

而更具体的失效：Lefthook 生成的 hooks **优先使用"安装它的那个 worktree"捕获的绝对二进制路径**，然后才尝试当前 worktree 的回退。所以：

> Shared hooks can therefore **run another worktree's pinned binary until that worktree disappears**, while concurrent installs write the same files.

**共享的 hooks 可能运行另一个 worktree 钉住的二进制，直到那个 worktree 消失**——而并发安装还在写同一个文件。

这是**共享可变状态**的经典事故：两个本该独立的实体，通过一个共享的隐式位置互相破坏。

### 判断

把 hooks 安装变成 **worktree 作用域**。防护清单极其详尽（择要）：

- `CI=true` 或 `GITHUB_ACTIONS=true` 时**在 Git 发现或变更之前就返回**——"自动化 job 不消费贡献者的 hooks"
- 要求 Git 2.26+（`git config --show-scope` 能报告值来自哪个作用域）
- **升级 format-0 仓库之前，拒绝直接的 common-config `extensions.*`**、拒绝 `core.worktree` 或 `core.bare=true`、拒绝**启用扩展后会激活的非空休眠配置**
- **这些检查禁用 include 展开**——"因为 Git 的仓库格式解析器也忽略被包含的目标"（**模拟对方的行为，包括它的盲区**）
- 仓库作用域的锁串行化迁移与写入，**释放时必须核对进程 ID、随机令牌、文件身份和确切内容**
- **死锁或无效锁需要人工恢复，而不是自动破锁**
- 每个 hook 目录带 JSON 所有权标记，**只允许替换那个确切过时的自有值**
- **`$GIT_COMMON_DIR/hooks` 里的现有文件永不被移除或重写**
- Lefthook 在改完 `core.hooksPath` 后失败时**恢复先前的值**；**回滚失败与安装失败一起报告**

### 凭什么这么判断

| 方案 | 否决理由 |
|---|---|
| 保持共享 hooks，依赖"当前 worktree 回退" | **捕获的绝对路径在它的 worktree 存在期间胜出，所以回退不提供版本或生命周期隔离** |
| 让每个 worktree 指向一个签入的 `.githooks` | **改变共享的 `core.hooksPath` 会禁用那些分支不含该目录的旧 worktree 的 hooks，而且仍然把每个 worktree 耦合到一个共享配置值** |
| **构建一个通用的 hook 管理器链式层** | 顺序、参数转发、失败语义和升级**变成与 Lefthook 隔离无关的仓库自有行为** |
| 白名单 provider 专属的 CI 凭证 include 路径 | **会把安装器安全耦合到 provider 的 checkout 内部**，并削弱对贡献者安装的严格校验 |
| 停止自动安装 hooks | 避免了共享写入，**但会让仓库廉价的提交/推送检查意外变成可选的——尤其是在短命的 agent worktree 里** |

第 3 条是"拒绝造通用层"的范例：**一个只为解决 X 的改动，不该顺手引进一套属于别的问题的仓库自有行为。**（与第 05 批"不随一次简化捎带进来"同源。）

第 5 条点出一个隐蔽后果：**让检查变成"可选"不是中立的**，它在短命的 worktree 里尤其致命——而 agent 恰好大量使用短命 worktree。

### 他们承认的代价

- 仓库在第一次安装后**变成 Git format-1 仓库**
- **自定义 worktree hook 管理器需要一个显式的集成选择**
- **旧式公共 hooks 保留在磁盘上供未升级的 worktree 使用：它们可能变陈旧，但自动移除它们会破坏一个尚未采用此安装器的已注册 worktree**

最后一条是"**迁移期间必须容忍双重存在**"——而且**容忍的方向明确偏保守**（宁可留陈旧的，不可破坏在用的）。

## 3. 把 Node LTS 下限提到 22.19

`2026-07-06-node-engine-floor.md`

### 他们遇到的事

根 `engines.node` 的 Node 22 分支**不只是 harness 源码直接调用的运行时 API 的契约**：

> it is a contract **for the installed workspace**, not only for the runtime APIs the harness source calls directly

它必须**不低于**在该分支上安装的依赖的 `engines.node` 声明。否则：

- **`pnpm install --engine-strict` 会在一个被广告的 LTS 版本上失败**
- 非严格安装会**运行在一个依赖支持的运行时之外**

### 判断与推理链

源码特性给出的边界：`node:sqlite` 丢实验标志在 **22.13**，原生 TypeScript 类型剥离成为默认在 **22.18**。

**但这些源码特性在 22.18 就通过了，真正抬高下限的是已安装的依赖**：`@earendil-works/pi-ai@0.79.3` 声明 `engines.node >=22.19.0`。所以 LTS 下限是 **22.19**。

然后是不相交范围的论证：**完全排除 Node 23**——23.0–23.5 仍至少有一个被标记的源码特性，**而 23 线是非 LTS/EOL，所以广告 `>=23.6` 会增加一条死的发布线和一条没有部署应该使用的 CI 腿**。

### `@types/node` 的 pin 逻辑（这段很实用）

保持钉在 22.x 线，理由是**失败要发生在编译期而不是运行期**：

> Pinning `@types/node` to the 22.x line turns that into a **compile error everywhere**.

对照被否决的方案：

| 方案 | 否决理由 |
|---|---|
| 让 `@types/node` 领先于下限（`^25`） | **类型领先于运行时下限，会让一个 Node 24/25-only 的 API 编译干净，只在 22.x 上运行时失败。** 钉到 22.x 把它变成每处都编译错误 |

以及矩阵与范围的两条：

| 方案 | 否决理由 |
|---|---|
| 矩阵写 `[22, 24, 26]` 而不是钉 `22.19` | **浮动的 major 条目会随时间长上去，并静默停止演练声明的 LTS 下限** |
| 开放式 `>=22.19` | 广告了对 23.0–23.5 的支持——**那里至少有一个特性仍被标记** |
| `>=22.13` 加版本条件测试标志 | **为一个狭窄范围增加一个版本条件标志，并把一个实验性标志依赖打扮成一等支持** |

### 他们承认的代价

> A future dependency or source API that raises the runtime floor must move `engines.node`, the compatibility matrix, and **this Agent Note** in the same change.

**一个未来的依赖或源码 API 若抬高运行时下限，必须在同一次变更里移动 `engines.node`、兼容矩阵和这篇 Agent Note。** 文档被列为**必须在同一变更里更新的三样东西之一**。

## 对索引里跨批模式的补充：模式 B 的边界终于清楚了

前几批我记录了三处"拒绝第二份真相"：**生成的 Agent Note 索引**、**`vendor/published.json` 账本**、**Knip 的例外清单**。而这一批，他们**接受**了一个生成文件（`THIRD_PARTY_NOTICES.md`），它同样是"从别处派生出来的第二份拷贝"。

同一类东西，为什么结论相反？原文给了答案：

**① 它是业务必需的，不是便利。** 开源合规**要求**这份披露存在——你不能"消除"它，只能选择"手写"还是"生成"。而索引只是发现路径的一种便利，账本只是状态的一种记录。

**② 自动化的位置不同。** 他们不是事后检查它是否新鲜，而是**在源头变化的同一时刻重生成**：

> Freshness is **maintained**, not merely enforced.

**③ 校验搭了已有的车。** 断言放进测试泳道本来就在跑的 spec，**零额外 CI 成本**。

由此我修正模式 B 的表述：

> **模式 B（修正）：能消除的第二份真相就消除；必须存在的第二份真相，就在源头变化的同一时刻自动重生成它，并让校验搭已有的车——绝不让"同步"成为某个人某天要记得做的事。**

判据的三问：**它是必需的吗？源变化时能自动重生成吗？校验能搭现成的车吗？** 三个都否，就该考虑消除它。

这条也解释了那个被否决的 doc-sync 门方案为什么输：**它唯一的失败模式是把同步成本推给一个人**（"在无关提交之后几分钟告诉他去重跑生成器"）。

## 这批的共同判断标准

**① 新鲜度要被"维护"，不只是被"强制"。**
在源头变化时重生成，而不是在事后告诉人去重跑。**让同步成为机制的一部分，而不是某个人的待办事项。**

**② 校验要搭已有的车。**
断言放进测试泳道本来就在跑的 spec——**零新门进程、零新调度槽位、零新 CI 步骤**。（第 01 批说过"门禁本身是要维护的代码"，这是对那条代价的直接回应。）

**③ 分层跟随真实分发，不跟随 manifest 区段。**
"机械上简单，在真实数据上两个方向都错。"**读 manifest 的字段名很容易，判断它是否真的随产物到达用户很难——但只有后者是对的。**

**④ 判断错误方向，并往安全的那一侧倾斜。**
"对一份法律声明来说，披露不足才是代价高昂的方向。"**每一个规则都要问：如果我错了，会往哪边错？**

**⑤ 测试要钉住"静默遗漏路径"。**
那些"否则会一声不响丢掉一个包"的输入形态，才是披露类产物承受不起的失败模式。**测的不是"它能工作"，而是"它不会安静地不工作"。**

**⑥ 隔离共享可变状态。**
一个 worktree 的安装不该改另一个 worktree 的行为。**隐式共享的位置（默认 hooks 目录）是这类事故的标准温床。**

**⑦ 拒绝把手头问题变成一个通用层。**
"构建通用 hook 管理器"被否决，因为**顺序、参数转发、失败语义、升级会变成与目标无关的仓库自有行为**。

**⑧ 让检查"意外可选"不是中立行为。**
"停止自动安装 hooks 会让廉价的提交/推送检查意外变成可选的，**尤其是在短命的 agent worktree 里**。"

**⑨ pin 比范围好，类型不能领先于运行时下限。**
浮动的 major 条目**会随时间长上去，并静默停止演练声明的下限**；类型跑在运行时前面，会把运行时故障伪装成编译通过。

**⑩ 文档和代码在同一次变更里移动。**
"必须移动 `engines.node`、兼容矩阵和这篇 Agent Note"——**文档是必须同步移动的三样东西之一，不是事后补的。**
