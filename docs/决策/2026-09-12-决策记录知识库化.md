## Problem

`docs/决策/` 累积了 110 篇记录，全部符合 `YYYY-MM-DD-标题.md` 命名，但**没有统一元数据**，只能靠文件名和记忆定位。要知道「哪些决策还在进行中」「某插件相关改过哪些决定」，只能全文翻找。

同时，待办 #7 原案要求「目录即状态机」——把 `docs/决策/` 重组为 `{proposed,implemented,rejected,archived}` 四个子目录。**但实测发现不可行/不划算**：

- 43/110 篇已有**非正式头部**（`- 状态：x` / `> 状态：x` / 裸 `状态：x` 三种写法并存），**67/110 完全没有**
- 按状态分目录要**移动 110 个历史文件**，破坏既有引用路径（手册、决策记录之间大量互引）
- 且「状态」是**会变的**：一篇 `implemented` 将来会 `archived`，每次状态流转都要**再移动一次文件**，git 历史会碎

## Decision

**用「元数据投影」替代「物理目录重组」，且不改动任何一个历史文件。**

1. **零侵入解析**：只读 `.md`，从文件名取日期、从正文头部取状态/决策人、从正文首标题取标题。解析不到的诚实标为「未标注」并在报告里逐个点名——**绝不批量补写**。
2. **状态「原文 + 类别」双字段**：保留 `statusRaw`（如 `✅ 已完成（v0.1.4 已…）`）与归纳出的 `statusKind`（进行中/已决策/已完成/记录/未标注）。归一的规则表**顺序敏感**：先判「进行中」，否则「实施完成，待 npm publish」会被误归为已完成。
3. **自包含单页**：内联**原始 markdown**（不预渲染），浏览器端用内置极简渲染器转换；全文内联所以搜索是纯本地、零外部请求。
4. **惯例**：新增决策记录后跑一次 `node shell/scripts/build-decision-index.mjs` 重建索引。知识库是**只读投影**——改元数据要改 `.md` 原文。

## Alternatives considered

| 备选 | 否决理由 |
|---|---|
| **YAML frontmatter 批量注入**（最初方案） | 67/110 篇没有状态头，批量填 = **替历史做 67 个未经查证的判断**，违反「断言必须有据」。改为只解析不补写。 |
| **物理目录重组为四状态目录**（待办 #7 原案） | 要移动 110 个历史文件、破坏既有互引路径；且状态会流转，每流转一次就要再移动，git 历史碎片化。用户已改向「元数据 + 生成 HTML」。 |
| **预渲染 HTML 后内联** | 体积翻倍，且正文失去「原文可搜索」这一性质。保留原始 markdown 更省也更可检索。 |
| **状态归一为四状态枚举** | 会吃掉 `已完成（v0.1.4 已发布）` 这类括号里的细节。改为双字段：原文忠实保留、类别供筛选。 |
| **只出 JSON 或只出 HTML** | 两者用途不同：JSON 供程序消费/二次加工，HTML 供人浏览。因此两者都生成，但 `decisions.json` **不入库**（可由脚本重建），`index.html` 入库。 |

## 实施记录：过程中修掉的三个真 bug

均为本次引入，全部由验证环节发现。

### 1. 状态抓取强制要求行首前缀 → 19 个假阴性

`grab()` 初版正则要求 `状态：` 前必须有 `-`/`*`/`>`，实测存在**裸写法**（行首直接 `状态：`）。
症状：状态覆盖只有 23/110，而独立探测是 42/109。**差值 19，且当时「未标注 86 = 67 + 19」精确吻合**，据此定位。

### 2. 同一行串联多字段 → 又漏 1 个

```markdown
> 日期：2026-09-10 · 状态：方案 B 已选定，可行性验证进行中
```

`状态：` 不在行首。修复后覆盖 23 → 41 → **42**，与独立探测精确相等。
副作用修正：`grab('日期')` 原会把整行后面全吃掉并污染 `dateNote`；正文里 `2026-08-29（晚）` 这类**带补充说明**的日期被误报为「与文件名不一致」——按前 10 字符比对后归零。

### 3. 渲染器死循环（最严重）

极简 markdown 渲染器的段落分支：一个**以 `|` 开头但不构成表格**的行，会被表格分支跳过、又被段落分支的排除正则 `\|` 挡住 → `while` 不执行、`i` 不推进 → **无限循环，浏览器会卡死页面**。
症状：验证器跑全部记录时 **120 s 超时**；修复后 **22 ms**。

修复：段落分支加 `if(i===guard){p.push(l);i++;}` 兜底推进，主循环加 `steps++<L.length*4+64` 迭代上限。

## 验证（三层，共 37 项断言）

1. **数据层报告**：覆盖率 + 缺口点名（无标题文件逐个列出，不只给一个数字）
2. **生成物验证**（`shell/scripts/verify-decision-index.mjs`，14 项）：内联 JS 语法检查、DATA 可 JSON.parse 且篇数 == 目录实际 `.md` 数、JS 引用的 11 个 DOM id 全部存在、全部记录渲染非空、渲染输出中未转义 `<script` 为 0 次、渲染耗时上限
3. **行为验证**（`shell/scripts/verify-decision-ui.mjs`，23 项）：迷你 DOM shim 真跑页面逻辑，交叉断言「点击筛选筛出条数 == 按同一数据现算的期望条数」

两个验证器的期望值**全部动态锚定**到目录实际文件数，不硬编码篇数——否则每新增一篇记录就要改验证器。

**两条教训**：

- **「写出成功」不等于「能用」**：只看构建器输出会漏掉死循环这个致命问题；生成物必须被独立验证。
- **验证器自己也会骗人**：本轮验证器先后误报 **3 次**，全部是验证器侧的问题，不是生成物的问题：
  1. 用 `;\n` 非贪婪正则提取内联 DATA，但生成物里 `var DATA={…};(function(){` **没有换行** → 把后续代码当成了 JSON 尾部；
  2. 单独 eval `md()` 时漏了它依赖的同作用域函数 `esc()` → `ReferenceError`；
  3. shim 的 `history.replaceState` 写成空函数 → 「深链是否写入」这条断言**恒为假**。

  出现误报要先证明「是生成物错还是验证器错」，不能默认生成物有问题。
