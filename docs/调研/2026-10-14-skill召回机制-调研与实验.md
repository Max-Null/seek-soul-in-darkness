## 一、问题从哪来

用户在 2026-10-14 提出一个观察：

> 「skill 列表似乎是会话开始时注入的，在上下文的头部，但是随着上下文的增加以及压缩，
> llm 会忽略掉 skill，进而不使用 skill。mcp 和其他工具也有这种情况。」

这条观察有两个可检验的断言：① 注入位置在头部；② 压缩/增长导致忽略。
下面逐一验证，**结论是：①对，②错——真正的变量是上下文压力，不是压缩。**

## 二、机制证据链（全部经源码或日志实测）

### 2.1 工具与 skill 走两条完全不同的通道

| | 工具（含 MCP） | skill 目录 |
|---|---|---|
| 身份 | `request/header` 里的 **API 参数** `tools`（225,369 字符，`reason: "initial"`） | 一条 `user/message`，`data.source.kind = "skill-catalog"` |
| 是否在对话历史里 | **不在** | **在** |
| 受压缩影响 | 不受（压缩只作用于对话历史） | 受（在压缩范围内） |
| 重发规则 | 每个 API 请求都带（这是 API 机制） | 只在 digest 变化或压缩遮蔽后重发 |

**关键旁证**：`request/context` 事件里的 `systemPromptUpdate` 值是 **`"in-history"`**（10 个字符）——
DSH 的系统提示本身就在历史里，不是独立字段。

### 2.2 压缩只豁免 `system/message`

`dsh-compaction-basic/lib/index.js`：

```
L390  * The `system/message` holding surface node 0, or `undefined` when another
L396  function systemHead(session, headSeq) { ... return head.type === "system/message" ? head : void 0 }
L401  * Resolve the next range starting at the first non-system surface node
L410  function selectCompactableRange(session, measurement, retainTokens) {
L415      const firstIdx = systemHead(session, surfaceNodes[0]) === void 0 ? 0 : 1;
```

从**第一个非 system 节点**起就是压缩范围。skill 目录是 `user/message`，**在范围里**。

摘要模板固定八节（`COMPACTION_INSTRUCTION`，同文件 L243 起）：
`Primary Request and Intent` / `Key Technical Concepts` / `Files and Code` / `Errors and Fixes` /
`Pending Jobs` / `Current Work` / `Next Step` / `Critical Context`。
**没有「可用技能」这一节** —— 目录被替换时，30 条 skill 名字没有地方留下来。

### 2.3 但压缩后会立刻重发目录（实测 16/16）

`dsh-tool-skill/lib/index.js` 的 `catalogHistory()` 用 **`session.surface.nodes`（可见面）** 判断目录在不在：

```js
const visible = new Set(agent.session.surface.nodes)
...
if (visible.has(event.seq)) return { visibleDigest: digest, published }
...
return { published }        // 曾经发过，但已不在可见面 → visibleDigest 为 undefined → 触发重发
```

**实测（扫 `~/.dsh/sessions-ssid` 全部 250 个会话文件）**：16 个发生过压缩的会话，
**16 个都在压缩后重发了目录，0 个失败**：

| 会话 | 压缩 seq | 新目录 seq | 间隔 |
|---|---|---|---|
| session-02c57 | 2043 | 2056 | 13 |
| session-feb7f | 1953 | 1970 | 17 |
| session-1e3ba | 419056 | 419061 | 5 |
| session-553ab | 462768 | 463206 | 438 |

重发用 `renderCatalogUpdate`（`update: true`），措辞是「目录变了，这张才是准的」——
而内容其实相同（同 digest）。`session-02c57` 里这种「目录又变了」的消息出现了 9 次。

**结论：压缩不丢目录。** 这条机制设计得扎实。

### 2.4 官方文档对「注入时机」的权威表述

`packages/skill/tool-skill/README.zh.md` §目录生命周期：

> 「**每次符合条件的 `agent/pre-step`**，该插件都会使用调用会话的 cwd 调用 `ctx.skills.snapshot()`…
> digest 变化时，下游 `enter` 决策会收到一条包含**完整替换目录**的持久用户角色消息」

即 **每次 pre-step 都检查，但只在 digest 变化时追加**。这与实测（本会话 25 轮只有 1 条目录，seq=12）一致。

> ⚠️ **注意区分「检查」与「追加」**：外部资料（见 §八）常把这两件事说成「每个请求都注入」，
> 因而高估了目录的常态成本。

### 2.5 无关但值得知道的注入差异

| 注入来源 | `source.kind` | 重发规则 | 本会话实测 |
|---|---|---|---|
| skill 目录 | `skill-catalog` | digest 变化 / 压缩遮蔽后 | 1 次（seq=12） |
| 工作区指令 | `agent-instructions` | 内容变化时 | 1 次（seq=10） |
| 运行时上下文 | `runtime-context` | **每个用户轮次** | 2 次（seq=11, 30） |
| 时间上下文 | `time-context` | 每轮 | 1 次（seq=13） |

## 三、会话日志的读取方法（下次直接用）

> 本节与 [长会话输出退化](../排查/2026-09-18-长会话输出退化.md) §二 的方法一致，
> 那篇是源出处（含 `scanZstdFrames()` 的完整帧头解析）。这里只补本文另行踩到的字段坑。

- **文件**：`~/.dsh/sessions-ssid/<工作区>/<session-id>/session.v4.jsonl.zstd`
  （早期会话是 `session.v3.jsonl.zstd` / `session.jsonl.zstd`；
  ⚠️ 格式已从 v3 走到 **v4**，写脚本时按魔数切帧，别按版本名判断）
- **格式**：**多帧 zstd 拼接**（每次追加一批事件写一帧）。必须逐帧解压，
  按普通压缩流解会在第二帧报 `Unknown frame descriptor`。按魔数 `28 b5 2f fd` 切分即可。
- ⚠️ **本机 PATH 里的 Node 22.12 没有 `zstdDecompressSync`**。要用壳自带的 **Node 24.21**：
  `%LOCALAPPDATA%\Programs\ssid-shell\resources\runtime\primary-runtime\dependencies\node\bin\node.exe`
- **字段坑**（踩过）：
  - `user/message` 的文本在 **`data.content`**（消息块数组），**不在** `data.message`；`data` 里**没有** `turn`
  - turn 归属靠 seq：最后一个 seq 更小的 `turn/start`
  - `tool/call` 有 `data.turn` / `data.step` / `data.name` / `data.arguments`
  - `assistant/message.usage` → 压力 = `inputTokens + cacheReadTokens + cacheWriteTokens`（provider 上报的真实计数）
- **压缩事件**：`compaction/start` / `compaction/summary` / `compaction/end` / `compaction/prune`

## 四、实测：调用率随压力衰减（核心数据）

**样本**：`~/.dsh/sessions-ssid` 全部会话，170 个 ≥293KB 的会话，共 2206 轮（后修正为 2070 轮，剔除 <5 轮的会话）。

### 4.1 会话内分箱（同一会话内部，控制任务类型）

| 压力区间 | 轮数 | skill 调用率 | 普通工具调用/轮 |
|---|---|---|---|
| <100k | 200 | 14.00% | 12.21 |
| 100-200k | 279 | 12.54% | 26.14 |
| 200-300k | 320 | 4.69% | 23.80 |
| 300-500k | 609 | 4.43% | 18.95 |
| 500-700k | 510 | **2.55%** | 17.75 |
| >700k | 288 | 5.90% | 28.88 |

**skill 掉到峰值的 1/7.7，而普通工具只降约 40%。** 不是整体注意力衰减。

### 4.2 固定位置后的压力效应（最干净的口径）

会话开头 25% 的轮次，只用用户**未显式点名**的轮次：

| 压力区间 | 轮数 | skill 调用率 |
|---|---|---|
| <100k | 77 | **19.48%** |
| 100-200k | 95 | 6.32% |
| 200-300k | 70 | 2.86% |
| 300-500k | 95 | 5.26% |
| 500-700k | 79 | **2.53%** |
| >700k | 22 | 4.55% |

**19.48% → 2.53%，跌 7.7 倍**：跨过 100k 即跌到峰值的 1/3 以下，主体下跌在 **100k–200k 之间**完成。

⚠️ 但**不是单调下降**：两个口径的最高压力档都有反弹（§4.1 的 >700k = **5.90%**，288 轮；本节 >700k = 4.55%，
22 轮），300-500k 档也小有回升（本节 = 5.26%）。反弹原因**没有查过**——小样本波动、或高压档的会话构成不同，
两种解释都还没有证据。主结论不受影响：「100k 以上显著低于 100k 以下」是量级差异，另有两条独立对照支持（§4.3）。

### 4.3 逐一排除的替代解释

| 替代解释 | 检验方式 | 结果 |
|---|---|---|
| 就是压缩导致的 | 位置×压力 格子内比未压缩 vs 已压缩 | **排除**——格子内差异散乱甚至反向（>60% 位置 >600k：未压缩 0.00%(34) vs 已压缩 4.10%(195)）；合计的 6.41% vs 3.45% 来自压力分布差异 |
| 长会话任务类型不同 | 按用户措辞分任务类 | **排除**——各任务类在同一压力下调用率 5.71%–9.23%，差异小；固定任务类型后压力效应依旧 |
| 用户只说了一次 | 拆「用户显式点名」成分 | **部分成立但不是主因**——点名轮次调用率 11.76% vs 未点名 3.89%，但 **68.63% 的调用发生在未点名轮次**（模型自己认出来的），这部分同样随压力崩塌。**⚠️ 2026-10-15 复核：这个 11.76% 是口径上界——它的「点名」判定是关键词命中而非「要求执行」，提问/反馈/讨论都进分母；同口径重跑得 8.7%、严口径 37.1%，且 22 条漏用里 21 条是模型自己手搓 git 把事做完了。详见 [动机复核](../决策/2026-10-15-旁观助手-动机复核.md)** |
| 目录在头部所以被忽略 | 按会话内位置分箱 | **弱**——位置效应非单调（中段低、结尾回升），远弱于压力效应 |

## 五、一个假警报（记录以免重复踩）

检查 31 个 SKILL.md 的 description 时，用**单行解析**得到 4 个 skill 的 description 只有 1 个字符 `>`：

```
mxy-commit-review / arch-live-map / mxy-design-doc / mxy-organize-code  →  desc = ">"
```

一度怀疑「目录里显示的是坏的 description」，那会是个惊人的发现。

**实际是我方解析器的问题**：这些 skill 用了 YAML 折叠块

```yaml
description: >
  代码审查 + 修复问题 + 二次审查……
  当用户提到"提交""提交代码"……时使用。
```

内核用的是 **`import { parse } from "yaml"`**（`dsh-skill-filesystem/lib/index.js:7`），真正的 YAML 解析器，
折叠块会被正确展开。**数据和显示都没问题。**

> **判据**：解析 frontmatter 时用真 YAML 解析器；用正则/单行解析会把折叠块（`>` / `|`）读成标记本身。

## 六、问题本质

压力是独立主导因素，**且是 skill 特有的**。为什么偏偏是 skill：

| | 普通工具 | skill |
|---|---|---|
| 性质 | **手段** —— 当前要读文件就调 `read` | **策略** —— 需要先意识到「这里有个现成流程该套一下」，再调一次工具去取 |
| 决策层级 | 一阶（直接执行） | **二阶（先做策略选择）** |
| 压力大时 | 基本不受影响（-40%） | **先被牺牲**（-87%） |

**skill 是这套体系里唯一需要二阶判断的工具**——这解释了为什么只有它受影响特别重，也解释了
为什么 MCP 工具（同样是手段）不受影响。

**结论：问题不是「目录被压缩掉了」，也不是「目录太远」，而是「压力一大，模型不再抬头看那份清单」。**
而且压缩后重发也不解决问题——重发只是把目录重新放回头部，下一次压力升上来照样被忽略。

## 七、七个实验（全部有脚本留档）

脚本在 `scripts/`（与本文同目录，见其 [README](./scripts/README.md) 的运行环境与分类）：

| # | 脚本 | 验证什么 | 结论 |
|---|---|---|---|
| 1 | `measure-skill-usage.mjs` | 压力 vs 调用率 | 19.67% → 2.55%（首版脚本口径，档位与 §4.1 不同） |
| 2 | `measure-position-vs-pressure.mjs` | 位置/压力何者主导 | 压力主导 |
| 3 | `measure-final.mjs` | 拆用户点名成分 | 点名占 31% 调用 |
| 4 | `measure-4.mjs` | 修字段 bug 后正式测量 | 压力是唯一独立因素 |
| 5 | `match-feasibility.mjs` | BM25 匹配可行性 | **不成立**（见 §7.1） |
| 6 | `exp-trigger-words.mjs` | 补触发词 vs 只接长 | **不成立**（见 §7.3） |
| 7 | `exp2-router.mjs` + `build-eval-set.mjs` | 换厂商独立模型做路由 | **不成立**（见 §7.2，49.0%） |

### 7.1 BM25 匹配不可行（两个结构性根因）

**根因一：语料层面无词可匹配。** 2125 条真实用户消息里：

| 情况 | 条数 | 占比 |
|---|---|---|
| 含 skill 全名 | 44 | **2.1%** |
| 仅含组成词（`commit`/`review`） | 288 | 13.6% |
| **都不含** | **1793** | **84.4%** |

用户说「整体审查一遍」「你拉取一下三库最新代码」「提交」，skill 叫 `ssid-code-review`、
`mxy-git-pull`、`mxy-commit-review`——字面匹配没有字面。

**根因二：CJK 语料下 BM25 被通用词淹没。** 实测「请依次处理以下 6 个插件的更新」
被判给 `dsh-upstream-watch`，**756 分**，贡献词全是 `dsh:79.4 插:62.7 插件:62.7 版:52.6 本:55.1`。
而真正的 `dsh-plugin-upgrade` 名字就在文本里、description 也不同，却排在后面。

**分数与语义几乎不相关**：模型真调用了 skill 的轮次 top-1 分 p50=**17.8**，
未调用的轮次 p50=**38.8**——高分反而更可能是错的。

### 7.2 独立模型做路由也不行（实验 2，判据未过）

**设计**：换厂商的独立模型（`qwen3.8-flash`，`workflow` 的 model 覆盖不可用——脚本环境不支持 `import`，
改为直接调 DashScope OpenAI 兼容端点）。评估集 **96 条**带真值正例 × 2 组对照。
判据事前定死：**top-1 ≥85% 成立 / <70% 不通**。

| 组 | n | top-1 | 判 none | 判错 | API 失败 |
|---|---|---|---|---|---|
| **给完整 description**（每条 420 字符） | 96 | **49.0%** | 10.4% | 40.6% | 0 |
| 只给 name（不给 description） | 96 | **49.0%** | 9.4% | 41.7% | 0 |

**判据未过，连 70% 的底线都没到。**

> ⚠️ **读这个数字前先看它的性质**：评估集只收「模型当年**真的调用过** skill」的轮次，真值因此
> ＝**那个模型的历史选择**（见 `build-eval-set.mjs` 的口径）。所以 49.0% 是**与历史选择的一致率**，
> 而不是「独立判断者判断得对不对」——两者只有在「历史选择本身都正确」的前提下才等价，而本节末段
> 恰好给出了反证。结论（没有匹配器能复现模型的选择）不受影响，但**别把 49.0% 读成「独立模型判断不准」**：
> 它否掉的是「复现选择」这一类方案，不涉及 §9.1 右列的「观察」。

**三个致命读数**：

1. **换厂商换模型只提升 6 个点**（BM25 43.1% → qwen 49.0%）→ **瓶颈不在算法**：
   字面匹配与语义匹配撞在同一堵墙上。
2. **description 完全不影响结论**——给与不给，准确率**逐位相同（49.0%）**。
   这是**第二次**独立观测到同一现象（§7.3 的「只接长」对照组也追平了「补触发词」组）。
3. **存在「吸引子」**：`aic-gate` 被误选了 **17 次**，而它的真值只有 2 条。   原因：它的 description（「判断某个东西**能不能往前走**」「这个**能交付吗**」「发布**生效了吗**」）
   **语义宽到离谱**，成了万能答案。反过来 100% 命中的四个语义域都极窄且唯一：

| skill | 准确率 | 被误判成什么 |
|---|---|---|
| mxy-git-pull | **16/16 = 100%** | — |
| omo-codemap | **5/5 = 100%** | — |
| aic-report | **4/4 = 100%** | — |
| doc-derivatives | **3/3 = 100%** | — |
| genui | 2/24 = 8% | `aic-gate`×7、none×4 |
| mxy-commit-review | 10/25 = 40% | `aic-gate`×5、none×4 |
| aic-gate | 0/2 = 0% | 被误判成别的（它是黑洞本身） |

**更本质的一层**：14 条被判 `none` 的样本，真值都是模型当年**真的调用过** skill 的轮次——
独立判断者看着同样的信息说「不需要」。**两者的判断标准不一致，不是谁更准。**

> **判据（重要，别再试第三种匹配器）**：「该用哪个 skill」这个判断**本身不适定**——
> 不是匹配器不够好、不是模型不够强、不是 description 没写好。
> 三次独立观测（BM25 / 事后补触发词 / 换厂商语义模型）都指向同一结论。
> 这同时解释了 §八 竞品调研的发现：**不是它们没想到，是这个判断本身做不对**——
> 所以所有竞品都只做「降低目录成本 + 赌模型主动读」。

**脚本**：`build-eval-set.mjs`（重建评估集）、`exp2-router.mjs`（跑路由实验，
key 从凭据文件读、不落盘）。评估集与结果落在 `.exp2/`（已 gitignore，含真实会话文本、不入库）。

### 7.3 补触发词也不行（对照实验）

**设计**：三组（基线 / 实验组=补触发词 / 对照组=只接长等量技术描述），
评估集 65 条带真值正例（3 个 skill：genui 24、mxy-commit-review 25、mxy-git-pull 16）。
**判据事前定死**：实验组 ≥80% 成立；<50% 判不可用。

| skill | n | 基线 top1 | 实验组 top1 | 对照组 top1 |
|---|---|---|---|---|
| genui | 24 | 0.0% | 8.3% | 0.0% |
| mxy-commit-review | 25 | 48.0% | 56.0% | **56.0%** |
| mxy-git-pull | 16 | 100.0% | 100.0% | 100.0% |
| **合计** | **65** | **43.1%** | **49.2%** | **46.2%** |

**三个决定性读数**：

1. **对照组追平实验组**（mxy-commit-review 上 56.0% vs 56.0%）——
   涨分来自「description 变长、token 变多」，**不是触发词起作用**。
2. **污染大于增益**：实验组只改善 4 条，却造成 **28 条**原本判对的样本被抢走（对照组同样 28 条）。
3. **`mxy-git-pull` 的 100% 反而证明原假设**：它的 description **本来就写着**
   「当用户提到「拉取代码」「拉取最新代码」「pull 一下」时使用」，且语义域单一。
   而 `genui` 基线 0%（description 在讲自己能画什么，没有一个用户说法），补 17 个触发词只到 8.3%。

**量级差距是根本原因**：一次输入的查询有几百 token，触发词只有几十个，BM25 的 IDF 还会压低常用词权重。

> **判据**：description 里「有完整用户说法」与「没有」是质变（100% vs 0%），
> 但**事后补几个词补不出来**。

**实验局限（如实记录）**：69 条正例、单一 BM25 判定口径、触发词是从正例里提炼的（有事后拟合成分）。
但「对照组追平实验组」这一条不受这些局限影响。

## 八、竞品调研（2026-10-14）

### 8.1 Soleur：skill 发现被压缩截断（最接近的同类案例）

来源：[jikig-ai/soleur 的 fix 计划](https://raw.githubusercontent.com/jikig-ai/soleur/afc95ddd9457eae1fbc6e2ead54abf1f1792f9a9/knowledge-base/project/plans/2026-03-14-fix-skill-discovery-context-compaction-plan.md)（2026-03-14）

**它的现象**：58 个 skill + 40 个 agent，元数据合计 ~5,230 词 / ~7k token 每轮注入。
压缩时 skill 元数据表**被静默截断** → 早先引用过的 skill 仍可用（在压缩上下文里缓存着），
**未被引用过的变成 "Unknown skill"**。`brainstorm`/`plan`（早期调用）能跑，
`work`/`compound`/`ship`（后期调用）报 Unknown。

**它的解法**（Prong 1 + Prong 2）：

- 削减 description：**删掉 `Triggers on "..."` 触发短语**（29/58 个 skill 有，共 ~435 词）
  → 目标从 2,729 词降到 **1,800 词以内**，并加**预算测试**（`components.test.ts` 里断言总量 ≤1800 词）+
  `verify-skills.sh` 校验脚本
- 理由：「模型不需要显式触发关键词，它从 skill 名和核心描述推断意图」
- 同类先例：agent description 从 ~15.8k token 砍到 ~2.9k（删 `<example>` 块，**82% 降幅**）

> ⚠️ **与我们的结论方向相反，原因是场景不同**：
> - 它的失败模式是 **Unknown skill（目录被截断/丢失）**；我们是 **目录在、模型不调用**
> - 它主张**删掉触发短语**（依赖 skill 名自解释，如 `gemini-imagegen`）；
>   我们的 skill 名（`mxy-commit-review`/`genui`）自解释性弱，而实测显示**有用户说法是质变**
> - 它能每轮注入全部元数据（Claude Code 行为）；**DSH 不是每轮注入**（§2.4）
>
> **可借鉴的是它的工程化手段**（预算测试 + 校验脚本 + 把「元数据是路由而非指令」讲清楚），
> **不是它的削词方向。**

### 8.2 dsh-skill-router：把目录成本从 O(n) 降到 ~600 token

来源：[mikuniemo/dsh-skill-router](https://github.com/mikuniemo/dsh-skill-router)（**专门针对 DeepSeek Harness**）

**它量化了一个我们没测的维度——目录的绝对成本**：

| skills 常驻数 | 目录成本/请求 |
|---:|---:|
| 50 | ~5,000 token |
| 1,246（实测真实库） | **~70,800 token** |

「在 200K 上下文里，**35% 在第一条消息之前就没了**。」

**它的方案**：把真 skill 移出扫描根（用 junction 链接到 `~/.dsh/skills-off/`），
只留一个 ~600 token 的 `skill-router` skill，再生成分类索引文件，模型按需 `read`。
**模型三步加载**：read router → read 一个索引 → read 一个 SKILL.md。

它的五个设计决策里，对我们最有参考价值的三条：

1. **链接指向 off-root，绝不指向扫描根**——否则索引记录的是会被移走的路径，产生死链（已向上游报过）
2. **DSH 扫五个根**（rank 100 project-dsh → 500 user-agents），只管理 `~/.dsh/skills` 会漏掉其余
3. **令牌数学要诚实**：DSH 对 description 有 `catalogDescriptionMaxLength`（默认 500）上限；
   CJK 下一个字符常等于一个 token，不能按 4 字符/token 估

**它自己声明的局限（关键）**：

> 「**Depends on the model actually reading the router.** Weak models may ignore the instructions;
> the router text states the rule explicitly, but that is the trade.」

**它把「模型会不会读」当成已知风险直接接受了。** 而这正是我们要解决的失效——
所以它对我们**只是部分有用**（降成本、减缓压力衰减），不是解药。

### 8.3 其余同类项目（同一思路：路由 + 渐进披露）

| 项目 | 定位 |
|---|---|
| [jax-agent/skill-router](https://github.com/jax-agent/skill-router) | 「One skill to route them all」——meta-skill，让 agent 拥有无限 skill 而不烧 context |
| [langchain-skill-router](https://pypi.org/project/langchain-skill-router/) | Per-turn skill routing for LangChain deepagents |
| [hussi9/skill-router](https://github.com/hussi9/skill-router) | Skill + Agent + Model + 思考深度自动路由（声称 90% routing accuracy） |
| [@starpivot/dsh-skill-router](https://www.npmjs.com/package/@starpivot/dsh-skill-router) | npm 上的 DSH skill router（npm/socket.dev 直连被 403 拦，未细读） |
| [open-gsd/gsd-core Discussion #993](https://github.com/open-gsd/gsd-core/discussions/993) | 「`agent_skills` 是否支持按任务上下文自动选 skill」——同类需求讨论 |

**行业共识**：**做路由 + 渐进披露，降低目录常驻成本**。
**没有任何一个项目声称解决了「模型不主动调用」**——所有方案都依赖模型主动读/主动调。

> **推论**：这个失效目前是**行业未解**的。我们要做的不是复刻它们的路由，
> 而是处理它们都绕开的那一半。

### 8.4 GitHub 直连受限（内网）

`github.com` 的 `web_fetch` 报 `fetch failed`，`raw.githubusercontent.com` 可用，
`npmjs.com` / `socket.dev` 返回 403（反爬）。**以后调研 GitHub 项目一律走 raw 通道。**

## 九、助手形态讨论：一个更对症的方向

用户在讨论中提出类比：

> 「能不能给主 Agent 找个团队成员作为助手，专门递工具，就像做手术时主导医生会配至少一个递工具的助手，
> 这样可以让主刀医生专注手术。」
> 「助手只需要看到 Agent 在做什么就行吧？」

### 9.1 这个方向的真正价值：换了问题类型

| | 「预测」方案（前面全部） | 「观察」方案 |
|---|---|---|
| 要回答 | 这轮**该用**哪个 skill（开放、要语义理解） | 这轮**有没有**该用却没用（封闭、看行为痕迹） |
| 判据 | BM25 top-1 命中——实测 40%，不达标 | 「用户说了『提交』，但本轮 tool/call 里没有 skill」——**规则可判，不必靠模型** |
| 依赖 | 必须猜对**是哪个** | 只需察觉**异常模式** |

**「该用哪个」猜不准，但「用户在催提交、Agent 却在手搓 git 命令」是客观事实，可直接检出。**

### 9.2 机制核实（关键事实，全部源码级）

| 问题 | 答案 | 依据 |
|---|---|---|
| `spawn_teammate` 能配工具集/模型吗？ | **不能**。只有 4 个参数：`name`/`description`/`prompt`/`context` | `dsh-experimental-tool-agent-team/lib/index.js` 的 `defineTool` |
| 底层 API 支持吗？ | **支持**。`ContinuableSubagentDescriptorData` 带 `agentModel`/`persona`/`toolFilter`；`ToolRestriction = { allow?, deny? }` | `dsh-agent-preset-registry/lib/typert.host.js:367` |
| teammate 只拿到 9 个 Team 工具吗？ | **不是**。它继承父级完整工具集（含 `read`/`pwsh`），9 个是**额外**给的 | `packages/subagent/subagent/README.zh.md:43`：「先加入父级的 agent-preset 组合…**加入父级组合正是子 agent 获得能力的途径**」 |
| agent-team 限制了吗？ | **没有**。其 `lib/index.js` 里 `toolFilter`/`restrict` 出现 **0 次** | 同文件扫描 |
| 队友能看到主 Agent 的实时行动吗？ | **不能**。Agent 间是消息传递，不是共享状态 | — |
| `context: fork` 是订阅吗？ | **不是，是一次性快照** | `subagent-fork-in-process/src/index.ts:84-86`：「The fork prefix is captured **ONCE**, at creation」 |
| 队友什么时候运行？ | **被唤醒才动**（`inactive` = 没有轮次在执行） | Team 工具文档 |

**所以「助手看到 Agent 在做什么」有两条通道**：

1. 主 Agent 用 `send_message` 转发（但它汇报什么由它自己决定——忘了 skill 的可能也忘报）
2. **助手自己读会话日志**（§三 的方法；这条不需要任何新增机制）

### 9.3 一个必须正视的约束

**如果助手是同一个模型 + 同一份 skill 目录，它会和主 Agent 犯同一个错。**
失效根源是判断力来源相同，不是信息缺失——给它更多信息不一定能修好它。

要让观察者真正独立，必须**换模型**（不同厂商不同盲区）或**换输入**（只喂压缩后的行动摘要）。
而在「观察」形态下，这个约束可以放宽：观察的是**客观行为痕迹**，判断难度本身低于语义预测。

### 9.4 机制张力与三层方案

**规则违反的检测需要「每轮都看」，而队友是「被唤醒才动」**——这两件事对不上。

| 层 | 形态 | 机制 | 代价 | 需要验证吗 |
|---|---|---|---|---|
| **1** | **纯规则**（推荐先做） | 插件在 `agent/pre-step` 读本轮 user 文本 + tool/call；命中「提交/拉取/审查」等词而本轮无 skill 调用 → 注入提醒 | 零模型、零延迟、确定性 100%；只能覆盖少数可枚举措辞 | **不需要** |
| 2 | 独立模型观察者 | 主 Agent 每轮调一次 `check_compliance` 工具；工具内部读日志 + 完整 skill 目录 + 换过的模型 | 每轮一次模型调用 | 需要（实验 2） |
| 3 | 常驻 teammate | 主 Agent 每轮 forward；助手读日志后 `send_message` 回来 | 主 Agent 多一步转发 + 等待延迟；收益是能跨轮积累理解 | 需要（实验 2） |

**第 1 层零成本且判据确定（不依赖任何模型准确率），可以立刻做。**

### T2 · 第 1 层纯规则（可立刻做，零成本）

在 `agent/pre-step` 里做最小检测：用户文本命中动作词（提交/拉取/审查/发版…）而本轮

## 十二、结论

1. **用户观察的①对②错**：skill 目录确实在头部（一条 `user/message`），
   但**压缩不是原因**——压缩后会立刻重发（实测 16/16）。
2. **真正的变量是上下文压力**：跨过 100k 即完成主体下跌（19.48% → 2.53%，跌 7.7 倍），高位有反弹（§4.2）。
3. **是 skill 特有的失效**：普通工具只降 40%，因为它需要二阶策略判断。
4. **工具定义（含 MCP）不受影响**——它是 API 参数，不在对话历史里，压缩碰不到它。
5. **三个「匹配」方案都被数据否掉**：BM25（756 分误匹配、分数与语义无关）、
   事后补触发词（对照组追平实验组）、换厂商独立模型（一致率 49.0%，§7.2）。
6. **业界未解**：竞品（Soleur / dsh-skill-router / skill-router 家族）都在做「路由 + 渐进披露」
   以降低目录成本，**没有一家声称解决了「模型不主动调用」**，全部依赖模型主动读/主动调。
7. **最有希望的方向是「观察」而非「预测」**：助手看 Agent 在做什么，
   把问题从开放语义判断降级为封闭的规则违反检测。
8. **最省的落点是纯规则**（第 1 层）：零模型、零延迟、判据确定，且不需要任何前置验证。
