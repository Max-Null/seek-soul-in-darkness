# 注入成本实测 · 第一批（2026-09-23）

> 起因：`docs/调研/2026-09-23-第三方插件调查与全家桶方向.md` §4.2 ① 提出「我们五个注入类插件从没测过每轮实际花多少」。
> 本文是第一批实测数据。**它改变了优化的方向。**

## 一、方法（以及为什么换了方法）

Aik358 那份调研的做法是「从真实会话日志里切出注入段量真值字节」。**这条路我们走不通**——实测本会话日志（`session.v3.jsonl.zstd`，808 帧全部解出、8.3 MB / 1572 行）：

- 事件类型里**只有 2 条 `request/header`**，内容是 `config`（provider / model / reasoningEffort / maxTokens）+ **完整的 180 个工具 schema**；
- **没有 system prompt、没有 messages**——注入文本不进日志。

于是改成两路取证：**能从日志取真值的取真值**（工具面），**静态段从各自源码提取字面量**。

## 二、数据

| 项 | 字节 | 粗估 token | 来源 |
|---|---|---|---|
| **工具面（180 个 schema）** | **171,580** | ≈ 43,000 | 会话日志 `request/header` **真值** |
| └ 其中 `dsh-memory` 的 11 个工具 | 10,353 | ≈ 2,600 | 同上 |
| `tool:memory` GUIDANCE（order 115） | 2,865 | ≈ 700 | `src/index.ts` 字面量 |
| `tone` DAILY_TEXT（order -85） | 1,077 | ≈ 270 | `src/index.ts` 字面量 |
| `chinese-thinking`（order -90） | 75 | ≈ 19 | `src/index.ts` 字面量 |
| `memory:recall` 动态注入 | ≤1500 字符 | ≈ 1,000 | 按预算上限（**未实测**） |

token 换算为粗估（英文 JSON 约 4 字符/token），仅供量级比较。

工具面里最大的十个：`pwsh` 4,445 B、`workflow` 4,014 B、`mcp__github__issue_write` 3,648 B、`mcp__github__pull_request_read` 2,574 B、`memory_save` 2,533 B……

**按来源拆开之后，杠杆的位置就具体了**（同一份 `request/header` 真值）：

| 来源 | 工具数 | 字节 | 占工具面 |
|---|---|---|---|
| **MCP: github** | 45 | 49,326 | **28.7%** |
| **MCP: codegraph** | 42 | 42,666 | **24.9%** |
| DSH 内核 + 其余插件 | 32 | 33,092 | 19.3% |
| MCP: playwright-headless | 25 | 18,006 | 10.5% |
| MCP: playwright-headed | 25 | 17,956 | 10.5% |
| 插件 `@max-null/dsh-memory` | 11 | 10,353 | 6.0% |

**MCP 合计 137 个工具 / 127,954 B = 74.6% 的工具面。** 其中三点值得单独指出：

- **github（45 个）+ codegraph（42 个）= 91,992 B = 53.6%**——两个 MCP 就过半；
- **playwright 的两条各 25 个工具，合计 21%**——它们是 `cordis.patch.yml` 里**有意**的两条条目（headless / headed，为的是「两者可同时开浏览器」，见该文件注释），代价就是每轮多付约 36 KB；
- 我们的 `dsh-memory` 11 个工具只占 **6%**——**我们一直在纠结的注入预算，在总账里是最小的那一格**。

## 三、结论：真正的大头不在我们一直在看的地方

**工具面是注入段的几十倍。**

- 对全部注入段之和（GUIDANCE + tone + chinese-thinking ≈ 4,017 B）约 **43 : 1**
- 对单个 GUIDANCE 段约 **60 : 1**

**这改变了优化的方向**：

1. 把 `memory:recall` 的预算从 1500 调到 1000 字符，是**千分之几**量级的动作；
2. 真正的杠杆在**工具面**——尤其 MCP 那批（`mcp__github__*` 十几个、`mcp__codegraph__*` 更多）；
3. `tools.restrict()` 能按 agent 收窄工具面，**那是唯一能改变量级的开关**。

**旁证**：Aik358 那份调研量的是它的 `<memory_system>` 段（18291 字符）并得出「超预算 228%」的结论——它同样**没有量工具面**。两个项目都在优化注入段，而成本的大头在两者都没看的地方。

## 四、未取到的部分（如实标注）

- **DSH 内核自身的 prompt 段**（identity / 各工具的用法指引 / persona）不在日志里，无法从真值量。要量它需要在**内核侧**加审计——那属于上游能力，或者说：**这块目前测不到**。
- `memory:recall` 的实际长度**未实测**（本文按预算上限标；要实测需要跑一次 `recallText` 拿真实数据，或给它加长度审计）。
- `dsh-guardian` 的三条动态提醒与 `dsh-allostasis` 的锚定消息**未量**（它们依赖运行时状态，本轮没跑）。

## 五、下一步（如果要继续）

1. **量工具面里 MCP 那批的占比**——`mcp__github__*`、`mcp__codegraph__*`、`mcp__playwright-*__*` 各占多少，是决定「要不要按 agent 收窄工具面」的依据；
2. **给 `memory:recall` 加长度审计**（一行诊断日志即可），把「按预算上限」换成真值；
3. 若要量内核段，**只能从上游入手**（`request/header` 里没有它，日志里也没有）。
